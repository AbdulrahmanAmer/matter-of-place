# The admin platform — 25 screens, what is on each, how each behaves

Route group `/admin/*` inside the site Worker, behind Supabase Auth (magic link) or an agent key. Roles: `admin`,
`chief_editor`, `managing_editor`, `visual_editor`, `media_ops`, `commercial`. Diagrams: `03-diagrams/admin-screens.md`.
Design: same tokens as the site (Bone/Ivory surfaces, Obsidian text, Jost labels, Cormorant headings), dense but calm,
one primary action per screen, every destructive or outward action confirms once and then runs as a job you can watch.

Shared UI (`src/admin/ui`): top bar (wordmark, environment badge, search, actor name + kind), left nav grouped as
below, `DataTable` (server-paged, filters in the URL, saved views), `Drawer` (details without losing the list),
`StatusPill`, `Timeline` (audit + job events for the entity), `ConfirmDialog`, `JobWatcher` (live status of jobs an action
created), `EmptyState`, `Toast`. Keyboard: `j/k` rows, `enter` open, `a` accept, `d` decline, `p` publish where allowed.

Navigation groups: **Work** (Dashboard, Requests, Properties, Media, Assets, Inquiries) · **Distribution** (Channels,
Newsletter) · **Money** (Invoices, Reports) · **Editorial** (Stories, Markets) · **Automation** (Recipes, Email templates,
Decline reasons, Channels & schedules, Revisions) · **System** (Jobs, Team, Settings, Audit log).

## How the key flows behave (no ambiguity for builders)
- **Decline** (screen 4): pick a reason → optional note → the email preview renders from `email_templates.declined` with the reason paragraph inserted → Send. Server function: transaction sets `workflow_state = Declined`, `decline_reason_id`, `reviewed_by/at`; audit row; event `submission.declined`; recipe sends the email as a job. The screen shows the job status in a toast and the timeline.
- **Accept** (4): same shape with `accepted_by/at`; event `submission.accepted`; the decision panel now offers "Issue invoice" and "Create property".
- **Issue invoice** (6): a managing_editor or admin presses "Issue & email" (owner B6). Picks product from the submission's package (editable), computes amount from `src/data/exposure.ts` through `priceFor` in `src/server/payments/pricing.ts` (the file stays the price source; nobody types the amount); `src/server/payments/service.ts` calls the SQL function `issue_invoice` (migration `<ts>_invoicing.sql`), which assigns `invoice_number` (`MOP-YYYY-NNNN`) from `invoice_counters`, gapless per UTC year, and writes the `payments` row with its `invoice_snapshot`, the audit row `payments.issue`, event `invoice.issued` and the system job `invoice_pdf` (key `invoice_pdf:<payment_id>`, through B8's `enqueue_job`) in one transaction (a rolled-back issue consumes no number and leaves no job; the service itself never enqueues and makes no outside call). The runner's `invoice_pdf` handler (`src/server/jobs/system/invoice-pdf.ts`) calls `ensureInvoicePdf` in `src/server/payments/invoice-pdf.ts`, which renders the snapshot to PDF (Browser-free: `pdf-lib`), stores it in the private Supabase Storage bucket `invoices` (created by B6's `<ts>_invoicing.sql`; no R2) at `<year>/<invoice_number>.pdf` and records the path in `payments.invoice_r2_key`; the seeded recipe on `invoice.issued` (`send_email`, template `invoice`, `attach: invoice_pdf`) emails it through Resend, and its attachment resolver (`src/server/payments/invoice-attachment.ts`) renders the PDF itself when the send runs first, so the email never depends on job order. The PDF link (`GET /api/admin/payments/:id/pdf`) answers 302 to a 60-second signed URL. State → `Invoice Issued`. Failure: unaccepted 409 `not_accepted`; incomplete `settings.invoice` 409 `invoice_not_ready`; a failed render, upload or send retries with B8's backoff and goes `dead` after 5 attempts (Jobs, 16); the PDF link answers 404 `pdf_not_ready` until the job ran and 503 `storage_unavailable` when Storage answers an error. Proof: `bunx vitest run tests/unit/payments/service.test.ts tests/unit/payments/pdf-route.test.ts` (B6 step 3); `bunx vitest run tests/unit/payments/invoice-pdf.test.ts tests/unit/payments/invoice-attachment.test.ts tests/unit/payments/invoice-pdf-job.test.ts` (B6 step 5); `E2E_TARGET=dev bunx playwright test --project admin tests/e2e/admin-invoice.spec.ts` on `mop-dev` (B6 step 9). The email runs today under `EMAIL_DRY_RUN=1` (row `skipped` with a `dry_` id, B6 step 8); real delivery is BLOCKED until Resend has a verified sending domain (E9).
- **Mark paid → Activate** (6): records method, reference, date; event `payment.marked`; "Activate agent" moves the submission to `Scheduled`, creates the property draft from the submission if none exists and creates the one `campaigns` row for the paid or waived payment (`activate_submission`, B6; nothing else writes `campaigns`).
- **Void** (6): an admin, signed in as a person (agents get 403 `human_only`), presses "Void" and gives a reason of 3 to 500 characters (`VoidDialog.tsx`, B6). `POST /api/admin/payments/:id/void` calls the SQL function `void_payment` (B6's `<ts>_invoicing.sql`, status value added by `<ts>_invoicing_enum.sql`), which sets `status = void`, stores the reason in `notes`, writes the audit row `payments.void` and event `invoice.voided` in one transaction; the seeded recipe `notify_admin_void` alerts staff. The number is never reused, the PDF stays in the `invoices` bucket, and the submission stays `Invoice Issued` until "Issue corrected invoice" issues the next number. Failure: a `paid` or `waived` payment 409 `wrong_state`; a reason under 3 characters 422; a non-admin role 403. Proof: `bunx vitest run tests/unit/payments/service.test.ts` (B6 step 3) and `bun run test:db -- tests/db/payments.db.test.ts` on `mop-dev` (B6 step 1).
- **Publish** (8): checklist must be green; transaction sets `editorial_state = published`, `published_at`, bumps `catalog_version`; event `property.published`; the recipe fans out renders; the screen's JobWatcher shows each asset arriving; Assets (10) receives them as pending.
- **Approve asset** (10): event `asset.approved`; `post_meta`, `post_x` and `post_linkedin` jobs, each only for an enabled channel and inside its posting window; digest queue updated; social_posts rows appear in Channels (12).
- **Recipe edit** (17): validation against each step's Zod schema on save; a revision row; the change applies to the next event. Dry run never inserts.
- **Agent on the queue** (S38): the same functions via `/api/admin/*` with a bearer key; screens show the agent's display name and an "agent" pill in every timeline entry.

## Counting
25 screens, 6 navigation groups, 18 events, 17 step types, 6 roles. Every screen's actions map to a server function
named in `06-architecture/architecture.md §4.2`. The role of every action is B7's matrix (`src/server/lib/authz.ts` and
`src/server/lib/permissions/<group>.ts`), proven by `bunx vitest run tests/unit/authz.matrix.test.ts`.
