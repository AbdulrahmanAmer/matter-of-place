## Findings

### F1 — Open redirect: /markets/* splat is put into a redirect href unnormalized, so /markets//evil.example gives 301 Location: //evil.example (MEDIUM, confidence high)

**Impact.** Unauthenticated open redirect from the brand's domain, usable for phishing and for bypassing link allow-lists or reputation filters. It needs a victim to click a link and gives no direct access to data or the server.

**Where.** `app/src/routes/_site.markets.$.tsx:6` in `Route.beforeLoad (createFileRoute "/_site/markets/$")` — CWE-601

**What.** The attacker controls the path after /markets/. TanStack's wildcard extraction (extractParams in router-core) takes path.substring(...) of the raw pathname, so for /markets//evil.example the _splat is "/evil.example" and the href becomes "//evil.example". Because redirect() is given an explicit href with no _builtLocation, Location is sent as-is. resolveRedirect only blocks dangerous protocols, and isDangerousProtocol returns false for "//host" because new URL() throws. The router's own protocol-relative guards (sanitizePath and decodePath) strip only a leading "//" on the request path, not one in the middle. The app's request pipeline (pipeline.ts routePath, redirects.ts) does not collapse it either.

**Exploit scenario.** An attacker sends a victim https://<site>/markets//attacker.example/login (or /markets/%5Cattacker.example, where the decoded splat "\\attacker.example" makes href "/\\attacker.example", which browsers read as //attacker.example). The site answers 301 with Location: //attacker.example/login and the browser follows it to the attacker's phishing page, launched from a link that starts with the trusted domain. The 301 status also lets browsers cache the redirect.

**Preconditions.**
- The victim must follow an attacker-supplied link
- The route /_site/markets/$ is deployed, which is the legacy-address redirect
- No edge layer in front of the Worker collapses // inside the path (Cloudflare and Nitro do not by default; this was not checked in the deployment)

**Fix.** Normalize the splat before building the href: strip leading slashes and backslashes, e.g. `const rest = (params._splat ?? "").replace(/^[\\/]+/, "")`. Better, use `redirect({ to: `/${rest}`, ... })` so buildLocation builds it, or reject any splat containing `\\` or an empty segment. Add a unit test that /markets//evil.example and /markets/%5Cevil.example redirect to a same-origin path.

**Verification.** 3/3 lens verifiers confirmed.

### F2 — Polynomial ReDoS in the budget regex of the public search matcher, run once per catalog card (MEDIUM, confidence medium)

**Impact.** Unauthenticated CPU exhaustion of the Worker that serves the public site and API. This is a partial availability loss and extra CPU billing, with no confidentiality or integrity impact. The catalog size sets the amplification, and the launch catalog may be small.

**Where.** `app/src/lib/search-match.ts:37` in `budgetFrom` — CWE-1333

**What.** The visitor's search `text` (POST /api/public/search, up to 500 chars after trim, no auth, no Turnstile) reaches `budgetFrom`, whose pattern has two adjacent whitespace quantifiers, `\s*\$?\s*`, in front of a mandatory digit. On a long whitespace run with no digit after it, V8 backtracks quadratically per start position and cubically over the unanchored scan; `scoreProperty` calls `budgetFrom` unconditionally for every card in the catalog.

**Exploit scenario.** An attacker POSTs {"text":"x<~498 spaces>x"} to /api/public/search. For each start position inside the space run, the regex tries every split of the run between the two `\s*` quantifiers (about k^2/2 steps), so one call costs on the order of 2e7 backtracking steps (estimated from the code, not measured). The matcher repeats this for every property card, so one request costs N times that of CPU on the Worker's single JS thread. A handful of parallel requests, each under the per-IP limit of 60 a minute, keep isolates busy and stall other requests served by the same isolate. On the Workers free plan the request is killed at the CPU cap.

**Preconditions.**
- The catalog has at least one visible property, because the regex runs once per card.
- Network access to /api/public/search. No authentication, token or Turnstile check is needed.
- The rate limit is in-memory, per IP and per isolate, so it does not stop a distributed or multi-isolate sender.

**Fix.** Collapse the adjacent quantifiers to a single `\s*` (for example `(?:under|below|...)?\s*\$?(\d+(?:\.\d+)?)\s*(m|million|k)\b`). Compute `budgetFrom(text)` and `bedroomsFrom(text)` once per request and pass the results into `scoreProperty` instead of re-running them per card. Optionally cap the query at a few hundred characters or collapse runs of whitespace before matching.

**Verification.** 3/3 lens verifiers confirmed.

### F3 — Agent key can rewrite the caption of an already human-approved asset, bypassing the human-approval gate (MEDIUM, confidence medium)

**Impact.** Integrity of public brand content: text a human never reviewed is published on the brand's social channels under a human approval. The house-voice lint limits the text but does not check accuracy or intent. The change is recorded in audit_log as an agent action, so it can be detected afterwards.

**Where.** `app/src/server/assets/service.ts:258` in `editCaption` — CWE-863

**What.** approveAsset refuses an agent actor ("A person approves this asset"), but editCaption only calls authorize(actor, "assets.caption"), which is agent-allowed by scope, and then the set_asset_caption RPC, which has no status check. The social publisher reads the caption from the live asset row at post time and treats a human approval of that asset id as still valid, so an agent can change approved copy and have it posted under the human's approval.

**Exploit scenario.** A person approves asset X (status approved, approved_by is a human user). An agent key holding scope `assets` and a decider role (media_ops or chief_editor) sends PUT /api/admin/assets/X/caption with new instagram/x/linkedin text that passes lintCaption (no banned words, only the property's known numbers, only the exact property link). set_asset_caption overwrites assets.caption and meta.captions with no status check. When post_to_channel runs, it loads the asset row, stillApproved() returns true because approved_by is a human, and captionFor() posts the agent's text to Instagram, X or LinkedIn. The human never approved that text. The same agent is refused by approveAsset and approve_asset, so this circumvents the intended manual-approval control.

**Preconditions.**
- Attacker holds an agent API key whose scopes include `assets` and whose user has the media_ops or chief_editor role
- Target asset is already approved but not yet posted, so the live caption is still read at post time
- Channel approval_mode is manual, so approval depends on a human

**Fix.** Refuse caption and alt_text edits when the asset status is not pending. In set_asset_caption, raise when v_asset.status <> 'pending'. Alternatively, drop the approval back to pending, or clear approved_by, when the caption of an approved asset changes. Make `assets.caption` humanOnly for approved assets, or snapshot the approved caption into the social_posts row and post that.

**Verification.** 3/3 lens verifiers confirmed.

### F4 — Operator and CI database clients connect to the Supabase pooler without TLS (MEDIUM, confidence medium)

**Impact.** Confidentiality and integrity of an administrative database session on the single project that becomes production. Exposure of the DB password's SCRAM material and of the data read and written, with possible SQL injection into the session.

**Where.** `app/scripts/db-push.mjs:142` in `connect` — CWE-319

**What.** The dbUrl is either DEV_DB_URL or the URL that pushMigrations builds at db-push.mjs:80 as `postgresql://postgres.<ref>:<password>@aws-0-us-east-1.pooler.supabase.com:5432/postgres`. Neither carries `sslmode` and no `ssl` option is passed. node-postgres only negotiates TLS when `ssl` or `sslmode` is set, so the session to a public internet host is plaintext. The same unprotected pattern is in assert-not-production.mjs:21, db-reset-dev.mjs:78 and :117, with-coming-soon.ts:73, with-maintenance.ts and seed-admin-users.ts:106.

**Exploit scenario.** The operator runs `bun run db:reset`, `with-coming-soon` or the seed scripts on an untrusted network, or a CI runner's path to the pooler is intercepted. An on-path attacker reads the SCRAM exchange and every query and result. These are the postgres-role session that reads settings, auth.users and agent_keys and truncates or rewrites tables, on the one project that becomes production. The attacker can capture the SCRAM exchange for offline guessing of the DB password. After authentication the stream is unprotected, so they can inject or alter statements in the live session.

**Preconditions.**
- The attacker holds an on-path network position (hostile Wi-Fi, compromised router or ISP) between the operator laptop or CI runner and aws-0-us-east-1.pooler.supabase.com
- The Supabase pooler accepts non-TLS clients, which is Supabase's default unless 'Enforce SSL' is switched on. Every script in the repo runs against it without TLS config, which suggests it does.
- The operator does not set PGSSLMODE in their shell

**Fix.** Pass `ssl: { rejectUnauthorized: true, ca: <Supabase CA> }` to every `new pg.Client`, or append `?sslmode=verify-full` with the CA. Put the connection options in one shared helper so the scripts cannot drift. Turn on 'Enforce SSL on incoming connections' for the Supabase project.

**Verification.** 3/3 lens verifiers confirmed.

### F5 — Channel enable guard (assertMayEnable) is never called: channels.channels_put can switch on Facebook and unverified channels, bypassing the admin-only new_channels flag (LOW, confidence high)

**Impact.** Privilege-separation bypass: staff who are not admins, and agent keys, can turn on channels the owner decided to keep disabled (Facebook, YouTube) and channels with no proven credentials. Facebook posts then go to the public Page and misconfigured channels generate failures. The effect is limited to channel configuration and public posting, and human approval is still required in manual mode.

**Where.** `app/src/server/automation/service.ts:365` in `putChannelSettings` — CWE-862

**What.** PUT /api/admin/automation/channel-settings/:channel accepts `enabled: true` from any chief_editor, media_ops or admin (or an agent key with the automation scope) and writes it through automation_put_channel, but the B10 invariant-9 guard `assertMayEnable` in app/src/server/channels/enable-guard.ts is not called by putChannelSettings, restoreRevision, or the SQL function. That guard is the only code enforcing that Facebook/YouTube stay locked behind the admin-only, human-only `new_channels` flag and that a channel has verified credentials before it is enabled.

**Exploit scenario.** A media_ops or chief_editor user, or an agent key scoped to `automation`, sends PUT /api/admin/automation/channel-settings/facebook with {"enabled":true}. `automation.flags_put` is admin and humanOnly, so this user could not set `new_channels`. The request passes `authorize(actor, "automation.channels_put")`, `channelPutInput` and the SQL patch-key check, and the row is enabled. The `post_meta` step with channels `from_settings` then includes Facebook, so approved covers and stories are published to the Facebook Page. The same call enables x, linkedin or instagram with no `token_checked_at` or ids proof, so posts fail and raise alerts. `automation.revisions_restore` can restore a revision with `enabled: true` the same way.

**Preconditions.**
- Authenticated session or agent key holding chief_editor, media_ops or admin on the automation scope
- The target channel has an adapter (facebook is implemented in meta.ts)

**Fix.** In putChannelSettings and restoreRevision, call `assertMayEnable(db, channel)` whenever the resulting `enabled` goes from false to true, before the RPC. Also enforce the rule inside automation_put_channel and automation_restore_revision in SQL so no other caller can bypass it. Add a test that PUT enabled:true on facebook returns 422 channel_locked without the flag.

**Verification.** 3/3 lens verifiers confirmed. The panel lowered the severity from MEDIUM to LOW (confirming votes LOW, LOW, LOW); the lowered rating stands.

### F6 — Agent guardrail on protected schedules ignores interval_days and last_run_at, so an agent key can still re-time or stall prune and reconcile (LOW, confidence high)

**Impact.** A scoped agent key can silently disable or stall the prune and reconcile maintenance jobs, which the project's own rule (H23, SEC-11) reserves for humans. If the external audit routine reads interval_days or last_run_at from its own row, the audit clock may be affected too; I did not confirm that. Integrity and availability of background maintenance are affected; no direct data disclosure.

**Where.** `app/src/server/automation/service.ts:199` in `guardSchedule` — CWE-863

**What.** An agent key with the automation scope sends PUT /api/admin/automation/schedule-settings/:key. guardSchedule, which is meant to stop agents from switching off or re-timing a protected clock (SEC-11), only tests next.enabled === false and a changed cron. The same PUT body is also allowed to carry interval_days and last_run_at, and those reach the automation_put_schedule RPC unchecked. The restoreRevision path calls the same guard and has the same gap.

**Exploit scenario.** With a scoped agent key the attacker sends PUT /api/admin/automation/schedule-settings/reconcile with {"last_run_at":"2099-01-01T00:00:00Z"}, or {"interval_days":90}. guardSchedule returns without throwing, because enabled and cron are absent from the patch. automation_put_schedule stores the values and nulls next_run_at. dueAt() then computes the next run from last_run_at or interval_days, so the runner-driven prune and reconcile clocks do not fire for months. enabled stays true and cron is unchanged, so the UI still shows them as on. The SQL function enqueues no notify_admin for schedule writes by an agent, unlike recipe and template writes.

**Preconditions.**
- The caller holds an agent API key with the automation scope and a writer role (chief_editor, media_ops or admin)
- The target key is one of the PROTECTED_SCHEDULES that the runner actually drives from interval_days or last_run_at (prune, reconcile)

**Fix.** Make guardSchedule refuse any agent patch to a protected key that changes interval_days or last_run_at, as well as enabled=false and cron. Better, enforce it in automation_put_schedule and automation_restore_revision by checking p_actor_kind, as the channel_settings restore already does. Add a notify_admin enqueue for agent schedule writes.

**Verification.** 3/3 lens verifiers confirmed.

### F7 — Repeat POST /submissions within 10 minutes hands any caller an upload grant and re-signed overwrite URLs for someone else's submission (LOW, confidence medium)

**Impact.** A caller with no relationship to the submission gets write access to another submitter's private `submissions` bucket objects. This is integrity loss: submitted photographs can be replaced with attacker-chosen images (restricted to image MIME types and size by the bucket). The attacker also learns the submission and media UUIDs. Confidentiality is not directly affected, and editorial review remains as a human check.

**Where.** `app/src/server/submissions/service.ts:161` in `create` — CWE-639

**What.** The public submit form (SubmitWizard -> services.submissions.send -> POST /api/public/submissions) is unauthenticated. The `create_submission` SQL function (supabase/sql/functions/create_submission.sql:29-48) treats any request with the same submitter email, normalised address and zip within 10 minutes as the same caller's double click. It returns the earlier submission's id and all of its media rows, with no proof that the requester is the original submitter. `create` then mints a valid `upload_token` for that id (service.ts:161) and signs upsert-enabled upload URLs for the first ten existing media paths (service.ts:153-157, `createSignedUploadUrl(path, { upsert: true })`).

**Exploit scenario.** An attacker knows an agent's public email and the address and zip of a listing, and the agent has just submitted it. The attacker POSTs /api/public/submissions with a valid Turnstile token, the agent's `submitterEmail` and the same address and zip. The dedupe branch ignores the attacker's `media` and returns the agent's submission id, the real media ids, a 2-hour `upload_token` and signed PUT URLs with upsert. The attacker PUTs their own image bytes to the agent's slots, replacing or racing the agent's photographs before the reconcile job or editorial review. The attacker can also call POST /submissions/:id/uploads with the token for any media row not yet marked uploaded.

**Preconditions.**
- Attacker knows the victim's submitter email, the property address and the zip
- The victim submitted within the previous 10 minutes
- The attacker passes Turnstile and the per-IP (3/hour) and per-email (5/day) limits

**Fix.** In the dedupe branch, do not return the upload grant or signed URLs unless the caller proves it is the original request. Options: return a fresh receipt with an empty `uploads` list and no `upload_token`, or bind the dedupe match to a client-held secret such as a per-draft nonce or the original `upload_token`. At minimum, sign only rows with `uploaded_at is null` and drop `upsert: true`, so an existing object cannot be overwritten through a replayed submission.

**Verification.** 3/3 lens verifiers confirmed. The panel lowered the severity from MEDIUM to LOW (confirming votes LOW, LOW, LOW); the lowered rating stands.

### F8 — Staff-address enumeration through response time on the unauthenticated sign-in link endpoint (LOW, confidence medium)

**Impact.** The attacker learns which email addresses belong to enabled staff, admins or agents. That list supports targeted phishing or credential attacks against the team. No access is gained directly.

**Where.** `app/src/server/team/service.ts:146` in `sendSignInLink` — CWE-208

**What.** POST /api/admin/auth/send-link is unauthenticated and the code promises that its answer never says which addresses hold a role. The staff branch awaits an extra Supabase Auth call (`signInWithOtp`, which dispatches the mail), while a non-staff address returns straight after the `staff_can_sign_in` RPC. The two paths have no padding, so an attacker can tell them apart by response time. This is inferred from the code; I could not run it to measure the gap.

**Exploit scenario.** The attacker obtains Turnstile tokens, then posts candidate editor or admin emails to /api/admin/auth/send-link. They time each response, and a candidate that holds an enabled role takes noticeably longer because of the extra Auth and mail round trip. Each candidate is tried once, so the per-email limit (3 per hour) never applies. The per-IP limit of 5 per hour can be spread across addresses.

**Preconditions.**
- The attacker can obtain Turnstile tokens, or the deployment lets Turnstile fall through as 'unreachable'.
- The attacker can measure response time with enough precision to separate the two paths.
- The attacker can spread requests across IPs to get past the 5 per hour per-IP limit.

**Fix.** Do not await the Auth call on the response path. Queue the send with waitUntil, or a job, and return SENT immediately. Alternatively pad both branches to a common minimum duration, so the staff and non-staff answers take the same time.

**Verification.** 3/3 lens verifiers confirmed.

### F9 — State-changing GET /api/consent?set= sets the consent cookie with no same-origin check (LOW, confidence medium)

**Impact.** An attacker can forge a visitor's analytics-consent record for the site. This undermines the validity of consent for tracking and can cause GA to load for people who did not opt in, a privacy-compliance exposure. It does not expose data or grant access. A `Sec-GPC: 1` header downgrades accept to decline.

**Where.** `app/src/server/public/consent.ts:30` in `setConsent` — CWE-352

**What.** `GET /api/consent?set=accept|decline` (routes/api/consent.ts registers a GET handler) writes the `mop_consent` cookie from a plain query parameter. The handler never checks `Origin`, `Sec-Fetch-Site` or `Sec-Fetch-Mode`. The Referer is used only to choose the return path, and a cross-origin or absent Referer falls back to `/` instead of refusing. A cross-site top-level navigation therefore reaches the handler, and the response's `Set-Cookie` is accepted despite `SameSite=Lax`.

**Exploit scenario.** An attacker page links or auto-navigates the victim's browser to `https://matterofplace.com/api/consent?set=accept`. The browser stores `mop_consent=1.1` and is redirected to `/`. The site then treats the visitor as having consented to analytics. Google Analytics loads because `consentGranted()` reads this cookie, and the victim never saw or used the consent notice. The same request with `set=decline` silently opts the victim out.

**Preconditions.**
- The victim's browser follows a cross-site top-level navigation to the URL
- The visitor's browser does not send `Sec-GPC: 1`

**Fix.** Treat the cookie-setting link as a same-origin action. Require `Sec-Fetch-Site: same-origin` or `none`, or an `Origin`/`Referer` on the site's own origin, before setting the cookie, and otherwise show a confirmation page. Alternatively, accept the choice only via POST with a CSRF token or a SameSite=Strict form.

**Verification.** 2/3 lens verifiers confirmed.

### F10 — Sign-in link endpoint leaks which emails are staff through response timing (LOW, confidence medium)

**Impact.** Confidentiality of the staff and admin address list. The code and its header comment promise that the answer never says which addresses are staff, and this defeats that. Each probe of a real staff address also sends them a genuine magic-link email.

**Where.** `app/src/server/team/service.ts:144` in `sendSignInLink` — CWE-208

**What.** The unauthenticated POST /api/admin/auth/send-link always returns {status:"sent"} so staff addresses stay hidden. A non-staff address returns immediately at the `!staff.data` branch. A staff address goes on to await a network call to Supabase Auth (signInWithOtp, which sends the mail), so the two cases differ by a measurable amount of time.

**Exploit scenario.** An attacker solves a Turnstile challenge, then POSTs {"email":"candidate@omnikom.com"} to /api/admin/auth/send-link and measures the response time. A fast reply means the address is not staff. A reply that takes an extra Supabase Auth plus SMTP round trip, hundreds of milliseconds or more, means the address holds an enabled role. Repeating this builds a list of staff and admin emails to use for phishing or targeted attacks.

**Preconditions.**
- The attacker needs a Turnstile token for each request.
- Per-IP limit of 5 requests an hour and per-email limit of 3 an hour, enforced in memory and in the database. These make bulk enumeration slow unless the attacker rotates IPs.
- Network jitter must be smaller than the Supabase Auth plus mail delay. I did not measure this.

**Fix.** Make the work done equal for both cases. For example, enqueue the Auth call with waitUntil and return at once, or run a dummy call or delay for non-staff addresses. Better, move the mail send off the request path and answer at a fixed time.

**Verification.** 3/3 lens verifiers confirmed.

### F11 — Media edge-cache key is the raw request origin+pathname, so the takedown purge of the canonical URL leaves other cached copies of a taken-down file serving for a year (LOW, confidence medium)

**Impact.** The takedown (a legal or rights-holder removal) is not effective for cached variants. The file stays publicly served from the company's own domain for up to a year, at the data centres where it was cached. The file was public before the takedown, so no new data is exposed. The harm is that a revocation is not enforced.

**Where.** `app/src/server/public/cache.ts:226` in `mediaCached` — CWE-459 (also CWE-41)

**What.** Any unauthenticated requester chooses the origin (a second Worker host such as the mta-sts custom domain) and the percent-encoding of the path (`%2F` for `/`, which `keyOf` decodes and accepts). `mediaCached` stores each variant under its own key `${origin}${pathname}` with `max-age=31536000, immutable`. The rights-takedown job purges only `<MEDIA_PUBLIC_BASE>/<key>`, so those copies are never removed and keep serving the file after Storage deletes it. Also CWE-41: The cache key is the raw request pathname, but media.ts keyOf() percent-decodes the same path before resolving the object. Several URLs can therefore map to one stored object, for example `/media/o%2Fslug%2F1-abcd1234.webp` and `/media/o/slug/1-abcd1234.webp`, and each gets its own 1-year `immutable` cache.put entry. takedown-media.ts deletes the object and then purges only the canonical `<MEDIA_PUBLIC_BASE>/<key>` URL (purge-cache.ts purgeUrls sends `{files}`). Entries stored under any other encoding are not purged.

**Exploit scenario.** Before a rights takedown, an attacker takes a published key from a public page and requests `https://mta-sts.matterofplace.com/media/<key>` or `https://matterofplace.com/media/o%2Fslug%2F1-ab12cd34.webp`. Each request caches the file under a different key for a year. The takedown job deletes the object and purges only `https://matterofplace.com/media/<key>`. The attacker's URLs keep returning 200 with the file from the edge cache until the entry expires or is evicted.

**Preconditions.**
- The attacker requests a non-canonical URL variant for the key before the takedown runs, so a cache entry exists
- The Worker is reachable on more than one host (the mta-sts custom domain, per B17 and cf-edge), or the attacker uses `%2F`-encoded slashes on the canonical host
- The takedown purge covers only the canonical `MEDIA_PUBLIC_BASE/<key>` URLs

**Fix.** Build the cache key from the canonical object key (`https://<fixed canonical origin>/media/<decoded key>`), not from `request.url`'s origin and raw pathname. Purge that same key on takedown. Optionally, refuse `/media/` on hosts other than the canonical one, and redirect or reject paths whose raw form differs from the canonical encoding. Also CWE-41: Build the cache key from the canonical decoded key, for example `${origin}/media/${key}`, rather than the raw pathname. Alternatively, 301 any request whose pathname differs from `/media/` plus the canonical key. Also purge by cache tag or prefix at takedown rather than by exact URL, and consider the `cf: { cacheEverything: true }` Storage fetch in media-store.ts readPublicObject, which can keep a deleted object cached under the supabase.co URL.

**Verification.** 3/3 lens verifiers confirmed.

### F12 — Retention job 'anonymises' email addresses with an unsalted, unkeyed SHA-256, so they stay re-identifiable (LOW, confidence medium)

**Impact.** Partial defeat of the retention and anonymisation control (G23, G16, S55). Email identity of data subjects past the retention window can be recovered or confirmed, and the same hash links rows across tables. Name, phone and message are blanked, so the exposure is limited to the email address.

**Where.** `app/supabase/sql/functions/retention_anonymise_inquiries.sql:25` in `retention_anonymise_inquiries` — CWE-759

**What.** The daily `retention` system job, run by the job-runner Edge Function (src/server/jobs/system/retention.ts, rpc retention_anonymise_inquiries and retention_anonymise_contacts), replaces a personal email address with the plain SHA-256 of that address. There is no salt, no pepper and no HMAC key, so anyone holding the anonymised rows can recompute the hash for candidate addresses and match it. Email addresses are a low-entropy, enumerable input, so this is pseudonymisation, not anonymisation.

**Exploit scenario.** After 24 months the job rewrites inquiries.email, contacts.email and submissions.submitter_email to `<sha256hex>@anonymised.invalid`. An attacker, insider or recipient of a DB dump or backup who holds a list of candidate addresses (breach corpora, a competitor's lead list, or a specific person to check) hashes each address with SHA-256 and matches it against the stored value. That confirms or recovers who made a given luxury-property inquiry or submission, after the data was supposed to be anonymous.

**Preconditions.**
- The attacker can read the anonymised rows: database, backup or export access, or an admin or staff view
- The attacker has candidate email addresses to hash, which is cheap for SHA-256
- The retention job has run and the 24-month policy has been reached

**Fix.** Do not derive the placeholder from the address. Use a random per-row token such as gen_random_uuid()::text || '@anonymised.invalid'. If cross-row linkage is needed, use an HMAC keyed with a server-held secret that is never stored in the database. Apply the same change to retention_anonymise_contacts.sql lines 32 and 39 and regenerate the migration with `bun run db:fn`.

**Verification.** 2/3 lens verifiers confirmed.

### F13 — Admin notification for agent automation changes is deduplicated on a client-chosen X-Request-ID, letting an agent silence repeat alerts (LOW, confidence medium)

**Impact.** A detective control meant to put each agent automation change in front of a human can be reduced to one alert per chosen id by the agent being monitored. Revisions and audit_log still record the edits, so this weakens detection rather than removing it.

**Where.** `app/supabase/sql/functions/automation_put_recipe.sql:43` in `automation_put_recipe` — CWE-807

**What.** pipeline.ts requestIdOf accepts any inbound x-request-id header matching ^[A-Za-z0-9-]{8,64}$. defineAdminRoute passes it into auditContext as p_request_id. automation_put_recipe and automation_put_template use 'agent_automation:' || p_request_id as the idempotency key of the notify_admin job, and enqueue_job silently returns null on a key conflict. An agent that reuses one request id across changes gets only the first alert.

**Exploit scenario.** An agent makes one recipe edit with header X-Request-ID: aaaaaaaa, so the admins get one 'Agent changed automation' mail. It then makes further recipe or template edits, for example stripping requires_approval from a step or retargeting a send_email step, each with the same X-Request-ID. enqueue_job hits the existing idempotency key and returns null without raising, so no further alert is sent. The revision and audit rows are still written, but the push notification that H23 promises is gone.

**Preconditions.**
- The caller holds an agent API key with the automation scope and a writer role
- The admins rely on the notify_admin mail rather than reviewing the revisions screen

**Fix.** Build the idempotency key from a server-generated value, such as the new revision id or gen_random_uuid(), not the client-supplied request id. Or make requestIdOf ignore inbound x-request-id for authenticated writes. The template function (automation_put_template.sql:45) and the matching lines in migrations 20261004115859_automation.sql and 20261008065636_automation_audit.sql carry the same pattern.

**Verification.** 3/3 lens verifiers confirmed.

### F14 — Duplicate-submission shortcut hands another submitter's id and media paths to anyone who knows their email, address and zip; the Worker then mints an upload token and overwrite-capable signed upload URLs for it (LOW, confidence medium)

**Impact.** Integrity of another party's submitted photographs. The submission is replaced without the owner's knowledge or any staff check, and the swapped files are later copied toward the property by copy_submission_media. The attacker also learns the victim's submission id and received_at.

**Where.** `app/supabase/sql/functions/create_submission.sql:39` in `create_submission` — CWE-639

**What.** The untrusted source is the public POST /submissions body. The 10-minute double-click lookup keys only on the unverified submitter_email, address and zip. A match returns the first submission's id and media rows instead of creating a new one. The Worker (src/server/submissions/service.ts create) does not check that the caller owns that submission. It issues uploadToken(row.id) and signed upload URLs created with { upsert: true } for the existing media storage paths.

**Exploit scenario.** A victim submits a listing. Within 10 minutes the attacker passes Turnstile and posts a form with the victim's email, address and zip. create_submission returns the victim's submission id and media rows. The Worker returns a valid upload_token and fresh signed upload URLs (upsert enabled) for the victim's media paths, including rows already marked uploaded. The attacker PUTs different bytes over the victim's photographs. Reconcile only inspects rows with uploaded_at null, so the swap after reconciliation is never re-checked against the stored sha256.

**Preconditions.**
- Attacker knows the victim's submitter email, property address and zip
- Attacker acts within 10 minutes of the victim's submission and within the signed-URL lifetime
- Attacker passes Turnstile and the public rate limits

**Fix.** Do not treat a duplicate as proof of identity. Return a fresh receipt with no upload token, or bind the retry to a secret issued with the first response, for example a client-held idempotency key or the upload token. Do not mint signed upload URLs for rows that already have uploaded_at set, and stop using upsert: true for submission media.

**Verification.** 3/3 lens verifiers confirmed.

### F15 — Unauthenticated submission overwrites an existing contact's name, phone and brokerage, keyed on an unverified email (LOW, confidence medium)

**Impact.** Integrity of the CRM-style contact record, which can be used for social engineering of staff. No confidentiality or availability impact.

**Where.** `app/supabase/sql/functions/create_submission.sql:64` in `create_submission` — CWE-639

**What.** The untrusted source is submitter_email, submitter_name, submitter_phone and brokerage from the public POST /submissions body. The contacts upsert conflicts on lower(email) and rewrites the existing person's record. Nothing proves the submitter controls that email, and the staff People screens read this row.

**Exploit scenario.** The attacker submits the public form with a known agent's email (already a contact) and their own name, phone number and brokerage. The contact row that staff use as the person record is rewritten. Staff who later call or mail that person from the People view reach attacker-chosen details.

**Preconditions.**
- The victim's email already exists in public.contacts
- Attacker passes Turnstile and the public rate limits

**Fix.** Do not update an existing contact from an unverified public request. Store the typed values only on the submission row, or write them to the contact only after the email is confirmed or a staff member reconciles them. Never overwrite name, phone or brokerage.

**Verification.** 3/3 lens verifiers confirmed.

### F16 — Retention 'anonymisation' replaces contact email with an unsalted SHA-256 of the address, which is dictionary-reversible (LOW, confidence medium)

**Impact.** The data kept after the retention period is pseudonymised, not anonymised. People whose personal data was supposed to be erased can be re-identified. This is a privacy and compliance failure, not a direct compromise of the system.

**Where.** `app/supabase/sql/functions/retention_anonymise_contacts.sql:39` in `retention_anonymise_contacts` — CWE-759

**What.** The retention job overwrites contacts.email, and the matching submissions.submitter_email at line 32, with encode(sha256(lower-cased email)) || '@anonymised.invalid'. There is no salt or secret key, so anyone holding the retained rows can recompute the digest for a candidate address and re-identify the person. The project's own write_audit comment says 'a hash is never stored, it can be reversed', yet this function relies on exactly that kind of hash.

**Exploit scenario.** A person who can read the retained rows takes a list of candidate addresses, such as a leaked mailing list or agent directory. Anyone with RLS SELECT on contacts, submissions or inquiries, or with a database backup or export, can read them. They compute sha256(lower(email)) for each candidate and match the digests against contacts.email, submissions.submitter_email and inquiries.email. A match shows that the person was a past submitter or contact, and links their rows across tables. Email addresses are low-entropy, so this is a cheap offline attack.

**Preconditions.**
- Attacker can read the retained rows (staff RLS SELECT, a backup, or an export)
- Attacker has candidate email addresses to test

**Fix.** Do not derive the placeholder from the address. Use a per-row random value, for example gen_random_uuid() or the row id, as the placeholder local part. If a stable pseudonym is needed, use an HMAC keyed with a secret held in Vault rather than a bare sha256. The contacts unique index on lower(email) only needs distinct values.

**Verification.** 3/3 lens verifiers confirmed.

### F17 — create_submission 10-minute dedupe hands the first submitter's id and media rows to anyone who repeats email, address and zip (LOW, confidence medium)

**Impact.** Integrity of a third party's pending submission media. The attacker also learns the submission id and uploaded file names. No read access to the images is shown.

**Where.** `app/supabase/migrations/20261004135327_public_write_events.sql:42` in `public.create_submission` — CWE-639

**What.** The duplicate check is keyed only on non-secret, guessable values: lower(submitter_email), the normalised address and zip, within 10 minutes. On a match the function returns the existing submission id and every submission_media row (id, index, name, storage_path) to the new caller. src/server/submissions/service.ts create() then mints uploadToken(row.id) and signs createSignedUploadUrl(path, { upsert: true }) for those same media paths. A second requester who is not the owner of the first submission therefore receives the upload capability for it.

**Exploit scenario.** Agent A submits a property with photographs. Within 10 minutes the attacker POSTs a submission with A's public email, the same address and zip, passing Turnstile and rate limits. The dedupe branch returns A's submission id and media ids. The Worker returns upload_token plus signed upsert upload URLs for A's storage paths (valid 2 hours). The attacker overwrites A's photographs, or uses the upload_token with POST /submissions/:id/uploads. The editors then review tampered media attributed to A. I did not execute this; it follows from the SQL and the Worker code read.

**Preconditions.**
- Attacker knows the victim's submitter email, property address and zip, which are often public for agents.
- The attack lands within 10 minutes of the victim's submission.
- Attacker passes the public endpoint's Turnstile and rate limit.

**Fix.** Do not return an existing submission's id or media rows to a caller who cannot prove ownership. Bind the dedupe to a secret, such as a client-generated idempotency key, or return a bare receipt without media or upload capability and let the Worker refuse to sign for a pre-existing row. Drop upsert: true for signed upload URLs of rows that already exist.

### F18 — payments UPDATE policy lets managing_editor void or alter issued invoices directly, bypassing admin-only void and frozen invoice data (LOW, confidence medium)

**Impact.** Integrity of financial records and of the payment gate on campaign activation. Admin-only voiding is bypassed and the audit trail is lost.

### F19 — Retention 'anonymisation' replaces email addresses with an unsalted SHA-256 of the address (re-identifiable, linkable) (LOW, confidence medium)

**Impact.** Personal data that should be irreversibly anonymised after retention remains re-identifiable by dictionary or known-address matching. This weakens GDPR/CCPA erasure and retention guarantees. Confidentiality of expired PII is only partly affected.

**Where.** `app/supabase/migrations/20261004065712_retention.sql:188` in `retention_anonymise_inquiries` — CWE-759

**What.** retention_anonymise_inquiries and retention_anonymise_contacts (lines 402 and 409) overwrite the personal email address with plain sha256(email) and no salt or secret pepper. Email addresses are low-entropy and enumerable, so anyone holding the stored value and a candidate address can recompute the digest and re-identify the person. The digest is also deterministic, so the same person's inquiries, submissions and contact rows stay linkable after the retention period. The repo's own write_audit says 'a hash is never stored, it can be reversed' (20261005050700_admin_audit.sql:74), and the Worker salts its IP hashes (hashKey(RATE_LIMIT_SALT, ...)); this path does neither.

**Exploit scenario.** After the 24-month retention job runs, inquiries.email, contacts.email and submissions.submitter_email hold '<sha256 hex>@anonymised.invalid'. Those tables are readable by every staff role (grant select ... to authenticated plus is_staff() policies in 20261001090900_rls.sql) and are present in database backups. An insider or whoever obtains a dump hashes lower(candidate@brokerage.com) for known agents or brokers, or for a data-subject's address, and matches it against the column. That confirms the person was in the dataset and re-links all of their anonymised rows, defeating the erasure the job is meant to deliver.

**Preconditions.**
- Attacker can read the anonymised rows: any staff role through RLS select, or a database backup or leak
- Attacker has candidate email addresses to test, which is realistic for real-estate agents and owners

**Fix.** Do not derive the placeholder from the address. Use a random per-row value such as 'anon-' || gen_random_uuid() || '@anonymised.invalid', which still satisfies the lower(email) uniqueness. If linkability is wanted, use an HMAC with a secret pepper kept outside the database (Vault or a Worker secret), not a bare digest. Apply the same change to supabase/sql/functions/retention_anonymise_*.sql, the source files these migrations copy.

**Verification.** 2/3 lens verifiers confirmed.

### F20 — Submitter-controlled property text goes into a headless Claude CLI that is started with no tool restrictions (LOW, confidence low)

**Impact.** Possible disclosure of files under the operator's app folder, including the Supabase service-role key in `.dev.vars`, into stored and possibly published caption fields. The model's output is also steerable, which affects caption integrity.

**Where.** `app/scripts/captions-runner.ts:96` in `runClaudeCli` — CWE-1427

**What.** A public submitter's free text (the `address` and `city` fields, up to 200 characters each) becomes `properties.title` and `properties.city`. `buildPrompt` in `src/server/assets/captions.ts` puts both into the prompt as `Title:` and `Place:` lines. The runner pipes that prompt to `claude -p` with no `--tools`, `--allowedTools`, `--disallowedTools`, `--permission-mode` or `--max-turns`.

**Exploit scenario.** 1) An attacker submits the public form with an instruction in `address` or `city`, for example telling the assistant to read `.dev.vars` and put its contents in `alt_text`. 2) Staff accept the submission, `create_property_from_submission` copies the text into the draft, and the property is published without that text being edited out. 3) The scheduled "MatterOfPlace Captions" task runs `claude -p` on the operator's laptop in the app folder. If the model follows the injected instruction and the CLI's default read tools are active, the file contents come back in `alt_text` or `slide_alts`. 4) Those fields are stored by `set_asset_text`, shown to editors, and may be auto-approved and published as Instagram, X or LinkedIn alt text.

**Preconditions.**
- Staff accept the submission and publish the property without removing the injected text from title or city
- The caption runner runs on a machine where `claude -p` has its read tools enabled in the app folder, which I could not confirm without running it
- The model follows the injected instruction
- Whoever reads or publishes the resulting alt text can see the leaked content

**Fix.** Start the CLI with tools disabled, for example `--tools ""` or `--disallowedTools` for every tool, with `--max-turns 1`. Run it from an empty temporary working directory. Treat property text as data: wrap it in delimiters, strip control and newline characters, cap its length, and lint `alt_text` and `slide_alts` like the other fields.

**Verification.** 2/3 lens verifiers confirmed.
