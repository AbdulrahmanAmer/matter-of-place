## Goal and observed exit
Every Saturday morning a cloud routine runs `mop-auditor`: it measures performance, technical SEO, AEO and GEO, keyword coverage, channels, security drift and uptime, compares with the last report, checks each free-tier line against its limit, lists the paths visitors and crawlers asked for that returned 404, reads the weekly KPIs that B11 computes, probes the caching contract (hit ratio, never-cached list), writes `workspace/audits/YYYY-MM-DD.md`, and opens one pull request per proposed fix. It never merges, never deploys, never holds a credential that could.
Observed exit (completion map B14): "report in `workspace/audits/`; PR opened." Proof: a manual first run produces `workspace/audits/<date>.md` that passes `lint-report.mjs`, plus a pull request from a branch named `audit/<date>-<slug>` that passes the scope check; then the scheduled routine repeats it the next Saturday. The Part C growth exit needs four consecutive weeks; that is measured after launch, not in this slice.

Invariants
1. Never deploys production. Production deploys run only from the `production` job of `deploy.yml` on `workflow_run` of `ci` after a push to `main` (B1b invariant 6a), which happens only when a human merges. An audit pull request gets a `pr-<n>` preview Worker from the `preview` job of `deploy.yml` like any pull request (B1b); that is a preview on `workers.dev` (against the one database before L1's launch switch, on the `local` adapter with no database key after it, ruling H35 (7)), not a deploy of the site. The routine's GitHub identity can push branches and open pull requests, cannot dispatch workflows (no Actions write), cannot push a change under `.github/workflows/` (no Workflows permission, so GitHub refuses the push), cannot merge, cannot edit secrets, cannot touch branch protection. `main` requires a review from the CEO and passing checks (S27). GitHub branch protection is not available on this plan (P-028), so `audit-scope` is the one job of its own workflow `.github/workflows/audit-scope.yml` on audit pull requests: a red check the CEO reads before merging, not a hard gate. It is not a job of `ci.yml` because `ci.yml` ignores `workspace/**`, `launch/**` and `**/*.md` at workflow level, so an audit pull request touching only a refused path such as `workspace/05-plans/B2.md`, `CLAUDE.md` or `.claude/agents/mop-auditor.md` would run no check at all; `audit-scope.yml` has no `paths` filter. The production job never sees an `audit/` branch name; the enforcement is the human merge, `deploy.yml` running only after `ci.yml` passes on the same SHA, and nobody force-pushing (G-009); `CODEOWNERS` is documentation until protection exists.
2. Scope guard in CI: `scripts/audit/scope-check.mjs` takes the changed paths of a pull request from a branch starting with `audit/` (repository-root relative, because the git root is `E:/Matter Of Place`, G-012) and fails `audit-scope` on any path outside the allowed list. Allowed: `app/src/routes/**` except `app/src/routes/api/**` (head and copy), `app/src/lib/**`, `app/src/components/**`, `app/src/styles/**`, `app/public/**`, `app/docs/**`, `workspace/audits/**`, `GOTCHAS.md`. So `.github/**`, `app/supabase/**`, `app/wrangler.toml`, any `.env*`, `app/src/server/**`, `app/src/routes/api/**`, `.claude/**` and any path holding secrets or auth are refused. Anything outside is a "proposal only" finding.
3. Read-only on data, with one exception: the auditor authenticates with an agent key whose role is `commercial` and whose scopes are the route group names `audit` and `automation` (B7 invariant 3). `audit.usage`, `audit.health`, `audit.notfound` and `audit.kpis` are actions of group `audit`, so no `jobs`, `channels` or `newsletter` scope is needed; the schedule row is a read of group `automation` (action `automation.get`, B8b). The one write the key can make is `audit.record_run` (group `audit`, G9), whose SQL function takes no argument but the actor and request id and updates only `schedule_settings.last_run_at` of the `audit` row. Every other write action of both groups excludes `commercial` (`audit.subject_export` and `audit.subject_delete` are admin and human only; B8b's puts are `chief_editor, media_ops, admin`), so the key cannot change `cron`, `enabled` or any other row. It cannot change roles, keys, settings (architecture 6). It never uses the Supabase service role, the Meta token or the Resend key.
4. Deterministic first: everything a script can measure is a script in `workspace/audits/tools/` (zero tokens); the model only ranks, explains and writes patches.
5. Every number in the report exists in the JSON sidecar; the lint fails on a number in a table cell that is missing from the sidecar.
6. Free tier: the routine spends Claude usage only; no new paid API. PageSpeed, Search Console, GA4, Cloudflare analytics and the uptime monitor's free plan are free.
7. One threshold table (GS-06): `workspace/audits/tools/limits.json` is the only place the P-009 limits and the 50, 70 and 90 percent thresholds are written. `usage.mjs` reads it; `src/server/audit/gauges.ts` mirrors it for the daily `health` job, and `tests/unit/audit/gauges.test.ts` fails when the two differ. Vendor-side notifications are a second net, not the definition: Supabase and Cloudflare send their own emails at thresholds the vendor chooses (ASSUMED 80 and 100 percent, which is why our 70 percent line exists).
8. The 404 log stores no personal data: no IP, no user agent, no query string, referrer reduced to its host, at most 1,000 rows a day (a write cap protects the free database from a crawler loop). A 301 from `redirects` or `slug_history` is not a 404 and is not logged; the redirect map is B3's (`resolveRedirect` in `src/start.ts`, built from the `getCatalog` snapshot's `redirects` and `slug_history`, architecture 13 rule 1), never read from the table on each request, and it answers before the pipeline, so a redirected path never reaches the 404 hook. Writes stay cheap (rule 8): `logNotFound` adds to a per-isolate buffer, flushed as one multi-row insert at most every 10 seconds or when it holds 20 rows. The timer is a `waitUntil` promise, because a Worker runs nothing after the response unless one holds it: the first row into an empty buffer calls `ctx.waitUntil(delay(10_000).then(flush))`; a row that brings the buffer to 20 calls `ctx.waitUntil(flush())`; `flush` swaps the buffer out before the insert, so a second flush never sends the same rows. The daily cap is checked in memory first, and a failed flush (rejected insert or timeout) drops the rows, logs one `logLine("warn", "not_found_flush_failed", { dropped })` (B1b's `src/server/lib/log.ts`; the event name is appended to `LogEvent` in `src/server/lib/log-events.ts` in the same commit, CS-08) and never fails the response; there is no retry. The hook sits after the cache lookup returns in B1b's pipeline (a hit or a render), so a 404 page served from the 60 second cache is counted too.
9. The robot never creates or edits the uptime monitor; the orchestrator does after the operator's sign-up (decision S59), and `uptime.mjs` only reads it.
10. Every route this slice adds under `/api/admin/*` answers through B7's `adminJson` (`Cache-Control: private, no-store`, `Vary: Cookie, Authorization`), proved by `tests/unit/audit/routes.test.ts`, and is never put in the Cache API (rule 6); on the wire B1b's pipeline replaces that handler value with exactly `no-store`, since `/api/admin/*` is a never-cached class (G65), which is what the cache probe expects; lists are paginated at 50 and the KPI and usage numbers come from indexed counts (rule 9). Nothing in this slice runs on a page view or calls an outside API there (rule 10).
11. The probe must not defeat the cache it measures: no cookie, no `Cache-Control: no-cache` request header, no query string on the measured pass.

Events emitted: none. Permissions: the agent account `mop-auditor` (kind `agent`, role `commercial`, scopes `audit` and `automation`, invariant 3), created on screen 23 by the admin; the key is shown once and stored only in the routine's environment. The four new read actions `audit.usage`, `audit.health`, `audit.notfound`, `audit.kpis` are entries in B7's `src/server/lib/permissions/audit.ts` with roles `chief_editor`, `managing_editor`, `commercial`, `admin` (CE ME CO AD); the fifth, the write action `audit.record_run` (G9), has roles `commercial`, `admin` (CO AD; agents allowed, so the `mop-auditor` key with scope `audit` may call it). ## Risks and gotchas (link GOTCHAS ids)
- P-009: the gauges are the point of this slice; the first line to cross 70 percent produces a `DECISION` row and a finding titled with the decision needed (G-011), not a silent upgrade.
- P-010: agent definitions load at session start; a routine reads the repository's current `.claude/agents` when it starts, so edits land on the next run. In-session, a brand-new agent type is unavailable.
- P-014 and P-017: a headless or cloud run that ends its turn kills anything it started in the background; the routine prompt must say "run every tool in the foreground and reply only after the report file exists".
- P-013: never rely on an inherited working directory in the tools; absolute paths or `cd ... && ...` in one call.
- Search Console data lags two to three days and is empty for a new property; the report says so instead of showing zeros as a fact. GA4 Data API needs a property with events; before launch it is empty, listed under `Not measured`.
- PageSpeed Insights lab data varies run to run; the tool takes the median of three runs per page.
- Cloudflare and Sentry limits vary by plan; the limits live only in `workspace/audits/tools/limits.json` (mirrored by `src/server/audit/gauges.ts`, checked by `gauges.test.ts`, invariant 7) and are edited when P-009 is re-checked (quarterly).
- The cloud routine cannot use a GUI; nothing here needs one.
- A finding that proposes copy must obey the guardrails (no em dash, no hyperbole, no guarantee); the lint enforces the em dash rule only, the rest is the reviewer's job on the PR.
- GS-04: a free-plan monitor checks every 5 minutes from outside; a page that returns 200 with wrong content is not detected here (the render gate and the audit do that). The `/status` wording lives in H1's incident runbook. Vendor free-plan terms are ASSUMED; re-check with P-009 quarterly.
- GS-06: vendor notifications cannot be set to 70 percent, so the health check and the report are the 70 percent alarm; Supabase egress, Actions minutes in a run with neither an Actions token nor a signed-in `gh` (G11, ruling H6) and Sentry errors without the optional token stay `Not measured`, caption model use is a token count from `jobs.result.usage` (G2) with no price, because captions run through the operator's Claude account and no API key exists (ruling H34), and is `Not measured` only before the first `write_captions` job; the operator's own Claude plan limits are not visible here (a caption job that waits is reported by B8's health line, H34 (6)); Supabase Storage egress is `Not measured` in the routine (Contract) and Supabase's usage email is its alarm; and a line without a source is never shown as `ok`. The Actions figure is approximate (run durations, not the billed per-job rounding); it is a 70 percent early warning, not an invoice.
- GG-02: a crawler loop can generate thousands of 404s; the 1,000 a day cap and the exclusion list bound the write cost (P-009: 500 MB database). The cap is counted in memory per isolate, so it bounds each isolate and the flush rate rather than the exact daily total; the weekly report shows the real count. The pipeline hook is in B1b's `pipeline.ts`; this is a one-line change reviewed there.
- GG-03: B11 owns the KPI definitions (`src/server/kpi/definitions.ts`), the computation (`collectWeeklyKpis`, SQL `kpi_weekly`), the email and its send job; B14 only reads them through `audit.kpis`, so the two cannot disagree. If `collectWeeklyKpis` fails or B11 step 13 is not built, the KPI section is listed under `## Not measured` with the reason, never shown as zeros.
- S52: the probe measures one pass of our own requests, not visitor traffic; Cloudflare analytics do not see in-Worker Cache API hits, so the report says "probe" and never claims a visitor ratio. The visitor ratio is H1's on the custom domain. UNPROVEN until L1. A 404 served from the 60 second cache is still logged (the hook runs after the cache hook returns), otherwise a crawler loop would be undercounted.
- Secrets in reports: the sidecar must never contain a token or the agent key; `lint-report.mjs` fails on the patterns and `SECRET_NAMES` values of Files (watched-fail z), and the report PR is opened only after the lint passes.
