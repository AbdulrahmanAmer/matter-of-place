# B14 — Audit robot

Lane: Be found (growth) · Stage: 3 BUILD, first real run in Stage 5 · Owner agent: mop-auditor (defined in `.claude/agents/mop-auditor.md`), built by mop-builder · Depends on: B13 (the audit checks what B13 makes; `check-seo.ts` and `validate-jsonld.ts` are reused), B10 and B11 (channel numbers), B7 (agent accounts, screen 23, `/api/admin/*`), B1 (branch protection, CI) · Unblocks: Part C "Growth finished when the audit robot has run four weeks in a row and its PRs have shipped", L1 week-one watch, the iterate loop

Decision applied: S27 (weekly, Saturday morning, cloud schedule, fixes as PRs, never deploys itself). P-009 (free-tier gauges, 70 percent triggers a decision).

## Goal and observed exit
Every Saturday morning a cloud routine runs `mop-auditor`: it measures performance, technical SEO, AEO and GEO, keyword coverage, channels and security drift, compares with the last report, checks each free-tier line against its limit, writes `workspace/audits/YYYY-MM-DD.md`, and opens one pull request per proposed fix. It never merges, never deploys, never holds a credential that could.
Observed exit (completion map B14): "report in `workspace/audits/`; PR opened." Proof: a manual first run produces `workspace/audits/<date>.md` that passes `lint-report.mjs`, plus a pull request from a branch named `audit/<date>-<slug>` that passes the scope check; then the scheduled routine repeats it the next Saturday. The Part C growth exit needs four consecutive weeks; that is measured after launch, not in this slice.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- The live site (production once L1 is done, otherwise the newest preview), `sitemap.xml`, `llms.txt`, robots.
- APIs: PageSpeed Insights, Search Console, GA4 Data API, Cloudflare GraphQL Analytics, Sentry stats, GitHub Actions usage, and our own `/api/admin/*` through one agent key for everything that lives in our database (jobs, channels, newsletter metrics, asset backlog, health, usage).
- The previous report (`workspace/audits/*.md` and its JSON sidecar) for deltas.
- `schedule_settings.audit` (screen 20, ASSUMED read by `GET /api/admin/schedules/audit`): if `enabled = false` the run exits after writing a one-line "skipped, disabled" note, so an operator switch exists without editing the routine.

Outputs
- `workspace/audits/YYYY-MM-DD.md` (report) and `workspace/audits/data/YYYY-MM-DD.json` (machine sidecar of every number, used by the next run's deltas).
- Pull requests, one per fix, each on `audit/YYYY-MM-DD-<slug>`, plus one report PR `audit/YYYY-MM-DD-report`.
- Bank entries: anything that bit the run goes into `GOTCHAS.md` as a process entry with proof in the same PR (mop-auditor rule).

Report format (checked by `scripts/audit/lint-report.mjs`)
1. Title line `# Audit YYYY-MM-DD`, then a front block: run id, site URL, previous report path, tool versions, and which data sources were configured.
2. `## Summary` exactly five lines.
3. `## Scorecard` table: Performance (LCP, CLS, INP, score per key page), Technical SEO, AEO and GEO, Keywords, Channels, Security, each with value, previous, delta, status.
4. `## Free-tier gauges` table from P-009: line, used, limit, percent, previous percent, source, status. Lines: Workers requests per day and per month, R2 storage, Supabase database size, Supabase storage, Supabase egress (if measurable), Edge Function calls, Resend sends today and this month, Resend contacts, GitHub Actions minutes, Sentry errors, Anthropic spend (from `settings` usage log, ASSUMED). Status `ok` under 50 percent, `watch` 50 to 70, `DECISION` at 70 or more, `LIMIT` at 90 or more.
5. `## Findings` ranked by `score = impact / effort` (impact 1 to 5, effort S=1, M=2, L=3). Each finding: id `A-YYYYMMDD-NN`, title, evidence (URL, metric, response excerpt or screenshot path), impact estimate, proposed fix with the file it touches, effort, score, PR link or "proposal only".
6. `## Proposed changes` list linking each PR.
7. `## Not measured` every source that was not configured or failed, with the reason and what would unblock it. A red or missing source is reported, never hidden.
8. No em dash anywhere; calm wording; no fix that adds popups, gimmicks, keyword stuffing or copy outside the editorial voice (brand guard).

Invariants
1. Never deploys. Deploys run only from `deploy.yml` on a merge to `main` by a human. The routine's GitHub identity can push branches and open pull requests, cannot dispatch workflows, cannot merge, cannot edit secrets, cannot touch branch protection. `main` requires a review from the CEO and passing checks (S27).
2. Scope guard in CI: a PR from a branch starting with `audit/` fails `audit-scope` if it touches `.github/**`, `supabase/migrations/**`, `wrangler.toml`, `.env*`, `src/server/**`, `src/routes/api/**`, or any path holding secrets or auth. Audit patches are limited to `src/routes` head and copy, `src/lib`, `src/components`, `src/styles`, `public`, `docs`, `workspace/audits`, `GOTCHAS.md`. Anything outside is a "proposal only" finding.
3. Read-only on data: the auditor authenticates with an agent key whose role is `commercial` (read only) and scopes `audit` and `reports`; it cannot change roles, keys, settings (architecture 6). It never uses the Supabase service role, the Meta token or the Resend key.
4. Deterministic first: everything a script can measure is a script in `workspace/audits/tools/` (zero tokens); the model only ranks, explains and writes patches.
5. Every number in the report exists in the JSON sidecar; the lint fails on a number in a table cell that is missing from the sidecar.
6. Free tier: the routine spends Claude usage only; no new paid API. PageSpeed, Search Console, GA4 and Cloudflare analytics are free.

Events emitted: none. Permissions: the agent account `mop-auditor` (kind `agent`, role `commercial`, scopes `audit`, `reports`, `jobs:read`, `channels:read`, `newsletter:read`), created on screen 23 by the admin; the key is shown once and stored only in the routine's environment.

## Risks and gotchas (link GOTCHAS ids)
- P-009: the gauges are the point of this slice; the first line to cross 70 percent produces a `DECISION` row and a finding titled with the decision needed (G-011), not a silent upgrade.
- P-010: agent definitions load at session start; a routine reads the repository's current `.claude/agents` when it starts, so edits land on the next run. In-session, a brand-new agent type is unavailable.
- P-014 and P-017: a headless or cloud run that ends its turn kills anything it started in the background; the routine prompt must say "run every tool in the foreground and reply only after the report file exists".
- P-013: never rely on an inherited working directory in the tools; absolute paths or `cd ... && ...` in one call.
- Search Console data lags two to three days and is empty for a new property; the report says so instead of showing zeros as a fact. GA4 Data API needs a property with events; before launch it is empty, listed under `Not measured`.
- PageSpeed Insights lab data varies run to run; the tool takes the median of three runs per page.
- Cloudflare and Sentry limits vary by plan; the limits are read from a single table in `usage.mjs` that mirrors P-009 and is edited when P-009 is re-checked (quarterly).
- The cloud routine cannot use a GUI; nothing here needs one.
- A finding that proposes copy must obey the guardrails (no em dash, no hyperbole, no guarantee); the lint enforces the em dash rule only, the rest is the reviewer's job on the PR.
- Secrets in reports: the sidecar must never contain a token or the agent key; `lint-report.mjs` greps for the credential names' patterns.

## Out of scope
Auto-merge, auto-deploy, editing production data, any write to Meta, Resend or Supabase, uptime paging (Sentry and the daily health job cover alerts), the dashboard gauges themselves (B7 reuses the collectors), competitor tracking, backlink monitoring, paid SEO tools, fixing findings that need migrations or server changes (proposal only, a human slices them).
