## Goal and observed exit
Every path the `http` adapters already call exists under `/api/public/*`, validated by the same Zod file the forms use, cached where it is a catalog read, rate limited and bot checked where it is a write, with a request id in every log line and every error body, and with a cache that keeps a warm public read off the database (S52, F24: this slice owns the read path, the memory layer, the Cache API layer, the key, the last-good fallback, `x-mop-cache` and event batching) (S8, S16, S17, S31, S35, S52; architecture 4.1, 1, 8, 9; `docs/architecture/services.md` for the wire contract).
Observed exit (completion map B3): every form persists a row, and `services.mode === "live"` on the preview. Proved by `scripts/api-smoke.mjs` against a preview, by a parity test that compares the live catalog response with the bundled data the local adapter serves, by a database call counter test showing that after warm-up public reads move the counter only by state checks, and by `scripts/cache-proof.mjs` under local `bunx wrangler dev`, where the edge layer answers `x-mop-cache: miss` and then `hit` (E16; L1 confirms it on the custom domain, F25 j).

The rate limit numbers for inquiries, submissions, subscribers and events come from `services.md`; the per-email buckets, the confirm, search, concierge and subject-request numbers are ASSUMED (architecture 9 asks for "per IP and per email" without values). DB-backed limits apply only to writes so reads and beacons cost no database write; memory limits are best effort per isolate and are backed by the Cloudflare rate-limit rule (applied by B1b's `scripts/cf-edge.mjs`, verified by H1-03). Daily windows (subject requests, submissions per submitter email) need `rate_limits` rows to live at least 24 hours (Data changes). The four form writes (`inquiries`, `submissions`, `subscribers`, `subjects/request`, the rows with `form: true` in `routes.ts`) also take a first memory check of 30 per minute per IP (ASSUMED) before Turnstile and before any database call (architecture 13 rule 8, invariant 17); beacons (`events`, `client-error`, and B17's `csp-report`), the POST reads (`search`, `concierge`), `submissions/:id/uploads` and `hooks/resend` take only the limit of their own row, so the 31st beacon in a minute is still accepted. `submissions/:id/uploads` has no Turnstile because its HMAC `upload_token` (2-hour expiry, `src/server/submissions/upload-token.ts`) already ties it to a submission that passed Turnstile; its bucket is `submissions-uploads:ip` (G72), and 12 an hour covers three 40-photograph submissions from one address (each needs at most 3 follow-up calls) with room for retries. Outbound calls per request stay inside the Workers free limit of 50 subrequests per invocation (E2E-02): `POST /submissions` makes at most 23 (Turnstile, `rate_limit_check`, `create_submission`, 20 signings) and `POST /submissions/:id/uploads` at most 22 (`rate_limit_check`, `submission_upload_paths`, 20 signings), proved by `tests/unit/subrequest-budget.test.ts` against a ceiling of 35. The six GET catalog routes accept no query parameter, so their cache key drops the whole query string (rule 3).

Error shape (extends `services.md`): `{ "error": { "code": string, "message": string, "issues"?: ZodIssue[], "requestId": string } }` plus header `x-request-id`; the cacheable errors, the catalog 404 and, from B13 step 11, the 410 `gone` (G23), are `public, s-maxage=60`, omit `requestId` from their body and carry no `x-request-id` when stored (invariant 16), the pipeline adds the header after the lookup. Every code and its status live in one place, `export const errorCodes = { ... } as const` in `src/server/lib/error-codes.ts` (API-03), and `AppError.code` is typed `keyof typeof errorCodes`, so a code no list knows is a type error; B7 adds its admin codes to the same object, and the 500 is `server` everywhere (the name `internal` is not used). Codes: `bad_request` 400 (malformed JSON, wrong content type), `validation` 422 (schema), `forbidden` 403 (Turnstile), `not_found` 404, `gone` 410 (a taken-down property slug; B13 adds the code to `error-codes.ts`, its storage to `cache.ts` and the row note to `routes.ts`, G23), `method_not_allowed` 405 (with `Allow`), `payload_too_large` 413 (over 64 KB), `rate_limited` 429 (with `Retry-After`), `server` 500, `unavailable` 503 (database unreachable and no last good copy exists, invariant 16), `storage_unavailable` 503 (a Supabase Storage outage at run time, H33 (2): raised by `media-store.ts`, by the Storage helpers that B6, B7 and B8 add and by `GET /media/<key>` when Storage fails, never by a catalog read; the job system retries it; the one shared error, F18 as amended by H33). The client maps 400 and 422 to "validation", 404 to "not-found", everything else to "server" (`src/services/http/client.ts`; B13 adds 410 to the `{ gone: true }` result), keeps the request id on the thrown error (`requestId` from the `x-request-id` response header, else from the body's `error.requestId`, G33, so B17's error boundary can show it on a client navigation), and the visitor only ever sees the calm copy in `lib/strings.ts`.

Invariants
1. Handlers are thin: parse, call one service function, return JSON (architecture 2). No handler imports `@supabase/supabase-js`; only `src/server/lib/db.ts` does.
2. Every response carries `x-request-id`. Every request writes exactly one structured log line, `logLine("info", "request", { requestId, route, status, ms, ipHash })` through B1b's `src/server/lib/log.ts` (signature `logLine(level, event: LogEvent, fields?)`, CS-08); ids go in fields, never in the event name. Logs never contain an email address, a message body, a raw IP or a token. No server file calls `console` (B1b's `no-console: 'error'`); the event names this slice writes (`request`, `public_read_stale`, `stale_report_failed`, `honeypot`, `turnstile_unreachable`, `event_pending`, `media_public_base_unset`, `env_optional_missing`, `analytics_store_failed`, `client_error_report_failed`) are appended to the `LogEvent` const array in `src/server/lib/log-events.ts`.
3. Every write validates with the Zod schema first and the database constraints second. A schema failure never reaches the database.
4. IPs are never stored raw: `ip_hash = sha256(RATE_LIMIT_SALT + ":" + ip)` (matches `docs/database/schema.md` intent), where `ip` is `clientIp(request)` of `ids.ts`, the one source for the hash, the rate-limit keys and Turnstile's `remoteip`.
5. Public reads return `published` rows only, and never a row of a coming-soon market or, in production, an `Illustrative` row (`src/server/catalog/visibility.ts`; B3 ships a pass-through marked `// STUB(B3b step 4): coming-soon and illustrative filtering` on the line above the function, invariant 20, and B3b implements it and removes the marker). The snapshot already holds published rows only (B2), and `applyVisibility` runs once per snapshot when `getCatalog` maps it, never per request.
6. Nothing external happens inside a request (architecture 1): no email, no post. The only outside call is Turnstile's siteverify (and Supabase through `db.ts`, Storage signing included, and, on `GET /media/<key>` only, the one Storage read of `readPublicObject` in `media-store.ts` on an edge miss, H33 (4)); Sentry reports (stale reads and `POST /client-error`) leave after the response through `waitUntil`. Side effects are event rows written by the SQL write functions in the row's transaction (G20, Events emitted); B3's Worker code calls no `emitEvent`.
7. The site and the API are same-origin, so `VITE_API_BASE_URL` is the relative `/api/public`. During SSR, loaders call the API in-process (no network hop) through an isomorphic fetch; in the browser they use `fetch`. ASSUMED: this avoids a Worker calling its own public URL, which double counts against the 100,000 requests a day and can be refused on shared hostnames. Proved in step 1.
8. The `services` contract, `src/services/types.ts`, changes in exactly two places and nowhere else: `listProperties(): Promise<PropertyCard[]>` (PERF-06; detail pages read `getProperty(slug)`, which still returns `Property`) and `submissions.send(input, files, onProgress?)`, whose optional third argument receives `UploadProgress = { done: number; total: number; failed: number; retry: () => Promise<void> }` (FE-04; the local adapter ignores it). Adapter files otherwise change only in transport (headers, fetch implementation, the upload queue).
9. Free tier only. No KV, no Queues, no Durable Objects (G-011).
10. Turnstile has three outcomes, not two (GD-05). `verifyTurnstile` returns `"pass"`, `"fail"` or `"unreachable"` (no answer within 2 seconds, ASSUMED, or a 5xx from Cloudflare). `"fail"` is 403 `forbidden`. `"unreachable"` accepts the write, stores `turnstile_ok = false` on `submissions` and `inquiries` (B7 screen 3 shows a badge), still applies every rate limit and the honeypot, and logs the event `turnstile_unreachable`. `subscribers` has no such column and its double opt-in is the check, so an unreachable Turnstile accepts the signup and logs it. With no secret configured (`local` only) the result is `"unreachable"` too, so local rows are honestly flagged. With a secret configured, an absent or empty token is `"fail"` and siteverify is not called. A siteverify `success: true` is still `"fail"` when its `hostname` is not a host allowed for `MOP_ENV` or its `action` is not the route's form action (INT-02 (5)): the allowed hosts are `matterofplace.com`, `www.matterofplace.com` and `matter-of-place.holy-meadow-4327.workers.dev` for `production`, `matter-of-place-dev.holy-meadow-4327.workers.dev` for `development`, any `pr-<n>.holy-meadow-4327.workers.dev` for `preview`, and any host for `local`; the action is the route's bucket name of G72 (`inquiries`, `submissions`, `subscribers`, `subjects-request`), which the browser passes to `getTurnstileToken(action)`. Both checks are skipped when the secret is one of Cloudflare's published test secrets (`1x...AA`, `2x...AA`, `3x...AA`), whose answers carry no real hostname, so previews, `matter-of-place-dev` and the tests keep working; the failing branch logs `turnstile_unreachable` only for a real outage, never for a mismatch.
11. Bot trap (GD-05): every public form carries one hidden text field named by `honeypotFieldName` (`"website"`, exported by `contracts.ts`, read by both the forms and the pipeline). The pipeline removes it before Zod; when it is non-empty the request gets a normal-looking `201 Receipt` (fresh random id), nothing is written, nothing is emitted, and one log line says `honeypot`. A bot learns nothing from the response.
12. Duplicates are flagged, never rejected (GD-05): in `create_submission`, a submission whose lower-cased submitter email and normalised address (lower case, single spaces, no punctuation) match a submission received in the last 30 days sets `submissions.duplicate_of` to the earliest such row and is otherwise processed normally. The 10-minute same-row rule for double clicks stays and runs first.
13. Subject requests (GP-01, CCPA): every request is a `subject_requests` row with `due_at = received_at + 45 days`, created before any reply; nothing is fulfilled in a request (B7 screen 25 exports or deletes by hand, after identity is checked by reply from the requester's own address). The Receipt never says whether a record exists for the email (no account enumeration). Emails in a request are personal data: never logged, scrubbed like every other write.
14. Redirects run before routing (GD-02, GG-01). B1b's `handle` in `src/server/lib/pipeline.ts` calls `deps.redirect`, which `src/start.ts` sets to `(request) => resolveRedirect(request, getDb())`, after minting the request id and before the cache hook, for GET and HEAD requests outside `/api`, `/admin`, `/media` and static assets (a `/media/` request also skips the HTML cache hook: its route stores its own entry, H33 (4)); a redirect answer is `Cache-Control: no-store` and never reaches the cache hook or the render. It answers from two sources taken from the `getCatalog` snapshot (`redirects` and `slug_history`, which B2 puts in `public_catalog_snapshot()`; it queries no table) and merged into one map built once per catalog version (a lookup costs one map read, no database call in the hot path): enabled rows of `redirects` (`from_path` to `to_path` with its `status`) and `slug_history` (`/property/<old>` to `/property/<current>`, `301`, only while the property is published). A slug in neither source falls through to `notFound()`.
15. One read path (architecture 13 rule 1, S52, F24). `src/server/public/state.ts` exports `getPublicState(db)` and `getCatalog(db)`. Cache layers and the key (rules 2, 3, 4, 5, 6, 7 and 12). `src/server/public/cache.ts` is the one module that stores and reads cached responses, for `kind` `json` (this slice) and `html` (called by the middleware of `src/start.ts`, whose order is B1b's), and, through `mediaCached` under a key of its own, the `GET /media/<key>` responses of H33 (4). Key: `https://cache.mop.internal/<release>/v<catalogVersion>/<kind>/<pathname>`, `release` from `SENTRY_RELEASE`, `kind` one of `html`, `json` or `doc` (sitemap, robots, llms files and feeds, which B13 and B17 store through the same module; F25 c); the query string is dropped (the six catalog GETs allow no parameter) and the key never depends on a cookie or a request header. A publish changes `catalog_version`, the next state check sees it and every key changes within 15 seconds, with no purge call. Stored responses carry no `x-request-id`, no `Set-Cookie` and no static security header, with one exception: the Content-Security-Policy header of an `html` entry (`Content-Security-Policy-Report-Only` while B1b ships it report-only) carries the hashes of that page's inline scripts, which B17 computes at render and the middleware passes in the built response, and `cachedResponse` stores it, together with the `Link` header (preloads and preconnects) that B17's `withPageCsp` sets on the same response, with that entry so a hit and a miss answer with the same policy and the same `Link` (F25 d, G40). Never stored: any non-GET or non-HEAD request, any `no-store` response, any response with `Set-Cookie`, any 5xx. Every error body that is not the cacheable catalog 404 or (from B13) the cacheable 410 `gone` is `Cache-Control: no-store`. Lifetimes (PERF-05): the key already holds the release and the catalog version, so a versioned `html` or `json` entry can never be stale and is stored with `s-maxage=31536000` (the Cache API's own eviction bounds it); `doc` entries keep `s-maxage=3600` and the cacheable 404 and 410 keep `s-maxage=60`. The long edge lifetime lives only on the stored copy: every response that leaves the Worker, hit or miss, carries `browserCacheControl(kind)` from B1b (the 404 and 410 keep `public, s-maxage=60`), so no shared cache outside Cloudflare ever holds a page for a year, and `stale-while-revalidate` is not written into the stored entry because the Cache API ignores it. A cached render is a pure function of (release, version, path) and reads no clock. Stale beats down: the last good state and snapshot stay in memory and under a last-good Cache API key, `https://cache.mop.internal/last-good/<release>/html/<pathname>` for `html` (an HTML page names the hashed asset files of its own build, so a new release never serves the previous release's HTML, DO-09) and `https://cache.mop.internal/last-good/<kind>/<pathname>` for `json` and `doc` (they name no asset file, so a new release with a broken database read still answers them `stale`), stored with `s-maxage=604800` and written only when this isolate has not yet written that path at that catalog version (a per-isolate `Map<string, number>` from last-good key to version); when the RPC errors or does not answer within 2 seconds, `getPublicState`, `getCatalog` and `edgeCached` serve the last good copy with `x-mop-cache: stale`, log once a minute and report to Sentry (mechanism in the `state.ts` line of Files); with no last good copy at all the answer is 503 `unavailable` (so after a deploy whose Worker cannot read the database, pages answer 503 and B1b's smoke rolls back).
