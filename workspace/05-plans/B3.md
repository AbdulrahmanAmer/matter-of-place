## Goal and observed exit
Every path the `http` adapters already call exists under `/api/public/*`, validated by the same Zod file the forms use, cached where it is a catalog read, rate limited and bot checked where it is a write, with a request id in every log line and every error body, and with a cache that keeps a warm public read off the database (S52, F24: this slice owns the read path, the memory layer, the Cache API layer, the key, the last-good fallback, `x-mop-cache` and event batching) (S8, S16, S17, S31, S35, S52; architecture 4.1, 1, 8, 9; `docs/architecture/services.md` for the wire contract).
Observed exit (completion map B3): every form persists a row, and `services.mode === "live"` on the preview. Proved by `scripts/api-smoke.mjs` against a preview, by a parity test that compares the live catalog response with the bundled data the local adapter serves, by a database call counter test showing that after warm-up public reads move the counter only by state checks, and by `scripts/cache-proof.mjs` under local `bunx wrangler dev`, where the edge layer answers `x-mop-cache: miss` and then `hit` (E16; L1 confirms it on the custom domain, F25 j).

The rate limit numbers for inquiries, submissions, subscribers and events come from `services.md`; the per-email buckets, the confirm, search, concierge and subject-request numbers are ASSUMED (architecture 9 asks for "per IP and per email" without values). DB-backed limits apply only to writes so reads and beacons cost no database write; memory limits are best effort per isolate and are backed by the Cloudflare rate-limit rule (applied by B1b's `scripts/cf-edge.mjs`, verified by H1-03). Daily windows (subject requests, submissions per agent email) need `rate_limits` rows to live at least 24 hours (Data changes). The four form writes (`inquiries`, `submissions`, `subscribers`, `subjects/request`, the rows with `form: true` in `routes.ts`) also take a first memory check of 30 per minute per IP (ASSUMED) before Turnstile and before any database call (architecture 13 rule 8, invariant 17); beacons (`events`, and B17's `csp-report`), the POST reads (`search`, `concierge`) and `hooks/resend` take only the limit of their own row, so the 31st beacon in a minute is still accepted. The six GET catalog routes accept no query parameter, so their cache key drops the whole query string (rule 3).

Error shape (extends `services.md`): `{ "error": { "code": string, "message": string, "issues"?: ZodIssue[], "requestId": string } }` plus header `x-request-id`; the cacheable errors, the catalog 404 and, from B13 step 11, the 410 `gone` (G23), are `public, s-maxage=60`, omit `requestId` from their body and carry no `x-request-id` when stored (invariant 16), the pipeline adds the header after the lookup. Codes: `bad_request` 400 (malformed JSON, wrong content type), `validation` 422 (schema), `forbidden` 403 (Turnstile), `not_found` 404, `gone` 410 (a taken-down property slug; B13 adds the code to `errors.ts`, its storage to `cache.ts` and the row note to `routes.ts`, G23), `method_not_allowed` 405 (with `Allow`), `payload_too_large` 413 (over 64 KB), `rate_limited` 429 (with `Retry-After`), `server` 500, `unavailable` 503 (database unreachable and no last good copy exists, invariant 16), `r2_unavailable` 503 (R2 not switched on; raised only by write helpers that B6, B7 and B8 add, never by a public read; the one shared error, F18). The client maps 400 and 422 to "validation", 404 to "not-found", everything else to "server" (`src/services/http/client.ts`; B13 adds 410 to the `{ gone: true }` result), keeps the request id on the thrown error (`requestId` from the `x-request-id` response header, else from the body's `error.requestId`, G33, so B17's error boundary can show it on a client navigation), and the visitor only ever sees the calm copy in `lib/strings.ts`.

Invariants
1. Handlers are thin: parse, call one service function, return JSON (architecture 2). No handler imports `@supabase/supabase-js`; only `src/server/lib/db.ts` does.
2. Every response carries `x-request-id`. Every request writes exactly one structured log line with `requestId`, `route`, `status`, `ms`, `ipHash`. Logs never contain an email address, a message body, a raw IP or a token.
3. Every write validates with the Zod schema first and the database constraints second. A schema failure never reaches the database.
4. IPs are never stored raw: `ip_hash = sha256(RATE_LIMIT_SALT + ":" + ip)` (matches `docs/database/schema.md` intent), where `ip` is `clientIp(request)` of `ids.ts`, the one source for the hash, the rate-limit keys and Turnstile's `remoteip`.
5. Public reads return `published` rows only, and never a row of a coming-soon market or, in production, an `Illustrative` row (`src/server/catalog/visibility.ts`; B3 ships a pass-through, B3b implements it). The snapshot already holds published rows only (B2), and `applyVisibility` runs once per snapshot when `getCatalog` maps it, never per request.
6. Nothing external happens inside a request (architecture 1): no email, no post. The only outside call is Turnstile's siteverify (and Supabase through `db.ts`). Side effects are event rows written by the SQL write functions in the row's transaction (G20, Events emitted); B3's Worker code calls no `emitEvent`.
7. The site and the API are same-origin, so `VITE_API_BASE_URL` is the relative `/api/public`. During SSR, loaders call the API in-process (no network hop) through an isomorphic fetch; in the browser they use `fetch`. ASSUMED: this avoids a Worker calling its own public URL, which double counts against the 100,000 requests a day and can be refused on shared hostnames. Proved in step 1.
8. The `services` contract, `src/services/types.ts`, does not change. Adapter files change only in transport (headers, fetch implementation).
9. Free tier only. No KV, no Queues, no Durable Objects (G-011).
10. Turnstile has three outcomes, not two (GD-05). `verifyTurnstile` returns `"pass"`, `"fail"` or `"unreachable"` (no answer within 2 seconds, ASSUMED, or a 5xx from Cloudflare). `"fail"` is 403 `forbidden`. `"unreachable"` accepts the write, stores `turnstile_ok = false` on `submissions` and `inquiries` (B7 screen 3 shows a badge), still applies every rate limit and the honeypot, and logs `turnstile: "unreachable"`. `subscribers` has no such column and its double opt-in is the check, so an unreachable Turnstile accepts the signup and logs it. With no secret configured (`local` only) the result is `"unreachable"` too, so local rows are honestly flagged.
11. Bot trap (GD-05): every public form carries one hidden text field named by `honeypotFieldName` (`"website"`, exported by `contracts.ts`, read by both the forms and the pipeline). The pipeline removes it before Zod; when it is non-empty the request gets a normal-looking `201 Receipt` (fresh random id), nothing is written, nothing is emitted, and one log line says `honeypot`. A bot learns nothing from the response.
12. Duplicates are flagged, never rejected (GD-05): in `create_submission`, a submission whose lower-cased agent email and normalised address (lower case, single spaces, no punctuation) match a submission received in the last 30 days sets `submissions.duplicate_of` to the earliest such row and is otherwise processed normally. The 10-minute same-row rule for double clicks stays and runs first.
13. Subject requests (GP-01, CCPA): every request is a `subject_requests` row with `due_at = received_at + 45 days`, created before any reply; nothing is fulfilled in a request (B7 screen 25 exports or deletes by hand, after identity is checked by reply from the requester's own address). The Receipt never says whether a record exists for the email (no account enumeration). Emails in a request are personal data: never logged, scrubbed like every other write.
14. Redirects run before routing (GD-02, GG-01). B1b's `handle` in `src/server/lib/pipeline.ts` calls `deps.redirect`, which `src/start.ts` sets to `(request) => resolveRedirect(request, getDb())`, after minting the request id and before the cache hook, for GET and HEAD requests outside `/api`, `/admin` and static assets; a redirect answer is `Cache-Control: no-store` and never reaches the cache hook or the render. It answers from two sources taken from the `getCatalog` snapshot (`redirects` and `slug_history`, which B2 puts in `public_catalog_snapshot()`; it queries no table) and merged into one map built once per catalog version (a lookup costs one map read, no database call in the hot path): enabled rows of `redirects` (`from_path` to `to_path` with its `status`) and `slug_history` (`/property/<old>` to `/property/<current>`, `301`, only while the property is published). A slug in neither source falls through to `notFound()`.
15. One read path (architecture 13 rule 1, S52, F24). `src/server/public/state.ts` exports `getPublicState(db)` and `getCatalog(db)`. Both functions and `handlePublic` take the database client as an argument (`getPublicState(db)`, `getCatalog(db)`, `handlePublic(request, db = getDb())`), so a test injects a counting client (F25 e; B4's 1,000 request proof uses it). `getPublicState` calls the RPC `public_state()` and memoises `{ catalogVersion, flags, comingSoonGlobal, comingSoonMarkets, site, illustrativeContent, ogStatic }` for `CATALOG_VERSION_TTL_MS` (15000, `0` in tests) per isolate; these seven key names (G39, which adds `ogStatic` to F25 b; `ogStatic` is the RPC's `og_static` passed through unchanged, `{}` when absent, and B13's `og.functions.ts` resolves its keys), and the snapshot's `redirects` and `slug_history`, are final. `illustrativeContent` is derived from `settings.environment` by `public_state()` and is what B3b's `applyVisibility` reads. Nothing in application code bumps `catalog_version`: B2's triggers bump it on publishing, unpublishing or editing published content, on a write to the public keys of `settings` (`flags`, `coming_soon_global`, `site`, `environment`, `og_static`; G21 narrows F25 a, so channel and token keys do not bump it), and on every write to `markets.coming_soon`, `redirects` and `slug_history`, so a flag or coming-soon change reaches cached pages within 15 seconds. `getCatalog` calls `public_catalog_snapshot()` only when the memoised catalog version differs from the state's, maps it once with `mappers.ts` (`comingSoon` from the state), runs `applyVisibility(rows, { state, env: { MOP_ENV } })` once on the mapped rows (`state` the memoised `PublicState`, `MOP_ENV` from `readVar("MOP_ENV")` of `src/server/lib/runtime-env.ts`, never from `env.ts`, so the module also loads in the job runner, G39; the exact `ctx` B3b's implementation reads) and memoises the mapped result per isolate. Every public list and detail endpoint, the in-process loaders of invariant 7, `search`, `concierge`, `resolveRedirect` and, for B3b and B13, flags, coming-soon, site settings, sitemap and llms entries read from these two and run no query of their own against any table. Visitor-visible counts and settings are derived from the snapshot or the state, never from a table. The two RPCs are the only database reads on a public request; the write functions are the only other database calls in this slice.
16. Cache layers and the key (rules 2, 3, 4, 5, 6, 7 and 12). `src/server/public/cache.ts` is the one module that stores and reads cached responses, for `kind` `json` (this slice) and `html` (called by the middleware of `src/start.ts`, whose order is B1b's). Key: `https://cache.mop.internal/<release>/v<catalogVersion>/<kind>/<pathname>`, `release` from `SENTRY_RELEASE`, `kind` one of `html`, `json` or `doc` (sitemap, robots, llms files and feeds, which B13 and B17 store through the same module; F25 c); the query string is dropped (the six catalog GETs allow no parameter) and the key never depends on a cookie or a request header. A publish changes `catalog_version`, the next state check sees it and every key changes within 15 seconds, with no purge call. Stored responses carry no `x-request-id`, no `Set-Cookie` and no static security header, with one exception: the Content-Security-Policy header of an `html` entry (`Content-Security-Policy-Report-Only` while B1b ships it report-only) carries the hashes of that page's inline scripts, which B17 computes at render and the middleware passes in the built response, and `cachedResponse` stores it, together with the `Link` header (preloads and preconnects) that B17's `withPageCsp` sets on the same response, with that entry so a hit and a miss answer with the same policy and the same `Link` (F25 d, G40). The pipeline and the middleware add `x-request-id` and the other security headers (B1b) after the lookup (invariant 2 still holds on every response). Never stored: any non-GET or non-HEAD request, any `no-store` response, any response with `Set-Cookie`, any 5xx. Every error body that is not the cacheable catalog 404 or (from B13) the cacheable 410 `gone` is `Cache-Control: no-store`. Stale beats down: the last good state and snapshot stay in memory and under the Cache API key `https://cache.mop.internal/last-good/<kind>/<pathname>`; when the RPC errors or does not answer within 2 seconds, `getPublicState`, `getCatalog` and `edgeCached` serve the last good copy with `x-mop-cache: stale`, log once a minute and report to Sentry (mechanism in the `state.ts` line of Files); with no last good copy at all the answer is 503 `unavailable`. Every public response carries `x-mop-cache: hit|miss|stale|bypass`. Every public GET response also carries `x-catalog-version`; a write response, and every error answered before the service call, carries `x-mop-cache: bypass` and no `x-catalog-version`, because reading the version after the memo expired would cost a state RPC (invariant 17). `typeof caches === "undefined"` (`vite dev`) and workers.dev make the edge layer a no-op that answers `miss`; the memory layer still works there. Under local `bunx wrangler dev` the Cache API works (E16), so the edge layer is proved there by this slice (step 12) and confirmed on the custom domain at L1.
17. Writes stay cheap (rule 8). The pipeline order for a write is: route and method, size cap, content type, honeypot, memory limit, Turnstile, Zod, DB limit (`rate_limit_check`), service call. A request rejected by the memory limit, by Turnstile or by Zod makes no database call. Analytics events are batched in the browser: `track()` queues, flushes every 10 seconds and on `visibilitychange`, at most 20 events per beacon, and `events.record` stores a batch with one multi-row insert. The 120 per minute memory limit counts beacons. Campaign attribution (G45): `track()` adds the session's `utm_source`, `utm_medium` and `utm_campaign` as `data.utm` to every envelope, only after analytics consent (mechanism in the `src/lib/analytics.ts` Change), and `events.record` stores `data` unchanged, so readers use `data->'utm'->>'utm_medium'` and its two siblings.
18. The database client counts its calls. `src/server/lib/db.ts` wraps the `fetch` given to `createClient` and exposes `dbCallCount()` and `resetDbCallCount()` (counts every request to Supabase, a plain integer in memory; it counts in every environment because an increment costs nothing, and it is read by tests and local runs only: no route, header or log line exposes it, proved by the Verification grep). It is a total used only by this slice's own warm-read assertions, which run before B4 exists; B4's 1,000 request proof and every later slice's per-name call assertion use B4's `countingDb(db)` from `tests/fixtures/db-counter.ts` over the injectable client (F24, F25 e). The counter is the test-time proof; H1 counts the real queries on the database with `pg_stat_statements` (E15, F25 i).

Events emitted (catalog of architecture 3.6, 18 events): none by B3's Worker code (G20). Each automation-starting write emits in SQL, inside the function that writes the row and in the same transaction: `create_submission` writes `submission.received`; `create_inquiry` (B8's new function, which replaces the inquiry insert of Inputs) writes `inquiry.received` with `{ inquiry_id }`; `upsert_subscriber` writes `subscriber.created` with `{ subscriber_id, sealed_token }` when the row is new or still unconfirmed and `p.sealed_token` is not null (ASSUMED A7, G12; the raw token is never a parameter); `confirm_subscriber` writes `subscriber.confirmed`; `create_subject_request` writes `subject_request.received` with `{ request_id, kind }` (G29). The `events` table and `emit_event` are B8's, so B3's functions ship without the `perform emit_event(...)` line and B8 step 2a re-creates them with it (`<ts>_public_write_events.sql`, B8 Files). Until B8 lands no event row exists and nothing is mailed; B3's tests assert no event, and B8 step 2a adds the one-event-row assertions to B3's API tests (B8 Change). From day one the services pass the payload keys those bodies read (`sealed_token` for subscribers, `kind` for subject requests). Analytics beacons are rows in `analytics_events`, not events.
Permissions: anonymous callers only, plus the Svix signature for the Resend hook. No route reads a session. Admin routes are B7, and so is the admin session check: it verifies the JWT locally against the project's ES256 key (E14, F25 i), with no call to Supabase Auth.

## Risks and gotchas (link GOTCHAS ids)
- G-005: routes import through `src/lib/queries.ts` and `services` only. Server code must not import `src/data/*` either; the bundled data reaches the server only in tests (parity test) and in `scripts/seed.ts`.
- G-006: `TURNSTILE_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, `RATE_LIMIT_SALT`, `RESEND_WEBHOOK_SECRET` are Worker secrets only. `VITE_TURNSTILE_SITE_KEY` is public and is the only new `VITE_*` name. Vite import protection (`vite.config.ts`, `**/server/**`) stops a client import of server code; step 1's grep proves it after the isomorphic fetch is added.
- G-004: `contracts.ts` changes (`markets`, media limits, `subjectRequestKinds` with `correction`) and the SQL checks land in the same commit as their migration; `enums.check.ts` from B2 guards the enums.
- G-011 and P-009: Workers free is 100,000 requests a day; in-process API calls do not add requests. Supabase free egress is 5 GB a month; a full catalog response is under 100 KB and is cached, so a cache miss costs well under 1 MB an hour. The 10 ms CPU limit is the real risk: `toProperty` on 16 rows and Zod parses are small, SSR is the larger cost: measured 2026-10-01 on the current build, `/` ran 6 to 52 ms and `/properties` 10 to 24 ms with no error 1102 in 36 requests (E3), already above 10 ms; B1b step 7 measures again and H1 decides. API route CPU is UNPROVEN until step 13.
- B3's `tests/api` are the committed-mode tests F22 allows, because they cross connections through supabase-js; the harness is B2's and everything else in this slice that touches SQL directly rolls back. DB tests share `mop-dev` with every other slice and run with `fileParallelism: false`; database tests of slices that run side by side share one concurrency group on `mop-dev` in CI, and every local committed run takes the `mop-dev-tests` advisory lock through B2's `committed(fn, cleanup)` (G34): use unique emails and `source_path = '/__test'` and clean up in teardown, so a failed run never leaves rows that skew the 16-property count or the rate-limit buckets (clear test buckets by `key_hash` in setup). `mop-dev` pauses after 7 idle days (P-009): a first request that times out is a paused project, not a defect.
- Cache API does nothing on `workers.dev` hostnames or in `vite dev`, so previews never hit the edge layer; they run on the memory layer alone, which is proved by the call counter test. The Cache API works under local `bunx wrangler dev` (E16), so the edge hit, the query-string rule and the stored 404 are proved by `scripts/cache-proof.mjs` in step 12 and the full catalog response (under 100 KB) is stored and served there; L1 confirms it on the custom domain and H1 measures the 95 percent ratio and HTML caching under real traffic at Stage 5, counting real queries with `pg_stat_statements` (E15). Headers, the versioned key and the last-good fallback are also asserted against a fake `caches`.
- Keep-warm (B8b, F25 h) calls the public handler in-process and always makes one state RPC; that is what keeps an isolate warm and the free database from pausing, since a cache hit alone would not touch it. B3 exposes `handlePublic(request, db)` and `getPublicState(db)` for it and adds nothing else.
- Rule 7 (stale beats down) depends on the isolate still being alive or the Cache API holding a `last-good` copy. A cold isolate on workers.dev with the database down has neither and answers 503 `unavailable`; that case is accepted and logged, not hidden.
- Rule 5: nothing in a cached JSON body varies by visitor. The mapper takes no request input; `readpath.test.ts` and `cache.test.ts` guard it, and B17 computes the script hashes for the HTML side (CSP by hashes, never nonces) and B3 stores the resulting header with the page's cache entry (F25 d).
- Supabase's signed upload URL lifetime is fixed by Supabase (documented as 2 hours), not the 15 minutes `services.md` states. UNPROVEN, check in step 8 and correct the doc.
- `navigator.sendBeacon` with a JSON `Blob` sends `content-type: application/json` same-origin, so `POST /events` needs no CORS. It cannot carry the Turnstile header, which is why events are memory rate limited instead.
- The double opt-in email (B5) is triggered by the catalog event `subscriber.created` (ASSUMED A7), written by `upsert_subscriber` once B8 step 2a re-creates it and only when `requestConfirmation` returned a sealed token (G12, G20); `requestConfirmation` is the single place B5 wires. Until B5 and B8 land subscribers stay unconfirmed and nothing is mailed. The raw token exists only in memory and is never stored; the AES-GCM sealed token travels in the `subscriber.created` payload (`{ subscriber_id, sealed_token }`) and the recipe's `send_email` step (template `interest_confirm`, or `newsletter_confirm` without markets) builds the link from it. No `confirm` template and no second sender exist (G12).
- Between B3 and B8 step 2a the public writes produce no event at all (no `events` table yet). That is the intended order, not a lost event: B7's queues read the rows, and from step 2a on each row and its event commit or roll back together (G20).
- Isolate memory limits reset on cold starts and differ per isolate. They stop accidents, not attackers; the Cloudflare rate-limit rule (B1b `scripts/cf-edge.mjs`, verified by H1-03) and Turnstile do that.
- Same-origin `VITE_API_BASE_URL=/api/public` makes `siteConfig.apiBaseUrl` relative. Nothing else reads it as an absolute URL today (`grep -rn apiBaseUrl src`): only `services/index.ts` and `analytics.ts`. Re-run that grep at step 12.
- Between this slice's merge and B3b's, the production workers.dev Worker serves the illustrative seed of `mop-dev` through the pass-through `applyVisibility`, as the local-mode build already does today; the host answers `noindex` (G19) and no domain points at it before L1.
- GD-05: Turnstile's fallback trades a little bot resistance for availability. An attacker cannot make Cloudflare unreachable for us, so the exposure is a real outage, during which rate limits, the honeypot and the admin badge (`turnstile_ok = false`) are the defences. UNPROVEN until a real outage; the unit test fakes it. The 2 second timeout is ASSUMED; Workers subrequests are cheap but each waiting second is wall time, not CPU.
