## Goal and observed exit
Every path the `http` adapters already call exists under `/api/public/*`, validated by the same Zod file the forms use, cached where it is a catalog read, rate limited and bot checked where it is a write, with a request id in every log line and every error body, and with a cache that keeps a warm public read off the database (S52, F24: this slice owns the read path, the memory layer, the Cache API layer, the key, the last-good fallback, `x-mop-cache` and event batching) (S8, S16, S17, S31, S35, S52; architecture 4.1, 1, 8, 9; `docs/architecture/services.md` for the wire contract).
Observed exit (completion map B3): every form persists a row, and `services.mode === "live"` on the preview. Proved by `scripts/api-smoke.mjs` against a preview, by a parity test that compares the live catalog response with the bundled data the local adapter serves, by a database call counter test showing that after warm-up public reads move the counter only by state checks, and by `scripts/cache-proof.mjs` under local `bunx wrangler dev`, where the edge layer answers `x-mop-cache: miss` and then `hit` (E16; L1 confirms it on the custom domain, F25 j).

The rate limit numbers for inquiries, submissions, subscribers and events come from `services.md`; the per-email buckets, the confirm, search, concierge and subject-request numbers are ASSUMED (architecture 9 asks for "per IP and per email" without values). DB-backed limits apply only to writes so reads and beacons cost no database write; memory limits are best effort per isolate and are backed by the Cloudflare rate-limit rule in HARDEN. Every write route also takes a first memory check of 30 per minute per IP (ASSUMED) before Turnstile and before any database call (architecture 13 rule 8, invariant 17). The six GET catalog routes accept no query parameter, so their cache key drops the whole query string (rule 3).

Error shape (extends `services.md`): `{ "error": { "code": string, "message": string, "issues"?: ZodIssue[], "requestId": string } }` plus header `x-request-id`; the one cacheable error, the catalog 404, omits `requestId` from its body and carries no `x-request-id` when stored (invariant 16), the pipeline adds the header after the lookup. Codes: `bad_request` 400 (malformed JSON, wrong content type), `validation` 422 (schema), `forbidden` 403 (Turnstile), `not_found` 404, `method_not_allowed` 405 (with `Allow`), `payload_too_large` 413 (over 64 KB), `rate_limited` 429 (with `Retry-After`), `server` 500, `unavailable` 503 (database unreachable and no last good copy exists, invariant 16), `r2_unavailable` 503 (R2 not switched on; raised only by write helpers that B6, B7 and B8 add, never by a public read; the one shared error, F18). The client maps 400 and 422 to "validation", 404 to "not-found", everything else to "server" (`src/services/http/client.ts`), and the visitor only ever sees the calm copy in `lib/strings.ts`.

Invariants
1. Handlers are thin: parse, call one service function, return JSON (architecture 2). No handler imports `@supabase/supabase-js`; only `src/server/lib/db.ts` does.
2. Every response carries `x-request-id`. Every request writes exactly one structured log line with `requestId`, `route`, `status`, `ms`, `ipHash`. Logs never contain an email address, a message body, a raw IP or a token.
3. Every write validates with the Zod schema first and the database constraints second. A schema failure never reaches the database.
4. IPs are never stored raw: `ip_hash = sha256(RATE_LIMIT_SALT + ":" + ip)` (matches `docs/database/schema.md` intent).
5. Public reads return `published` rows only, and never a row of a coming-soon market or, in production, an `Illustrative` row (`src/server/catalog/visibility.ts`; B3 ships a pass-through, B3b implements it). The snapshot already holds published rows only (B2), and `applyVisibility` runs once per snapshot when `getCatalog` maps it, never per request.
6. Nothing external happens inside a request (architecture 1): no email, no post. Side effects are `emitEvent` calls.
7. The site and the API are same-origin, so `VITE_API_BASE_URL` is the relative `/api/public`. During SSR, loaders call the API in-process (no network hop) through an isomorphic fetch; in the browser they use `fetch`. ASSUMED: this avoids a Worker calling its own public URL, which double counts against the 100,000 requests a day and can be refused on shared hostnames. Proved in step 1.
8. The `services` contract, `src/services/types.ts`, does not change. Adapter files change only in transport (headers, fetch implementation).
9. Free tier only. No KV, no Queues, no Durable Objects (G-011).
10. Turnstile has three outcomes, not two (GD-05). `verifyTurnstile` returns `"pass"`, `"fail"` or `"unreachable"` (no answer within 2 seconds, ASSUMED, or a 5xx from Cloudflare). `"fail"` is 403 `forbidden`. `"unreachable"` accepts the write, stores `turnstile_ok = false` on `submissions` and `inquiries` (B7 screen 3 shows a badge), still applies every rate limit and the honeypot, and logs `turnstile: "unreachable"`. `subscribers` has no such column and its double opt-in is the check, so an unreachable Turnstile accepts the signup and logs it. With no secret configured (`local` only) the result is `"unreachable"` too, so local rows are honestly flagged.
11. Bot trap (GD-05): every public form carries one hidden text field named by `honeypotFieldName` (`"website"`, exported by `contracts.ts`, read by both the forms and the pipeline). The pipeline removes it before Zod; when it is non-empty the request gets a normal-looking `201 Receipt` (fresh random id), nothing is written, nothing is emitted, and one log line says `honeypot`. A bot learns nothing from the response.
12. Duplicates are flagged, never rejected (GD-05): in `create_submission`, a submission whose lower-cased agent email and normalised address (lower case, single spaces, no punctuation) match a submission received in the last 30 days sets `submissions.duplicate_of` to the earliest such row and is otherwise processed normally. The 10-minute same-row rule for double clicks stays and runs first.
13. Subject requests (GP-01, CCPA): every request is a `subject_requests` row with `due_at = received_at + 45 days`, created before any reply; nothing is fulfilled in a request (B7 screen 25 exports or deletes by hand, after identity is checked by reply from the requester's own address). The Receipt never says whether a record exists for the email (no account enumeration). Emails in a request are personal data: never logged, scrubbed like every other write.
14. Redirects run before routing (GD-02, GG-01). `src/start.ts` calls `resolveRedirect(request, db)` for GET and HEAD requests outside `/api`, `/admin` and static assets. It answers from two sources taken from the `getCatalog` snapshot (`redirects` and `slug_history`, which B2 puts in `public_catalog_snapshot()`; it queries no table) and merged into one map built once per catalog version (a lookup costs one map read, no database call in the hot path): enabled rows of `redirects` (`from_path` to `to_path` with its `status`) and `slug_history` (`/property/<old>` to `/property/<current>`, `301`, only while the property is published). A slug in neither source falls through to `notFound()`.
15. One read path (architecture 13 rule 1, S52, F24). `src/server/public/state.ts` exports `getPublicState(db)` and `getCatalog(db)`. Both functions and `handlePublic` take the database client as an argument (`getPublicState(db)`, `getCatalog(db)`, `handlePublic(request, db = getDb())`), so a test injects a counting client (F25 e; B4's 1,000 request proof uses it). `getPublicState` calls the RPC `public_state()` and memoises `{ catalogVersion, flags, comingSoonGlobal, comingSoonMarkets, site, illustrativeContent }` for `CATALOG_VERSION_TTL_MS` (15000, `0` in tests) per isolate; these key names, and the snapshot's `redirects` and `slug_history`, are final (F25 b). `illustrativeContent` is derived from `settings.environment` by `public_state()` and is what B3b's `applyVisibility` reads. Nothing in application code bumps `catalog_version`: B2's triggers bump it on publishing, unpublishing or editing published content and on every write to `settings`, `markets.coming_soon`, `redirects` and `slug_history` (F25 a), so a flag or coming-soon change reaches cached pages within 15 seconds. `getCatalog` calls `public_catalog_snapshot()` only when the memoised catalog version differs from the state's, maps it once with `mappers.ts` (`comingSoon` from the state) and memoises the mapped result per isolate. Every public list and detail endpoint, the in-process loaders of invariant 7, `search`, `concierge`, `resolveRedirect` and, for B3b and B13, flags, coming-soon, site settings, sitemap and llms entries read from these two and run no query of their own against any table. Visitor-visible counts and settings are derived from the snapshot or the state, never from a table. The two RPCs are the only database reads on a public request; the write functions are the only other database calls in this slice.
16. Cache layers and the key (rules 2, 3, 4, 5, 6, 7 and 12). `src/server/public/cache.ts` is the one module that stores and reads cached responses, for `kind` `json` (this slice) and `html` (called by the middleware of `src/start.ts`, whose order is B1b's). Key: `https://cache.mop.internal/<release>/v<catalogVersion>/<kind>/<pathname>`, `release` from `SENTRY_RELEASE`, `kind` one of `html`, `json` or `doc` (sitemap, robots, llms files and feeds, which B13 and B17 store through the same module; F25 c); the query string is dropped (the six catalog GETs allow no parameter) and the key never depends on a cookie or a request header. A publish changes `catalog_version`, the next state check sees it and every key changes within 15 seconds, with no purge call. Stored responses carry no `x-request-id`, no `Set-Cookie` and no static security header, with one exception: the Content-Security-Policy header of an `html` entry (`Content-Security-Policy-Report-Only` while B1b ships it report-only) carries the hashes of that page's inline scripts, which B17 computes at render and the middleware passes in the built response, and `cachedResponse` stores it with that entry so a hit and a miss answer with the same policy (F25 d). The pipeline and the middleware add `x-request-id` and the other security headers (B1b) after the lookup (invariant 2 still holds on every response). Never stored: any non-GET or non-HEAD request, any `no-store` response, any response with `Set-Cookie`, any 5xx. Every error body that is not the cacheable catalog 404 is `Cache-Control: no-store`. Stale beats down: the last good state and snapshot stay in memory and under the Cache API key `https://cache.mop.internal/last-good/<kind>/<pathname>`; when the RPC errors or does not answer within 2 seconds, `getPublicState`, `getCatalog` and `edgeCached` serve the last good copy with `x-mop-cache: stale`, log once a minute and report to Sentry; with no last good copy at all the answer is 503 `unavailable`. Every public response carries `x-mop-cache: hit|miss|stale|bypass` and `x-catalog-version`; a write answers `bypass`. `typeof caches === "undefined"` (`vite dev`) and workers.dev make the edge layer a no-op that answers `miss`; the memory layer still works there. Under local `bunx wrangler dev` the Cache API works (E16), so the edge layer is proved there by this slice (step 12) and confirmed on the custom domain at L1.
17. Writes stay cheap (rule 8). The pipeline order for a write is: route and method, size cap, content type, honeypot, memory limit, Turnstile, Zod, DB limit (`rate_limit_check`), service call. A request rejected by the memory limit, by Turnstile or by Zod makes no database call. Analytics events are batched in the browser: `track()` queues, flushes every 10 seconds and on `visibilitychange`, at most 20 events per beacon, and `events.record` stores a batch with one multi-row insert. The 120 per minute memory limit counts beacons.
18. The database client counts its calls. `src/server/lib/db.ts` wraps the `fetch` given to `createClient` and exposes `dbCallCount()` and `resetDbCallCount()` (counts every request to Supabase, test and local only, a plain integer in memory). B4 builds the 1,000 request proof on it (F24); this slice uses it for its own warm-read assertions. The counter is the test-time proof; H1 counts the real queries on the database with `pg_stat_statements` (E15, F25 i).

Events emitted (through `src/server/lib/events.ts`, catalog of architecture 3.6): none for `subjects/request` (no catalog event exists; B7 reads `subject_requests`), `inquiry.received` after an inquiry insert, `submission.received` after a submission insert, `subscriber.created` after a new or still unconfirmed subscriber (A7; no token in the payload), `subscriber.confirmed` after a confirmation click. Analytics beacons are rows in `analytics_events`, not events.
Permissions: anonymous callers only, plus the Svix signature for the Resend hook. No route reads a session. Admin routes are B7, and so is the admin session check: it verifies the JWT locally against the project's ES256 key (E14, F25 i), with no call to Supabase Auth.

## Risks and gotchas (link GOTCHAS ids)
- G-005: routes import through `src/lib/queries.ts` and `services` only. Server code must not import `src/data/*` either; the bundled data reaches the server only in tests (parity test) and in `scripts/seed.ts`.
- G-006: `TURNSTILE_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, `RATE_LIMIT_SALT`, `RESEND_WEBHOOK_SECRET` are Worker secrets only. `VITE_TURNSTILE_SITE_KEY` is public and is the only new `VITE_*` name. Vite import protection (`vite.config.ts`, `**/server/**`) stops a client import of server code; step 1's grep proves it after the isomorphic fetch is added.
- G-004: `contracts.ts` changes (`markets`, media limits) and the SQL checks land in the same commit as their migration; `enums.check.ts` from B2 guards the enums.
- G-011 and P-009: Workers free is 100,000 requests a day; in-process API calls do not add requests. Supabase free egress is 5 GB a month; a full catalog response is under 100 KB and is cached, so a cache miss costs well under 1 MB an hour. The 10 ms CPU limit is the real risk: `toProperty` on 16 rows and Zod parses are small, SSR is the larger cost: measured 2026-10-01 on the current build, `/` ran 6 to 52 ms and `/properties` 10 to 24 ms with no error 1102 in 36 requests (E3), already above 10 ms; B1b step 7 measures again and H1 decides. API route CPU is UNPROVEN until step 13.
- B3's `tests/api` are the committed-mode tests F22 allows, because they cross connections through supabase-js; the harness is B2's and everything else in this slice that touches SQL directly rolls back. DB tests share `mop-dev` with every other slice and run with `fileParallelism: false`; database tests of slices that run side by side share one concurrency group on `mop-dev` (F21): use unique emails and `source_path = '/__test'` and clean up in teardown, so a failed run never leaves rows that skew the 16-property count or the rate-limit buckets (clear test buckets by `key_hash` in setup). `mop-dev` pauses after 7 idle days (P-009): a first request that times out is a paused project, not a defect.
- Cache API does nothing on `workers.dev` hostnames or in `vite dev`, so previews never hit the edge layer; they run on the memory layer alone, which is proved by the call counter test. The Cache API works under local `bunx wrangler dev` (E16), so the edge hit, the query-string rule and the stored 404 are proved by `scripts/cache-proof.mjs` in step 12 and the full catalog response (under 100 KB) is stored and served there; L1 confirms it on the custom domain and H1 measures the 95 percent ratio and HTML caching under real traffic at Stage 5, counting real queries with `pg_stat_statements` (E15). Headers, the versioned key and the last-good fallback are also asserted against a fake `caches`.
- Keep-warm (B8b, F25 h) calls the public handler in-process and always makes one state RPC; that is what keeps an isolate warm and the free database from pausing, since a cache hit alone would not touch it. B3 exposes `handlePublic(request, db)` and `getPublicState(db)` for it and adds nothing else.
- Rule 7 (stale beats down) depends on the isolate still being alive or the Cache API holding a `last-good` copy. A cold isolate on workers.dev with the database down has neither and answers 503 `unavailable`; that case is accepted and logged, not hidden.
- Rule 5: nothing in a cached JSON body varies by visitor. The mapper takes no request input; `readpath.test.ts` and `cache.test.ts` guard it, and B17 computes the script hashes for the HTML side (CSP by hashes, never nonces) and B3 stores the resulting header with the page's cache entry (F25 d).
