Invariants
1. A new test is not finished until it has been watched failing for the right reason (global rule 2). `scripts/watchfail.mjs` does this deterministically and appends to `tests/WATCHED-FAIL.md`; every mutation is also kept as an entry of the registry `tests/mutations/<slice>.json` (`{ id, kind?, test, file, find, replace, run, expect }`, `kind: "sql"` entries carry `sql` instead of `file`, `find` and `replace`), so it can be replayed later, and `tests/unit/mutation-registry.test.ts` fails when a test file has no entry (T-07).
2. A patch that does not apply is a failed run, not a green one: the script exits 2 if the text to mutate is not found exactly once (a stale registry entry), and 1 when a mutation stays green or goes red for another reason (BAD).
3. Tests never call a paid service or send real email. Turnstile uses Cloudflare's always-pass test keys on both sides: every test build sets `VITE_TURNSTILE_SITE_KEY=1x00000000000000000000AA` (the public always-pass site key, B3 runbook; never the GitHub variable, which holds the real key for `main`, E10) and the Worker gets `TURNSTILE_SECRET=1x0000000000000000000000000000000AA` in `.dev.vars`. No test calls Resend: the Worker never sends (B5), and every address a test writes is on the reserved domain `fixtures.invalid`, which no mail server accepts. Events are written in SQL (G20): until B8 step 2a's SQL functions and B8b's recipes exist, a test write creates no job at all. Once they exist, the `send_email` job runs in the Edge Function on `mop-dev`, and B5's `send_email` step (B5 step 4) checks the recipient's domain first: any `.invalid`, `.test` or `.example` address ends `skipped` with `error = 'reserved_domain'` and no call to Resend, whether the send is live or a dry run (G14; `mop-dev` sends for real only once B5 step 5 sets `EMAIL_LIVE=1` with the key that exists since setup A3, E17, and even then only to allow-listed addresses, B5 invariant 6). So `test:e2e:live` stays runnable on `mop-dev` after B5 step 5. Proof once B5 step 4 lands: `bun run db:psql -- -c "select count(*) from email_messages where to_email like '%@fixtures.invalid' and status = 'sent'"` prints 0.
4. Tests never write to the production database (H35 (5)). There is one Supabase project, `mop-dev` (H35 (1)); it becomes the production database at L1's launch switch, so no guard decides by project ref or host. Every entry point of this plan that commits rows or flips a setting first calls B2's `scripts/lib/assert-not-production.mjs`, which reads `settings.environment` over its own connection to `DEV_DB_URL` and refuses with `refusing: production database` (exit 1, before any write) when it is `production`: `scripts/load-fixtures.ts`, `scripts/e2e-coming-soon.ts`, the `E2E_DATASET=1` branch of `tests/e2e/global-setup.ts` (the e2e data set) and `live-forms.spec.ts` (in `beforeAll`). `tests/db/global-setup.ts` (B2) guards the `db` project and its committed mode the same way. `tests/fixtures/service.ts` holds no guard of its own (H35 (5) removed its host check); every writer that uses it has called the guard first. B2's unit test proves that each of these files imports the module; on the CI stack, which is never marked production, the guard passes. Before the launch switch, because `mop-dev` is shared, every db test of this plan runs inside a transaction that is rolled back (`withRollback` from B2's harness in `tests/fixtures/db.ts`, over `DEV_DB_URL`), so nothing it writes survives. None of B4's database tests uses `committed(fn, cleanup)`: F22 allows committed mode only for B3's `tests/api`, B6's parallel invoice-number test and B8's claim, queue and cron tests, which need rows visible across connections; B4's tests need no such thing, so they all roll back. B4 creates no auth user (its tests never call B2's `createAuthUser` or `createStaffUser`). Rows that a transaction cannot cover (rows written over HTTP by the live specs, and the committed dataset of `fixtures:load`) are idempotent, marked by an email on `fixtures.invalid` and removed by `removeFixtureRows` over `DEV_DB_URL` (in `afterAll` for the live specs) (never by a supabase-js `delete`, which runs in its own transaction and is refused by `refuse_hard_delete`). This plan never runs the production seed: L1's launch switch runs it once (H35 (4)). After that switch every laptop run of the entry points above refuses, and the `db` and `e2e` layers run only in CI (H35 (6)). Tests that need a pristine database use a scratch schema on `mop-dev` or a throwaway cluster from the native PostgreSQL 18 (`initdb` in a temp folder; no pg_cron, pgmq or pg_net there). One writer at a time (G34): `scripts/e2e-coming-soon.ts`, `scripts/load-fixtures.ts`, the `E2E_DATASET=1` branch of `tests/e2e/global-setup.ts` and `live-forms.spec.ts` (from `beforeAll` to the end of its `afterAll`) each hold `select pg_advisory_lock(hashtext('mop-dev-tests'))` on one `pg` connection to `DEV_DB_URL` while they commit rows or flip the flag, through `holdDevLock()` in `tests/fixtures/dev-lock.ts`, and release it with `pg_advisory_unlock` at the end. `holdDevLock()` is a no-op when `MOP_DEV_LOCK_HELD=1`, which `e2e-coming-soon.ts` sets for the Playwright run it spawns, so a cleanup inside that run never waits on its parent's lock. In CI none of this touches `mop-dev`: the `db` and `e2e` jobs run on their own ephemeral stack, so they need no lock, no concurrency group and no secret (H1 (b), T-01).

10. The caching contract is proved here in three parts (architecture 13, S52, F24, F25). (1) Memory layer: a database call counter wraps the injectable `db` client that `getPublicState(db)`, `getCatalog(db)` and the public request handler receive (F25 e). After warm-up, 1,000 public page and catalog requests move the counter only by state checks (at most one `public_state` call per 15 seconds of test time) and by one `public_catalog_snapshot` call per catalog version; a table read (`from`) on a public request is a failure, which is rule 1 (one read path) made executable, and so is any RPC name other than those two (search is the in-Worker index over the snapshot, F25 g, so a search moves no counter). The test reads only through the two RPCs; its single write is one `bump_catalog_version()` call (a version number on `mop-dev`, harmless and not rolled back), and its write-path probes send an invalid body so that no row is created. The key names of the raw `public_state()` RPC payload (exactly seven: `catalog_version`, `flags`, `coming_soon_global`, `coming_soon_markets`, `site`, `illustrative_content`, `og_static`) and of the snapshot (`redirects`, `slug_history` among them) are final (F25 b as amended by G39) and the test asserts them on `serviceClient().rpc(...)`; the object `getPublicState(db)` returns is B3's camelCase mapping (`catalogVersion`, `flags`, `comingSoonGlobal`, `comingSoonMarkets`, `site`, `illustrativeContent`, `ogStatic`) and the test asserts those names on it. (2) Query hydration: B3 owns it in `src/router.tsx`; B4 proves by an e2e test that a page load makes no catalog fetch (F25 f). (3) Edge layer: the Cache API works under local `bunx wrangler dev` (E16), so B4 proves it locally on the built artifact by reading the `x-mop-cache` header, miss then hit, with a random query string hitting the same entry, and that the stored Content-Security-Policy header is the same on a hit and a miss (F25 d, j); L1 confirms it on the custom domain and H1 measures the hit ratio with `pg_stat_statements` (E15). A write to the public keys of `settings` (`flags`, `coming_soon_global`, `site`, `environment`, `og_static`, G21), to `markets.coming_soon`, `redirects` or `slug_history` bumps `catalog_version` by B2's trigger (F25 a as narrowed by G21); other `settings` keys (channels, tokens) do not. So no code bumps it by hand and the only deliberate calls are the one above and the one in `edge-cache.spec.ts`; live and coming-soon runs set `CATALOG_VERSION_TTL_MS=0` so a flag flip is seen at once instead of within 15 seconds.
