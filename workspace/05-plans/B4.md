The route sweep (the core of B4)
- Every page route is loaded at 1440x900 (project `desktop`) and 390x844 (project `phone`, `isMobile`, `hasTouch`) and must satisfy: HTTP 200 (or the expected status for redirects and the 404 route); exactly one `h1` (the 404 page has one: "This place is not on our map."); a `<main>` landmark; `<html lang="en">`; a `<title>` that contains "Matter of Place" exactly once (G-003); a non-empty meta description and a canonical link; no `console.error`, no uncaught page error, no failed same-origin request with status 400 or higher; every `<img>` has an `alt` attribute; no horizontal overflow (`document.documentElement.scrollWidth <= window.innerWidth`, and no element wider than the viewport outside an `overflow-x: auto` ancestor); axe with tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` reports no violation of impact `serious` or `critical` that is not in the baseline.
- Route list (`tests/e2e/fixtures/routes.ts`): static `/`, `/properties`, `/markets`, `/stories`, `/editorial-standard`, `/submit`, `/exposure`, `/about`, `/contact`, `/faq`, `/legal`; dynamic `/$market` (3), `/$market/guide` (3), `/$market/$region` (12), `/property/$slug` (16 in the full seed), `/stories/$slug` (all bundled stories); `/sitemap.xml` (status and XML content type only); not found `/no-such-page`. Redirect routes are covered by `redirects.spec.ts`: `/markets/california` to `/california`, `/place-notes` to `/stories`, `/pricing` to `/exposure`, `/california/san-diego` to `/california/la-jolla`, all 301.
- In local mode the parameters come from `src/data/*`; in live mode from `GET /api/public/*` of the target. In a coming-soon database there are no property pages, so the fixture returns none and `coming-soon.spec.ts` (B3b) covers the empty states.
- The axe baseline (`tests/e2e/axe-baseline.json`) lists `{ route, rule, target, reason, ticket }`. The test fails on any violation not in the baseline (a new problem) and on any baseline entry that no longer occurs (a fixed problem must leave the list), so the file can only shrink. ASSUMED: the first run will not be clean (warm grey text tokens are a known contrast risk); every baseline entry becomes a visual-pass ticket (S40).
- Structured data and machine-readable files (GQ-02). On every page route the sweep also collects each `<script type="application/ld+json">`, parses it (a parse error fails the route), requires `@context` to be `https://schema.org`, and compares the `@type` values found (including inside an `@graph`) with `jsonLdExpectations[routeClass]` from `tests/e2e/fixtures/routes.ts`. The map starts with the types that `src/lib/seo.ts` already emits (an empty list means "any valid block is fine") and B13 fills it with the required types per route class when its builders land (home: `Organization`, `WebSite`; property: `RealEstateListing`, `BreadcrumbList`; story: `Article`; FAQ: `FAQPage`). `/robots.txt`, `/llms.txt` and `/llms-full.txt` join the route list as `seoFileRoutes` only when their route file exists under `src/routes` (the list is computed from the same directory read as `routeFileCoverage`, so it is deterministic and never an environment switch); each must answer 200 with `text/plain`, and the two `llms` files must start with an H1 line and contain only absolute `https` links. The typed builders (`schema-dts`) and the per-page-type parser tests are B13's; this is the end-to-end net under them.
- Performance budget (GQ-01). Six pages, `lighthouseRoutes(mode)`: `/`, `/properties`, the first property, the first market, `/exposure`, `/submit` (the auditor's list, B13). One file, `budget.json`, holds the hard limits that fail the PR: LCP 2500 ms, CLS 0.1, JavaScript 150 KB transferred (gzip) on first load. `lighthouserc.json` runs mobile Lighthouse three times per page (median) against the preview URL and asserts them at level `error`. B13 adds the tighter targets as warnings and the page-by-page tuning; it edits these two files rather than creating them.

Invariants
1. A new test is not finished until it has been watched failing for the right reason (global rule 2). `scripts/watchfail.mjs` does this deterministically and appends to `tests/WATCHED-FAIL.md`.
2. A patch that does not apply is a failed run, not a green one: the script exits 2 if the text to mutate is not found exactly once.
3. Tests never call a paid service or send real email. Turnstile uses Cloudflare's always-pass test keys; Resend is mocked.
4. Tests never touch `mop-prod`. The `db` and live projects refuse any `SUPABASE_URL` whose host is not `<DEV_SUPABASE_PROJECT_REF>.supabase.co` (`hbokkmpgpqhrnemgsqra` today), and refuse a database whose `settings.environment` is `production` (`tests/db/global-setup.ts`, `scripts/load-fixtures.ts`). Because `mop-dev` is shared, every db test of this plan runs inside a transaction that is rolled back (`withRollback` from B2's harness in `tests/fixtures/db.ts`, over `DEV_DB_URL`), so nothing it writes survives. None of B4's database tests uses `committed(fn, cleanup)`: F22 allows committed mode only for B3's `tests/api`, B6's parallel invoice-number test and B8's claim, queue and cron tests, which need rows visible across connections; B4's tests need no such thing, so they all roll back. Rows that a transaction cannot cover (auth users made with B2's `createAuthUser` and `createStaffUser`, rows written over HTTP by the live specs) are idempotent, marked (`fixtures.invalid`, `/__e2e`) and removed in `afterAll`. The seed is never run with `--target prod` here (BLOCKED until launch, F17); tests that need a pristine database use a scratch schema on `mop-dev` or a throwaway cluster from the native PostgreSQL 18 (`initdb` in a temp folder; no pg_cron, pgmq or pg_net there).
5. External fonts are blocked in CI (`page.route` on `fonts.googleapis.com` and `fonts.gstatic.com`) so runs are deterministic and offline-tolerant. ASSUMED trade-off: layout can differ slightly from real fonts, so an `@overflow` subset runs against the real preview URL after deploy (step 10).
6. One flaky pass counts as a failure in CI (`failOnFlakyTests`), so a retry cannot hide a defect. ASSUMED: one retry only to collect a trace.
7. Free tier: Actions minutes are the budget (P-009). The plan aims for under 10 minutes per PR push; measured in step 10, not assumed.
8. Test data is deterministic (GQ-03). Factories take their clock from `tests/fixtures/clock.ts` (`FIXED_NOW = 2026-10-01T12:00:00Z`), their randomness from a seeded generator (`mulberry32(seed)`), and their ids from `deterministicUuid(namespace, n)`, so two runs produce the same rows and the same ids. No factory calls `Date.now()`, `Math.random()` or `crypto.randomUUID()` (a unit test greps the files). Every row a factory or the dataset inserts is marked by an agent or inquirer email on the reserved domain `fixtures.invalid`, so cleanup and counts never touch other rows.
9. The illustrative seed is the catalog baseline; the factories are for operational rows the seed does not hold (submissions in every workflow state, invoices, jobs). A factory writes through the service role and respects B2's rules: `rights_version`, `rights_confirmed_at` and `rights_ip_hash` are always set, and deleting goes through a transaction that sets `mop.retention = 'on'` because the hard-delete guard refuses anything else.
10. The performance budget has one source, `budget.json`. `tests/unit/perf-budget.test.ts` fails when `lighthouserc.json` asserts a looser limit than `budget.json` holds, when the six URLs differ from `lighthouseRoutes`, or when an assertion level is `warn` for a hard limit.

Events emitted: none. Permissions: none; test helpers use the `mop-dev` service key (from the environment, never committed) and never ship. Nothing in this plan needs R2: the seed runs with `--images skip` and the sweep reads bundled images (R2 is off, S50).

## Risks and gotchas (link GOTCHAS ids)
- G-001: the `routes-covered` watched-fail creates and deletes a route file; never touch `routeTree.gen.ts`, and delete the temporary file before running `bun run dev` or `build`, which would regenerate the tree.
- G-003: the sweep's title check is the regression guard for the double brand; `seo.test.ts` remains the unit guard.
- G-007: tests do not assert colour values; contrast is axe's job, tokens are the styling rule.
- G-011 and P-009: Actions minutes. Estimated per push (UNPROVEN until step 10): `check` 2, `build` 1.5, `db` 2 (no stack to start, one `gen:types` call and the tests), `e2e` 6 (build 1.5, sweep about 3), `e2e-live` 6 only on matching diffs. About 15 minutes at worst, about 10 typical; 2,000 minutes allow about 130 pushes a month. Mitigations already in the plan: cancel superseded runs, `paths-ignore` for docs, path-gated live job.
- Playwright on Windows local runs needs `bun run test:e2e:install` once; CI uses `--with-deps`. Use absolute paths in npm scripts if a script is run from another folder (P-013).
- `wrangler dev` uses workerd; on the runner it needs no extra install. Local secrets go in `.dev.vars` (gitignored): the `mop-dev` URL and service key (live mode writes to `mop-dev`) and the Turnstile always-pass test secret, never the production Turnstile secret and never a `mop-prod` value. CI writes it from `PREVIEW_WORKER_SECRETS_JSON` (E10); a later slice's preview secret is added as a key to that GitHub secret, never by editing `ci.yml` or `deploy.yml`.
- Blocking external fonts changes layout; the `@overflow` preview run is the compensation. If real fonts overflow where fallback fonts do not, that is a real defect the preview run will find.
- Automated axe checks cover only part of what accessibility needs (contrast, names, landmarks, ARIA validity) and do not replace a keyboard pass. HARDEN includes a manual keyboard and screen-reader pass for the submit wizard and the dialogs.
- The first baseline may be long. Do not widen the impact filter to hide it; each entry needs a `reason` and a `ticket`.
- The state machine exists in three places (SQL function, `workflow.ts`, this spec table). Changing one without the other two must be red: (c) covers TS against spec, B2's test covers TS against SQL.
- `failOnFlakyTests` needs Playwright 1.52 or newer; check the installed version at step 1 and drop the option (keeping `retries: 0`) if it is older.
- `mop-dev` is shared and on the free tier (500 MB, pauses after 7 idle days, P-009): fixture rows are tiny and removed after each run; a paused project makes the `db` job fail with a connection error, not a test failure, so restore it before debugging tests. A test that needs pg_cron, pgmq or pg_net runs on `mop-dev` only; one that needs a pristine database uses a scratch schema or a native PostgreSQL 18 cluster (no extensions).
- GQ-01: Lighthouse on a `workers.dev` preview is pessimistic, because the Cache API does not work there (B1b), so LCP for server-rendered pages includes a cold render. UNPROVEN that the hard limits hold on the preview; the first measured numbers go into `tests/README.md`. If a page fails on the preview and would pass behind the custom domain, that is a decision recorded in `PROJECT-STATE.md` (measure against the production host after Stage 5), not a silent loosening of `budget.json`. Shared runners are noisy, hence three runs and the median. Cost: about 4 minutes per preview run (UNPROVEN until step 10), which is why the step is path-gated; it adds to the P-009 Actions estimate above.
- GQ-01 and B13: both plans describe `lighthouserc.json`, `budget.json` and a Lighthouse run. Here B4 creates the files and the preview-URL run first (landing order); B13 then edits them and keeps its `seo` job for `check-seo.ts`, `validate-jsonld.ts` and `validate-llms.ts` only, so Lighthouse does not run twice per push. If B13 lands with its own `lhci` call in the `seo` job, remove one (single writer per file).
- GQ-02: until B13 lands its builders, `jsonLdExpectations` is nearly empty and the sweep proves only that present blocks parse and use the right context. That is weaker than the final check and is recorded as UNPROVEN for required types until B13 fills the map and its watched-fail (h) runs.
- GQ-03: `createJob` targets the `jobs` columns of architecture 3.6, but `jobs` is created by B8, which lands after B4. Until then the job factory is compiled against the documented columns and its db case is skipped with a printed line; that is UNPROVEN, and B8 step 1 must remove the skip and run `tests/db/factories.db.test.ts`. `createInvoice` depends on B2's `payments` (exists) and does not call `next_invoice_number()` (B6 replaces it), so B6's change cannot break it.
- GQ-03: deleting factory rows with a plain `delete` fails by design (B2 invariant 4, `refuse_hard_delete`). `removeFixtureRows` sets `mop.retention = 'on'` inside its transaction; a test author who bypasses it gets a clear database error, not a leftover row.
