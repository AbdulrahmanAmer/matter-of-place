## Goal and observed exit
Every published property produces its owned creative without a designer in the loop: cover 1200×630 (with an X crop 1200×675 and a LinkedIn crop 1200×627 rendered beside it), carousel 1080×1350 with 6 to 8 slides (plus a 1080×1080 LinkedIn set of its first 3 to 4 images), story 1080×1920, newsletter block, and (Campaign tier only, S24) standalone email; captions and alt text written by Haiku through the operator's Claude account on his laptop (S20, S58, ASSUMED H34) under brand-voice lint, in three variants per property (Instagram, X short, LinkedIn editorial, S48); everything lands in `assets` as `pending` and waits for a human on `/admin › Assets` (screen 10, S23).
Observed exit (completion map B9): "PNGs for one property match the chosen design." Proof is three things together: the CEO's picks recorded in `workspace/08-creative/DIRECTION.md` and PROJECT-STATE; a render run of the fixture property whose image dimensions are asserted by a script; a contact sheet of the run placed next to the chosen option PNGs for a human match check.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- Event `property.published` (architecture 3.6) fans out to the steps `render_cover`, `render_carousel`, `render_story`, `write_captions`, `build_newsletter_block` and `render_variants` (the step module is this slice's; the image library it calls, `scripts/variants.ts`, is B2's); `render_reel` is owned by B12. B7 emits `{ property_id, slug, tier, market, submission_id? }`; B8's runner passes it as `payload.data` to `run(ctx, params, data)` (envelope `jobs.payload = { params, data }`, B8).
- Step module shape from B8: `{ type, heavy, paramsSchema, run(ctx, params, payload), onResult? }`. Every B9 module imports `heavy` and `paramsSchema` for its type from `src/server/automation/step-specs.ts` (B8b invariant 1) and never declares its own; heavy modules dispatch through `dispatchHeavy(ctx, job, extra)` from `src/server/jobs/steps/heavy.ts` (B8), which merges `extra` into `payload.data` of the dispatch and returns it as the job's `result`. The three render steps pass `extra = { spec, spec_hash, revision, asset_id }`, so a render script reads the spec at `job.payload.data.spec` and `onResult` reads `job.result.spec_hash`, `job.result.revision` and `job.result.asset_id`; `render_variants` passes `extra = { media }` (Files).
- A render spec, built deterministically from the property row and its `property_media.variants` (thumb, card, hero, og, carousel): `RenderSpec = { kind, property: { id, slug, title, city, state, market, price, currency, beds, baths, interiorSqFt, yearBuilt, type }, images: [{ url, alt, orientation, w, h }], slides?: SlideSpec[], out: { key_prefix } }` (`key_prefix` is `assets/<property_id>/<kind>/r<revision>/`, the folder of the keys in bucket `media`). The serialized job stays under the `workflow_dispatch` input limit of 65,535 characters that B8's `dispatchHeavy` checks (SEC-02: dispatch goes to `/actions/workflows/render.yml/dispatches` with the job as the one input `job`) because it carries URLs and text only.
- Every B9 module the job runner loads (the step modules under `src/server/jobs/steps/`, and what they import: `src/server/assets/{spec,captions,voice,links}.ts`, `src/templates/social/slides.ts`) writes each relative, `@/server/` or `@/domain/` import with the `.ts` extension, because Deno 2 refuses extensionless specifiers (CS-01); the `deno` step of the CI `check` job checks them through `supabase/functions/job-runner/index.ts` (B3 adds the step, B8 points it at the runner).
- Haiku for `write_captions` only, through the operator's Claude account on his laptop (S58, ASSUMED H34). H34 (1) removed the Anthropic key of S20 from every list of secrets: no key exists in function secrets, in GitHub or in `.env`, and nothing waits for one. `write_captions` is a step of the third execution class, `local`, beside light and heavy (H34 (2)): B8's job runner never executes it, its job stays `queued` until `scripts/captions-runner.ts` (Files) claims it on the laptop, and screen 10 and B8's health read a queued one as "waiting for the caption runner". An editor can always type the captions by hand on screen 10, which completes the waiting job with `{ manual: true }` (H34 (5)); nothing downstream waits on the laptop. Tests never call the real CLI: they set `CAPTIONS_CLI` to the stub `tests/fixtures/claude-stub.ts` (H34 (7)).

Outputs
- `assets` rows, one per `(property_id, kind, revision)`: `files` (`[{ media_key, w, h, bytes, role }]`, `role` is an ASSUMED extra key used by B12 for `video` and `poster`, and by this slice for the channel crops: `x` (1200×675) and `linkedin` (1200×627) on the `cover` asset, `linkedin_set` (1080×1080, 3 to 4 files, with `index`) on the `carousel` asset; the base files are `main` (the 1200×630 cover, the 1080×1920 story) and `slide` (each 1080×1350 carousel slide, with `index` from 0); consumers such as B10 and B13 pick a file by `role`, never by position; no new asset kind), `caption` (the Instagram caption), `alt_text`, `meta jsonb` (ASSUMED new column: `captions { instagram, x, linkedin }` (the `caption` column mirrors `captions.instagram`), `slide_alts[]`, `spec_hash`, `caption_lint`, newsletter block copy, standalone subject and preheader), `status`.
- Files in the public Supabase Storage bucket `media` of the one project (ASSUMED H33 (1)) at `assets/<property_id>/<kind>/r<revision>/<name>.<hash8>.<ext>`. Every file this slice renders is a JPEG (`jpg`, `image/jpeg`, quality 92): Instagram's `image_url` accepts JPEG only (Meta's IG User Media reference, "Format: JPEG", for image, carousel item and story containers), X, LinkedIn and Open Graph readers accept it, and H33 (8) keeps the stored files small for the 1 GB wall (WebP except where a channel needs JPEG or PNG; every file here is read by a channel, and a photographic JPEG is several times smaller than a PNG); B12 passes `mp4` and `jpg`, G30. `hash8` is the first 8 hex characters of the SHA-256 of the file bytes (content-hashed media key, architecture 13 layer Media, F24); every upload to `media` sets `cache-control: public, max-age=31536000, immutable` (H33 (3)); the stored `files[].media_key` carries the hashed name, so no URL is ever built by guessing and a re-render is a new key, never an overwrite. The public address of every file is `/media/<key>` on our own domain: B3's resource route streams it from Storage with the same cache header and makes no database query (H33 (4)). Every URL in this slice that leaves the admin pages is built by B3's `mediaUrl(key, { absolute: true })` from `src/server/lib/media-store.ts`, which prefixes the function secret `MEDIA_PUBLIC_BASE` (ASSUMED H33 (2), (4); the name replaced `MEDIA_BASE_URL` of G3): the dev Worker's origin followed by `/media` before L1's launch switch, the production Worker's origin followed by `/media` from L1 step 1d, and `https://matterofplace.com/media` from L1 step 4e, because Meta, mail clients and the render scripts fetch the files from outside (B10). `render.yml` holds no media base: every image a render script fetches arrives in the spec as an absolute URL. No second base variable exists, and no URL in this slice points at a `supabase.co` address. The render scripts keep a local mode (`--out <dir>`, no upload, no network) for the fixture runs of steps 1 to 6.
- Static OG set for non-property pages, seven keys `home`, `markets`, `market-california`, `market-new-york`, `market-florida`, `stories`, `default` (G5). The set pages use is committed files: B13 runs this slice's `bun scripts/render-og-static.mjs --out public/og/static`, which writes `public/og/static/<key>.png` (stable names, no hash, 1200×630), and commits them; they are served as static assets and need no Storage. The manual job `render_og_static` is optional: it uploads a newer set to bucket `media` at `og/static/<key>.<hash8>.png` with `putIfMissing` (seven small flat cards, so they stay PNG), and its `onResult` writes the `settings` row `og_static` = `{ <key>: { media_key, w: 1200, h: 630 } }` (one call of the SQL function `set_og_static`, Data changes, with the service role; a public `settings` key, so it bumps `catalog_version`, G21); B13 prefers a key found there over the committed file. These keys carry the content hash like every key in `media` (H33 (3)), so a newer card is a new key and a new address and needs no purge; there is no stable key and no `putStable`.
- Events: `asset.approved` and `asset.rejected` (both in the 18-event catalog of architecture 3.6), emitted with `emit_event` inside the SQL functions `approve_asset` and `reject_asset` (Data changes), in the same transaction as the status change and the audit row. Payloads: `asset.approved` `{ asset_id, property_id, kind, tier, market }` (the shape B10 reads), `asset.rejected` `{ asset_id, property_id, kind, tier, market, note }`. `assets` has no tier or market column: `tier` is `properties.campaign_tier` and `market` is `properties.market_slug` of the asset's property, read in the same transaction (the same source for `rerender_asset`'s job payload). No new event types.

Invariants
1. Nothing here posts, sends or publishes. Output only ever reaches `pending` (S23). Approval is a separate human action (or the auto path defined in B10).
2. Determinism: same `spec_hash` means same pixels. Templates take data only; no clocks, no randomness, no network inside a template. Fonts are self-hosted files, never a CDN.
3. Idempotency: recipe jobs use `event_id:step_id` (B8). A re-render is a new `revision` row plus a manual job with key `<job type>:<property_id>:<revision>` (B8 invariant 1 manual form; for the render kinds this reads `render_<kind>:<property_id>:<revision>`; `newsletter_block` and `standalone_email` share one job type, so their key is `build_newsletter_block:<property_id>:<kind>:<revision>` and `payload.data.kind` names the kind); the old revision becomes `rejected` with note `superseded`. Kind to job type: `cover` to `render_cover`, `carousel` to `render_carousel`, `story` to `render_story`, `reel` to `render_reel` (B12), `newsletter_block` and `standalone_email` to `build_newsletter_block`. The job's `payload.data` carries `revision`, and every B9 step writes `payload.data.revision` when present, else the current revision (the highest one not `rejected`).
4. Approval guard, per kind (trigger `assets_approve_guard`, before update when `status` becomes `approved`): `cover`, `carousel`, `story`, `reel` need non-empty `files`, `caption` and `alt_text`, and `meta->>'caption_lint'` not equal to `failed`; `newsletter_block` needs `meta.block.title`, `meta.block.deck`, `meta.block.image_key`, `meta.block.image_url` and `alt_text` non-empty (it has no PNG, so `files` may be empty); `standalone_email` needs `meta.subject`, `meta.preheader` and `meta.block` non-empty. A reject needs a note (trigger `assets_reject_note`). `tests/db/assets.db.test.ts` has one passing and one refused approval per kind.
5. Brand voice is checked by code, not trusted to the model: no em dashes, no words from the banned list (stunning, dream, must-see, luxury living, "just listed" and the rest in `src/server/assets/voice.ts`), no exclamation marks, at most 2,200 characters for Instagram, 280 for the X caption with the property link counted at its shortened length (ASSUMED 23, UNPROVEN, confirmed by B10 step 3a) and 3,000 for LinkedIn (ASSUMED, UNPROVEN), no hashtags at launch (ASSUMED), no guarantee language (leads, buyers, sales), no price framed as merit (in code: a sentence that contains the price or any `$` amount must not also contain a word from `MERIT_WORDS` in `voice.ts`: exceptional, finest, best, premier, prestigious, worth), every number in a caption must appear in the property row. A caption that fails lint twice is stored with `meta.caption_lint = "failed"` and cannot be approved (invariant 4) until a human edits it through `editCaption`, which re-lints and sets `caption_lint = "edited"` only when every variant passes.
6. The visual grammar is fixed by the chosen direction: small wordmark, dominant image, LOCATION, price, minimal specs ("5 BED · 4.5 BATH · 4,320 SF"). No gradient, glow, gold, big agent headshot, or "JUST LISTED" (mop-designer brand rules, G-007).
7. Tier gate: `standalone_email` assets are created only when `payload.tier = "Campaign"` (S24); `build_newsletter_block` and `write_captions` re-check the tier themselves, so a mis-edited recipe cannot create one. The `reel` tier guard is B12's invariant 1 in `render-reel.ts`.
8. Media keys are content-hashed and never overwritten (architecture 13, F24): `scripts/lib/media-key.mjs` computes `hash8` from the bytes, and `scripts/lib/media-store.mjs` uploads every key with `x-upsert: false` and the immutable header of H33 (3), so an existing key is never replaced and the edge and the browser never need a purge for an asset. The one exception is a rights takedown (E2E-01): the light system job `takedown_media` (`src/server/jobs/system/takedown-media.ts`, enqueued by B7's `unpublish_property` when `p_takedown` is true) deletes every key of the property, each `assets.files[].media_key` and `properties.og_image_key` included, with B3's `deleteObjects("media", keys)` from `src/server/lib/media-store.ts` (Storage's remove) and then purges their `/media/<key>` addresses from Cloudflare's cache (H33 (6)); it needs only `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, which the job runner already holds. No B9 code deletes an object of bucket `media`, and the render steps never run for it again because their state guard refuses a property that is not `published`.
9. Admin reads are not cached and stay cheap (architecture 13 rules 6 and 9): the six `/api/admin/assets*` routes answer `Cache-Control: no-store`, which B1b's pipeline sets on all of `/api/admin/*` (G65; the handlers set none), `listAssets` is paginated at 50 on the existing indexes, and no public read in this slice touches a table (assets are never on a public page; the only public image is the OG card, served at `/media/<key>` by B3's route, which makes no database query (H33 (4)), and `property.published` fan-out reads the property row inside a job, not on a page view).
10. Variants first (B8b invariant 6). `render_variants` runs in the same parallel fan-out as the steps that read its output, so `render_cover` (needs `og`), `render_carousel` and `render_story` (need `carousel`), `build_newsletter_block` (needs `og`) and `write_captions` (needs `carousel`, so its slide alts follow the same `planCarousel` input as the render) first call `variantsReady(db, propertyId, variant)` from `src/server/assets/spec.ts`. While any `property_media` row of the property lacks that key in `variants`, the step returns `{ status: "retry_at", at: now + 2 minutes, reason: "variants_pending" }` (no attempt consumed, B8 invariant 3). Here and in every other `retry_at` and age check of this slice, `now` is `ctx.now`, B8's `StepContext.now`, a `Date` (G58); no step reads the clock itself, so `steps.test.ts` fixes the time through the context. The wait is measured from the `created_at` of the asset stub the step upserted first (every step, `write_captions` and `build_newsletter_block` included, upserts its stub or stubs before it waits, so the clock always has a start; `render_variants` itself has no stub and does not wait), so a re-render restarts the clock; after 60 minutes the step throws `NonRetryableError("variants_missing")` and the job goes `dead`. B12 states the same rule for `render_reel`.
11. Failures are visible on the card. `assets.render_error` is written only by the trigger `assets_job_error` on `jobs` (Data changes): when the job named in `assets.job_id` moves to `failed` or `dead`, the asset gets `render_error = jobs.error`; a later `onResult` on `done` clears it. Screen 10 shows the error with Re-render.
12. A second publish never overwrites approved work. A property can emit `property.published` again (archived, back to draft, review, published; B7), which creates new `event_id:step_id` jobs. A recipe job (no `payload.data.revision`) checks the row `upsert_asset_stub` returns for its kind (it returns the status): when the current revision is `approved` or `published`, that kind is skipped and nothing is written to it; when every kind the step handles is skipped, the step returns `{ status: "done", result: { skipped: "already_approved" } }` without a dispatch. This holds for the three render steps, `write_captions` (per kind) and `build_newsletter_block` (per kind); `render_reel` follows the same rule in B12's `render-reel.ts`. A changed property gets new creative only through Re-render, which makes a new revision. `steps.test.ts` case "approved cover untouched by a second publish".

## Risks and gotchas (link GOTCHAS ids)
- G-012: the render workflow is at the repository root, `working-directory: app` per job.
- G-007: templates use tokens only; the social token block is added to `tokens.css` first.
- G-004: `src/domain/assets.ts` names equal generated types and snake_case columns; `meta`, `revision`, `role` change all three together.
- G-006: the service role key and the callback secret are never `VITE_*`; ASSUMED H34 (1) removed the Anthropic key and H33 (2) removed the R2 keys, so neither exists anywhere.
- G-011 and P-009: captions are the only model use and run through the operator's Claude account on his laptop (H34), so they cost no API spend; a publish makes one CLI call when the runner claims its job. While the laptop is off the jobs wait, screen 10 shows "waiting for the caption runner" and B8's health notifies an admin after 24 hours (H34 (6)); an editor can type the captions instead. No Browser Rendering binding: screenshots run in Actions.
- P-026-style traps: Windows path of Chrome in `launch/engine/chrome.mjs` does not exist on Linux, which is why the render scripts take `CHROME_PATH`. Verify on the runner, UNPROVEN until step 10 runs (it waits only for B8 step 7, which sets the dispatch token made on 2026-10-02 as a function secret, ASSUMED E22).
- P-038 and S50: no Docker on the laptop, no `supabase start` or `db reset` there; database proofs run in the PR's CI `db` job on its ephemeral stack (ASSUMED H1 b, GitHub-hosted runners may run containers) through B2's harness `tests/fixtures/db.ts` (F22), and this lane never pushes an unmerged migration to `mop-dev` (H1 d). Steps 1 to 9 need no bucket; the three buckets are B2's (H33 (1)). After the launch switch the database tests of this slice run only in the CI `db` job (H35 (6)).
- Workers free plan: one Worker request may make at most 50 subrequests (vendor documentation, UNPROVEN here). `render_variants` `onResult` runs inside B8's callback request, so it makes 3 calls whatever the photo count (JOB-03); a change that adds a call per photograph breaks a 40-photograph property. The line goes into GOTCHAS P-009 and architecture's free-tier list (handed to their owners).
- One render per upload batch (ASSUMED H3): B7's `request_property_render` coalesces an upload burst into one job per property, and `claim_media_for_render` keeps two jobs from rendering the same row, so a 40-photograph upload costs one Actions run, not forty (PERF-01, E2E-08, JOB-08).
- `src/server/hooks/render.ts` (B8) is not edited: B9 uses `onResult` for success and the `assets_job_error` trigger for failure, so the hook needs no asset knowledge.
- The job runner builds image URLs with `mediaUrl(key, { absolute: true })`, so it needs `MEDIA_PUBLIC_BASE` in its own environment (a Supabase function secret, H33 (2)) as well as the Worker's, and there it must be the absolute `/media` base of ASSUMED H33 (4), because Meta, mail clients and the render scripts fetch the files from outside; with the name unset the three render steps and `build_newsletter_block` throw `NonRetryableError("media_public_base_missing")` before building a spec or a block, and the card shows the error with Re-render. Step 10 sets the function secret now; L1 steps 1d and 4e set the production values on the same project (H35 (1)).
- Staged originals (G25): a `render_variants` job that dies leaves its staged files in bucket `submissions` with `staging_path` set; screen 9 shows the row as failed and Retry re-runs it. Nothing deletes a staged file before its stripped copy and its variants are stored in bucket `media`.
- The 1 GB Storage wall (ASSUMED H33 (8), P-009): `submissions`, `media` and `documents` share 1 GB, and only cache misses of `/media/<key>` count against the 5 GB of Storage egress a month. This slice stays inside it by storing JPEG renders only, the stripped copy at most 2560 px on its long edge and never the uploaded original (it is deleted from `submissions` once its variants exist); every re-render adds new keys and old revisions keep theirs, so re-renders spend the wall too.
