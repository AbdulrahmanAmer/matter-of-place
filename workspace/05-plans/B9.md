## Goal and observed exit
Every published property produces its owned creative without a designer in the loop: cover 1200×630 (with an X crop 1200×675 and a LinkedIn crop 1200×627 rendered beside it), carousel 1080×1350 with 6 to 8 slides (plus a 1080×1080 LinkedIn set of its first 3 to 4 images), story 1080×1920, newsletter block, and (Campaign tier only, S24) standalone email; captions and alt text written by Haiku (S20) under brand-voice lint, in three variants per property (Instagram, X short, LinkedIn editorial, S48); everything lands in `assets` as `pending` and waits for a human on `/admin › Assets` (screen 10, S23).
Observed exit (completion map B9): "PNGs for one property match the chosen design." Proof is three things together: the CEO's picks recorded in `workspace/08-creative/DIRECTION.md` and PROJECT-STATE; a render run of the fixture property whose PNG dimensions are asserted by a script; a contact sheet of the run placed next to the chosen option PNGs for a human match check.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- Event `property.published` (architecture 3.6) fans out to the steps `render_cover`, `render_carousel`, `render_story`, `write_captions`, `build_newsletter_block` and `render_variants` (the step module is this slice's; the image library it calls, `scripts/variants.ts`, is B2's); `render_reel` is owned by B12. B7 emits `{ property_id, slug, tier, market, submission_id? }`; B8's runner passes it as `payload.data` to `run(ctx, params, data)` (envelope `jobs.payload = { params, data }`, B8).
- Step module shape from B8: `{ type, heavy, paramsSchema, run(ctx, params, payload), onResult? }`. Every B9 module imports `heavy` and `paramsSchema` for its type from `src/server/automation/step-specs.ts` (B8b invariant 1) and never declares its own; heavy modules dispatch through `dispatchHeavy(ctx, job, extra)` from `src/server/jobs/steps/heavy.ts` (B8), which merges `extra` into `payload.data` of the dispatch and returns it as the job's `result`. The three render steps pass `extra = { spec, spec_hash, revision, asset_id }`, so a render script reads the spec at `job.payload.data.spec` and `onResult` reads `job.result.spec_hash`, `job.result.revision` and `job.result.asset_id`; `render_variants` passes `extra = { media }` (Files).
- A render spec, built deterministically from the property row and its `property_media.variants` (thumb, card, hero, og, carousel): `RenderSpec = { kind, property: { id, slug, title, city, state, market, price, currency, beds, baths, interiorSqFt, yearBuilt, type }, images: [{ url, alt, orientation, w, h }], slides?: SlideSpec[], out: { r2_prefix } }`. Payload stays under the 64 KB dispatch limit (B8) because it carries URLs and text only.
- Haiku through the Anthropic API for `write_captions` only. Secret `ANTHROPIC_API_KEY` in Supabase function secrets, never `VITE_*` (G-006); no Anthropic account or key exists yet (E9), so it is set with `supabase secrets set` once the operator supplies it, and everything that calls the live model is BLOCKED until then (tests use a mocked client). Model id stored in `settings.caption_model`, seeded by this slice's migration (Data changes); ASSUMED default a current Haiku id, confirm at build.

Outputs
- `assets` rows, one per `(property_id, kind, revision)`: `files` (`[{ r2_key, w, h, bytes, role }]`, `role` is an ASSUMED extra key used by B12 for `video` and `poster`, and by this slice for the channel crops: `x` (1200×675) and `linkedin` (1200×627) on the `cover` asset, `linkedin_set` (1080×1080, 3 to 4 files, with `index`) on the `carousel` asset; the base files are `main` (the 1200×630 cover, the 1080×1920 story) and `slide` (each 1080×1350 carousel slide, with `index` from 0); consumers such as B10 and B13 pick a file by `role`, never by position; no new asset kind), `caption` (the Instagram caption), `alt_text`, `meta jsonb` (ASSUMED new column: `captions { instagram, x, linkedin }` (the `caption` column mirrors `captions.instagram`), `slide_alts[]`, `spec_hash`, `caption_lint`, newsletter block copy, standalone subject and preheader), `status`.
- Files in R2 at `assets/<property_id>/<kind>/r<revision>/<name>.<hash8>.<ext>` (`png` for this slice's renders, except the carousel `slide` files and the story `main` file, which are `jpg` because Instagram's `image_url` accepts JPEG only (Meta's IG User Media reference, "Format: JPEG", for image, carousel item and story containers); B12 passes `mp4` and `jpg`, G30), where `hash8` is the first 8 hex characters of the SHA-256 of the file bytes (content-hashed media key, architecture 13 layer Media, F24), uploaded with `Cache-Control: public, max-age=31536000, immutable`; the stored `files[].r2_key` carries the hashed name, so no URL is ever built by guessing and a re-render is a new key, never an overwrite. Public through the R2 custom domain (`media.matterofplace.com` in production, G47; Meta must be able to fetch it, see B10); every public URL in this slice is built by B3's `mediaUrl(key)` in `src/server/lib/r2.ts`, which prefixes `MEDIA_BASE_URL` (B3 and B1b own the name); no second base-URL variable exists. R2 is off and no bucket exists (E8, S50): every upload and every public URL is BLOCKED until the operator turns R2 on, so the render scripts have a local mode (`--out <dir>`, no upload) that every step before step 10 uses.
- Static OG set for non-property pages, seven keys `home`, `markets`, `market-california`, `market-new-york`, `market-florida`, `stories`, `default` (G5). The set pages use is committed files: B13 runs this slice's `bun scripts/render-og-static.mjs --out public/og/static`, which writes `public/og/static/<key>.png` (stable names, no hash, 1200×630), and commits them; they are served as static assets and need no R2. The manual job `render_og_static` is optional and only useful once R2 is on: it uploads a newer set to `og/static/<key>.png` with `putStable`, and its `onResult` writes the `settings` row `og_static` = `{ <key>: { r2_key, w: 1200, h: 630 } }` (one call of the SQL function `set_og_static`, Data changes, with the service role; a public `settings` key, so it bumps `catalog_version`, G21); B13 prefers a key found there over the committed file. These R2 keys are stable, not hashed, so they are uploaded with `Cache-Control: public, max-age=3600` and never `immutable`; a changed card shows within the hour without a purge.
- Events: `asset.approved` and `asset.rejected` (both in the 18-event catalog of architecture 3.6), emitted with `emit_event` inside the SQL functions `approve_asset` and `reject_asset` (Data changes), in the same transaction as the status change and the audit row. Payloads: `asset.approved` `{ asset_id, property_id, kind, tier, market }` (the shape B10 reads), `asset.rejected` `{ asset_id, property_id, kind, tier, market, note }`. `assets` has no tier or market column: `tier` is `properties.campaign_tier` and `market` is `properties.market_slug` of the asset's property, read in the same transaction (the same source for `rerender_asset`'s job payload). No new event types.

Invariants
1. Nothing here posts, sends or publishes. Output only ever reaches `pending` (S23). Approval is a separate human action (or the auto path defined in B10).
2. Determinism: same `spec_hash` means same pixels. Templates take data only; no clocks, no randomness, no network inside a template. Fonts are self-hosted files, never a CDN.
3. Idempotency: recipe jobs use `event_id:step_id` (B8). A re-render is a new `revision` row plus a manual job with key `<job type>:<property_id>:<revision>` (B8 invariant 1 manual form; for the render kinds this reads `render_<kind>:<property_id>:<revision>`); the old revision becomes `rejected` with note `superseded`. Kind to job type: `cover` to `render_cover`, `carousel` to `render_carousel`, `story` to `render_story`, `reel` to `render_reel` (B12), `newsletter_block` and `standalone_email` to `build_newsletter_block`. The job's `payload.data` carries `revision`, and every B9 step writes `payload.data.revision` when present, else the current revision (the highest one not `rejected`).
4. Approval guard, per kind (trigger `assets_approve_guard`, before update when `status` becomes `approved`): `cover`, `carousel`, `story`, `reel` need non-empty `files`, `caption` and `alt_text`, and `meta->>'caption_lint'` not equal to `failed`; `newsletter_block` needs `meta.block.title`, `meta.block.deck`, `meta.block.image_key`, `meta.block.image_url` and `alt_text` non-empty (it has no PNG, so `files` may be empty); `standalone_email` needs `meta.subject`, `meta.preheader` and `meta.block` non-empty. A reject needs a note (trigger `assets_reject_note`). `tests/db/assets.db.test.ts` has one passing and one refused approval per kind.
5. Brand voice is checked by code, not trusted to the model: no em dashes, no words from the banned list (stunning, dream, must-see, luxury living, "just listed" and the rest in `src/server/assets/voice.ts`), no exclamation marks, at most 2,200 characters for Instagram, 280 for the X caption with the property link counted at its shortened length (ASSUMED 23, UNPROVEN, confirmed by B10 step 3a) and 3,000 for LinkedIn (ASSUMED, UNPROVEN), no hashtags at launch (ASSUMED), no guarantee language (leads, buyers, sales), no price framed as merit (in code: a sentence that contains the price or any `$` amount must not also contain a word from `MERIT_WORDS` in `voice.ts`: exceptional, finest, best, premier, prestigious, worth), every number in a caption must appear in the property row. A caption that fails lint twice is stored with `meta.caption_lint = "failed"` and cannot be approved (invariant 4) until a human edits it through `editCaption`, which re-lints and sets `caption_lint = "edited"` only when every variant passes.
6. The visual grammar is fixed by the chosen direction: small wordmark, dominant image, LOCATION, price, minimal specs ("5 BED · 4.5 BATH · 4,320 SF"). No gradient, glow, gold, big agent headshot, or "JUST LISTED" (mop-designer brand rules, G-007).
7. Tier gate: `standalone_email` assets are created only when `payload.tier = "Campaign"` (S24); `build_newsletter_block` and `write_captions` re-check the tier themselves, so a mis-edited recipe cannot create one. The `reel` tier guard is B12's invariant 1 in `render-reel.ts`.
8. Media keys are content-hashed and never overwritten (architecture 13, F24): `scripts/lib/media-key.mjs` computes `hash8` from the bytes, `scripts/lib/r2.mjs` refuses to put an existing hashed key with different bytes and sets the immutable header on every hashed upload (the stable `og/static/` keys take the one-hour header instead), so the edge and the browser never need a purge for an asset.
9. Admin reads are not cached and stay cheap (architecture 13 rules 6 and 9): the six `/api/admin/assets*` routes answer `Cache-Control: no-store` through B7's admin wrapper, `listAssets` is paginated at 50 on the existing indexes, and no public read in this slice touches a table (assets are never on a public page; the only public image is the OG card, served from R2 by its key, and `property.published` fan-out reads the property row inside a job, not on a page view).
10. Variants first (B8b invariant 6). `render_variants` runs in the same parallel fan-out as the steps that read its output, so `render_cover` (needs `og`), `render_carousel` and `render_story` (need `carousel`), `build_newsletter_block` (needs `card`) and `write_captions` (needs `carousel`, so its slide alts follow the same `planCarousel` input as the render) first call `variantsReady(db, propertyId, variant)` from `src/server/assets/spec.ts`. While any `property_media` row of the property lacks that key in `variants`, the step returns `{ status: "retry_at", at: now + 2 minutes, reason: "variants_pending" }` (no attempt consumed, B8 invariant 3). The wait is measured from the `created_at` of the asset stub the step upserted first (every step, `write_captions` and `build_newsletter_block` included, upserts its stub or stubs before it waits, so the clock always has a start; `render_variants` itself has no stub and does not wait), so a re-render restarts the clock; after 60 minutes the step throws `NonRetryableError("variants_missing")` and the job goes `dead`. B12 states the same rule for `render_reel`.
11. Failures are visible on the card. `assets.render_error` is written only by the trigger `assets_job_error` on `jobs` (Data changes): when the job named in `assets.job_id` moves to `failed` or `dead`, the asset gets `render_error = jobs.error`; a later `onResult` on `done` clears it. Screen 10 shows the error with Re-render.
12. A second publish never overwrites approved work. A property can emit `property.published` again (archived, back to draft, review, published; B7), which creates new `event_id:step_id` jobs. A recipe job (no `payload.data.revision`) checks the row `upsert_asset_stub` returns for its kind (it returns the status): when the current revision is `approved` or `published`, that kind is skipped and nothing is written to it; when every kind the step handles is skipped, the step returns `{ status: "done", result: { skipped: "already_approved" } }` without a dispatch. This holds for the three render steps, `write_captions` (per kind) and `build_newsletter_block` (per kind); `render_reel` follows the same rule in B12's `render-reel.ts`. A changed property gets new creative only through Re-render, which makes a new revision. `steps.test.ts` case "approved cover untouched by a second publish".
