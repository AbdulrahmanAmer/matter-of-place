Invariants
1. Nothing in the browser holds a Supabase key (architecture 1). No grant to `anon` on any table, function or sequence, and no `execute` for `public` on any function in schema `public` (Postgres grants it to `public` by default, so migration 10 revokes it and changes the default). `authenticated` gets only the table privileges the RLS matrix needs plus `execute` on `role_in` and `is_staff`. `service_role` gets its grants explicitly in migration 10, so the result never depends on the project's default privileges (`db:reset` drops them with the schema; a fresh `mop-prod` still has them). Public reads go through the Worker with the service role, and only through the two RPCs of invariant 16 (architecture 13, F24).
2. Every table has RLS enabled, and a table without a policy for a role is closed to that role. Default privileges for new tables revoke everything from `anon` and `authenticated`, so a forgotten grant fails closed.
3. `audit_log`, and later `events` and `automation_revisions`, are append-only: a trigger raises on update and delete even for the service role.
4. Only these delete paths exist (GD-04): cascades from foreign keys, `admin` deleting `agent_keys` (architecture 3.7), and the retention job. Nothing else hard-deletes: a `before delete` trigger `refuse_hard_delete()` on `properties`, `stories`, `subscribers`, `submissions`, `inquiries`, `payments` and `campaigns` raises unless the transaction has set `mop.retention = 'on'` (`set_config('mop.retention', 'on', true)`, called only by B8's `retention` job and by test helpers). It binds the service role too, because RLS does not. Retiring content is soft: `archived_at` on `properties`, `stories` and `subscribers`.
5. A submission cannot reach `Invoice Issued` or later without `accepted_at`, and cannot reach `Scheduled` without a `payments` row whose status is `paid` or `waived` (S32). The transition graph is one function, mirrored by `src/domain/workflow.ts`, and a database test compares them.
6. `properties.editorial_state = 'published'` if and only if `published_at` is not null (`check ((editorial_state = 'published') = (published_at is not null))`, so unpublishing clears `published_at`); `editorial_state = 'archived'` if and only if `archived_at` is not null (both checks on `stories` too). Only `published` rows are ever public; `agent_review` is not. `hero_rank` and `featured_rank` are unique among non-null values (partial unique indexes `properties_hero_rank_key` and `properties_featured_rank_key`, `where ... is not null`). `properties.market_slug` and `region_slug` must agree (composite foreign key).
7. Markets are exactly `california`, `new-york`, `florida` (brand guardrail: no other market). `subscribers.markets` is a subset of those three.
8. `settings.catalog_version` increases by one on every change to published catalog content, to `slug_history` and `redirects`, to `markets.coming_soon`, and to any `settings` key other than `catalog_version` itself (flags, site, `coming_soon_global`, `environment`), and never on its own update. These are triggers in this slice; no application code bumps the version by hand (architecture 13 rule 4, F25 a).
9. Free tier: 500 MB (P-009). `analytics_events` is partitioned monthly and kept 13 months (architecture 10; this supersedes the earlier ASSUMED 6 months). At about 24 MB per 120,000 events (200 bytes a row) that is about 24 MB a month, so 13 months at that volume is about 310 MB, most of the free database. The number is data, not code: `retention_policies.analytics_events` can be lowered by an admin, and the health job (B14) warns at 70 % of the 500 MB line.
10. Optimistic locking (GD-01): `properties.version int not null default 1` is incremented by the `before update` trigger `properties_version_bump` on every update, whatever the path, so any write invalidates every outstanding expected version. The edit path for the Worker's server functions is `save_property(p_id, p_expected_version, p_patch jsonb)` (how it applies the patch: Data changes item 8), which raises SQLSTATE `40001` with message `version_conflict` (B7 maps it to HTTP 409) when `p_expected_version` differs from the stored one, and SQLSTATE `22023` with message `invalid_patch_key` when the patch carries a key outside its allow-list. The `authenticated` update policy on `properties` (architecture 3.7) exists for the RLS matrix; no server function writes through it. The seed (service role, `mop-dev` and preview only) is the one sanctioned writer that upserts without `save_property`. `version` belongs to the admin row type (`PropertyRow`); the public `Property` payload never carries it (G-004 note in Risks).
11. Slugs (GD-02): `properties.first_published_at timestamptz` records the first publication and is never cleared or moved (trigger `enforce_slug_immutable`, before insert or update: on insert it is `new.published_at`, on update `coalesce(old.first_published_at, new.published_at)`, whatever the statement wrote). Once `first_published_at` is set, `properties.slug` cannot change: the same trigger raises `slug_immutable`, so the slug stays reserved after unpublish, archive, takedown and a return to `draft`. Before first publication a rename writes the old slug to `slug_history (slug pk, property_id, changed_at)`, and a new slug may not equal any `slug_history.slug` of another property. B3 serves a `301` from `slug_history` before `notFound()`; B13 keeps those slugs out of the sitemap.
12. Rights record (GP-03): every submission row carries `rights_version` (the licence-terms text version the agent accepted), `rights_confirmed_at` and `rights_ip_hash` (`sha256(RATE_LIMIT_SALT:ip)`, never a raw IP), all not null. The constant `currentRightsVersion` in `contracts.ts` is what B3 writes and the form displays. Takedown is a soft state: B7's takedown sets `editorial_state = 'archived'`, `archived_at` and `properties.taken_down_at` (column created here in migration 4, written only by B7); the row and its slug stay, the snapshot lists the slug under `gone`, B13 answers `410 Gone` for it, and the reason is B7's `audit_log.note`. A property that is only unpublished or archived, with `taken_down_at` null, answers 404.
13. Uploads (GQ-07): accepted types `image/jpeg`, `image/png`, `image/heic`, `image/webp`; 25 MB per file (26,214,400 bytes); at most 40 files per submission. The same numbers live in the `uploadLimits` constant of `contracts.ts`, in `[storage] file_size_limit` and the bucket MIME list, in check constraints on `submission_media`, and in a `before insert` trigger that refuses a 41st `submission_media` row for one `submission_id`; `uploads.db.test.ts` compares the four places (step 9). `scripts/variants.ts` accepts the four types and converts HEIC to JPEG before variants.
14. Migration headers (GD-07): every file in `supabase/migrations` opens with either a `-- down:` block (the SQL that undoes it, applied in production only as a new forward migration) or `-- irreversible: <reason>` (for example `alter type ... add value`). `tests/db/migration-headers.test.ts` fails a file with neither, including files later slices add.
15. Preview links (GG-07): `properties.preview_nonce uuid` is part of the signed preview token B7 mints (`<property_id>.<expires>.<hmac>`, 7 days, page served `noindex`); changing the nonce revokes every outstanding link. No table stores tokens.
16. Two public reads, no others (architecture 13 rule 1, S52, F24): `public_state()` returns one jsonb `{catalog_version, flags, coming_soon_global, coming_soon_markets, site, illustrative_content}` from `settings` (`flags` is the `settings` row with key `flags`, `{}` when absent; `site` the row with key `site`; `illustrative_content` is a boolean derived from the `settings` row `environment`: true only when it is exactly `development` or `preview`; a missing row or any other value is false, so a database nobody configured hides illustrative content, F26 c) and `markets.coming_soon` (key `coming_soon_markets`: `{"california": true, ...}`, so the per-market empty state of architecture 11 is read from the state and not from `markets`). These six key names are final (F25 b). `public_catalog_snapshot()` returns one jsonb `{catalog_version, markets, regions, market_notes, market_guide_entries, representatives, properties (each with media, features and related), stories, redirects (enabled rows only), slug_history, gone}` where `gone` lists the slugs of properties whose `taken_down_at` is not null (B13 answers `410`); an archived or unpublished property or story without a takedown is in neither `properties` nor `gone` and answers 404, and an old slug of a renamed draft answers `301` from `slug_history` (B3). Each property object carries its public columns, including `video` (B12 writes it, B13 reads it for `VideoObject`). The key names equal the table names and rows stay snake_case, final (F25 b); B3 maps them once per version. Only `published` rows appear; `agent_review`, `review`, `draft` and `archived` rows never do, and the snapshot carries no `version`, `preview_nonce`, `search_text`, `created_by`, `updated_by`, `author_id`, `submission_id`, `source`, `campaign_tier`, `archived_at` or any other staff column. Both functions are `language sql` with a body of exactly one `select` statement, `security definer`, `stable`, `set search_path = ''`, so `catalog_version` inside the snapshot is read in the same statement as the rows and the two never disagree. Execute is revoked from `public`, `anon` and `authenticated` and granted to `service_role` only. Public search, the concierge, the sitemap, the llms files and redirects are served from the snapshot in the Worker, so nothing public queries a table. Public search is an index built in the Worker over the snapshot, with plural folding (B3, F25 g); the Postgres full-text function is not used for it, and `properties.search_text` and its GIN index are not read by a public request.

Events emitted: none (B8 owns `events`). Permissions: architecture 3.7, encoded in `20261001090900_rls.sql` and tested as a matrix. Summary: select for every staff role; submissions decide by chief_editor and managing_editor; properties write by chief_editor, managing_editor, visual_editor; payments by managing_editor and admin; `decline_reasons` by chief_editor, managing_editor, admin (admin-screens 19; B8b's put functions write it under the service role and B8b adds no policy); team tables by admin. ## Risks and gotchas (link GOTCHAS ids)
- G-010: `docs/database/schema.sql` is the Lovable sketch. Only enum names are reused; columns, types and policies come from architecture 3. Deleting the file at step 14 removes the temptation.
- G-004: the rule now spans `supabase/migrations`, `src/db/types.ts`, `src/domain/*` and the Zod contracts. Step 11 updates the G-004 entry (paths, proof, `enforced-by:`).
- P-038 and S50: no Docker, no `supabase start`, `db reset` or `db diff`. `db:reset` is destructive and only ever aims at `mop-dev` (guard in the script); a migration already pushed to `mop-prod` is never edited, only followed by a new one.
- G-011 and P-009: pg_cron, partitions and the `submissions` bucket are free. `mop-dev` and `mop-prod` each pause after 7 idle days; `mop-prod` needs the keep-warm before launch (B8b), which always makes one `public_state()` call, because a cache hit alone would not touch the database (F25 h). Storage 1 GB: submission photographs at 25 MB each fill it after about 40 full-size uploads, so B7 must move accepted photographs to R2 and delete the originals from the bucket.
- G-008: the Supabase CLI on Windows can emit CRLF. `gen-types.mjs` normalises; the postwrite hook rejects CRLF otherwise.
- bun 1.3 skips dependency install scripts unless the package is in `trustedDependencies`. `supabase` downloads its binary in a postinstall; without the entry `bunx supabase` may work while `node_modules/.bin/supabase` does not. The global CLI 2.98.2 is a fallback.
- F22 and F21: B4 extends `tests/fixtures/db.ts` (factories) and the `db` project and adds the CI `db` job; it must not recreate them. `MOP_DB_URL` and `MOP_TEST_DB_URL` are retired, the one name is `DEV_DB_URL`. Database tests of slices that run side by side share one concurrency group on `mop-dev`.
- The `service_role` key bypasses RLS: the matrix proves user roles, not the Worker. The Worker's own checks are tested in B3 and B7.
- The `audit_log` immutability trigger also blocks the service role by design; a wrong row is corrected with a new row.
- The row lock in `enforce_submission_media_limit` is UNPROVEN under real concurrency: proving it needs two committed sessions, which F22 does not allow in B2's tests; the serial 41st-row test and watched-fail (m) stay.
- Cross-plan: B8 lists `events` under its own migration, but B3 emits events before B8 lands. B3's `emitEvent` stub bridges the gap. B8b must not create `decline_reasons`.
- UNPROVEN until step 12: Bun loading `src/data/*` with the asset-loader plugin (imports of `.jpg`). Fallback: a one-off `scripts/lib/data-snapshot.ts` generated with Vite's SSR build; record the choice.
- ASSUMED region `us-east-1` for both projects; a project's region cannot change later.
- GD-04: `refuse_hard_delete` also blocks test cleanup and manual fixes. Tests and the runbook wrap deletes in a transaction that sets `mop.retention = 'on'`; the setting is transaction-local, so nothing leaks. A wrong row is archived, not deleted.
- GD-01 and G-004: `version` exists in the table and in `PropertyRow`, and is deliberately absent from the public `Property` type and payload; the admin DTO in B7 carries it. The three-file rule holds because the public mapper (B3) lists fields explicitly, so a new column does not leak; the parity test in B3 would name a leaked `version`.
- GD-03: 13 months of analytics is about 310 MB at the assumed volume (invariant 9), so retention of `analytics_events` is the first line to lower if the free database passes 70 %. The `retention` job itself is B8's; here the policies are data and the guard is code.
- GP-04: re-encoding the original loses no pixels that matter but changes bytes, so `sha256` in `submission_media` (of the upload) differs from the sha8 in the R2 key (of the stripped file). Both are recorded; nothing compares them. Accepted photographs must pass through `stripExif` when B7 moves them from the `submissions` bucket to R2, and B9's render workflow must import the same helper; an original with GPS must never reach R2. UNPROVEN for HEIC until the fixture converts in step 13.
- GG-07: the signed preview link needs a signing secret (`PREVIEW_TOKEN_SECRET`, Worker secret, created by B7 and carried in `PREVIEW_WORKER_SECRETS_JSON`, F12) and a public route that serves the unpublished dossier with `noindex` and `private, no-store`. Neither is built in B2; B2 supplies the state, `preview_nonce` and the visibility rule.
- Cross-plan, caching (architecture 13, F24): B3's read path (`getPublicState`, `getCatalog`) must call `public_state()` and `public_catalog_snapshot()` through supabase-js `rpc` and never `from('properties')` or any other table on a public request; B3 maps the snake_case snapshot once per version; `getPublicState`, `getCatalog` and the public request handler take an injectable database client (F25 e), which B4's call counter wraps, so on a warm Worker it counts only those two RPCs; B3 owns the query hydration in `src/router.tsx` and B4 proves by an e2e test that a page load makes no catalog fetch (F25 f); B3b reads flags, coming-soon and `illustrative_content` from the state. If the snapshot grows past the 500 KB mark of step 12 the design is revisited, not patched here.
