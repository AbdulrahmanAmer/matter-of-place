Invariants
1. Nothing in the browser holds a Supabase key (architecture 1). No grant to `anon` on any table, function or sequence, and no `execute` for `public` on any function in schema `public` (Postgres grants it to `public` by default, so migration 10 revokes it and changes the default). `authenticated` gets only the table privileges the RLS matrix needs plus `execute` on `role_in` and `is_staff`. `service_role` gets its grants explicitly in migration 10, so the result never depends on the project's default privileges (`db:reset` drops them with the schema; a fresh `mop-prod` still has them). Public reads go through the Worker with the service role, and only through the two RPCs of invariant 16 (architecture 13, F24).
2. Every table has RLS enabled, and a table without a policy for a role is closed to that role. Default privileges for new tables revoke everything from `anon` and `authenticated`, so a forgotten grant fails closed.
3. `audit_log` (B2) and `automation_revisions` (B8b) are append-only and kept forever: a trigger raises on update and delete even for the service role. Because `audit_log` can never be changed, personal data never enters it (invariant 18, DB-03). `events` (B8) is append-only except the one update of `processed_at` from null to a value (B8b's fan-out) and the deletion of rows processed more than 180 days ago inside a transaction that set `mop.retention = 'on'` (the `events_processed` retention row that B8's `<ts>_retention.sql` seeds, G16, G43); B8's `events_append_only` trigger implements and tests that, not B2.
4. Only these delete paths exist (GD-04): cascades from foreign keys, `admin` deleting `agent_keys` (architecture 3.7), and the retention job. Nothing else hard-deletes: a `before delete` trigger `refuse_hard_delete()` on `properties`, `stories`, `subscribers`, `submissions`, `inquiries`, `payments` and `campaigns` raises unless the transaction has set `mop.retention = 'on'` (`set_config('mop.retention', 'on', true)`, called only by B8's `retention` job and by test helpers). It binds the service role too, because RLS does not. Retiring content is soft: `archived_at` on `properties`, `stories` and `subscribers`.
5. A submission cannot reach `Invoice Issued` or later without `accepted_at`, and cannot reach `Scheduled` without a `payments` row whose status is `paid` or `waived` (S32). It cannot reach `Withdrawn` while a `paid` or `waived` payment exists (DL-04). A terminal state (`Declined`, `Withdrawn`, `Completed`) is reachable from every state: `Published` goes to `Completed` directly when no post was ever made (DL-09). The transition graph is one function, mirrored by `src/domain/workflow.ts`, and a database test compares them. The graph is checked only when `workflow_state` changes; an update that leaves it unchanged (a note, a reviewer) passes the graph check, and `Invoice Issued` to `Invoice Issued` stays in the graph for B6's reissue.
6. `properties.editorial_state = 'published'` if and only if `published_at` is not null (`check ((editorial_state = 'published') = (published_at is not null))`, so unpublishing clears `published_at`); `editorial_state = 'archived'` if and only if `archived_at` is not null (both checks on `stories` too). Only `published` rows are ever public; `agent_review` is not. `hero_rank` and `featured_rank` are unique among non-null values (partial unique indexes `properties_hero_rank_key` and `properties_featured_rank_key`, `where ... is not null`). `properties.market_slug` and `region_slug` must agree (composite foreign key `(region_slug, market_slug)` to `regions (slug, market_slug)`; a mismatch raises SQLSTATE `23503`, step 5).
7. Markets are exactly `california`, `new-york`, `florida` (brand guardrail: no other market). `subscribers.markets` is a subset of those three.
8. `settings.catalog_version` increases by one on every change to published catalog content, to `slug_history` and `redirects`, to `markets.coming_soon`, and to the public `settings` keys only: `flags`, `coming_soon_global`, `site`, `environment`, `og_static` (G21, which narrows F25 a); it never moves on its own update, and channel, token and other admin keys (`meta`, `x`, `linkedin`, `caption_model`, `invoice`, `email`, `notifications`, `agent_daily_limits`, `resend`) do not move it. These are triggers in this slice; no application code bumps the version by hand (architecture 13 rule 4, F25 a).
9. Free tier: 500 MB (P-009). `analytics_events` is partitioned monthly and kept 13 months (architecture 10; this supersedes the earlier ASSUMED 6 months). At about 24 MB per 120,000 events (200 bytes a row) that is about 24 MB a month, so 13 months at that volume is about 310 MB, most of the free database. The number is data, not code: `retention_policies.analytics_events` can be lowered by an admin, and the health job (B14) warns at 70 % of the 500 MB line.
10. Optimistic locking (GD-01): `properties.version int not null default 1` is incremented by the `before update` trigger `properties_version_bump` on every update that changes a column an editor can see, whatever the path, so any such write invalidates every outstanding expected version. The system-maintained columns `hero_image` (trigger `property_media_hero_image`), `video` (B12's `attach_reel`) and `og_image_key` (B9's `approve_asset`) do not count (DB-16): an update that changes only those, plus `updated_at`, `version` and the generated `search_text`, keeps `version`, so a photograph rendering while an editor types never causes a false 409. The list is `systemPropertyColumns` in `tests/db/schema-manifest.ts`, and a test checks that the trigger's text names the same columns. The edit path for the Worker's server functions is `save_property(p_id, p_expected_version, p_patch jsonb)` (how it applies the patch: Data changes item 8), which raises SQLSTATE `40001` with message `version_conflict` (B7 maps it to HTTP 409) when `p_expected_version` differs from the stored one, and SQLSTATE `22023` with message `invalid_patch_key` when the patch carries a key outside its allow-list. The `authenticated` update policy on `properties` (architecture 3.7) exists for the RLS matrix; no server function writes through it. The seed (service role, `mop-dev` and preview only) is the one sanctioned writer that upserts without `save_property`. `version` belongs to the admin row type (`PropertyRow`); the public `Property` payload never carries it (G-004 note in Risks).

Slugs (GD-02): `properties.first_published_at timestamptz` records the first publication and is never cleared or moved (trigger `enforce_slug_immutable`, before insert or update: on insert it is `new.published_at`, on update `coalesce(old.first_published_at, new.published_at)`, whatever the statement wrote). Once `first_published_at` is set, `properties.slug` cannot change: the same trigger raises `slug_immutable`, so the slug stays reserved after unpublish, archive, takedown and a return to `draft`. Before first publication a rename writes the old slug to `slug_history (slug pk, property_id, changed_at)`, and a new slug may not equal any `slug_history.slug` of another property. B3 serves a `301` from `slug_history` before `notFound()`; B13 keeps those slugs out of the sitemap.

14. Migration headers (GD-07) and expand then contract (DB-08): every file in `supabase/migrations` opens with either a `-- down:` block (the SQL that undoes it, applied in production only as a new forward migration) or `-- irreversible: <reason>` (for example `alter type ... add value`), and its first statement after that header is `set lock_timeout = '5s';`. 17. One path for migrations (ASSUMED H1, DB-01, E2E-06, DO-05): `bun run db:push` runs `scripts/db-push.mjs`, never a bare `supabase db push`. Before pushing it refuses, naming each item: `refusing: branch migrations <files>` when the target is `mop-dev`, `MOP_SINGLE_LANE` is not `1` and the local file names in `supabase/migrations` differ from `git ls-tree --name-only origin/main supabase/migrations/`; `refusing: remote-only migrations <versions> (rebase onto origin/main first)` when the target holds a version with no local file; `refusing: out-of-order migration <file> (regenerate the timestamp with supabase migration new)` when a local version not yet applied is older than the newest applied one; `refusing: edited migration <version> (an applied migration is never edited; add a new one)` when the sha256 of an applied file differs from the one recorded in `public.migration_checksums`.
