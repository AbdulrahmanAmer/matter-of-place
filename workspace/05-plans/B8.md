## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- `emit_event(type, entity, entity_id, payload, actor_id)` SQL function, called inside every state-changing transaction (architecture 1). Server code outside a transaction uses `emitEvent()` in `src/server/lib/events.ts`, which calls the same function through RPC. B3's public writes emit inside their SQL function from step 2a on: `create_submission` emits `submission.received`, `confirm_subscriber` emits `subscriber.confirmed`, and the new `create_inquiry(p jsonb)` inserts the inquiry and emits `inquiry.received` with `{ inquiry_id }`. `subscriber.created` stays an `emitEvent` RPC from B3's `requestConfirmation`, because B5 seals the token into the job there.
- `enqueue_job(p_type text, p_payload jsonb, p_idempotency_key text, p_heavy boolean default false, p_status job_status default 'queued', p_run_after timestamptz default now(), p_event_id uuid default null, p_recipe_id uuid default null, p_step_id text default null) returns uuid`: the new job id, or null when the key already exists; it sends the pgmq message only when the status is `queued`. TS wrapper `enqueueJob(db, { type, idempotencyKey, params?, data?, heavy?, runAfter? }): Promise<string | null>` in `src/server/lib/jobs.ts`, for system jobs that have no event (health, prune, manual forward). Manual system jobs use `enqueue_job_manual(p_type text, p_entity_id uuid, p_payload jsonb) returns uuid` (TS `enqueueManualJob(db, { type, entityId, data })`), which takes a transaction advisory lock on `p_type || p_entity_id` and computes `n` = 1 + the count of jobs whose key starts with `<type>:<entity_id>:`.
- `fanoutPendingEvents()` and `runDueSchedules()` are called by the runner every tick. B8 ships both as stubs that return 0. B8b replaces `src/server/automation/fanout.ts`; B8b also replaces `src/server/jobs/scheduler.ts`. The stub signatures are the contract: `fanoutPendingEvents(db, limit): Promise<number>` and `runDueSchedules(db, now): Promise<number>`.
- Step modules: `{ type, heavy, paramsSchema, run(ctx, params, payload) }` plus optional `onResult(ctx, job, result)` for heavy steps (architecture 2, tech-stack 5 "a job type"). `StepContext` is `{ db, env, log, now, job: { id, type, attempts, result, eventId } }`, where `job` is the claimed row, so a step can read what an earlier attempt stored in `jobs.result`. `StepResult` is `{ status: "done", result? }` or `{ status: "retry_at", at, reason, result? }`; the runner writes `result` into `jobs.result` in both cases (B15 keeps its delivery counter there), and a step never updates `jobs` itself.

Job payload envelope (pinned here, produced by B8b's planner and by `enqueueJob()`): `jobs.payload = { params, data }`. `params` is the recipe step's validated parameters, snapshotted when the job is created so a later recipe edit never changes a job already queued; `data` is the event payload (or the system job's input). The runner calls `step.run(ctx, job.payload.params, job.payload.data)`. `enqueueJob()` writes `params = {}` when the caller gives none. The heavy `client_payload.payload` is this whole envelope.

Outputs
- `jobs` rows with lifecycle `queued` to `running` to `done`, or `failed` (retry pending) and `dead`, plus `waiting_approval` and `cancelled` (architecture 3.6, screen 16; a deliberate cancel is not painted red as `dead`).
- One `job_events` row per transition. ASSUMED columns: `id`, `job_id fk`, `at`, `kind` (`created|claimed|done|failed|dead|dispatched|callback|approved|cancelled|manual_retry|requeued|stale`), `from_status`, `to_status`, `attempt`, `message`, `data jsonb`, `actor_id`.
- Heavy jobs: `repository_dispatch` event type `render` with `client_payload = { job_id, attempt, type, payload, env, callback_url }` (at most 10 top-level keys and 64 KB, GitHub limit; payloads carry ids and R2 keys, never files). `env` is the dispatching Edge Function's `MOP_ENV` (`development` or `production`); `callback_url` is its Supabase function secret `RENDER_CALLBACK_URL`, so each Supabase project calls back the Worker that reads the same database. `render.yml` maps `env` to the bucket (`development` to `mop-media-dev`, `production` to `mop-media`, B2 names) and refuses any other value; `post-callback.mjs` posts to `callback_url` and refuses a host other than `matterofplace.com` or one ending in `.holy-meadow-4327.workers.dev`.
- Callback: `POST /api/hooks/render/callback` with `X-MOP-Timestamp` (unix seconds) and `X-MOP-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>" keyed by RENDER_CALLBACK_SECRET>`. Body `{ job_id, attempt, status: "done"|"failed", result?, error?, retryable?, run_url }`; `retryable` defaults to true, and `retryable: false` makes the hook call `fail_job` with `p_dead => true` so a deterministic render failure is not dispatched again. Responses: 200 applied or already applied or stale attempt (`{ ignored: "stale_attempt" }`, so Actions stops retrying), 400 malformed, 401 bad signature or timestamp older than 300 seconds, 404 unknown job.

Invariants
1. Idempotency key is `event_id:step_id` for recipe jobs, `<type>:<UTC date>` for daily system jobs (`health`, `prune`, `retention`, `meta_token_refresh`), `reconcile_uploads:<UTC date>T<HH:MM>` with the minute rounded down to the quarter hour for the 15-minute upload reconcile, `<type>:<entity_id>:<n>` for manual system jobs (`n` from `enqueue_job_manual`). Enqueue is `insert ... on conflict (idempotency_key) do nothing`. A second insert never creates a second job.
2. A job runs at most once concurrently: `claim_job` is one `update ... where status in (...) returning *`; a lost claim returns no row.
3. Retries never consume an attempt when a step returns `{ status: "retry_at", at, reason }` (used by the email daily cap in B5). Any thrown error consumes one. `NonRetryableError` goes straight to `dead`.
4. Backoff: `delay = min(30 s * 2^(attempts-1), 1 h)` with plus or minus 20 percent jitter; `attempts >= max_attempts` (default 5) means `dead`. Total time before dead is about 8 minutes.
5. The database row is the truth. pgmq messages are wake-ups; a lost message is repaired by the reaper, a duplicate message is archived when its job is no longer runnable. Every function that makes a job runnable again (`fail_job` with a retry pending, `requeue_job` for `retry_at` and manual retry, `approve_job`) calls `pgmq.send(queue, jsonb_build_object('job_id', id), greatest(0, extract(epoch from run_after - now()))::int)` and stores the new `msg_id`. `reap_stale_jobs()` also re-sends a message for every `queued` or `failed` job with `run_after < now() - interval '5 minutes'` whose `msg_id` is absent from its queue table. The runner dispatches at most 3 heavy jobs per tick (`HEAVY_PER_TICK = 3` in `runner.ts`).
6. Callbacks are matched on `job_id` and `attempt`. A callback for an older attempt is acknowledged and ignored.
7. Nothing external happens inside a Worker request (architecture 1). The Worker only inserts rows.
8. Free tier only (G-011, P-009): pgmq, pg_cron, pg_net and Vault are Supabase free extensions. No Cloudflare Queues, no Durable Objects.

Events emitted: `health.failed`, by `src/server/jobs/system/health.ts` through `emitEvent(db, { type: "health.failed", entity: "system", entityId: null, payload: { date, failed: [{ check, message }] } })` when at least one check has status `fail`, at most once per run (the run is daily, key `health:<UTC date>`); B8b's recipe `send_health_alert` turns it into the `admin_alert` email. No other system job emits a catalog event; a dead job is surfaced by screen 16, screen 2 and the health check `dead_jobs_24h`. B8 owns the `events` table and the 17 catalog types listed in architecture 3.6 (the `CatalogEventType` list of `src/server/lib/events.ts`). It also moves the emission of `submission.received`, `inquiry.received` and `subscriber.confirmed` into B3's SQL write functions (step 2a).

Permissions (admin-screens 16, architecture 3.7)
| Action | Roles |
|---|---|
| list, get jobs and events | all six roles |
| retry, cancel | media_ops, admin |
| approve a `waiting_approval` job | media_ops, admin; `humanOnly` (an agent gets 403 `human_only`, the same rule as B7 invariant 3, because approval is the human gate of S23 and S46) |
| agents | same routes and same roles through bearer key, scope `jobs`, except approve |

## Risks and gotchas (link GOTCHAS ids)
- G-012: `render.yml` lives at `E:\Matter Of Place\.github\workflows\`, jobs use `working-directory: Matter Of Place Codebase`. Nested `.github` never runs.
- G-011 and P-009: cron every minute is 43,200 Edge calls a month against 500,000; heavy fan-out costs one Actions run per asset (about 5 per publish, one minute minimum each) against 2,000 minutes. Measure in HARDEN; batching several jobs per run is the first optimisation (not built here).
- G-004: `src/domain/jobs.ts` field names equal generated types and snake_case columns; change together.
- G-006: `GITHUB_DISPATCH_TOKEN`, `JOB_RUNNER_SECRET`, `RENDER_CALLBACK_SECRET` are never `VITE_*`.
- Edge Functions run in Deno; `src/server/jobs` must not import Node-only or Worker-only modules (no `cloudflare:workers`, no `node:fs`). Enforced by the `deno` job that step 5 adds to `ci.yml` (Deno is not installed on the laptop, E11; hosted runners are fine, E7); locally `bun run typecheck` plus the `--use-api` deploy of step 5 is the proof. The same applies to B3's `reconcileUploads` and B1b's `sentry.ts`, which the function imports. `npm:` imports of this kind already run on the Edge runtime (E5).
- R2 from the Edge Function: no Worker binding exists there, so the S3-compatible API is needed. ASSUMED new secrets `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` in Supabase function secrets and in GitHub Actions; tech-stack 4 should list them. R2 is off until the operator enables it (E8, S50): no B8 step creates or writes a bucket. B8 reuses `src/server/lib/r2.ts` and its `r2_unavailable` error from B3 (F18) and `scripts/lib/r2.mjs` from B9 (F17), and creates neither; a step that needs R2 while it is off returns `r2_unavailable` and the job waits, it does not fail the steps around it. `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` already exist in GitHub but are UNPROVEN (E8). First user is B6 (invoice PDF), which carries the block.
- GitHub `repository_dispatch` needs a fine-grained token with Contents write on this repo only. It does not exist yet (not in E10) and only the operator can mint it (P-037). ASSUMED scope; check at step 7. Until then heavy jobs cannot be dispatched, light jobs are unaffected.
- Callback host per environment: `mop-dev` heavy jobs call back the Worker named in its function secret `RENDER_CALLBACK_URL`. The production Worker reads `mop-prod` (B1b), so it can never answer a `mop-dev` job (404 unknown job); only preview Workers read `mop-dev`, and they are deleted when their pull request closes. Until a stable dev host exists, the dev secret is repointed at a live preview before a heavy proof.
- No Docker (S50, P-038): nothing here runs `supabase start`, `db reset`, `db diff` or `functions serve`. DB tests (F22 harness, `DEV_DB_URL`) and the self-test run on `mop-dev`; the job functions need pgmq and pg_net, so a throwaway native PostgreSQL 18 cluster cannot host them.
- Recipe and event names are fixed by architecture 3.6; adding an 18th event type is a spec change, not a B8 decision.
- Visibility timeout (120 s) is shorter than the stale-lock limit (5 minutes) on purpose; the claim function handles the duplicate message. Long steps (over 100 s) are not allowed in the light queue; make them heavy.
- Supabase free projects pause after 7 idle days; the cron itself is activity, and B8b's `keepwarm` schedule is the explicit guard.
- GD-03: `retention` is the only code that hard-deletes (architecture 10). Storage deletes are irreversible; the first production run is a `dry_run` whose counts the admin reads, and the health check `retention_stalled` (B8) fails when an enabled `delete` or `anonymise` policy has not run for 2 days or left eligible rows behind (`remaining` above 0 in the `retention.run` audit row). It runs as a fixed pg_cron entry, not from `schedule_settings`, because that table's key check has no `retention` value; B8b's schedules migration must leave `retention` and `meta_token_refresh` scheduled (it only unschedules `prune`).
- G-004: `inquiries.anonymised_at` and `retention_policies` appear in the domain types, the API and the columns together; grep the names in `src/domain` and the migrations before finishing.
- GS-01: writing a refreshed token into Vault relies on Vault being writable from the Edge Function's service role, UNPROVEN until step 8a runs on `mop-dev`. The Page token that comes from a long-lived user token does not expire (B10), so the refresh path may never fire; the alert path is the guaranteed part. Agent keys (90 days), Resend and R2 tokens are rotated by hand per the runbook; the job does not touch them.
