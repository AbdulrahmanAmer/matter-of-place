## Goal and observed exit
The machine room: every side effect is a row in `jobs` with an idempotency key, run by an Edge Function on pg_cron, with heavy work dispatched to GitHub Actions and finished by a signed callback (S12, S17, architecture 1 and 5).
Observed exit (completion map B8): "a publish creates jobs that complete and report". Proven in two parts. Part 1, before B8b exists: `scripts/job-selftest.ts` enqueues `test.selftest_light` and `test.selftest_heavy` through `enqueue_job` (fan-out is still a stub, so no event is involved), the light one reaches `done` in under 90 seconds, the heavy one round-trips through `render.yml` and its callback and reaches `done`. Part 2, after B7 and B8b: publishing a property in `/admin` creates the `property.published` jobs and screen 16 shows them complete.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- `emit_event(type, entity, entity_id, payload, actor_id)` SQL function, called inside every state-changing transaction (architecture 1). Server code outside a transaction uses `emitEvent()` in `src/server/lib/events.ts`, which calls the same function through RPC.
- `enqueue_job(...)` SQL function and `enqueueJob()` TS wrapper for system jobs that have no event (health, prune, manual forward).
- `fanoutPendingEvents()` and `runDueSchedules()` are called by the runner every tick. B8 ships both as stubs that return 0. B8b replaces `src/server/automation/fanout.ts`; B8b also replaces `src/server/jobs/scheduler.ts`. The stub signatures are the contract: `fanoutPendingEvents(db, limit): Promise<number>` and `runDueSchedules(db, now): Promise<number>`.
- Step modules: `{ type, heavy, paramsSchema, run(ctx, params, payload) }` plus optional `onResult(ctx, job, result)` for heavy steps (architecture 2, tech-stack 5 "a job type").

Job payload envelope (pinned here, produced by B8b's planner and by `enqueueJob()`): `jobs.payload = { params, data }`. `params` is the recipe step's validated parameters, snapshotted when the job is created so a later recipe edit never changes a job already queued; `data` is the event payload (or the system job's input). The runner calls `step.run(ctx, job.payload.params, job.payload.data)`. `enqueueJob()` writes `params = {}` when the caller gives none. The heavy `client_payload.payload` is this whole envelope.

Outputs
- `jobs` rows with lifecycle `queued` to `running` to `done`, or `failed` (retry pending) and `dead`, plus `waiting_approval`. ASSUMED: one extra enum value `cancelled` (screen 16 has a Cancel action and architecture 3.6 has no matching state; using `dead` would paint a deliberate cancel red). Reconcile architecture 3.6 and admin-screens 16 when this lands.
- One `job_events` row per transition. ASSUMED columns: `id`, `job_id fk`, `at`, `kind` (`created|claimed|done|failed|dead|dispatched|callback|approved|cancelled|manual_retry|requeued|stale`), `from_status`, `to_status`, `attempt`, `message`, `data jsonb`, `actor_id`.
- Heavy jobs: `repository_dispatch` event type `render` with `client_payload = { job_id, attempt, type, payload }` (at most 10 top-level keys and 64 KB, GitHub limit; payloads carry ids and R2 keys, never files).
- Callback: `POST /api/hooks/render/callback` with `X-MOP-Timestamp` (unix seconds) and `X-MOP-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>" keyed by RENDER_CALLBACK_SECRET>`. Body `{ job_id, attempt, status: "done"|"failed", result?, error?, run_url }`. Responses: 200 applied or already applied or stale attempt (`{ ignored: "stale_attempt" }`, so Actions stops retrying), 400 malformed, 401 bad signature or timestamp older than 300 seconds, 404 unknown job.

Invariants
1. Idempotency key is `event_id:step_id` for recipe jobs, `<type>:<UTC date>` for daily system jobs (`health`, `prune`), `<type>:<entity_id>:<n>` for manual system jobs. Enqueue is `insert ... on conflict (idempotency_key) do nothing`. A second insert never creates a second job.
2. A job runs at most once concurrently: `claim_job` is one `update ... where status in (...) returning *`; a lost claim returns no row.
3. Retries never consume an attempt when a step returns `{ status: "retry_at", at, reason }` (used by the email daily cap in B5). Any thrown error consumes one. `NonRetryableError` goes straight to `dead`.
4. Backoff: `delay = min(30 s * 2^(attempts-1), 1 h)` with plus or minus 20 percent jitter; `attempts >= max_attempts` (default 5) means `dead`. Total time before dead is about 8 minutes.
5. The database row is the truth. pgmq messages are wake-ups; a lost message is repaired by the reaper, a duplicate message is archived when its job is no longer runnable.
6. Callbacks are matched on `job_id` and `attempt`. A callback for an older attempt is acknowledged and ignored.
7. Nothing external happens inside a Worker request (architecture 1). The Worker only inserts rows.
8. Free tier only (G-011, P-009): pgmq, pg_cron, pg_net and Vault are Supabase free extensions. No Cloudflare Queues, no Durable Objects.

Events emitted: none new. B8 owns the `events` table and the 14 catalog types listed in architecture 3.6. ASSUMED: system jobs do not emit catalog events; a dead job is surfaced by screen 16, screen 2 and the daily health job, not by a 15th event.

- G-006: `GITHUB_DISPATCH_TOKEN`, `JOB_RUNNER_SECRET`, `RENDER_CALLBACK_SECRET` are never `VITE_*`.
- Edge Functions run in Deno; `src/server/jobs` must not import Node-only or Worker-only modules (no `cloudflare:workers`, no `node:fs`). Enforce with `deno check` in CI. UNPROVEN until step 5 runs.
- R2 from the Edge Function: no Worker binding exists there, so the S3-compatible API is needed. First user is B6 (invoice PDF).

- Recipe and event names are fixed by architecture 3.6; adding a 15th event type is a spec change, not a B8 decision.
- Visibility timeout (120 s) is shorter than the stale-lock limit (5 minutes) on purpose; the claim function handles the duplicate message. Long steps (over 100 s) are not allowed in the light queue; make them heavy.
- Supabase free projects pause after 7 idle days; the cron itself is activity, and B8b's `keepwarm` schedule is the explicit guard.
- GD-03: `retention` is the only code that hard-deletes (architecture 10). - GS-01: writing a refreshed token into Vault relies on Vault being writable from the Edge Function's service role, UNPROVEN until step 8a runs on `mop-dev`.
