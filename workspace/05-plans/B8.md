## Goal and observed exit
The machine room: every side effect is a row in `jobs` with an idempotency key, run by an Edge Function on pg_cron, with heavy work dispatched to GitHub Actions and finished by a signed callback (S12, S17, architecture 1 and 5).
Observed exit (completion map B8): "a publish creates jobs that complete and report". Proven in two parts. Part 1, before B8b exists: `scripts/job-selftest.ts` enqueues `test.selftest_light` and `test.selftest_heavy` through `enqueue_job` (fan-out is still a stub, so no event is involved), the light one reaches `done` in under 90 seconds, the heavy one round-trips through `render.yml` and its callback and reaches `done` (the heavy half is BLOCKED until the operator mints `GITHUB_DISPATCH_TOKEN`, see step 7; its callback target on `mop-dev` is B1b's stable dev Worker `matter-of-place-dev`, G19; the light half and every other step run without it). Part 2, after B7 and B8b: publishing a property in `/admin` creates the `property.published` jobs and screen 16 shows them complete.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- `emit_event(type, entity, entity_id, payload, actor_id)` SQL function, called inside every state-changing transaction (architecture 1). Server code outside a transaction uses `emitEvent()` in `src/server/lib/events.ts`, which calls the same function through RPC. B3's public writes emit inside their SQL function from step 2a on: `create_submission` emits `submission.received`, `confirm_subscriber` emits `subscriber.confirmed`, B3's `create_inquiry(p jsonb)` keeps its insert and emits `inquiry.received` with `{ inquiry_id }` (G49), `create_subject_request` emits `subject_request.received` with `{ request_id, kind }` (G29), and `upsert_subscriber` emits `subscriber.created` with `{ subscriber_id, sealed_token }` whenever the call stores a fresh `confirm_token_hash` (a new or still unconfirmed row, a re-subscribe of an unsubscribed or archived address, or a confirmed `interest:` row that receives a Place Notes `source` into `pending_source`: B3's body, DL-06) and `p->>'sealed_token'` is not null (G12, G20). The Worker seals the token before the call: `requestConfirmation(token)` in B3's `src/server/subscribers/confirmation.ts` returns the sealed token or null (null from B3's stub and whenever `CONFIRM_TOKEN_SECRET` is unset; B5 replaces the body with `sealToken(token, env.CONFIRM_TOKEN_SECRET)`) and emits nothing; `subscribers/service.ts` passes the value as `sealed_token` to `upsert_subscriber`. No TS code emits a catalog event that a SQL write function emits (G20).
- `enqueue_job(p_type text, p_payload jsonb, p_idempotency_key text, p_heavy boolean default false, p_status job_status default 'queued', p_run_after timestamptz default now(), p_event_id uuid default null, p_recipe_id uuid default null, p_step_id text default null, p_max_attempts int default 5) returns uuid` (`p_max_attempts` is written to `jobs.max_attempts`; a caller that enqueues a type which calls an outside provider passes, by name, the `maxAttempts` its registry entry declares, 12, invariant 4, DL-10, E2E-03): the new job id, or null when the key already exists; it sends the pgmq message only when the status is `queued`, and when it inserts it writes exactly one `job_events` row of kind `created` (none when the key already exists). SQL write functions of other slices call it inside their own transaction, so the job, its `created` row and its message commit or roll back with the write: B7's `set_market_coming_soon` and B8b's `open_market_on_publish` (called by the `bump_catalog_version` step) enqueue `market_open_notice` this way (G58). TS wrapper `enqueueJob(db, { type, idempotencyKey, params?, data?, heavy?, runAfter?, maxAttempts? }): Promise<string | null>` in `src/server/lib/jobs.ts` (`maxAttempts` becomes `p_max_attempts`; absent means the SQL default 5), for system jobs that have no event (health, prune, manual forward). Manual system jobs use `enqueue_job_manual(p_type text, p_entity_id uuid, p_payload jsonb, p_max_attempts int default 5) returns uuid` (TS `enqueueManualJob(db, { type, entityId, data, maxAttempts? })`), which takes a transaction advisory lock on `p_type || p_entity_id` and computes `n = 1 + coalesce(max(split_part(idempotency_key, ':', 3)::int) filter (where split_part(idempotency_key, ':', 3) ~ '^[0-9]+$'), 0)` over the keys that start with `<type>:<entity_id>:` (only keys whose third part is numeric count, so a free-form key sharing the prefix cannot break the int cast; B10 already moved its story key to `reconcile_story:<post_id>`) (DB-09: pruning only removes keys, so the maximum plus one never equals a key that still exists, where a count collides once `:1` is pruned). A caller that gets null back treats it as a failure (B7 and B10 raise `enqueue_failed`, DB-09).
- `fanoutPendingEvents()` and `runDueSchedules()` are called by the runner every tick, `fanoutPendingEvents(db, 50)` with the sweep limit of JOB-07 (B8b's sweep leaves out an event whose `event_fanout_failures.next_at` is still ahead). B8 ships both as stubs that return 0, each marked `// STUB(B8b step 4): <what replaces it>` on the line above the function (CS-11), so `scripts/stubs.ts` fails `bun run check` once B8b is closed with either marker still present. B8b replaces `src/server/automation/fanout.ts`; B8b also replaces `src/server/jobs/scheduler.ts`. The stub signatures are the contract: `fanoutPendingEvents(db, limit): Promise<number>` and `runDueSchedules(db, now): Promise<number>`.
- Step modules: `{ type, heavy, paramsSchema, maxAttempts?, timeoutMs?, run(ctx, params, payload) }` plus optional `onResult(ctx, job, result)` for heavy steps (architecture 2, tech-stack 5 "a job type"); `heavy`, `paramsSchema`, `maxAttempts` and `timeoutMs` come from B8b's step spec, and a system job registration in `system/index.ts` carries the same two optional numbers (DL-10, JOB-02). `StepContext` is `{ db, env, log, now, signal, report, job: { id, type, attempts, claim, result, eventId } }`, where `job` is the claimed row, so a step can read what an earlier attempt stored in `jobs.result`; `claim` is the token `claim_job` wrote into `locked_by` (JOB-02); `log` is B1b's `logLine` (CS-08); `signal` is the step's `AbortSignal`, which every outside `fetch` passes (JOB-02); `report(error, { fingerprint, level? })` sends one Sentry event through the runner's `report` (INT-04). `now` is a `Date`, taken once by `runOnce` when it claims the job (`opts.now ?? new Date()`) and the same value for the whole run of that job; `env` is the `opts.env` object `runOnce` was given (the job runner passes `Deno.env.toObject()`), passed unchanged to every step `run`, system handler and `onResult` it calls; `onResult` of a heavy step runs later in the Worker, where `handleRenderCallback(db, request, env)` builds the same shape from the `jobs` row it read for `job_id`, with `now` one `new Date()` taken when the callback is accepted and `env` the Worker env the route passes; steps read `ctx.now` as a value and never call it (tests pass a fixed `Date` as `opts.now`). `StepResult` is `{ status: "done", result? }`, `{ status: "retry_at", at, reason, result? }` or, for heavy steps only and only as returned by `dispatchHeavy`, `{ status: "dispatched", result? }` (the job stays `running` until its callback); the runner writes `result` into `jobs.result` in every case (B15 keeps its delivery counter there), and a step never updates `jobs` itself. A step that throws B3's shared `r2_unavailable` error (F18) is treated by the runner as `{ status: "retry_at", at: now + 1 hour, reason: "r2_unavailable" }`, so no attempt is used while R2 is off (E8). A job whose type `getStep` does not know is treated as `{ status: "retry_at", at: now + 15 minutes, reason: "unknown_step" }`, with no attempt used, until it is 24 hours past its `created_at`, and only then goes `dead` with `unknown_step` (E2E-06, DO-10), so a lane gap or a runner rollback never kills jobs. Each step runs under `AbortSignal.timeout(timeoutMs ?? 20000)`, at most 40000 for a light step; an abort is a retryable failure `step_timeout` that uses one attempt (JOB-02).
- Heavy dispatch: `dispatchHeavy(ctx, job, extra?)` in `src/server/jobs/steps/heavy.ts` builds `client_payload = { job_id, claim, type, payload, env, callback_url }`, where `claim` is `ctx.job.claim` (JOB-02) and `payload` is `{ params, data: { ...data, ...extra } }` (B12 passes `{ spec, spec_hash, revision }`; B9's steps pass their media list), refuses a serialised `client_payload` longer than 65,535 characters (the limit of one `workflow_dispatch` input; UNPROVEN exact limit, measured once in step 7) with `NonRetryableError("payload_too_large")` before any call, and calls `dispatch.ts`, which POSTs `https://api.github.com/repos/${GITHUB_REPO}/actions/workflows/render.yml/dispatches` with `Authorization: Bearer ${GITHUB_DISPATCH_TOKEN}`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, `signal: ctx.signal` and body `{ ref: "main", inputs: { job: JSON.stringify(client_payload) } }`, expecting 204 (JOB-01, SEC-02: `workflow_dispatch` needs only Actions write, so the token cannot push to `main`). On 204 it returns `{ status: "dispatched", result: extra }` and the runner calls `finish_job` with `p_dispatched => true`, which stores `extra` in `jobs.result` and writes the `dispatched` row in `job_events` while the job stays `running` under its claim, so `onResult` reads `job.result.spec_hash`. `GITHUB_DISPATCH_TOKEN` or `GITHUB_REPO` unset: `{ status: "retry_at", at: now + 1 hour, reason: "dispatch_not_configured" }` (no attempt used, no call). A 5xx answer or a network error throws (normal backoff, invariant 4). 401, 403, 404 or 422 throws `NonRetryableError("dispatch_<status>")`, so the job goes `dead` and shows on screen 16.

Job payload envelope (pinned here, produced by B8b's planner and by `enqueueJob()`): `jobs.payload = { params, data }`. `params` is the recipe step's validated parameters, snapshotted when the job is created so a later recipe edit never changes a job already queued; `data` is the event payload (or the system job's input). The runner calls `step.run(ctx, job.payload.params, job.payload.data)`. `enqueueJob()` writes `params = {}` when the caller gives none. The heavy `client_payload.payload` is this whole envelope.

Outputs
- `jobs` rows with lifecycle `queued` to `running` to `done`, or `failed` (retry pending) and `dead`, plus `waiting_approval` and `cancelled` (architecture 3.6, screen 16; a deliberate cancel is not painted red as `dead`).
- One `job_events` row per transition. ASSUMED columns: `id`, `job_id fk`, `at`, `kind` (`created|claimed|done|failed|dead|dispatched|callback|approved|cancelled|manual_retry|requeued|stale`), `from_status`, `to_status`, `attempt`, `message`, `data jsonb`, `actor_id`.
- Heavy jobs: one `workflow_dispatch` run of `render.yml` whose one input `job` is the JSON of `client_payload = { job_id, claim, type, payload, env, callback_url }` (at most 65,535 characters; payloads carry ids and R2 keys, never files). `env` is the dispatching Edge Function's `MOP_ENV` (`development` or `production`); `callback_url` is its Supabase function secret `RENDER_CALLBACK_URL`, so each Supabase project calls back the Worker that reads the same database. `render.yml` passes `env` to the scripts as `MOP_ENV`, from which B9's `scripts/lib/r2.mjs` derives the bucket (`production` gives `mop-media`, anything else `mop-media-dev`, B2 names; G52), and `checkJob` refuses any value other than `development` or `production`; `post-callback.mjs` posts to `callback_url` and refuses a host other than `matterofplace.com` or one ending in `.holy-meadow-4327.workers.dev`; it copies `job_id` and `claim` from the job JSON into the callback body.
- Callback: `POST /api/hooks/render/callback` with `X-MOP-Timestamp` (unix seconds) and `X-MOP-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>" keyed by RENDER_CALLBACK_SECRET>`. Body `{ job_id, claim, status: "done"|"failed", result?, error?, retryable?, run_url }`; `retryable` defaults to true, and `retryable: false` makes the hook call `fail_job` with `p_dead => true` so a deterministic render failure is not dispatched again. Responses: 200 applied or already applied or stale claim (`{ ignored: "stale_claim" }` when the job is no longer `running` under that claim, for example after a reap and a manual retry, JOB-02; Actions then stops retrying), 400 malformed, 401 bad signature or timestamp older than 300 seconds, 404 unknown job, 503 `unavailable` when the Worker's `RENDER_CALLBACK_SECRET` is unset (nothing is verified or changed, so `post-callback.mjs` retries and, failing that, the reaper fails the job after 30 minutes; the same rule as B3's `hooks.handleResend`). The Worker reads the secret through B3's `src/server/lib/env.ts` as an optional key (Change), so a Worker without it still starts. The signature is computed and compared through `hmac.ts`, which calls B1b's `crypto.ts` (`hmacSha256`, `toHex`, `timingSafeEqual`; CS-04).
- Liveness (DO-03 and JOB-04 as one mechanism, rulings H9 and H10): `ops_heartbeats(name text primary key, at timestamptz not null, detail jsonb)` is written only by `beat(p_name text, p_detail jsonb)`. `runOnce` calls `beat('runner', jsonb_build_object('claimed', <n>))` in its `finally`, B8b's `runKeepWarm` calls `beat('keepwarm', ...)` and B1b's `backup.yml` calls `select beat('backup', ...)` next to its `claim_schedule`. A runner the cron cannot reach (a 401 after a secret rotation, a 500, a boot error, a paused project) never reaches `runOnce`, so a stale `runner` row covers it and `net._http_response` is not read. `ops_health(p_now timestamptz) returns jsonb` answers `{ ok, failing: [<names>] }` with the names `runner` (beat older than 3 minutes), `keepwarm` (absent or older than 25 minutes, only while the `keepwarm` row of `schedule_settings` is enabled), `backup` (absent or older than 26 hours, only while the `backup` row of `schedule_settings` is enabled), `stale_queue` (a `queued` job whose `run_after` is more than 15 minutes old) and `dead_jobs` (a job that went `dead` in the last 24 hours). `GET /api/hooks/ops-health/<token>` compares the token with the Worker secret `OPS_HEALTH_TOKEN` in constant time (`timingSafeEqual` of `crypto.ts`), makes one `ops_health` RPC and answers `Cache-Control: no-store` (rule 6 covers `/api/hooks/*`), 200 `ok` or 503 `fail: <names joined by ",">`; a wrong token or an unset secret answers 404 and makes no RPC. A third UptimeRobot keyword monitor (keyword `ok`, every 5 minutes, alerting the admin mailbox; B14 records it) polls the route, so a stopped runner reaches the admin without the runner or Resend. `jobs_liveness(p_now timestamptz default now()) returns jsonb` answers `{ runner_beat_at, oldest_due_age_s }` (the `runner` row's `at`, and the age in seconds of the oldest `queued` or `failed` job with `run_after <= p_now`) for B8b's keep-warm tick, which reports `job_runner_stalled` to Sentry from the Worker (B8b invariant 15 c).

Invariants
1. Idempotency key is `event_id:step_id` for recipe jobs, `<type>:<UTC date>` for daily system jobs (`health`, `prune`, `retention`, `meta_token_refresh`), `reconcile:<UTC date>T<HH:MM>` with the minute rounded down to the quarter hour for the 15-minute `reconcile` system job (set by B8b's scheduler from the `reconcile` row of `schedule_settings`, `*/15 * * * *`, G10), `<type>:<entity_id>:<n>` for manual system jobs (`n` from `enqueue_job_manual`), and the key a caller sets for a job it enqueues directly: `market_open:<slug>` for `market_open_notice` (B7 and B8b, G37, G58); `render_variants:<property_id>:<uuid>` for the one `render_variants` job per property per upload batch that B7's `request_property_render(p_property_id)` enqueues or reuses (ruling H11, which supersedes the per-photograph key of G54, G66 and G69 (3): it returns the id of a `queued` `render_variants` job of that property when one exists, else enqueues one with `run_after = now() + interval '90 seconds'` as a debounce, and B9's `run` dispatches only the rows `claim_media_for_render` gives it); `copy_submission_media:<property_id>` for B7's light system job that copies a request's photographs outside the admin request (E2E-02, PERF-07); and `takedown_media:<property_id>` for the system job `unpublish_property` enqueues on a takedown (E2E-01, step 10a). Enqueue is `insert ... on conflict (idempotency_key) do nothing`. A second insert never creates a second job.
2. A job runs at most once concurrently: `claim_job` is one `update ... where status in (...) returning *` that sets `locked_by = gen_random_uuid()::text` (the claim token, returned with the row) and `locked_at = now()` and never changes `attempts`; a lost claim returns no row. `finish_job`, `fail_job` and `requeue_job` with `p_kind => 'requeued'` act only when `status = 'running' and locked_by = p_claim`, and otherwise return false and change nothing, so a late runner or a late callback never finishes a job that another run now holds (JOB-02). One attempt rule: `fail_job` is the only function that increments `attempts`.
3. Retries never consume an attempt when a step returns `{ status: "retry_at", at, reason }` (used by the email daily cap in B5). Any thrown error, a `step_timeout` abort and an expired lease (`lease_expired`, invariant 5) consume one; an `unknown_step` wait consumes none (Contract). `NonRetryableError` goes straight to `dead`.
4. Backoff: `delay = min(30 s * 2^(attempts-1), 1 h)` with plus or minus 20 percent jitter; `attempts >= max_attempts` means `dead`. `max_attempts` is set per job: 5 by default (about 8 minutes before dead) and 12 for every type that calls an outside provider (`send_email`, `notify_admin`, `post_meta`, `post_x`, `post_linkedin`, `webhook_omnikom`, `write_captions`, `invoice_pdf`, `newsletter_send`, `market_open_notice` and the heavy render dispatches; about 5 hours before dead with the 1 hour cap), so an ordinary provider incident does not dead-letter invoices, posts or lead forwards (DL-10, E2E-03). The formula does not change.
5. The database row is the truth. pgmq messages are wake-ups; a lost message is repaired by the reaper, and a handled message or a duplicate whose job is no longer runnable is deleted with `job_queue_delete`: nothing is archived, so pgmq's archive tables stay empty and `job_events` is the record (JOB-10, ruling H15). Every function that makes a job runnable again (`fail_job` with a retry pending, `requeue_job` for `retry_at` and manual retry, `approve_job`) calls `pgmq.send(queue, jsonb_build_object('job_id', id), greatest(0, extract(epoch from run_after - now()))::int)` and stores the new `msg_id`. `reap_stale_jobs()` also re-sends a message for every `queued` or `failed` job with `run_after < now() - interval '5 minutes'` whose `msg_id` is absent from its queue table. The runner dispatches at most 3 heavy jobs per tick (`HEAVY_PER_TICK = 3` in `runner.ts`). It reads a batch of messages and claims each job right before running it; it starts no new job after 40 seconds of its 50 second budget, and a message it read but never claimed reappears after the 120 second visibility timeout (JOB-02). `reap_stale_jobs()` fails a `running` light job whose `locked_at` is more than 5 minutes old through the fail path (error `lease_expired`, one attempt used, backoff, `dead` at `max_attempts`, one `stale` row in `job_events`) and never resets a job for free (JOB-02).
6. Callbacks are matched on `job_id` and `claim`, the `locked_by` token of the run that dispatched (JOB-02: an attempt number repeats after a manual retry, a claim never does). A callback whose claim no longer holds the job is acknowledged with `{ ignored: "stale_claim" }` and changes nothing.
7. Nothing external happens inside a Worker request (architecture 1). The Worker only inserts rows. A Worker request may make at most 50 outbound subrequests (Workers free plan, GOTCHAS P-009) and every database or Storage call counts, so an `onResult` makes a number of database or Storage calls that does not depend on the size of the result (JOB-03): a render callback makes at most 5 calls (the job read, the step's fixed calls, `finish_job`) for 1 photograph or 40, and work that grows with a request's size, such as copying a request's photographs (E2E-02), runs as a job in the job runner.
8. Free tier only (G-011, P-009): pgmq, pg_cron, pg_net and Vault are Supabase free extensions. No Cloudflare Queues, no Durable Objects.
9. Liveness never depends on what it watches (DO-03, JOB-04): the runner, keep-warm and backup each write their `ops_heartbeats` row, and the token-gated `ops-health` hook with an outside monitor reads them (Outputs). The daily `health` job and its `notify_admin` mail are a second path, never the alarm for a stopped runner.

Events emitted: `health.failed`, by `src/server/jobs/system/health.ts` through `emitEvent(db, { type: "health.failed", entity: "system", entityId: null, payload: { date, failed: [{ check, message }], summary, link_path: "/admin/jobs" } })`, where `summary` is `"<n> checks failed: "` followed by the failed check names joined by `", "`, when at least one check has status `fail`, at most once per run (the run is daily, key `health:<UTC date>`); B8b's recipe row `notify_admin_health` runs `notify_admin` (template `admin_notify`, B5, `params.headline` "Health check failed"), whose job `data` is this payload, so it carries the `summary` and `link_path` that G13 requires. Each check whose status is `fail` is also reported once through `ctx.report(new Error("HealthCheckFailed: <check>"), { fingerprint: ["health", <check>], level: "error" })` (INT-04), so a failed check reaches the owner through Sentry while Resend cannot deliver. There is no `admin_alert` template (G13). No other system job emits a catalog event; a dead job is surfaced by screen 16, screen 2 and the health check `dead_jobs_24h`. B8 owns the `events` table and the 18 catalog types listed in architecture 3.6, including `subject_request.received` (G29; the `CatalogEventType` list of `src/server/lib/events.ts`). It also moves the emission of `submission.received`, `inquiry.received`, `subscriber.confirmed`, `subscriber.created` and `subject_request.received` into B3's SQL write functions (step 2a, G20).

- Callback host per environment: `mop-dev` heavy jobs call back the Worker named in its function secret `RENDER_CALLBACK_URL`, which is B1b's stable dev Worker `matter-of-place-dev` (G19; deployed on every push to `main` with the preview secret bundle, so it reads `mop-dev` and holds `RENDER_CALLBACK_SECRET`). Preview Workers are never named there, because they are deleted when their pull request closes. Until `mop-prod` exists the production Worker also holds the `mop-dev` pair (G19); L1 points `mop-prod`'s secret at `https://matterofplace.com/api/hooks/render/callback`.
- No Docker (S50, P-038): nothing here runs `supabase start`, `db reset`, `db diff` or `functions serve`. DB tests (F22 harness, `DEV_DB_URL`) and the self-test run on `mop-dev`; the job functions need pgmq and pg_net, so a throwaway native PostgreSQL 18 cluster cannot host them.
- Recipe and event names are fixed by architecture 3.6: the catalog is 18 events (G29); a 19th is a spec change, not a B8 decision.
- Visibility timeout (120 s) is shorter than the stale-lock limit (5 minutes) on purpose; the claim function handles the duplicate message. Long steps are not allowed in the light queue: a light step runs under at most 40 seconds (`timeoutMs`, JOB-02); make longer work heavy.
- Supabase free projects pause after 7 idle days; the cron itself is activity, and B8b's `keepwarm` schedule is the explicit guard.
- GD-03: `retention` is the only code that hard-deletes (architecture 10). Storage deletes are irreversible; the first production run is a `dry_run` whose counts the admin reads, and the health check `retention_stalled` (B8) fails when an enabled `delete` or `anonymise` policy has not run for 2 days or left eligible rows behind (`remaining` above 0 in the `retention.run` audit row). It runs as a fixed pg_cron entry, not from `schedule_settings`, because that table's key check has no `retention` value; B8b's schedules migration must leave `retention` and `meta_token_refresh` scheduled (it only unschedules `prune`).
- G-004: `inquiries.anonymised_at` and `retention_policies` appear in the domain types, the API and the columns together; grep the names in `src/domain` and the migrations before finishing.
- GS-01: writing a refreshed token into Vault relies on Vault being writable from the Edge Function's service role, UNPROVEN until step 8a runs on `mop-dev`. The Page token that comes from a long-lived user token does not expire (B10), so the refresh path may never fire; the alert path is the guaranteed part. Agent keys (90 days), Resend and R2 tokens are rotated by hand per the runbook; the job does not touch them.

## Out of scope
Recipe planning and fan-out logic (B8b), the 17 catalog step implementations (B5 for `send_email` and `notify_admin`, B9 to B12 and the owners in B8b's step table for the rest), the recipe editor, Slack or Telegram alerting, Stripe or Meta webhooks, batching several renders in one Actions run, Cloudflare Queues.
