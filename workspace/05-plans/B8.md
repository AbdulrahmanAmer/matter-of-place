## Goal and observed exit
The machine room: every side effect is a row in `jobs` with an idempotency key, run by an Edge Function on pg_cron, with heavy work dispatched to GitHub Actions and finished by a signed callback (S12, S17, architecture 1 and 5).
Observed exit (completion map B8): "a publish creates jobs that complete and report". Proven in two parts. Part 1, before B8b exists: `scripts/job-selftest.ts` enqueues `test.selftest_light` and `test.selftest_heavy` through `enqueue_job` (fan-out is still a stub, so no event is involved), the light one reaches `done` in under 90 seconds, the heavy one round-trips through `render.yml` and its callback and reaches `done` (the heavy half is BLOCKED until the operator mints `GITHUB_DISPATCH_TOKEN`, see step 7; its callback target on `mop-dev` is B1b's stable dev Worker `matter-of-place-dev`, G19; the light half and every other step run without it). Part 2, after B7 and B8b: publishing a property in `/admin` creates the `property.published` jobs and screen 16 shows them complete.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- `emit_event(type, entity, entity_id, payload, actor_id)` SQL function, called inside every state-changing transaction (architecture 1). Server code outside a transaction uses `emitEvent()` in `src/server/lib/events.ts`, which calls the same function through RPC. B3's public writes emit inside their SQL function from step 2a on: `create_submission` emits `submission.received`, `confirm_subscriber` emits `subscriber.confirmed`, B3's `create_inquiry(p jsonb)` keeps its insert and emits `inquiry.received` with `{ inquiry_id }` (G49), `create_subject_request` emits `subject_request.received` with `{ request_id, kind }` (G29), and `upsert_subscriber` emits `subscriber.created` with `{ subscriber_id, sealed_token }` when the row is new or still unconfirmed and `p->>'sealed_token'` is not null (G12, G20). The Worker seals the token before the call: `requestConfirmation(token)` in B3's `src/server/subscribers/confirmation.ts` returns the sealed token or null (null from B3's stub and whenever `CONFIRM_TOKEN_SECRET` is unset; B5 replaces the body with `sealToken(token, env.CONFIRM_TOKEN_SECRET)`) and emits nothing; `subscribers/service.ts` passes the value as `sealed_token` to `upsert_subscriber`. No TS code emits a catalog event that a SQL write function emits (G20).
- `enqueue_job(p_type text, p_payload jsonb, p_idempotency_key text, p_heavy boolean default false, p_status job_status default 'queued', p_run_after timestamptz default now(), p_event_id uuid default null, p_recipe_id uuid default null, p_step_id text default null) returns uuid`: the new job id, or null when the key already exists; it sends the pgmq message only when the status is `queued`, and when it inserts it writes exactly one `job_events` row of kind `created` (none when the key already exists). SQL write functions of other slices call it inside their own transaction, so the job, its `created` row and its message commit or roll back with the write: B7's `set_market_coming_soon` and B8b's `open_market_on_publish` (called by the `bump_catalog_version` step) enqueue `market_open_notice` this way (G58). TS wrapper `enqueueJob(db, { type, idempotencyKey, params?, data?, heavy?, runAfter? }): Promise<string | null>` in `src/server/lib/jobs.ts`, for system jobs that have no event (health, prune, manual forward). Manual system jobs use `enqueue_job_manual(p_type text, p_entity_id uuid, p_payload jsonb) returns uuid` (TS `enqueueManualJob(db, { type, entityId, data })`), which takes a transaction advisory lock on `p_type || p_entity_id` and computes `n` = 1 + the count of jobs whose key starts with `<type>:<entity_id>:`.
- `fanoutPendingEvents()` and `runDueSchedules()` are called by the runner every tick. B8 ships both as stubs that return 0. B8b replaces `src/server/automation/fanout.ts`; B8b also replaces `src/server/jobs/scheduler.ts`. The stub signatures are the contract: `fanoutPendingEvents(db, limit): Promise<number>` and `runDueSchedules(db, now): Promise<number>`.
- Step modules: `{ type, heavy, paramsSchema, run(ctx, params, payload) }` plus optional `onResult(ctx, job, result)` for heavy steps (architecture 2, tech-stack 5 "a job type"). `StepContext` is `{ db, env, log, now, job: { id, type, attempts, result, eventId } }`, where `job` is the claimed row, so a step can read what an earlier attempt stored in `jobs.result`. `now` is a `Date`, taken once by `runOnce` when it claims the job (`opts.now ?? new Date()`) and the same value for the whole run of that job, including `onResult`; steps read `ctx.now` as a value and never call it (tests pass a fixed `Date` as `opts.now`). `StepResult` is `{ status: "done", result? }`, `{ status: "retry_at", at, reason, result? }` or, for heavy steps only and only as returned by `dispatchHeavy`, `{ status: "dispatched", result? }` (the job stays `running` until its callback); the runner writes `result` into `jobs.result` in every case (B15 keeps its delivery counter there), and a step never updates `jobs` itself. A step that throws B3's shared `r2_unavailable` error (F18) is treated by the runner as `{ status: "retry_at", at: now + 1 hour, reason: "r2_unavailable" }`, so no attempt is used while R2 is off (E8).
- Heavy dispatch: `dispatchHeavy(ctx, job, extra?)` in `src/server/jobs/steps/heavy.ts` builds `client_payload = { job_id, attempt, type, payload, env, callback_url }` where `payload` is `{ params, data: { ...data, ...extra } }` (B12 passes `{ spec, spec_hash, revision }`; B9's steps pass their media list), refuses a serialised `client_payload` above 64 KB with `NonRetryableError("payload_too_large")` before any call, and calls `dispatch.ts`, which POSTs `https://api.github.com/repos/${GITHUB_REPO}/dispatches` with `Authorization: Bearer ${GITHUB_DISPATCH_TOKEN}`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28` and body `{ event_type: "render", client_payload }`, expecting 204. On 204 it returns `{ status: "dispatched", result: extra }` and the runner writes a `dispatched` row in `job_events`, so `onResult` reads `job.result.spec_hash`. `GITHUB_DISPATCH_TOKEN` or `GITHUB_REPO` unset: `{ status: "retry_at", at: now + 1 hour, reason: "dispatch_not_configured" }` (no attempt used, no call). A 5xx answer or a network error throws (normal backoff, invariant 4). 401, 403, 404 or 422 throws `NonRetryableError("dispatch_<status>")`, so the job goes `dead` and shows on screen 16.

Job payload envelope (pinned here, produced by B8b's planner and by `enqueueJob()`): `jobs.payload = { params, data }`. `params` is the recipe step's validated parameters, snapshotted when the job is created so a later recipe edit never changes a job already queued; `data` is the event payload (or the system job's input). The runner calls `step.run(ctx, job.payload.params, job.payload.data)`. `enqueueJob()` writes `params = {}` when the caller gives none. The heavy `client_payload.payload` is this whole envelope.

Outputs
- `jobs` rows with lifecycle `queued` to `running` to `done`, or `failed` (retry pending) and `dead`, plus `waiting_approval` and `cancelled` (architecture 3.6, screen 16; a deliberate cancel is not painted red as `dead`).
- One `job_events` row per transition. ASSUMED columns: `id`, `job_id fk`, `at`, `kind` (`created|claimed|done|failed|dead|dispatched|callback|approved|cancelled|manual_retry|requeued|stale`), `from_status`, `to_status`, `attempt`, `message`, `data jsonb`, `actor_id`.
- Heavy jobs: `repository_dispatch` event type `render` with `client_payload = { job_id, attempt, type, payload, env, callback_url }` (at most 10 top-level keys and 64 KB, GitHub limit; payloads carry ids and R2 keys, never files). `env` is the dispatching Edge Function's `MOP_ENV` (`development` or `production`); `callback_url` is its Supabase function secret `RENDER_CALLBACK_URL`, so each Supabase project calls back the Worker that reads the same database. `render.yml` passes `env` to the scripts as `MOP_ENV`, from which B9's `scripts/lib/r2.mjs` derives the bucket (`production` gives `mop-media`, anything else `mop-media-dev`, B2 names; G52), and `checkJob` refuses any value other than `development` or `production`; `post-callback.mjs` posts to `callback_url` and refuses a host other than `matterofplace.com` or one ending in `.holy-meadow-4327.workers.dev`.
- Callback: `POST /api/hooks/render/callback` with `X-MOP-Timestamp` (unix seconds) and `X-MOP-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>" keyed by RENDER_CALLBACK_SECRET>`. Body `{ job_id, attempt, status: "done"|"failed", result?, error?, retryable?, run_url }`; `retryable` defaults to true, and `retryable: false` makes the hook call `fail_job` with `p_dead => true` so a deterministic render failure is not dispatched again. Responses: 200 applied or already applied or stale attempt (`{ ignored: "stale_attempt" }`, so Actions stops retrying), 400 malformed, 401 bad signature or timestamp older than 300 seconds, 404 unknown job, 503 `unavailable` when the Worker's `RENDER_CALLBACK_SECRET` is unset (nothing is verified or changed, so `post-callback.mjs` retries and, failing that, the reaper fails the job after 30 minutes; the same rule as B3's `hooks.handleResend`). The Worker reads the secret through B3's `src/server/lib/env.ts` as an optional key (Change), so a Worker without it still starts.

Invariants
1. Idempotency key is `event_id:step_id` for recipe jobs, `<type>:<UTC date>` for daily system jobs (`health`, `prune`, `retention`, `meta_token_refresh`), `reconcile:<UTC date>T<HH:MM>` with the minute rounded down to the quarter hour for the 15-minute `reconcile` system job (set by B8b's scheduler from the `reconcile` row of `schedule_settings`, `*/15 * * * *`, G10), `<type>:<entity_id>:<n>` for manual system jobs (`n` from `enqueue_job_manual`), and the key a caller sets for a job it enqueues directly: `market_open:<slug>` for `market_open_notice` (B7 and B8b, G37, G58) and `render_variants:<media_id>:<staging_path>` for B7's per-upload `render_variants` job, which is new for every replace because a replace stages at a new `staging_path` (G54). Enqueue is `insert ... on conflict (idempotency_key) do nothing`. A second insert never creates a second job.
2. A job runs at most once concurrently: `claim_job` is one `update ... where status in (...) returning *`; a lost claim returns no row.
3. Retries never consume an attempt when a step returns `{ status: "retry_at", at, reason }` (used by the email daily cap in B5). Any thrown error consumes one. `NonRetryableError` goes straight to `dead`.
4. Backoff: `delay = min(30 s * 2^(attempts-1), 1 h)` with plus or minus 20 percent jitter; `attempts >= max_attempts` (default 5) means `dead`. Total time before dead is about 8 minutes.
5. The database row is the truth. pgmq messages are wake-ups; a lost message is repaired by the reaper, a duplicate message is archived when its job is no longer runnable. Every function that makes a job runnable again (`fail_job` with a retry pending, `requeue_job` for `retry_at` and manual retry, `approve_job`) calls `pgmq.send(queue, jsonb_build_object('job_id', id), greatest(0, extract(epoch from run_after - now()))::int)` and stores the new `msg_id`. `reap_stale_jobs()` also re-sends a message for every `queued` or `failed` job with `run_after < now() - interval '5 minutes'` whose `msg_id` is absent from its queue table. The runner dispatches at most 3 heavy jobs per tick (`HEAVY_PER_TICK = 3` in `runner.ts`).
6. Callbacks are matched on `job_id` and `attempt`. A callback for an older attempt is acknowledged and ignored.
7. Nothing external happens inside a Worker request (architecture 1). The Worker only inserts rows.
8. Free tier only (G-011, P-009): pgmq, pg_cron, pg_net and Vault are Supabase free extensions. No Cloudflare Queues, no Durable Objects.

Events emitted: `health.failed`, by `src/server/jobs/system/health.ts` through `emitEvent(db, { type: "health.failed", entity: "system", entityId: null, payload: { date, failed: [{ check, message }], summary, link_path: "/admin/jobs" } })`, where `summary` is `"<n> checks failed: "` followed by the failed check names joined by `", "`, when at least one check has status `fail`, at most once per run (the run is daily, key `health:<UTC date>`); B8b's recipe row `notify_admin_health` runs `notify_admin` (template `admin_notify`, B5, `params.headline` "Health check failed"), whose job `data` is this payload, so it carries the `summary` and `link_path` that G13 requires. There is no `admin_alert` template (G13). No other system job emits a catalog event; a dead job is surfaced by screen 16, screen 2 and the health check `dead_jobs_24h`. B8 owns the `events` table and the 18 catalog types listed in architecture 3.6, including `subject_request.received` (G29; the `CatalogEventType` list of `src/server/lib/events.ts`). It also moves the emission of `submission.received`, `inquiry.received`, `subscriber.confirmed`, `subscriber.created` and `subject_request.received` into B3's SQL write functions (step 2a, G20).

## Risks and gotchas (link GOTCHAS ids)
- G-012: `render.yml` lives at `E:\Matter Of Place\.github\workflows\`, jobs use `working-directory: Matter Of Place Codebase`. Nested `.github` never runs.
- G-011 and P-009: cron every minute is 43,200 Edge calls a month against 500,000; heavy fan-out costs one Actions run per asset (about 5 per publish, one minute minimum each) against 2,000 minutes. Measure in HARDEN; batching several jobs per run is the first optimisation (not built here).
- G-004: `src/domain/jobs.ts` field names equal generated types and snake_case columns; change together.
- G-006: `GITHUB_DISPATCH_TOKEN`, `JOB_RUNNER_SECRET`, `RENDER_CALLBACK_SECRET` are never `VITE_*`.
- Edge Functions run in Deno; `src/server/jobs` must not import Node-only or Worker-only modules (no `cloudflare:workers`, no `node:fs`). Enforced locally by `deno check --config supabase/functions/job-runner/deno.json supabase/functions/job-runner/index.ts` from the app folder (deno 2.8.1 is installed on the laptop, ASSUMED E11) and in CI by the `deno` job that step 5 adds to `ci.yml`; the `--use-api` deploy of step 5 is the runtime proof. The same applies to B3's `reconcileUploads` and B1b's `sentry.ts`, which the function imports. `npm:` imports of this kind already run on the Edge runtime (E5).
- R2 from the Edge Function: no Worker binding exists there, so a step that needs R2 uses the S3-compatible API through B3's `src/server/lib/r2.ts`. No B8 code writes R2. ASSUMED function secrets `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` once R2 is on; the bucket follows `MOP_ENV` (`mop-media-dev` or `mop-media`) and there is no `R2_BUCKET` in a file, a secret, a variable or on a command line (G52); in Actions `render.yml` sets `MOP_ENV` from `client_payload.env` and `scripts/lib/r2.mjs` derives the bucket from it (G52, Files). R2 is off until the operator enables it (E8, S50): no B8 step creates or writes a bucket. B8 reuses `src/server/lib/r2.ts` and its `r2_unavailable` error from B3 (F18) and `scripts/lib/r2.mjs` from B9 (F17), and creates neither; when a step throws `r2_unavailable`, `runner.ts` requeues the job with `run_after` one hour ahead and no attempt used (Contract, `runner.test.ts`), so it waits and does not fail the steps around it. `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` already exist in GitHub but are UNPROVEN (E8). Invoices do not use R2 (G26); the first R2 users are B9's renders, which carry the block.
- GitHub `repository_dispatch` needs a fine-grained token with Contents write on this repo only. It does not exist yet (not in E10) and only the operator can mint it (P-037). ASSUMED scope; check at step 7. Until then heavy jobs cannot be dispatched: each one waits with `retry_at` reason `dispatch_not_configured` and uses no attempt (Contract); light jobs are unaffected.
- Callback host per environment: `mop-dev` heavy jobs call back the Worker named in its function secret `RENDER_CALLBACK_URL`, which is B1b's stable dev Worker `matter-of-place-dev` (G19; deployed on every push to `main` with the preview secret bundle, so it reads `mop-dev` and holds `RENDER_CALLBACK_SECRET`). Preview Workers are never named there, because they are deleted when their pull request closes. Until `mop-prod` exists the production Worker also holds the `mop-dev` pair (G19); L1 points `mop-prod`'s secret at `https://matterofplace.com/api/hooks/render/callback`.
- No Docker (S50, P-038): nothing here runs `supabase start`, `db reset`, `db diff` or `functions serve`. DB tests (F22 harness, `DEV_DB_URL`) and the self-test run on `mop-dev`; the job functions need pgmq and pg_net, so a throwaway native PostgreSQL 18 cluster cannot host them.
- Recipe and event names are fixed by architecture 3.6: the catalog is 18 events (G29); a 19th is a spec change, not a B8 decision.
- Visibility timeout (120 s) is shorter than the stale-lock limit (5 minutes) on purpose; the claim function handles the duplicate message. Long steps (over 100 s) are not allowed in the light queue; make them heavy.
- Supabase free projects pause after 7 idle days; the cron itself is activity, and B8b's `keepwarm` schedule is the explicit guard.
- GD-03: `retention` is the only code that hard-deletes (architecture 10). Storage deletes are irreversible; the first production run is a `dry_run` whose counts the admin reads, and the health check `retention_stalled` (B8) fails when an enabled `delete` or `anonymise` policy has not run for 2 days or left eligible rows behind (`remaining` above 0 in the `retention.run` audit row). It runs as a fixed pg_cron entry, not from `schedule_settings`, because that table's key check has no `retention` value; B8b's schedules migration must leave `retention` and `meta_token_refresh` scheduled (it only unschedules `prune`).
- G-004: `inquiries.anonymised_at` and `retention_policies` appear in the domain types, the API and the columns together; grep the names in `src/domain` and the migrations before finishing.
- GS-01: writing a refreshed token into Vault relies on Vault being writable from the Edge Function's service role, UNPROVEN until step 8a runs on `mop-dev`. The Page token that comes from a long-lived user token does not expire (B10), so the refresh path may never fire; the alert path is the guaranteed part.
