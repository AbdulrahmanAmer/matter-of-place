### CS-01 · critical · Code shared with the Deno job runner is written with extensionless imports, which Deno 2 refuses, and the gate that would catch it arrives eight slices late
Lens: code-standards · Touches: B1b, B3, B5, B8, B8b, B12, B15, B16

**Problem.** The job-runner Edge Function imports src/server/jobs/**, src/server/automation/**, B3's state.ts, mappers.ts, visibility.ts, r2.ts, errors.ts, log.ts, runtime-env.ts and reconcile.ts, B1b's sentry.ts, and B12's reel-spec.ts. The house style and the plans use extensionless specifiers. Deno 2.8.1 refuses these with TS2307, through the import map as well as by relative path. B1b and B3 write those files before B8 step 5 adds the first `deno check`. So the Operations lane goes red at B8 step 5, and every shared file needs its imports rewritten under the 48-hour deadline. Until then, nothing that runs in the job runner can be deployed. B3's portability grep checks which modules a file imports, not how it writes the specifier.

**Evidence.** Re-measured in the scratchpad. `fn/deno.json` holds `{"imports":{"@/server/":"../src/server/"}}`, and `fn/index.ts` imports `@/server/lib` while `src/server/use.ts` imports `./lib`. `deno check --config fn/deno.json fn/index.ts` gives `TS2307 [ERROR]: Cannot find module '.../src/server/lib'. Maybe add a '.ts' extension or run with --sloppy-imports`, exit 1. Plans prescribe extensionless specifiers: B15 line 80 (`@/server/omnikom/client`, `@/server/lib/hmac`), B8b line 139 ('other server files by relative path or `@/server/`'), B12 line 15 ('imports it as `@/server/assets/reel-spec`'). B8 line 104: the deno CI job is added at B8 step 5. A grep for sloppy, extensionless or '.ts extension' over ASSUMED, B*.md, architecture and tech-stack finds no ruling. tsconfig.json line 17 already sets `allowImportingTsExtensions: true` (with noEmit), so `.ts` specifiers typecheck and Vite resolves them today.

**Do this.** Ruling in ASSUMED section G before B1b. It binds B1b, B3, B5, B8, B8b, B12, B15, B16, architecture section 2 and AGENTS.md. (1) Every relative, `@/server/` or `@/domain/` import or re-export in the Deno-loaded set carries the `.ts` extension. The set is src/server/lib/{errors,log,runtime-env,sentry,r2,events,jobs,crypto}.ts, src/server/public/{state,mappers}.ts, src/server/catalog/visibility.ts, src/server/submissions/reconcile.ts, src/server/jobs/**, src/server/automation/**, src/server/omnikom/**, src/server/assets/reel-spec.ts, src/server/subscribers/confirm-email.ts and src/domain/**. (2) An eslint block for those globs uses `no-restricted-syntax` with three selectors, for ImportDeclaration, ExportNamedDeclaration and ExportAllDeclaration, of the form `ImportDeclaration[source.value=/^([.]|@.(server|domain))/]:not([source.value=/[.]ts$/])` and the message 'Deno-loaded file: import with the .ts extension'. The reviewer's selector does not work: esquery cannot parse a `/` inside the regex and throws `Invalid regular expression: /^(.{1,2}|@/: Unterminated group`. The corrected form was tested and flags `./lib`, `@/server/foo` and `export ... from "../q"` while passing `./lib.ts`, `@/server/foo.ts` and `zod`. (3) Move the first `deno check` to B3. B3 creates `supabase/functions/job-runner/deno.json` with the `@/server/` entry and the `zod` and `@supabase/supabase-js` lines, and B8 then adds its own lines and index.ts. B3 also creates a two-line `scripts/deno-portable.ts` that imports the B3 portable set, and the CI job `deno` runs `deno check --config supabase/functions/job-runner/deno.json scripts/deno-portable.ts` from B3 on. B8 points the job at index.ts. (4) `verbatimModuleSyntax: true` (see standards) makes B3's `import type { Db }` rule a compiler error. It costs nothing: measured, `tsc --noEmit -p tsconfig.json --verbatimModuleSyntax true` exits 0 on today's code. Proof (watched-fail): remove `.ts` from one import in state.ts, and both `bun run lint` and the deno job go red.

### CS-03 · major · Admin routes are wired by hand in every file across nine slices, and nothing checks that each write verifies CSRF
Lens: code-standards · Touches: B6, B7, B8, B8b, B9, B10, B11, B14, B16, H1

**Problem.** The public side is safe by construction: handlePublic, a route table and routes-parity.test.ts. The admin side is safe only if each builder takes care. Each `src/routes/api/admin/*.ts` file calls requireActor, verifyCsrf on writes, the service, adminJson and fromRpcError itself, and B6, B7, B8, B8b, B9, B10, B11, B14 and B16 each add files. A route that forgets verifyCsrf is a forgeable state change from a logged-in staff browser, and no test anywhere goes red. A route that forgets requireActor is caught only at H1 (H1-15 walks every write per role), which is the last phase before launch.

**Evidence.** tech-stack.md line 230 gives the admin route path as a file calling `requireActor(request, db)`, `verifyCsrf` on writes, the service, `adminJson` and `fromRpcError`. B7 line 78 defines `verifyCsrf(request)` only as a function (double submit, bearer exempt). B7's watched-fail (j) tests the function, not each route. `grep -i csrf workspace/05-plans/H1.md` finds 0 lines. A grep for handleAdmin, adminRoutes or admin-routes over all plans finds 0 hits. H1-15 (H1 line 44) covers authorization per role, not CSRF.

**Do this.** B7 step 1 creates `src/server/admin/pipeline.ts` with `handleAdmin(request, db = getDb())` and `src/server/admin/routes.ts` with `export const adminRoutes: AdminRoute[]`, where a row is `{ path, method, action, auth?: 'none', input?: ZodSchema, reauth?: true, service }`. `auth: 'none'` is used only by auth.send-link and auth.callback, which run before a session exists. handleAdmin runs in a fixed order: requireActor (unless `auth: 'none'`); assertSessionFresh, plus requireRecentAuth when `reauth`; verifyCsrf for every method other than GET or HEAD (bearer exempt inside verifyCsrf, as today); the Zod parse; `authorize(actor, row.action)`; the service; adminJson; and fromRpcError on throw. Each route file becomes `POST: ({ request }) => handleAdmin(request)`. `tests/unit/admin-routes-parity.test.ts` fails when a file under src/routes/api/admin has no row, when a row has no file, or when a row's `action` is not in the authz matrix. Later slices add rows, not wiring. H1 gains a row: a POST to every non-GET `adminRoutes` entry with a valid session cookie and no X-MOP-CSRF header answers 403 `csrf`. Watched-fail: skip verifyCsrf in handleAdmin, and the H1 probe and a unit case in admin-routes-parity go red.

### INT-07 · major · Credentials and versions with a known end date get no early warning; an Anthropic 404 is unmapped
Lens: integrations · Touches: B8, B9, B10, B14, B16

**Problem.** Some provider dependencies end on a date known in advance, and the plan notices each one only when production work starts failing. The fine-grained GitHub dispatch token has an expiry date. When it lapses, every render answers 401 and goes dead, and the whole asset and social pipeline stops. The LinkedIn dated API version is detected only after it is sunset. The Anthropic model in settings.caption_model is checked only by caption-golden.ts, run by hand. When that model is retired the API answers 404, which B9 does not map, so the job retries to dead. A builder must also guess the class of a 404. Resend domain verification, needed for every mail, is never re-checked after setup.

**Evidence.** B8.md:69: the health checks are database-only; B14 adds usage_gauges and B16 adds site_identity. B8.md:135: dispatch 401 goes dead, and `grep -n "expir" B8.md` finds no tracking of the dispatch token. B9.md:60: Anthropic errors are mapped for "429, a 5xx or a timeout" and "a 400 or 401", with no 404. B9.md:131: the model check exists only in scripts/caption-golden.ts. B10.md:109: LinkedIn version_expired is raised only on a 426, VERSION_MISSING or NONEXISTENT_VERSION answer.

**Do this.** Add src/server/jobs/system/health/providers.ts, appended to B8's health check list (the way B14 and B16 append theirs). Each check runs only when its credential exists and returns 'skip' otherwise. github_dispatch: GET https://api.github.com/repos/{GITHUB_REPO} with the token, then read the `github-authentication-token-expiration` response header; warn under 14 days, fail on 401 or when expired. anthropic_model: GET https://api.anthropic.com/v1/models/{settings.caption_model}; fail on 404. resend_domain: GET https://api.resend.com/domains; fail unless matterofplace.com has status `verified`. linkedin_version: a pure check of settings.linkedin.api_version (YYYYMM) that warns once it is 10 months old. Meta is covered by INT-06. In B9, map an Anthropic 404 or not_found_error to NonRetryableError('anthropic_model_missing'). Tests in health-providers.test.ts use recorded responses (a header 10 days out gives warn, a models 404 gives fail, an absent credential gives skip), and captions.test.ts gains the 404 case.

### SEC-08 · major · The dev loader exports every .env value into every builder shell, including production credentials and the account-admin Cloudflare token
Lens: security · Touches: B2, B3, B3b, B14, B16, H1, L1

**Problem.** Every DB test, smoke run and seed starts with a loader that exports all names in the root `.env`. That file holds `mop-admin` as `CLOUDFLARE_API_TOKEN`, which is full-account and is the variable wrangler reads automatically. It holds `SUPABASE_ACCESS_TOKEN`, which reaches all projects. From L1 on it also holds PROD_SUPABASE_SERVICE_ROLE_KEY, PROD_DB_URL and the PROD_* Worker secrets. AI builders run headless with `--dangerously-skip-permissions` (P-010). In such a shell, a stray `bunx wrangler deploy` uses the admin token, and the pinned name (G-002) is `matter-of-place`, so it overwrites production. A `--target prod` flag picks up live credentials. Any dependency running in the test process can read every one of these values. The first two exposures exist today; the production ones arrive at L1 and remain for every builder after launch.

**Evidence.** B3.md:14 and ASSUMED E10: `set -a; . <(tr -d '\r' < "/e/Matter Of Place/.env" | grep -E '^[A-Z0-9_]+='); set +a`. The same loader appears in ASSUMED, B3, B3b, B14 and B16. tech-stack.md:165-168: local `.env` holds `CLOUDFLARE_API_TOKEN` (`mop-admin`), `SUPABASE_ACCESS_TOKEN` and, at launch, `PROD_SUPABASE_SERVICE_ROLE_KEY`, `PROD_DB_URL` and the PROD_* secrets. GOTCHAS P-010, G-002.

**Do this.** (1) Split the file. `.env` keeps dev values only. A new `.env.ops`, git-ignored and in the same folder, holds `CLOUDFLARE_API_TOKEN` (mop-admin), `CF_EDGE_TOKEN`, `SUPABASE_ACCESS_TOKEN`, every `PROD_*` name and `BACKUP_PASSPHRASE` (or the age identity, see SEC-10). L1, the H1 production rows, cf-edge.mjs and the rotation runbook read it.
(2) Add `scripts/load-env.mjs --profile dev|ops`. It prints `export` lines for an explicit allow-list per profile and never prints values to the terminal. Every plan replaces the inline loader with `eval "$(node scripts/load-env.mjs --profile dev)"`. ASSUMED E10 records the new command.
(3) `scripts/lib/guard-env.mjs` is imported first by `tests/db/global-setup.ts` and by every dev script (seed, api-smoke, seed-admin-users). It throws, naming the variable, when `process.env` has any name matching `^PROD_|^SUPABASE_ACCESS_TOKEN$|^CLOUDFLARE_API_TOKEN$|^CF_EDGE_TOKEN$|^BACKUP_`. Scripts that legitimately need ops (seed `--target prod`, bootstrap-admin `--target prod`) call `guardEnv({ allowOps: true })` only behind their existing `--confirm-production` flag. Tested in `tests/unit/env-guard.test.ts`.
(4) `ready.mjs` checks that the names of both files are in their correct file.
Watched-fail: export PROD_DB_URL and run `bun run test:db`, and it aborts naming the variable.
