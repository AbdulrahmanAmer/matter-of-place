### DO-03 · critical · Monitoring depends on the things it monitors: a dead job runner, cron or database sends no alert
Lens: delivery-ops · Touches: B1b, B8, B8b, B14, H1, L1

**Ruling (CTO):** Accepted as the single liveness mechanism; see ruling JOB-04 for how the two findings merge.

**Problem.** (1) The daily `health` check is a job that the runner itself executes, and its alert path is runner -> `notify_admin` -> `send_email` -> Resend. If the runner stops (a bad function deploy, a wrong Vault `job_runner_secret`, a function that answers 401 or 500, a paused project), `health` never runs and `stale_queue` never fires. **Ruling (CTO):** Accepted, unified with DO-03 into ONE liveness mechanism (H2): the table is DO-03's `ops_heartbeats(name text primary key, at timestamptz not null, detail jsonb)` written by `beat(p_name, p_detail)`; the runner's heartbeat is the row `runner` (this finding's `runner_heartbeat` table and `record_runner_tick` are not created; `runOnce` calls `beat('runner', ...)` in its `finally`); `jobs_liveness()` reads that row and the oldest due job; the token-gated health route and the third UptimeRobot monitor are DO-03's.

The `health` job and its `notify_admin` both run through the runner. `cron_failures` reads `cron.job_run_details`, where `select net.http_post(...)` always succeeds because pg_net is asynchronous, so a 401 or 500 from the function never shows there. L1's go-live check and B8 step 6 use the same table as proof that the runner is ticking. The external uptime check covers only `/` and `/api/public/markets`. The outage is found when a customer complains.

**Evidence.** B8.md:54 health is `select enqueue_job('health', ...)` run by the runner; B8.md:69 `cron_failures` = `health_cron_failures` over `cron.job_run_details` with `status = 'failed'`. (4) Replace the L1 and B8 step 6 proofs with `select last_ok_at > now() - interval '2 minutes' from runner_heartbeat`. (5) Add a `scheduled.test.ts` case where a stale heartbeat gives exactly one capture, with a watched-fail.
