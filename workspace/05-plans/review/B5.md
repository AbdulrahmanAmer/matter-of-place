### API-01 · critical · Invites fail as written, and magic links fail across devices and when mail scanners open them
Lens: api · Touches: B5, B7, H1

**Problem.** Staff sign-in sends Supabase's `{{ .ConfirmationURL }}` (a GET to `/auth/v1/verify` that uses up the one-time token). It then redirects to `auth.callback.ts`, which calls `exchangeCodeForSession`. That is the PKCE flow, and the code verifier is a cookie the Worker set on the browser that asked for the link. This causes three failures. (1) Invites: the default verify redirect puts the session in the URL fragment. A server route never receives the fragment, so every invited editor lands on a callback with no code, and onboarding is broken from the first invite. (2) Cross-device: a staff member who asks for the link on a laptop and opens it on a phone, or in a mail app's in-app browser, has no verifier cookie there, so the exchange fails. (3) Mail scanners such as Microsoft Defender Safe Links prefetch the verify URL. That uses up the token, and the real click fails with "Token has expired or is invalid". S10 makes magic links the only staff sign-in, so all three lock staff out, and nobody can see why.

**Evidence.** B7.md:84: "`auth.callback.ts` exchanges the code with `exchangeCodeForSession`" and `emailRedirectTo: <origin>/api/admin/auth/callback`. B5.md:73-74: the templates use the literal `{{ .ConfirmationURL }}` for magic link and invite. B7.md:122 and :157: invites go through `auth.admin.inviteUserByEmail`. `grep -n -i "pkce\|code_verifier\|TokenHash\|token_hash" workspace/05-plans/B5.md B7.md` finds only `scripts/probe-amr.ts` (B7.md:133), which already uses `verifyOtp({ token_hash })` but only as a dev probe. B5.md:178 accepts scanner clicks for the newsletter confirm link only. ASSUMED section G has no ruling on this. Supabase documentation (docs/guides/auth/auth-email-templates, read this session through the Supabase docs search) says: under "Email prefetching", "the `{{ .ConfirmationURL }}` sent will be consumed instantly which leads to a 'Token has expired or is invalid' error". Under "Redirecting the user to a server-side endpoint", "the session is returned in the query fragments by default, you won't be able to access it on the server-side", and it recommends `{{ .TokenHash }}` links verified with `verifyOtp`. None of this has been run on mop-dev (UNPROVEN until the tests below run).

**Do this.** Change both templates to the token-hash form in `scripts/build-auth-templates.ts` and the generated `supabase/templates/magic-link.html` and `invite.html` (B5 step 8). The magic link becomes `{{ .SiteURL }}/admin/auth/confirm?token_hash={{ .TokenHash }}&type=email&next={{ .RedirectTo }}` (`email` is the current `EmailOtpType`; `magiclink` is deprecated), and the invite uses the same URL with `type=invite`. Add the page `src/routes/admin/auth.confirm.tsx`. On GET it only renders one "Continue to Matter of Place" button inside a form that POSTs to `/api/admin/auth/verify`, so a scanner's GET changes nothing. The new route `src/routes/api/admin/auth.verify.ts` is CSRF-exempt like `send-link`, but it refuses a request whose `Origin` header is present and is not the site's own origin (403 `csrf`). It calls `supabase.auth.verifyOtp({ type, token_hash })` through `session.ts`, then does exactly what `auth.callback.ts` does today: it reads `user_roles` (no enabled row means sign out and redirect to `?state=disabled`), sets the session cookies and `mop_csrf`, and redirects to `safeNext(next)`. Remove `auth.callback.ts` and every `exchangeCodeForSession`, and drop `emailRedirectTo` to the callback from `signInWithOtp`; the template builds the link itself. Tests: (a) `tests/unit/auth-verify.test.ts` with a stubbed client: a GET of the confirm page makes zero Auth calls, a POST with a token hash sets three cookies and redirects through `safeNext`, a foreign `Origin` gets 403, and the open-redirect and disabled cases move over from `auth-callback.test.ts`. ### API-04 · major · The sign-in link and agent-key traffic have no rate limit, so free-tier quotas can be exhausted
Lens: api · Touches: B1b, B3, B5, B7, H1

**Problem.** `POST /api/admin/auth/send-link` is anonymous, has no Turnstile, no memory limit and no DB limit. Each call makes a database lookup (`staff_can_sign_in`), and for a staff address it sends one Supabase Auth mail through Resend SMTP. Supabase throttles the same address to about one mail a minute, but a script that cycles the few staff addresses still uses up Resend's 100 mails a day. Every transactional mail shares that quota (acknowledgements, invoices, the confirm emails), and the attack also fills Supabase's project-wide auth-mail limit, which locks out staff sign-in. S16 already requires Turnstile on every form, and the sign-in form is a form. Agent keys have only a daily cap on decisions. A Claude session or routine stuck in a retry loop against `/api/admin/*` at one request a second uses most of the Worker's 100,000 requests a day, which the public site shares. An invalid bearer costs one `agent_key_by_hash` query, and nothing throttles that either.

**Evidence.** B7.md:84: "`auth.send-link.ts` calls `staff_can_sign_in`; only when it is true does it call `supabase.auth.signInWithOtp`", with no limit. `grep -n "send-link" H1.md B17.md` finds nothing. B3.md:38-40: limits exist only for `/api/public`. B1b.md:102 and H1.md:32: the one Cloudflare rule matches `starts_with(http.request.uri.path, "/api/public/")`. B7.md:27: the agent cap covers only decline and accept decisions. B7.md:83: `agent_key_by_hash` runs on every agent request. P-009: Workers free 100k requests a day, Resend free 100 a day. B5.md:159: whether auth mail counts in Resend's daily count is UNPROVEN. PROJECT-STATE S16: "Turnstile on every form".

**Do this.** (1) `send-link` uses B3's existing helpers in this order: `checkMemory('auth_link:ip', ip, 5, 60s)`; `verifyTurnstile` (S16; the sign-in form renders the widget), where `fail` answers 200 `sent` and does nothing; then one `rate_limit_check` call with two checks, `auth_link:ip` at 10 per hour and `auth_link:email` (sha256 of the lower-cased address) at 5 per hour. A limit hit still answers 200 `sent`, so nothing is revealed, and logs `auth_link_limited`. Seed the Supabase Auth email rate limit in `supabase/config.toml` `[auth.rate_limit] email_sent = 30` (per hour), pushed with `supabase config push`, so the provider has a ceiling too. An exceeded limit is 429 `rate_limited` with `Retry-After`. This adds one DB write per agent request, which is acceptable at agent volumes. (3) `scripts/cf-edge.mjs` widens the one free rule's expression to `starts_with(http.request.uri.path, "/api/public/") or starts_with(http.request.uri.path, "/api/admin/auth/")`, and H1-03 changes its check to match. ### INT-11 · major · Resend errors are classified by HTTP status only, but each status covers several different errors
Lens: integrations · Touches: B5, B11

**Problem.** B5 maps 429 to RateLimited, 422 to Invalid and 5xx to Transient, and gives no retry time for 429. Resend's answers are finer than that. Status 429 is one of three: rate_limit_exceeded (retry in seconds), daily_quota_exceeded (retry after the UTC day rolls over) or monthly_quota_exceeded (retry next month). Treating all three alike either calls Resend every minute for a day or waits a day for a one-second limit. 409 concurrent_idempotent_requests and resource_locked mean retry shortly. 409 invalid_idempotent_request means the same key was used with a different body, which happens when a template edit lands between two attempts after the first was delivered. **Evidence.** B5.md:90: "RateLimited (429) becomes retry_at, Transient (5xx, network) a normal retry with B8 backoff, Invalid (422) a NonRetryableError", with no 409, 401 or 403 case and no retry time. Resend's error reference (context7 /llmstxt/resend_llms-full_txt, resend.com/docs/api-reference/errors) lists invalid_idempotency_key 400; missing_api_key and restricted_api_key 401; invalid_permission, restricted_api_key, suspended_api_key and validation_error 403; concurrent_idempotent_requests, invalid_idempotent_request and resource_locked 409; daily_quota_exceeded, monthly_quota_exceeded and rate_limit_exceeded 429; application_error 500; service_unavailable 503.

**Do this.** Classify on the body's `name` first and the status second, through one table RESEND_ERRORS in src/server/email/resend-errors.ts that both resend-client.ts and B11's resend.ts import. rate_limit_exceeded and 503: retry_at at now + max(Retry-After, 2 s). daily_quota_exceeded: retry_at at the next UTC midnight + 1 minute, plus a health warn. monthly_quota_exceeded: retry_at on the 1st of next month, plus a Sentry report (INT-04). concurrent_idempotent_requests and resource_locked: retry_at in 30 s. invalid_idempotent_request: email_message_finish 'sent' with error 'idempotent_conflict' and no resend, plus a Sentry warning. missing_api_key, restricted_api_key, suspended_api_key, invalid_permission, 403 validation_error and invalid_idempotency_key: NonRetryableError. Table-driven test resend-errors.test.ts with one case per name.
