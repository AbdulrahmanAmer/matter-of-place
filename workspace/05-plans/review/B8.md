### DO-03 · critical · Monitoring depends on the things it monitors: a dead job runner, cron or database sends no alert
Lens: delivery-ops · Touches: B1b, B8, B8b, B14, H1, L1

**Ruling (CTO):** Accepted as the single liveness mechanism; see ruling JOB-04 for how the two findings merge.

**Problem.** (1) The daily `health` check is a job that the runner itself executes, and its alert path is runner -> `notify_admin` -> `send_email` -> Resend. If the runner stops (a bad function deploy, a wrong Vault `job_runner_secret`, a function that answers 401 or 500, a paused project), `health` never runs and `stale_queue` never fires. (2) The `job-runner` pg_cron row only runs `net.http_post(...)`, which queues an HTTP request. `cron.job_run_details` records `succeeded` even when the function answers 401 or 500. So the L1 preflight, the L1 step 1d proof and the week-one 'cron ticks continuing' check would all report a broken runner as healthy. (3) The two uptime monitors poll `/` and `/api/public/markets`. Both are edge-cached and, by design (rule 7, stale beats down), keep answering 200 when the database is down. The result: a stopped runner means no signup confirmations, no submission acknowledgements and no admin notices, and nothing alerts. The first signal is the Saturday audit or a complaint.

**Evidence.** architecture.md line 136: '`job-runner` every minute (B8 `<ts>_job_cron.sql`, `net.http_post` to the Edge Function)'. B8.md line 69: `stale_queue` ('meaning the runner is not ticking') is a check inside `health.ts`, which the runner runs. L1.md line 31 (preflight): '`select count(*) from cron.job_run_details where status = 'succeeded' and start_time > now() - interval '5 minutes'` is above 0 (the job runner is ticking)'. L1.md line 112: 'cron ticks continuing (`... select max(start_time) from cron.job_run_details`)'. B14.md line 70: the monitors are `https://matterofplace.com/` and `/api/public/markets`. architecture.md line 205 (rule 7): stale content is served when the database errors. `grep -n -i "heartbeat\|dead.man\|_http_response"` over 05-plans, architecture and tech-stack returns no hits.

**Do this.** Add a dead-man's switch that depends on neither the runner nor Resend, and uses only the free UptimeRobot plan that B14 already requires. (1) B8 migration `<ts>_ops_heartbeat.sql`: table `ops_heartbeats(name text primary key, at timestamptz not null, detail jsonb)` with RLS on and no policy, plus `beat(p_name text, p_detail jsonb)` (security definer, fixed `search_path`, execute granted to `service_role` only). The runner calls `beat('runner', {claimed})` at the start of every `runOnce`, `runKeepWarm` calls `beat('keepwarm')`, and `backup.yml` calls `select beat('backup', ...)` next to its `claim_schedule`. A 401 or 500 never reaches `runOnce`, so a stale runner beat already covers the HTTP failure, and `net._http_response` is not needed. (4) The owner adds a third UptimeRobot keyword monitor (keyword `ok`, every 5 minutes, alerting the admin mailbox). Record it in `workspace/audits/monitoring/uptime.json`, and make B14's `--check-config` expect three monitors. **Problem.** `onResult` runs inside the Worker request that receives the callback (B8 `handleRenderCallback`). **Evidence.** B9.md:65 `onResult` "per row: calls `ctx.db.rpc("set_media_variants" ...)`; removes the staged object with `ctx.db.storage.from("submissions").remove([staging_path])`; then ... `ctx.db.rpc("clear_media_staging" ...)`" and `run` "selects the property's `property_media` rows whose `staging_path` is not null". (2) `jobs_liveness()` (security definer, service role) returns `{ last_ok_at, oldest_due_age_s, http_errors_1h }`. `oldest_due_age_s` is the age of the oldest `queued` or `failed` job with `run_after <= now()`. `http_errors_1h` counts `net._http_response` rows from the last hour that are `timed_out` or have a non-2xx `status_code`; pg_net keeps these rows for 6 hours, and today the runner tick is the only pg_net caller. When `last_ok_at` is older than 5 minutes, `oldest_due_age_s > 900` or `http_errors_1h > 3`, it calls B1b's `captureException(new Error("job_runner_stalled"))` with a fixed fingerprint, so Sentry's new-issue email reaches the admin. An RPC error is logged once and swallowed, like the existing `keepwarm state_rpc_failed`. (4) Replace the L1 and B8 step 6 proofs with `select last_ok_at > now() - interval '2 minutes' from runner_heartbeat`. (5) Add a `scheduled.test.ts` case where a stale heartbeat gives exactly one capture, with a watched-fail.

### API-02 · major · Admin routes have no declarative contract, so each of about 75 handler files assembles authorization, CSRF and recent-auth by hand
Lens: api · Touches: B6, B7, B8, B8b, B9, B10, B11, B14, H1

**Problem.** Public routes go through one pipeline driven by `routes.ts`. Admin routes do not.
