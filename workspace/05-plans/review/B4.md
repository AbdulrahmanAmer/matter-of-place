### E2E-06 · critical · The three S54 lanes push migrations and job-runner builds from their own branches into the one shared mop-dev, which the Supabase CLI refuses, and an edited migration drifts silently
Lens: end-to-end · Touches: B1b, B2, B4, B8, B17

**Problem.** PLAN.md runs phase 1 as three lanes, each in its own worktree and branch. Every slice proof runs `bun run db:push` against mop-dev, and `preview-db` does the same on each PR push. As soon as lane B pushes a migration that lane A's branch does not contain, lane A's next `db push` stops with the CLI error 'Remote migration versions not found in local migrations directory'. When a lane pushes a migration whose timestamp is older than one already applied, the CLI stops with 'Found local migration files to be inserted before the last migration on remote database' unless `--include-all` is passed. Both errors offer `migration repair` as the way out, and that is the hack a builder under a 48-hour clock will reach for. The proof of every database step in every lane then goes red for a reason unrelated to the step. Separately, `db push` skips a version it has already applied, so when a reviewer asks for a change and the builder edits that migration, mop-dev keeps the old DDL. B4 then generates types from the stale schema, the tests pass, and mop-prod later applies the edited file. The same collision hits the job runner: `deploy.yml` deploys `job-runner` to mop-dev from a PR branch whenever `src/server` changed, so the last lane to deploy removes the other lanes' steps. Their jobs then die with `unknown_step` (B8 runner: 'an unknown type to dead with `unknown_step`').

**Evidence.** PLAN.md lines 29-33: 'each lane in its own git worktree and branch, each landing on `main` through CI. What already makes this safe: one writer at a time on `mop-dev` (G34, the advisory lock)'. That lock serialises writers but does not reconcile migration history. B4 line 94: '`bun run db:push` (B2's name, idempotent: a migration `preview-db` already applied is skipped)'. B8 line 105: the PR job deploys `bunx supabase functions deploy job-runner --use-api --project-ref ${{ secrets.DEV_SUPABASE_PROJECT_REF }}` when `git diff ... -- supabase/functions src/server` prints anything. B2 line 162 protects only mop-prod: 'a migration already pushed to `mop-prod` is never edited'. B7 line 162 has the mop-dev rule for B7's own files only. The installed CLI (`C:/Users/DELL/scoop/apps/supabase/current/supabase.exe`, v2.98.2) contains both strings: 'Remote migration versions not found in local migrations directory.' and 'Found local migration files to be inserted before the last migration on remote database.' B1b line 83 (`preview-cleanup`) covers only the unmerged-PR case, with a comment and a manual `db:reset`.

**Do this.** (1) Put the guard in front of B2's `db:push` script: a new `scripts/db-push.mjs`, which `bun run db:push` runs before `supabase db push`. Over `DEV_DB_URL` it reads `supabase_migrations.schema_migrations.version` and fails, naming each version, when the remote holds a version that is not in the local folder ('rebase onto origin/main first'). It also fails when a local version not yet applied is older than the newest applied version ('regenerate the timestamp with `supabase migration new`', as B17 already does for its own file). Use a hash of our own and do not compare the CLI's `statements` column, which depends on the CLI's statement splitter. (2) Landing rule in PLAN.md and B2: a migration lands on `main` in its own small PR (migration plus regenerated `src/db/types.ts`) before the code that needs it, and every lane rebases on `origin/main` before any `db:push`. `--include-all` and `migration repair` are never used on mop-dev or mop-prod without the orchestrator. (3) Job runner: deploy `job-runner` to mop-dev only from `main` (deploy.yml on push to main) or from a branch that contains `origin/main` (check with `git merge-base --is-ancestor origin/main HEAD`). In `runner.ts`, `unknown_step` becomes `retry_at now + 15 minutes` with no attempt used, for up to 24 hours from `created_at`, and only then dead, so a missing step module (a lane gap or a rollback) never kills jobs. (4) GOTCHAS gets a P-entry for the lane collision. Proof: `bunx vitest run tests/unit/db-push-guard.test.ts` (fake history: a remote-only version, an older local version and a changed file hash each exit 1 naming the version; a clean state exits 0). ### JOB-03 · critical · The render_variants callback makes three Worker subrequests per photograph, so a normal 40-photo property goes over the Workers free limit of 50
Lens: jobs · Touches: B4, B8, B9

**Ruling (CTO):** Accepted as part of ruling PERF-01 (H3).

**Problem.** `onResult` runs inside the Worker request that receives the callback (B8 `handleRenderCallback`). For `render_variants` it makes three calls per photograph: the `set_media_variants` RPC, a Storage `remove`, then the `clear_media_staging` RPC. Each per-upload job renders every staged row of the property, so one callback can carry up to 40 rows, which means about 120 subrequests plus the job read and `finish_job`. The Workers free plan allows 50 subrequests per request (vendor documentation, not measured here; P-009 does not list this limit). The request fails at about photo 16. The `fail_job` that follows is itself over the limit. The job stays `running` until the 30-minute reaper re-dispatches a full Actions run, and each retry hits the same wall. This failure is deterministic on the normal path once R2 is on.

**Evidence.** B9.md:65 `onResult` "per row: calls `ctx.db.rpc("set_media_variants" ...)`; removes the staged object with `ctx.db.storage.from("submissions").remove([staging_path])`; then ... `ctx.db.rpc("clear_media_staging" ...)`" and `run` "selects the property's `property_media` rows whose `staging_path` is not null". B8.md:75: `handleRenderCallback` calls the step's `onResult` in the Worker. architecture.md:170 "25 MB and 40 files per submission". `grep -rni subrequest workspace/05-plans` → only B3.md (Turnstile). GOTCHAS P-009 has no subrequest line.

**Do this.** Keep `onResult` in the Worker but make its number of calls fixed, whatever the payload size. In B9 `render-variants.ts`: (1) one RPC `apply_media_variants(p_items jsonb)`, which runs the guarded `staging_path = p_staging_path` update for every item and returns `[{ media_id, staging_path, stored }]`; (2) one `storage.from("submissions").remove(paths)` call with every signed path; (3) one RPC `clear_media_staging(p_items jsonb)` for the rows that were stored. This keeps the clear-after-remove order of B9 watched-fail (n). Including the job read and `finish_job`, a callback then makes 5 subrequests for 1 photo or 40. In `run`, replace the per-row `createSignedUrl` with one `createSignedUrls(paths, 7200)`. Add to the B8 Contract: "an `onResult` makes a number of database or Storage calls that does not depend on the size of the result". Add the 50-subrequest line to P-009 and to architecture's free-tier list. Tests: `steps.test.ts` wraps the fake client in B4's `countingDb` and asserts exactly 3 calls from `onResult` for a 40-item result. `render-hook.test.ts` asserts at most 5 calls for a whole 40-item callback. Watched-fail: put the per-row loop back and the 40-item case goes red.

### DO-04 · major · The production gate is check + build only: a PR with red db or e2e checks, or a re-run of an older ci run, still deploys
Lens: delivery-ops · Touches: B1b, B4

**Problem.** There is no branch protection. Nothing blocks merging a PR whose `db`, `e2e`, `e2e-live`, `deno`, `seo` or `preview`/Lighthouse checks are red. The only guard is RUNBOOK's convention that the orchestrator re-verifies before merging, and three lanes will be merging under a 48-hour deadline. The push run of `ci` on `main` runs only `check`, `build` and `audit`, and that is all the `production` job waits for. Re-running an older green `ci` run on `main` (for example a flaky run retried after newer code has already deployed) fires `workflow_run` again and redeploys the older SHA over newer code, while the schema stays at the newer version.

**Evidence.** B1b.md line 79: 'so a push to `main` runs `check`, `build` and `audit`'. B1b.md line 84: the `production` job's only condition is `workflow_run.conclusion == 'success' && workflow_run.event == 'push'`. RUNBOOK.md lines 20-21: the orchestrator 'only then merges the pull request into `main`' (a convention). GOTCHAS P-028: 'protection of `main` is a CI rule, not a GitHub setting'.

It calls `gh api repos/{o}/{r}/commits/$GITHUB_SHA/pulls` to find the merged PR, then reads the check runs of that PR's head SHA. It exits 1 with `unverified merge <sha>: <job> <conclusion>` unless every name in the constant `REQUIRED_PR_CHECKS` (`check`, `build`, `db`, `e2e`, `deno`, `seo`, `preview`; `e2e-live` only when present, because it is path-filtered) concluded `success`. A code commit with no PR also exits 1. Because `production` already waits for `ci` success, no change to `deploy.yml` is needed for this part.
