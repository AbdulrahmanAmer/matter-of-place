### CS-01 · critical · Code shared with the Deno job runner is written with extensionless imports, which Deno 2 refuses, and the gate that would catch it arrives eight slices late
Lens: code-standards · Touches: B1b, B3, B5, B8, B8b, B12, B15, B16

**Problem.** The job-runner Edge Function imports src/server/jobs/**, src/server/automation/**, B3's state.ts, mappers.ts, visibility.ts, r2.ts, errors.ts, log.ts, runtime-env.ts and reconcile.ts, B1b's sentry.ts, and B12's reel-spec.ts. The house style and the plans use extensionless specifiers. Deno 2.8.1 refuses these with TS2307, through the import map as well as by relative path. B1b and B3 write those files before B8 step 5 adds the first `deno check`. So the Operations lane goes red at B8 step 5, and every shared file needs its imports rewritten under the 48-hour deadline. Until then, nothing that runs in the job runner can be deployed. B3's portability grep checks which modules a file imports, not how it writes the specifier.

**Evidence.** Re-measured in the scratchpad. `fn/deno.json` holds `{"imports":{"@/server/":"../src/server/"}}`, and `fn/index.ts` imports `@/server/lib` while `src/server/use.ts` imports `./lib`. `deno check --config fn/deno.json fn/index.ts` gives `TS2307 [ERROR]: Cannot find module '.../src/server/lib'. Maybe add a '.ts' extension or run with --sloppy-imports`, exit 1. Plans prescribe extensionless specifiers: B15 line 80 (`@/server/omnikom/client`, `@/server/lib/hmac`), B8b line 139 ('other server files by relative path or `@/server/`'), B12 line 15 ('imports it as `@/server/assets/reel-spec`'). B8 line 104: the deno CI job is added at B8 step 5. A grep for sloppy, extensionless or '.ts extension' over ASSUMED, B*.md, architecture and tech-stack finds no ruling. tsconfig.json line 17 already sets `allowImportingTsExtensions: true` (with noEmit), so `.ts` specifiers typecheck and Vite resolves them today.

**Do this.** Ruling in ASSUMED section G before B1b. It binds B1b, B3, B5, B8, B8b, B12, B15, B16, architecture section 2 and AGENTS.md. (1) Every relative, `@/server/` or `@/domain/` import or re-export in the Deno-loaded set carries the `.ts` extension. The set is src/server/lib/{errors,log,runtime-env,sentry,r2,events,jobs,crypto}.ts, src/server/public/{state,mappers}.ts, src/server/catalog/visibility.ts, src/server/submissions/reconcile.ts, src/server/jobs/**, src/server/automation/**, src/server/omnikom/**, src/server/assets/reel-spec.ts, src/server/subscribers/confirm-email.ts and src/domain/**. (2) An eslint block for those globs uses `no-restricted-syntax` with three selectors, for ImportDeclaration, ExportNamedDeclaration and ExportAllDeclaration, of the form `ImportDeclaration[source.value=/^([.]|@.(server|domain))/]:not([source.value=/[.]ts$/])` and the message 'Deno-loaded file: import with the .ts extension'. The reviewer's selector does not work: esquery cannot parse a `/` inside the regex and throws `Invalid regular expression: /^(.{1,2}|@/: Unterminated group`. The corrected form was tested and flags `./lib`, `@/server/foo` and `export ... from "../q"` while passing `./lib.ts`, `@/server/foo.ts` and `zod`. (3) Move the first `deno check` to B3. B3 creates `supabase/functions/job-runner/deno.json` with the `@/server/` entry and the `zod` and `@supabase/supabase-js` lines, and B8 then adds its own lines and index.ts. B3 also creates a two-line `scripts/deno-portable.ts` that imports the B3 portable set, and the CI job `deno` runs `deno check --config supabase/functions/job-runner/deno.json scripts/deno-portable.ts` from B3 on. B8 points the job at index.ts. (4) `verbatimModuleSyntax: true` (see standards) makes B3's `import type { Db }` rule a compiler error. It costs nothing: measured, `tsc --noEmit -p tsconfig.json --verbatimModuleSyntax true` exits 0 on today's code. Proof (watched-fail): remove `.ts` from one import in state.ts, and both `bun run lint` and the deno job go red.

### CS-04 · major · HMAC, constant-time compare and hashing are specified in eight places; one names an API that does not exist outside Workers, and two functions share the name hashKey
Lens: code-standards · Touches: B1b, B3, B5, B7, B8, B10, B15, H1

**Problem.** Every slice that needs a signature writes its own Web Crypto code: Svix verification inline in hooks/resend.ts, the bearer compare in sentry-test.ts, sha256Hex and hashKey in ids.ts, HMAC in preview-token.ts, signBody and verifyBody in hmac.ts, appsecret_proof in meta.ts, AES-GCM in confirm-email.ts, and key hashing in agent-keys.ts. Each site can compare with `===`, mix hex, base64 and base64url, or import a key with the wrong usages. A fix in one site never reaches the others. Two concrete defects are already in the plans. (1) B1b prescribes `crypto.subtle.timingSafeEqual`, a Cloudflare Workers extension that does not exist in Node, Bun or Deno. B1b's own unit proof runs in vitest's node environment and would throw a TypeError, and any copy of it in Deno-loaded code would fail in the job runner. (2) `hashKey` means `hashKey(salt, value)` in ids.ts (B3) and a one-argument sha256 hex in agent-keys.ts (B7). H1's rotation drill imports the B7 one, so an auto-import of the wrong one gives a hash that never matches.

**Evidence.** Measured: `node -e "typeof crypto.subtle.timingSafeEqual"` prints undefined, and so do Bun and `deno eval`. B1b line 98: the sentry-test bearer is 'compared in constant time (`crypto.subtle.timingSafeEqual` over equal-length byte arrays)'. B1b line 122: proof `bunx vitest run tests/unit/sentry-test-route.test.ts`; vitest.config.ts uses environment node. B3 line 72: ids.ts `hashKey(salt, value)`, `newToken()`, `sha256Hex`. B7 line 81: agent-keys.ts `hashKey` (sha256 hex). B3 line 86: Svix check inside resend.ts. B7 line 38: preview token HMAC-SHA256. B8 line 74: `src/server/lib/hmac.ts` with `signBody` and `verifyBody`, name frozen by F17. B10 line 44: appsecret_proof HMAC-SHA256. B5 line 93: AES-GCM sealToken and openToken.

**Do this.** B1b creates `src/server/lib/crypto.ts`. It is in the Deno-portable set with `.ts` imports and reads no environment. It exports `hmacSha256(key: string | Uint8Array, message: string): Promise<Uint8Array>`; `timingSafeEqual(a: Uint8Array, b: Uint8Array): boolean`, written in plain TypeScript as a length check then an XOR-accumulate loop, never crypto.subtle.timingSafeEqual; `sha256Hex`; `toHex`; `fromBase64`; `toBase64Url`; `randomToken(bytes = 32)`; `aesGcmSeal`; and `aesGcmOpen`. The following import from it instead of calling Web Crypto: sentry-test.ts, hooks/resend.ts, ids.ts (re-exports, no second body), preview-token.ts, hmac.ts (signBody and verifyBody stay under the frozen F17 name as thin wrappers), meta.ts, confirm-email.ts and agent-keys.ts. Rename agent-keys.ts's function to `hashAgentKey`, binding B7, H1 line 74 and H1-38. `tests/unit/crypto.test.ts` runs the RFC 4231 HMAC-SHA256 vectors and Svix's documented example, in the unit project, which runs under Node. The architecture test gains a case: `crypto.subtle` appears under src/** only in src/server/lib/crypto.ts. scripts/post-callback.mjs (Node) stays separate and shares B8's contract vector.

### DB-09 · major · Manual job keys count existing rows, so after done jobs are pruned the next key collides and retry, forward or metrics refresh silently does nothing
Lens: database · Touches: B7, B8, B10, B15

**Problem.** `enqueue_job_manual` builds `<type>:<entity_id>:<n>` with `n` = 1 + the number of existing jobs with that prefix, and done jobs are deleted after 30 days (`jobs_done`). Example:
- `:1` and `:2` exist, and `:1` is pruned;
- the count is 1, so `n` = 2;
- `on conflict do nothing` fires and no job is made.

This will happen in normal use:
- `refresh_social_post_metrics` on the same post three times over two months;
- a third Omnikom re-forward of an inquiry;
- a repeat `retry_social_post`. In this case the post has already moved `failed` to `scheduled` in the same transaction, so it waits forever with no job.

Each caller still writes its audit row and answers 202. The original point about a LIKE scan is dropped: `jobs` is small after pruning.

**Evidence.** B8.md:14: "`enqueue_job_manual` ... takes a transaction advisory lock on `p_type || p_entity_id` and computes `n` = 1 + the count of jobs whose key starts with `<type>:<entity_id>:`".
B8.md:28: "Enqueue is `insert ... on conflict (idempotency_key) do nothing`".
ASSUMED.md G48: `jobs_done` (30 days, delete).
B10.md:160: `retry_social_post` moves `failed` to `scheduled` and enqueues through `enqueue_job_manual`; `refresh_social_post_metrics` uses key `reconcile:<post_id>:<n>`.
B7.md:111: forward key `webhook_omnikom:<inquiry_id>:<n>`.

**Do this.** 1. Change one expression in B8's `enqueue_job_manual`, keeping the advisory lock: `n = 1 + coalesce(max(split_part(idempotency_key, ':', 3)::int), 0)` over the keys with that prefix. Pruning only removes keys, and max + 1 can never equal a key that still exists, so B8's existing `:1` and `:2` test still holds.

2. `retry_social_post`, `forward_inquiry` and `refresh_social_post_metrics` raise `enqueue_failed` when `enqueue_job_manual` returns null, so the state change and the audit row roll back instead of reporting success.

Proof: a case in `tests/db/jobs.db.test.ts`.
- Create `:1` and `:2`, then delete `:1` under `mop.retention`.
- The next call returns a non-null id with key `:3`.

Watched-fail: restore `count(*)` and the case goes red.

### DB-13 · major · Function bodies are re-copied by hand from one slice's migration into another's, across parallel lanes
Lens: database · Touches: B2, B3, B8, B9, B10, B15

**Problem.** Several shared functions are redefined in later migrations by hand-copying an earlier body:
- `create_inquiry` is created by B3, re-bodied by B8 step 2a to add `emit_event`, then re-bodied by B15 ("B8's body unchanged plus attribution");
- `upsert_subscriber`, `create_submission`, `confirm_subscriber` and `create_subject_request` are re-bodied by B8;
- `approve_asset` is dropped and re-created by B10 "copied unchanged from B9".

B8 and B15 sit in different phase-1 lanes. A lane that copies the body it saw when it branched silently drops the other lane's line, for example the `emit_event` call that drives every inquiry mail and the Omnikom forward. Both migrations apply cleanly, git sees no conflict because they are different files, and `supabase db diff` is not available here (E7).

The original proposal to replace cross-slice triggers with a dispatcher function is dropped. That dispatcher would itself be re-bodied by each slice, the same hazard, and the triggers are what keep slices additive.

**Evidence.** ASSUMED.md G49: "B8 step 2a replaces their bodies (`create or replace`) to add the event row".
B15 Data changes: "`create or replace function create_inquiry(p jsonb)` ... B8's body ... unchanged ... plus the column `attribution`".
B10 Data changes: "The rest of the body is copied unchanged from B9's migration".
PLAN.md:38: B8 in the Operations lane, B15 in the Public lane.

**Do this.** 1. `supabase/sql/functions/<name>.sql` holds the one current `create or replace` text of every function in `public`. A slice changes a function only by editing that file. Two lanes editing the same function then meet as a git merge conflict on one file instead of silently diverging.

2. `bun run db:fn <name> [<name>...]` (`scripts/db-fn.mjs`) writes a new `supabase migration new fn_<name>` file containing that text. It prepends `drop function if exists` when the signature in the file differs from the one in the latest migration.

3. Add `tests/db/function-source.db.test.ts`. For each file, compare its body (the text between the dollar-quote tags, trimmed) with `pg_proc.prosrc`, which Postgres stores verbatim. Do not compare `pg_get_functiondef`, because it reformats the header. Also fail on any `public` function that has no file, apart from extension-owned ones (`pg_depend` deptype `e`).

Watched-fail: write a migration that re-bodies `create_inquiry` without the `emit_event` line while the file keeps it, and the test goes red.
