### CS-01 · critical · Code shared with the Deno job runner is written with extensionless imports, which Deno 2 refuses, and the gate that would catch it arrives eight slices late
Lens: code-standards · Touches: B1b, B3, B5, B8, B8b, B12, B15, B16

**Problem.** The job-runner Edge Function imports src/server/jobs/**, src/server/automation/**, B3's state.ts, mappers.ts, visibility.ts, r2.ts, errors.ts, log.ts, runtime-env.ts and reconcile.ts, B1b's sentry.ts, and B12's reel-spec.ts. The house style and the plans use extensionless specifiers. Deno 2.8.1 refuses these with TS2307, through the import map as well as by relative path. B1b and B3 write those files before B8 step 5 adds the first `deno check`. So the Operations lane goes red at B8 step 5, and every shared file needs its imports rewritten under the 48-hour deadline. Until then, nothing that runs in the job runner can be deployed. B3's portability grep checks which modules a file imports, not how it writes the specifier.

**Evidence.** Re-measured in the scratchpad. `fn/deno.json` holds `{"imports":{"@/server/":"../src/server/"}}`, and `fn/index.ts` imports `@/server/lib` while `src/server/use.ts` imports `./lib`. `deno check --config fn/deno.json fn/index.ts` gives `TS2307 [ERROR]: Cannot find module '.../src/server/lib'. Maybe add a '.ts' extension or run with --sloppy-imports`, exit 1. Plans prescribe extensionless specifiers: B15 line 80 (`@/server/omnikom/client`, `@/server/lib/hmac`), B8b line 139 ('other server files by relative path or `@/server/`'), B12 line 15 ('imports it as `@/server/assets/reel-spec`'). B8 line 104: the deno CI job is added at B8 step 5. A grep for sloppy, extensionless or '.ts extension' over ASSUMED, B*.md, architecture and tech-stack finds no ruling. tsconfig.json line 17 already sets `allowImportingTsExtensions: true` (with noEmit), so `.ts` specifiers typecheck and Vite resolves them today.

**Do this.** Ruling in ASSUMED section G before B1b. It binds B1b, B3, B5, B8, B8b, B12, B15, B16, architecture section 2 and AGENTS.md. (1) Every relative, `@/server/` or `@/domain/` import or re-export in the Deno-loaded set carries the `.ts` extension. The set is src/server/lib/{errors,log,runtime-env,sentry,r2,events,jobs,crypto}.ts, src/server/public/{state,mappers}.ts, src/server/catalog/visibility.ts, src/server/submissions/reconcile.ts, src/server/jobs/**, src/server/automation/**, src/server/omnikom/**, src/server/assets/reel-spec.ts, src/server/subscribers/confirm-email.ts and src/domain/**. (2) An eslint block for those globs uses `no-restricted-syntax` with three selectors, for ImportDeclaration, ExportNamedDeclaration and ExportAllDeclaration, of the form `ImportDeclaration[source.value=/^([.]|@.(server|domain))/]:not([source.value=/[.]ts$/])` and the message 'Deno-loaded file: import with the .ts extension'. The reviewer's selector does not work: esquery cannot parse a `/` inside the regex and throws `Invalid regular expression: /^(.{1,2}|@/: Unterminated group`. The corrected form was tested and flags `./lib`, `@/server/foo` and `export ... from "../q"` while passing `./lib.ts`, `@/server/foo.ts` and `zod`. (3) Move the first `deno check` to B3. B3 creates `supabase/functions/job-runner/deno.json` with the `@/server/` entry and the `zod` and `@supabase/supabase-js` lines, and B8 then adds its own lines and index.ts. B3 also creates a two-line `scripts/deno-portable.ts` that imports the B3 portable set, and the CI job `deno` runs `deno check --config supabase/functions/job-runner/deno.json scripts/deno-portable.ts` from B3 on. B8 points the job at index.ts. (4) `verbatimModuleSyntax: true` (see standards) makes B3's `import type { Db }` rule a compiler error. It costs nothing: measured, `tsc --noEmit -p tsconfig.json --verbatimModuleSyntax true` exits 0 on today's code. Proof (watched-fail): remove `.ts` from one import in state.ts, and both `bun run lint` and the deno job go red.

### DB-16 · major · System-maintained property columns bump properties.version, so editors get false 409s while photographs render
Lens: database · Touches: B2, B7, B12

**Problem.** `properties_version_bump` adds 1 on every update. Several writers change `properties` with no editor involved:
- `sync_property_hero_image` (G66, G69(1)), when the first photograph renders, is replaced or the sequence changes;
- `attach_reel` (B12), which writes `video` when a reel is approved;
- `approve_asset` for a cover (G6), which writes `og_image_key`.

G66 renders each photograph when it is attached. In the main intake flow an editor attaches photographs and then edits the text while renders run, so their next save, publish or rank change fails with `version_conflict` (409) for a change they cannot see.

None of these columns can be overwritten by an editor's save: `save_property` refuses `hero_image`, and the patch allow-list excludes the others. So the bump protects nothing here.

This was point 4 of the original DB-13, split out because it stands alone.

**Evidence.** B2.md:118: "It is an ordinary row update: `properties_version_bump` raises `version`" (for the `hero_image` trigger).
B2.md:59: "incremented by the `before update` trigger `properties_version_bump` on every update, whatever the path".
ASSUMED.md G66: "`attach_media` and `replace_media` (B7) enqueue `render_variants` for that one photograph on a draft".
B12.md:22: `attach_reel` writes `properties.video`.
ASSUMED.md G6: `approve_asset` sets `properties.og_image_key`.

**Do this.** 1. In B2, `properties_version_bump` returns `new` without incrementing when `(to_jsonb(new) - array['hero_image','video','og_image_key','updated_at','version']) = (to_jsonb(old) - array['hero_image','video','og_image_key','updated_at','version'])`. `updated_at`'s trigger runs first, by alphabetical trigger order, so it must be in the list. The catalog bump and `enforce_publish_gate` are unaffected.

2. Name the excluded columns once, as `systemPropertyColumns` in `schema-manifest.ts`. The test reads the trigger's `prosrc` to check that the two lists agree.

Proof: a case in `catalog-version.db.test.ts` or `integrity.db.test.ts`:
- read `version`, set a media row's `r2_key` so the hero trigger fires, then call `save_property(p_expected_version => <read>)`, which succeeds;
- an editor field change still raises the version.

Watched-fail: remove the early return and the first case raises 40001.

### JOB-01 · major · The heavy-dispatch token needs Contents write, which can push to an unprotected main that auto-deploys; PR code on mop-dev holds it
Lens: jobs · Touches: B8, B12, H1

**Problem.** `repository_dispatch` needs a fine-grained token with Contents: write. With that permission the token can also push commits to `main`. `main` has no branch protection (P-028), and the production job deploys whatever `ci` passes on `main`. The token is a Supabase function secret of the job runner, and B8 deploys the runner to `mop-dev` from every pull request, so PR code and its npm dependencies run with the token in `Deno.env`. A leak lets an attacker ship code to production without the human merge review, which is the only production gate. `workflow_dispatch` needs only Actions: write, and `render.yml` already accepts it with the same JSON. The token has not been minted yet (A13 is open), so the switch costs nothing now.

**Evidence.** B8.md:161 "`repository_dispatch` needs a fine-grained token with Contents write on this repo only"; completion-map.md:23 A13 "Contents write on this repository only". B8.md:84: `render.yml` already has `workflow_dispatch` with a required string input `job`. B8.md:105: `preview-db` deploys `job-runner` to `mop-dev` from pull requests. GOTCHAS P-028: no branch protection. architecture.md:159: production gate is human merge review.

**Do this.** `src/server/jobs/dispatch.ts` POSTs to `https://api.github.com/repos/${GITHUB_REPO}/actions/workflows/render.yml/dispatches` with body `{ ref: "main", inputs: { job: JSON.stringify(client_payload) } }` and expects 204, keeping the unset, 5xx and 4xx outcomes of the B8 Contract. `render.yml` drops the `repository_dispatch` trigger and reads only `inputs.job`: `MOP_JOB: ${{ inputs.job }}`, `MOP_ENV: ${{ fromJSON(inputs.job).env }}`, `concurrency: render-${{ fromJSON(inputs.job).job_id }}`. The `if:` expressions of the `render` and `reel` jobs (B8, B12) become `fromJSON(inputs.job).type != / == 'render_reel'`. The 64 KB check stays, because workflow inputs are limited to 65,535 characters. The token spec in B8 Risks, completion-map A13, tech-stack row 19 and section 4, and H1's rotation table becomes: fine-grained, this repository only, Actions: read and write plus Metadata: read, no Contents. Tests: `tests/unit/jobs/dispatch.test.ts` asserts the URL ends `/actions/workflows/render.yml/dispatches`, `JSON.parse(body.inputs.job)` equals the payload, and the body has `ref: "main"`. `render-job.test.ts` asserts that `render.yml` contains no `repository_dispatch`. Also update the diagrams in plans-b.md, big-diagram.md and architecture.md:15. Remaining exposure, accepted: an Actions-write token can re-run old workflow runs or dispatch `render.yml` with a crafted payload; the callback still needs a running job and its claim (JOB-02).

### JOB-02 · major · The plans disagree on who counts attempts, a reclaimed job never uses one, nothing limits how long a step runs, and callbacks are matched on an attempt number that a manual retry resets
Lens: jobs · Touches: B8, B9, B12

**Problem.** B8 says `fail_job` increments `attempts`. The sequence diagram says `claim_job` does. The reaper "resets" a stale running light job, with no attempt rule. A builder will either count twice, so jobs die after about 3 failures, or never count a reclaim. In the second case a step that kills its isolate is reclaimed every 5 minutes forever, with no dead state, no Sentry report and no health signal. That can be a hung provider call cut at the Edge Function wall clock (150 s on free per vendor docs, UNPROVEN here) or a step over the 2 s CPU limit. `StepContext` has no abort signal and the runner sets no per-step limit. Separately, `manual_retry` sets `attempts` to 0, so `(job_id, attempt)` repeats over a job's life. A late callback from a run that was reaped and then retried by hand can match the new dispatch. Finally, `net.http_post` in the cron row sets no timeout, so pg_net's default (5 s per vendor docs) cuts the request well before a 50 s tick ends.

**Evidence.** B8.md:120: `fail_job` "increments `attempts`"; `requeue_job` `manual_retry` "sets `attempts` to 0". workspace/03-diagrams/plans-b.md:68 "claim_job sets running, locked_by, attempts plus 1". B8.md:67 "`reaper.ts` resets stale `running` light jobs". B8.md:16 StepContext `{ db, env, log, now, job }`. B8.md:33 invariant 6 "Callbacks are matched on `job_id` and `attempt`". B8.md:53 `net.http_post` with no timeout argument. `grep -n "AbortSignal\|signal" workspace/05-plans/B8.md` → no hits.

**Do this.** (1) One attempt rule, in B8 invariant 2 and `<ts>_jobs.sql`: `claim_job` never changes `attempts`, and `fail_job` increments it. Fix plans-b.md diagram 2. (2) A claim token in the existing `locked_by` column: `claim_job` sets `locked_by = gen_random_uuid()::text` and returns it. `finish_job`, `fail_job` and `requeue_job` take `p_claim text` (second, required parameter) and act only when `status = 'running' and locked_by = p_claim`; otherwise they return false and change nothing. Heavy dispatch sends `claim` in `client_payload` in place of `attempt`. The callback body carries it back, and `handleRenderCallback` answers 200 `{ ignored: "stale_claim" }` on a mismatch. (3) The reaper takes the fail path for a `running` light job with `locked_at < now() - interval '5 minutes'`: error `lease_expired`, one attempt used, backoff, `dead` at `max_attempts`, and a `stale` row in `job_events`. It never resets a job for free. (4) `StepContext` gains `signal: AbortSignal`. The runner runs each step under `AbortSignal.timeout(spec.timeoutMs ?? 20000)`, at most 40 000 for light steps, and treats an abort as a retryable failure `step_timeout`. Every outside `fetch` passes `ctx.signal`. (5) The runner claims each pgmq message right before running it, which is the diagram's order; say so in B8 Files. It starts no new job after 40 s. Read messages it never claimed reappear after the 120 s visibility timeout. (6) `<ts>_job_cron.sql` passes `timeout_milliseconds := 55000` to `net.http_post`, so the tick is not cut short and `net._http_response` records the real status (JOB-04). Tests: `jobs.db.test.ts` (a stale job reaped at `attempts = max_attempts - 1` goes `dead` with `lease_expired`; `finish_job` with a wrong claim returns false), `runner.test.ts` (a step that never resolves is aborted at `timeoutMs` with exactly one attempt used), `render-hook.test.ts` (a callback with the claim from before a manual retry is `stale_claim`). Each test gets a watched-fail.

### SEC-02 · major · GITHUB_DISPATCH_TOKEN is planned with Contents write: one leaked job-runner secret can push to main and deploy
Lens: security · Touches: B8, B9, B12, H1

**Problem.** `repository_dispatch` needs Contents write, so the token planned for the job runner can push commits. Main has no protection (P-028), and deploy.yml deploys every ci-green push to main. The job runner is also the process with the most secrets: the service role, Meta, X, LinkedIn, Anthropic, Resend and Omnikom. Its npm: imports float (SEC-13). One compromised import or a step that logs env therefore yields arbitrary code in production with all Worker secrets, plus edits to every workflow. Both mop-dev and mop-prod hold the token.

**Evidence.** B8.md:161 `GitHub repository_dispatch needs a fine-grained token with Contents write on this repo only`. B8.md:66 `POST https://api.github.com/repos/${GITHUB_REPO}/dispatches`. B8.md:84: render.yml already has `workflow_dispatch` with one required string input `job` (the same JSON). tech-stack.md:134: `GITHUB_DISPATCH_TOKEN` is a Supabase function secret. GOTCHAS P-028.

**Do this.** B8:
- `src/server/jobs/dispatch.ts` calls `POST /repos/${GITHUB_REPO}/actions/workflows/render.yml/dispatches` with `{ ref: "main", inputs: { job: JSON.stringify(client_payload) } }` and still expects 204.
- render.yml drops its `repository_dispatch` trigger. Every expression becomes the `inputs.job` branch only (`fromJSON(inputs.job).type`, `.env`, `.job_id` for concurrency). B12's `reel` job condition changes the same way.
- `dispatchHeavy` keeps its size check, renamed to the workflow_dispatch input limit of 65,535 characters for the serialized job (UNPROVEN exact limit; measure once in B8 step 7).

Proof, operator-run in B8 step 7 and recorded in its log: `curl -s -o /dev/null -w '%{http_code}' -X PUT -H "Authorization: Bearer $GITHUB_DISPATCH_TOKEN" https://api.github.com/repos/AbdulrahmanAmer/matter-of-place/contents/probe.txt -d '{"message":"x","content":"eA=="}'` prints 403, and the dispatch call prints 204.

### SEC-13 · major · The job runner's npm: imports float on every deploy, Actions are pinned by mutable tag, and workflows set no default token permissions
Lens: security · Touches: B1b, B8, B12, B14, H1

**Problem.** The Edge Function holds the most secrets and is bundled at each `functions deploy` from `npm:` specifiers with major-only ranges and no `deno.lock`. bunfig's `minimumReleaseAge` does not apply on that path, so a freshly compromised release of a dependency such as `@react-email/render@1` ships straight into the runner. Every `uses:` is a mutable tag (`@v4`, `@v2`), so a retagged action runs with whatever its job holds, including the deploy token (SEC-01). Only deploy.yml declares `permissions:`. ci.yml, backup.yml, render.yml, audit-deps.yml and audit-scope.yml inherit the repository default for GITHUB_TOKEN. Dropped from the original finding: `minimumReleaseAge` already exists in `bunfig.toml` (86400), and keeping `bun audit` non-blocking until H1 is a reasonable call for a 48-hour build.

**Evidence.** ASSUMED E5: `npm:cron-parser@5`, `npm:@react-email/render@1`, `npm:react@19`. B8.md:58: deno.json pins only zod exactly. B8.md:104 `denoland/setup-deno@v2`, `deno check` with no lock. B12.md:78 `actions/upload-artifact@v4`. B1b.md:80: only deploy.yml sets `permissions: contents: read, pull-requests: write`. A grep for `deno.lock|commit SHA|persist-credentials` in workspace/05-plans finds nothing. app/bunfig.toml: `minimumReleaseAge = 86400` (already present).

**Do this.** B8:
- Every `npm:` specifier in `supabase/functions/job-runner/deno.json` is an exact version.
- `deno.lock` is committed, generated with `deno cache --lock=deno.lock` against the import map.
- The `deno` CI job runs `deno check --frozen --config supabase/functions/job-runner/deno.json supabase/functions/job-runner/index.ts`. `--frozen` exists in deno 2.8.1.
- Whether `supabase functions deploy --use-api` honours the lock is UNPROVEN. B8 step 5 measures it by deploying with a deliberately stale lock. If the lock is ignored, the exact pins are the guard and the result is recorded in ASSUMED E5.
B1b, applying to every workflow later slices add:
- Every `uses:` is pinned to a 40-character commit SHA with a `# vX.Y.Z` comment. The existing Dependabot `github-actions` entry keeps them current.
- Each workflow sets top-level `permissions: {}`, and each job grants only what it needs. `actions/checkout` uses `persist-credentials: false` (the `gh pr comment` step already uses GH_TOKEN from env).
`hygiene.test.ts` reads every file in `.github/workflows/` (today it reads three by name) and asserts:
- every `uses:` matches `@[0-9a-f]{40}`;
- each file has a top-level `permissions:`;
- `supabase/functions/job-runner/deno.lock` exists;
- `bunfig.toml` keeps `minimumReleaseAge` of at least 86400.
Watched-fail: change one pin to `@v4`, and the test goes red.
