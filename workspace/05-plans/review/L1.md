### DO-03 · critical · Monitoring depends on the things it monitors: a dead job runner, cron or database sends no alert
Lens: delivery-ops · Touches: B1b, B8, B8b, B14, H1, L1

**Ruling (CTO):** Accepted as the single liveness mechanism; see ruling JOB-04 for how the two findings merge.

**Problem.** (1) The daily `health` check is a job that the runner itself executes, and its alert path is runner -> `notify_admin` -> `send_email` -> Resend. If the runner stops (a bad function deploy, a wrong Vault `job_runner_secret`, a function that answers 401 or 500, a paused project), `health` never runs and `stale_queue` never fires. (2) The `job-runner` pg_cron row only runs `net.http_post(...)`, which queues an HTTP request. `cron.job_run_details` records `succeeded` even when the function answers 401 or 500. So the L1 preflight, the L1 step 1d proof and the week-one 'cron ticks continuing' check would all report a broken runner as healthy. (3) The two uptime monitors poll `/` and `/api/public/markets`. Both are edge-cached and, by design (rule 7, stale beats down), keep answering 200 when the database is down. The result: a stopped runner means no signup confirmations, no submission acknowledgements and no admin notices, and nothing alerts. The first signal is the Saturday audit or a complaint.

**Evidence.** architecture.md line 136: '`job-runner` every minute (B8 `<ts>_job_cron.sql`, `net.http_post` to the Edge Function)'. B8.md line 69: `stale_queue` ('meaning the runner is not ticking') is a check inside `health.ts`, which the runner runs. L1.md line 31 (preflight): '`select count(*) from cron.job_run_details where status = 'succeeded' and start_time > now() - interval '5 minutes'` is above 0 (the job runner is ticking)'. L1.md line 112: 'cron ticks continuing (`... select max(start_time) from cron.job_run_details`)'. B14.md line 70: the monitors are `https://matterofplace.com/` and `/api/public/markets`. architecture.md line 205 (rule 7): stale content is served when the database errors. `grep -n -i "heartbeat\|dead.man\|_http_response"` over 05-plans, architecture and tech-stack returns no hits.

**Do this.** Add a dead-man's switch that depends on neither the runner nor Resend, and uses only the free UptimeRobot plan that B14 already requires. (1) B8 migration `<ts>_ops_heartbeat.sql`: table `ops_heartbeats(name text primary key, at timestamptz not null, detail jsonb)` with RLS on and no policy, plus `beat(p_name text, p_detail jsonb)` (security definer, fixed `search_path`, execute granted to `service_role` only). The runner calls `beat('runner', {claimed})` at the start of every `runOnce`, `runKeepWarm` calls `beat('keepwarm')`, and `backup.yml` calls `select beat('backup', ...)` next to its `claim_schedule`. A 401 or 500 never reaches `runOnce`, so a stale runner beat already covers the HTTP failure, and `net._http_response` is not needed. (2) RPC `ops_health(p_now timestamptz)` returns `{ok, failing:[...]}` and fails on: a runner beat older than 3 minutes, a keepwarm beat older than 25 minutes, a backup beat older than 26 hours (only once `schedule_settings.backup` is enabled), a `queued` job whose `run_after` is more than 15 minutes old, or any `dead` job in the last 24 hours. (3) Add `GET /api/hooks/ops-health/<token>`, built through the tech-stack §5 API-route path. It compares the token to a new Worker secret `OPS_HEALTH_TOKEN` in constant time, makes one RPC call, answers `no-store` (rule 6 already covers `/api/hooks/*`), and returns 200 `ok` or 503 `fail: <names>`. (4) The owner adds a third UptimeRobot keyword monitor (keyword `ok`, every 5 minutes, alerting the admin mailbox). Record it in `workspace/audits/monitoring/uptime.json`, and make B14's `--check-config` expect three monitors. (5) In the L1 preflight, step 1d and the week-one table, replace the three `cron.job_run_details` proofs with `select now() - at < interval '3 minutes' from ops_heartbeats where name = 'runner'`. Tests: `tests/db/ops-health.db.test.ts` (a runner beat 4 minutes old reports `runner`; a dead job reports `dead_jobs`). Watched-fail: set a wrong `job_runner_secret` in Vault on `mop-dev` (restore it afterwards); the endpoint must answer 503 naming `runner` within 5 minutes.

### JOB-04 · critical · Nothing outside the job runner notices when the runner stops, so every email and webhook stops without an alert
Lens: jobs · Touches: B1b, B8, B8b, H1, L1

**Ruling (CTO):** Accepted, unified with DO-03 into ONE liveness mechanism (H2): the table is DO-03's `ops_heartbeats(name text primary key, at timestamptz not null, detail jsonb)` written by `beat(p_name, p_detail)`; the runner's heartbeat is the row `runner` (this finding's `runner_heartbeat` table and `record_runner_tick` are not created; `runOnce` calls `beat('runner', ...)` in its `finally`); `jobs_liveness()` reads that row and the oldest due job; the token-gated health route and the third UptimeRobot monitor are DO-03's.

**Problem.** The runner can stop working in several ways: a bad deploy, a Vault `job_runner_secret` that no longer matches the function secret after a rotation, a Deno import error at boot, or the project paused. When it stops, every receipt, invoice, confirmation, inquiry forward and post stops too, and nobody is told. The `health` job and its `notify_admin` both run through the runner. `cron_failures` reads `cron.job_run_details`, where `select net.http_post(...)` always succeeds because pg_net is asynchronous, so a 401 or 500 from the function never shows there. L1's go-live check and B8 step 6 use the same table as proof that the runner is ticking. The external uptime check covers only `/` and `/api/public/markets`. The outage is found when a customer complains.

**Evidence.** B8.md:54 health is `select enqueue_job('health', ...)` run by the runner; B8.md:69 `cron_failures` = `health_cron_failures` over `cron.job_run_details` with `status = 'failed'`. L1.md:31 "`select count(*) from cron.job_run_details where status = 'succeeded' ...` is above 0 (the job runner is ticking)". architecture.md:173 "an external uptime check every 5 minutes on `/` and `/api/public/markets`". `grep -rni "heartbeat\|runner_stalled\|_http_response" workspace/05-plans workspace/06-architecture` → no hits.

**Do this.** (1) `<ts>_jobs.sql` adds a one-row table `runner_heartbeat(id int primary key check (id = 1), last_tick_at timestamptz, last_ok_at timestamptz, last_error text, release text)`, written only by `record_runner_tick(p_ok boolean, p_error text, p_release text)`. `runOnce` calls it in a `finally` block at the end of every tick. (2) `jobs_liveness()` (security definer, service role) returns `{ last_ok_at, oldest_due_age_s, http_errors_1h }`. `oldest_due_age_s` is the age of the oldest `queued` or `failed` job with `run_after <= now()`. `http_errors_1h` counts `net._http_response` rows from the last hour that are `timed_out` or have a non-2xx `status_code`; pg_net keeps these rows for 6 hours, and today the runner tick is the only pg_net caller. (3) B8b's Worker `scheduled()` keep-warm runs every 10 minutes in production only and makes one `jobs_liveness` RPC. When `last_ok_at` is older than 5 minutes, `oldest_due_age_s > 900` or `http_errors_1h > 3`, it calls B1b's `captureException(new Error("job_runner_stalled"))` with a fixed fingerprint, so Sentry's new-issue email reaches the admin. An RPC error is logged once and swallowed, like the existing `keepwarm state_rpc_failed`. (4) Replace the L1 and B8 step 6 proofs with `select last_ok_at > now() - interval '2 minutes' from runner_heartbeat`. (5) Add a `scheduled.test.ts` case where a stale heartbeat gives exactly one capture, with a watched-fail.

### PERF-02 · major · cron.job_run_details is never purged and grows by roughly 200 to 350 MB a year against the 500 MB database line
Lens: performance-cost · Touches: B8, L1

**Ruling (CTO):** Accepted (CTO; the operator is told): raw `analytics_events` keep 90 days, daily aggregates keep 13 months. Architecture section 10 is amended.

**Problem.** pg_cron writes one `cron.job_run_details` row per run. `job-runner` alone fires 1,440 times a day, which is about 525,000 rows a year. Each row holds the stored `net.http_post` command and its status, at about 0.4 to 0.7 KB. No plan deletes them, and no `retention_policies` row covers them. Within roughly a year this table alone takes half of the free 500 MB, and above the line the project refuses writes. B14's 70 percent `db_bytes` gauge will notice the growth, but nothing exists to act on it except a manual delete.
