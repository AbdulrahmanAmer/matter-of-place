### SEC-03 · critical · JSON-LD is serialized with plain JSON.stringify into a raw script sink, and inlineHashes would allow-list whatever script that produces
Lens: security · Touches: B13, B17, H1

**Problem.** Text from the public submission form can become stored XSS in cached public HTML. `create_property_from_submission` sets `title` from `submissions.address` and `story` from `submissions.story` (G62, B7.md:101). B13 builds RealEstateListing and Article JSON-LD from those fields. `pageHead` puts `JSON.stringify(jsonLd)` into a head script, and TanStack renders that string with `dangerouslySetInnerHTML`. `JSON.stringify` leaves `</script>` unescaped, so a title or story that contains `</script><script>...` closes the data block and starts an executable script. A published page is cached and served to every visitor on the origin that also serves /admin. B17's `inlineHashes(html)` hashes every inline script in the rendered page, so the injected script gets its own hash and stays allowed even after `csp_enforce` is switched on. Publishing still needs an editor, but S38 agents read the same public text and the seeded managing_editor agent can publish.

**Evidence.** app/src/lib/seo.ts:52 `scripts: jsonLd ? [{ type: "application/ld+json", children: JSON.stringify(jsonLd) }] : []`. node_modules/@tanstack/react-router/dist/esm/Asset.js:127-130 (data script) `dangerouslySetInnerHTML: { __html: children }`. B17.md:16 hashes `each inline script of the page`. B17.md:63 `inlineHashes(html)`. B13.md:66 extends `pageHead`'s `jsonLd` and names no escaping. A grep for `u003c|escapeJson|serializeJson` over workspace/05-plans finds nothing. B17.md:16 also has `script-src ... https://*.googletagmanager.com`, while B17.md:20 and G41 load only gtag.js from www.googletagmanager.com.

**Do this.** (1) `src/lib/seo.ts` exports `serializeJsonForScript(value)`. It runs `JSON.stringify`, then replaces `<` with `<`, `>` with `>`, `&` with `&`, U+2028 with ` ` and U+2029 with ` `. `pageHead` and every B13 JSON-LD builder use only this function. B13 adds the edit to its existing Change to seo.ts.
(2) B17 `inlineHashes`:
- Never hash a non-executable type (`application/ld+json`, `application/json`). These need no hash.
- Hash an executable inline script only when its opening tag carries TanStack's marker `class="$tsr"` (router-core/dist/esm/ssr/ssr-server.js:423; re-check the marker on each router upgrade) or when its exact text appears in an allow-list in `src/server/lib/csp-allowlist.ts` for app-owned bootstrap scripts.
- Any other executable inline script is left unhashed and reported to Sentry once per render as `csp_unexpected_inline_script`.
(3) Replace `https://*.googletagmanager.com` in script-src with `https://www.googletagmanager.com/gtag/js`. If the report-only reports on the preview show GA4 needs another path, fall back to the host `https://www.googletagmanager.com` with no wildcard and record the measurement. UNPROVEN until the reports are read.
(4) Canary test `tests/unit/csp-inline.test.ts` renders `/property/<slug>` and `/stories/<slug>` from a fixture whose every string field is `</script><script>window.__x=1</script>`. It asserts that the HTML contains no `<script>window.__x` and that the CSP hash set equals the hash set of a clean fixture.
Watched-fail: revert the serializer to `JSON.stringify`, and the test goes red.

### T-01 · critical · Every branch and every lane shares one mutable cloud schema (mop-dev): unmerged migrations break unrelated PRs and lanes, and the tests check a schema the branch does not have
Lens: testing · Touches: B1b, B2, B4, B6, B10, B11, B13, H1

**Ruling (CTO):** Accepted as the mechanism of ruling DB-01 (b): one CI job `db` on an ephemeral `supabase start` stack; seed gains the target `local` (127.0.0.1 only). See DB-01 for the single rule.

**Problem.** preview-db pushes each PR's migrations to the shared mop-dev, and the CI db job does the same, then generates types from mop-dev and diffs them against the branch. What follows: (1) Once PR A has pushed a migration, every other PR's db job fails the drift guard, even a PR with no migration of its own, because gen:types always runs and the types now include A's tables. And `supabase db push` in any PR without A's file fails with the remote-version-not-found error. (2) If a builder edits a migration in place after the first push, db push skips the version as already applied, so the tests run against the old body. (3) An abandoned PR's schema stays on mop-dev until someone runs db:reset by hand, and B2's script refuses while foreign migrations exist. (4) GitHub keeps one running and one pending job per concurrency group and cancels the older pending one, so with three lanes the db, e2e-live and preview-db jobs in group mop-dev get cancelled (B1b already accepts this and answers 'rerun'). (5) Because these jobs need secrets, Dependabot PRs get no db or e2e run at all. The same collision happens outside CI. Under S54, three lanes (PLAN.md:38) each push their own unmerged migrations to the same mop-dev from separate worktrees, and B10 and B11's step proofs run `bun run db:reset` in the Content lane while the Operations lane's migrations are live there. Either the guard refuses, or the reset wipes the other lanes' state. The gate turns red for reasons unrelated to the diff, and builders learn to rerun or ignore it.

**Evidence.** B1b.md:81 'If the push fails because mop-dev holds a migration version the branch does not have (another PR's unmerged migration), the job fails red ... recovery is the orchestrator running bun run db:reset'. B1b.md:153 'a busy hour can cancel a pending preview-db ... the fix is gh run rerun'. B4.md:94 db job: 'bun run gen:types ... and git diff --exit-code src/db/types.ts' (runs whether or not a migration changed), 'concurrency: { group: mop-dev, cancel-in-progress: false }', and the `github.actor != 'dependabot[bot]'` guard on all three jobs. B4.md:167 'a test:e2e:coming-soon toggle in a concurrent e2e-live run can change what the sweep sees ... rerun'. B2.md:74 'refusing: foreign migrations'. B10.md:176 and B11.md:130 'Proof: bun run db:reset'. PLAN.md:38 three parallel lanes. ASSUMED.md E7 'GitHub's hosted runners are not the operator's machine'. tech-stack.md:102 'No job needs Docker (S50)'.

**Do this.** CI: give the db and e2e-live jobs (and e2e, if it stays separate after T-04) a database of their own, created on the runner. Steps: `bunx supabase start -x studio,imgproxy,realtime,logflare,vector,supavisor,mailpit,edge-runtime`. This keeps Postgres 17 with pg_cron, pgmq and pg_net, plus PostgREST, GoTrue, storage-api and kong, which migration 11 and B6's bucket inserts need. Then `bunx supabase db reset --local` applies the branch's migrations from zero, followed by `bunx supabase gen types typescript --local --schema public > src/db/types.ts && git diff --exit-code src/db/types.ts`, then `bun run seed -- --target local` (F17 freezes `--target dev|prod`, so B2 adds `local` as a target that only accepts 127.0.0.1), then the tests with DEV_DB_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres and SUPABASE_URL plus the service key taken from `supabase status -o env`. Remove `group: mop-dev` and the Dependabot exclusion from those jobs. The service.ts and load-fixtures guards accept the 127.0.0.1 host as well as the mop-dev ref. mop-dev then receives migrations only from main: the deploy.yml `dev` job runs `db:push` after a merge. preview-db stops pushing PR migrations, and for a PR that changes supabase/migrations it comments 'preview needs merged schema' and skips the deploy. Lanes: the same rule applies on the laptop. A lane never pushes an unmerged migration to mop-dev. Its db tests run in its PR's CI database, and locally only on the native PostgreSQL 18 with H1's pg-shims.sql when they need no Supabase extension. B10 and B11's proofs change `db:reset` to `db:push`, as B13.md:105 already does. Add a hygiene.test.ts case that fails if a ci.yml job contains `group: mop-dev` or links DEV_SUPABASE_PROJECT_REF. Fallback if Docker on runners is refused: PGDG postgresql-17, postgresql-17-cron and postgresql-17-pgmq through apt, with H1's pg-shims.sql extended for auth and storage. Fidelity is lower (no GoTrue for admin sign-in, and pg_net is UNPROVEN in PGDG).

### FE-02 · major · The admin renders inside the public root layout: site header and footer, consent notice, GA4, web vitals, service worker and the public stylesheet all reach /admin
Lens: frontend · Touches: B3, B3b, B7, B13, B16, B17

**Problem.** RootLayout in __root.tsx wraps every route in the public Header and Footer, and the root head links the public styles.css. Later slices mount more public-only behaviour in the same root: B13's Ga4Loader, B17's startWebVitals() and registerServiceWorker(), and the ConsentNotice in the footer. No plan gives the admin its own layout or excludes /admin from these. src/routes/admin.tsx is a child of the root, so every admin screen gets the public chrome and stylesheet under its AdminShell. Once a staff member has consented on the public site, GA4 loads on admin pages and sends paths such as /admin/requests/<uuid> to Google. web_vitals calls track() from admin pages, which breaks B7 invariant 10 ('admin actions do not call track()'). Global public classes such as .field in forms.css also apply to admin markup.

**Evidence.** app/src/routes/__root.tsx:57-66: RootLayout renders `<Header /> <Outlet /> <Footer />`, and head() links appCss for every route. B7.md:85: '`src/routes/admin.tsx` (layout, guard, `ssr: false`, imports `src/styles/admin/index.css`)'. B13.md:72: '__root.tsx ... also mounts `Ga4Loader` once'. B17.md:89: '__root.tsx ... one `useEffect` calls `startWebVitals()` and `registerServiceWorker()`'. B7.md:34 (invariant 10) keeps admin out of track(). src/styles/components/forms.css:3 `.field {`. `grep -rno 'pathless\|_site\.[a-z]*' workspace/05-plans` finds only `_site.sql` migration names. The only admin test of the public chrome is the print case at B7.md:175.

**Do this.** Add a route-tree ruling to ASSUMED G and B3 (the first slice to edit __root.tsx under G33). __root.tsx becomes the bare document: html, head, Scripts, QueryClientProvider, and the root loader for state and site queries only. Every public page file moves under it (_site.index.tsx, _site.property.$slug.tsx and so on; URLs do not change; the generated tree is never hand-edited, G-001). src/routes/admin.tsx stays a sibling and links only the admin stylesheet. B13, B16 and B17 then edit _site.tsx instead of __root.tsx for these mounts, and G33's shared-file list names _site.tsx. Tests: tests/e2e/admin-signin.spec.ts asserts that /admin/sign-in has no .site-header and no cookie notice element, and makes no request to googletagmanager.com when consent is pre-set to granted. A unit test asserts that startWebVitals is not called when _site.tsx is not mounted.

### PERF-06 · major · Every public page dehydrates the full Property[] (galleries and variants included) into its HTML; there is no list shape and no document budget
Lens: performance-cost · Touches: B3, B4, B13

**Problem.** `propertiesQuery()` returns full `Property` objects, and B3 adds `variants` to every gallery image. Home, market, region, collection, property detail and story routes all call `ensureQueryData(propertiesQuery())`, and B3's router dehydrates the whole query cache into the server HTML. With 20 to 30 KB per property (PERF-03), 50 properties put about 1 MB of JSON inline in every page and in `GET /api/public/properties`. That hurts phone LCP and parse time, costs Worker CPU to serialise on every miss, and fills cache storage. B4's Lighthouse assertions cover LCP, CLS and script size only, so CI never sees the document grow. At launch the production catalog is empty (coming soon), but the contract in `types.ts` is expensive to change once the pages are built on it.

**Evidence.** src/services/types.ts:24 `listProperties(): Promise<Property[]>`. `propertiesQuery` is loaded by src/routes/index.tsx:21, $market.index.tsx:19, $market.$region.tsx:32, properties.tsx:24, property.$slug.tsx:31, stories.$slug.tsx:14 (grep). B3.md:22: `GET /properties` returns 200 `Property[]`. B3.md:117: `dehydrate: () => ({ queryClientState: dehydrate(queryClient) })`. B4.md:70: assertions "LCP 2500 ms, CLS 0.1, `resource-summary:script:size` 153600 bytes" only.

**Do this.** Add `PropertyCard` to `src/domain/property.ts` and the Zod contracts. It holds the fields the card, filter and search components read (slug, title, place, marketSlug, regionSlug, type, style, architect, price, currency, beds, baths, interiorSqFt, heroRank, featuredRank) and only the hero `card` variant. Add `toPropertyCard` in `mappers.ts`, computed once per version. `GET /api/public/properties` and `listProperties()` return `PropertyCard[]`. Detail pages load `getProperty(slug)` plus the related cards. The shared matcher runs over cards. B4: add the Lighthouse CI assertion `resource-summary:document:size` (`maxNumericValue` 61440 transfer bytes) to `lighthouserc.json` and the number to `budget.json`, so `perf-budget.test.ts` covers it. Add `tests/api/payload-budget.api.test.ts` against PERF-03's 100-property fixture: the list response is at most 600 bytes per item, and `/` HTML is at most 120 KB uncompressed.

### T-04 · major · The CI route sweep and form tests run a build mode that is never deployed, and the live-mode run is path-gated past the files that break hydration and the browser-to-Worker contract
Lens: testing · Touches: B3, B4, B13

**Problem.** The CI e2e job builds in local mode (VITE_API_BASE_URL unset, bundled src/data) and checks forms against `t.forms.localSent`, a notice production never shows. Production and previews are live-mode builds. So the sweep (titles, h1, axe, JSON-LD, overflow) never runs on a live build in CI; only the @overflow subset runs on the preview. The live run (live-forms, hydration, edge) starts only when the diff touches `src/server src/services supabase src/routes/api`. That filter leaves out src/router.tsx, the very file B4's watched-fail (s) mutates to prove hydration, and also src/lib/queries.ts, src/domain/contracts.ts, src/components/forms/** and every page route loader. A front-end change that breaks hydration or the form contract therefore merges with the live specs skipped.

**Evidence.** B4.md:94 e2e job 'builds once in local mode ... runs E2E_TARGET=built E2E_MODE=local bun run test:e2e'; e2e-live filter '-- src/server src/services supabase src/routes/api'. B4.md:58 forms.spec 'valid input reaches the success notice with t.forms.localSent text'. B4.md:134 watched-fail (s) 'in src/router.tsx (B3) remove the dehydrate and hydrate wiring'. F12: VITE_API_BASE_URL is /api/public for deployed builds.

**Do this.** Merge e2e and e2e-live into one job that builds once in live mode (`VITE_API_BASE_URL=/api/public VITE_TURNSTILE_SITE_KEY=1x00000000000000000000AA bun run build`) and runs sweep.spec.ts, redirects, live-forms, hydration and edge on it, with no path filter. If minutes force a filter, it is `src/** supabase/** package.json bun.lock` and nothing narrower. forms.spec.ts runs in live mode too: its validation and dataLayer cases are unchanged, the contact, newsletter and inquiry success cases are the live-forms ones (row read back by email), and the wizard's final POST is fulfilled by `page.route('**/api/public/submissions**', ...)`, so no Storage object is left (B3's api test already covers the real write). Local mode stays for `bun run dev` only. Running the sweep inside the job that holds the database also removes B4.md:167's cross-run coming-soon race. Add a hygiene.test.ts case: no ci.yml job sets E2E_MODE=local, and any e2e path filter includes `src/`. Proof: watched-fail (s) pushed on a draft PR turns the hydration spec red in CI.

### T-12 · major · Ten jobs and four separate builds of the same SHA per push will exhaust the 2,000 private-repo Actions minutes during the three-lane build, and then CI and deploys stop
Lens: testing · Touches: B1b, B4, B8, B13

**Ruling (CTO):** Accepted. Lanes run `bun run check`, unit tests and the build locally; CI runs on pull requests into `main` and on `main` only, drafts skip the database, Playwright and Lighthouse jobs. Minutes are measured as ruling DO-08 says.

**Problem.** A PR push starts check, build, audit, db, e2e, e2e-live, deno and seo (ci.yml), plus preview-db and preview (deploy.yml). build, e2e, e2e-live and preview each run `bun run build` separately. Each job repeats checkout and bun install, and GitHub bills each job rounded up to the minute, path-skipped jobs included. B4's own estimate of 10 to 15 minutes per push gives about 130 to 160 pushes a month. S54's three lanes, with about 21 slices pushed per builder group plus up to two fix rounds each, plus the merges to main (ci, dev and production), will produce more than that within the 48 hours. When the minutes run out no workflow runs, including the deploy.yml production job that L1 needs to launch. B4 measures minutes only at step 10, after the fact.

**Evidence.** B1b.md:79 'B4 appends the db, e2e and e2e-live jobs, B8 the deno job and B13 the seo job'. B4.md:94 e2e 'builds once in local mode', e2e-live 'builds once in live mode'; B1b.md:82 preview builds again. B4.md:151 'About 15 minutes at worst, about 10 typical; 2,000 minutes allow about 130 pushes a month'. P-009 'GitHub Actions on a private repo: 2,000 minutes/month'. E9 'GitHub (private ...)'.

**Do this.** In ci.yml, one `build` job makes the live artifact (T-04) and uploads `.output/` with actions/upload-artifact, and the e2e, seo and Lighthouse steps download it instead of rebuilding. Fold `audit` and `deno` into `check` as steps. Give every non-database job `concurrency: { group: ci-${{ github.head_ref || github.ref }}, cancel-in-progress: true }`. Run the database, Playwright and Lighthouse jobs only when `github.event.pull_request.draft == false` and add `ready_for_review` to the triggers. Builders push drafts per group, and the merge gate (T-03) requires a non-draft green run. Have the orchestrator read usage before each phase with `gh api /users/{owner}/settings/billing/actions` (UNPROVEN on the enhanced billing platform; the fallback is the billing page by hand) and record it in POSITION.md. hygiene.test.ts asserts that `bun run build` appears in exactly one ci.yml job.
