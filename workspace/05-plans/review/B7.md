### API-01 · critical · Invites fail as written, and magic links fail across devices and when mail scanners open them
Lens: api · Touches: B5, B7, H1

**Problem.** Staff sign-in sends Supabase's `{{ .ConfirmationURL }}` (a GET to `/auth/v1/verify` that uses up the one-time token). It then redirects to `auth.callback.ts`, which calls `exchangeCodeForSession`. That is the PKCE flow, and the code verifier is a cookie the Worker set on the browser that asked for the link. This causes three failures. (1) Invites: the default verify redirect puts the session in the URL fragment. A server route never receives the fragment, so every invited editor lands on a callback with no code, and onboarding is broken from the first invite. (2) Cross-device: a staff member who asks for the link on a laptop and opens it on a phone, or in a mail app's in-app browser, has no verifier cookie there, so the exchange fails. (3) Mail scanners such as Microsoft Defender Safe Links prefetch the verify URL. That uses up the token, and the real click fails with "Token has expired or is invalid". S10 makes magic links the only staff sign-in, so all three lock staff out, and nobody can see why.

**Evidence.** B7.md:84: "`auth.callback.ts` exchanges the code with `exchangeCodeForSession`" and `emailRedirectTo: <origin>/api/admin/auth/callback`. B5.md:73-74: the templates use the literal `{{ .ConfirmationURL }}` for magic link and invite. B7.md:122 and :157: invites go through `auth.admin.inviteUserByEmail`. `grep -n -i "pkce\|code_verifier\|TokenHash\|token_hash" workspace/05-plans/B5.md B7.md` finds only `scripts/probe-amr.ts` (B7.md:133), which already uses `verifyOtp({ token_hash })` but only as a dev probe. B5.md:178 accepts scanner clicks for the newsletter confirm link only. ASSUMED section G has no ruling on this. Supabase documentation (docs/guides/auth/auth-email-templates, read this session through the Supabase docs search) says: under "Email prefetching", "the `{{ .ConfirmationURL }}` sent will be consumed instantly which leads to a 'Token has expired or is invalid' error". Under "Redirecting the user to a server-side endpoint", "the session is returned in the query fragments by default, you won't be able to access it on the server-side", and it recommends `{{ .TokenHash }}` links verified with `verifyOtp`. None of this has been run on mop-dev (UNPROVEN until the tests below run).

**Do this.** Change both templates to the token-hash form in `scripts/build-auth-templates.ts` and the generated `supabase/templates/magic-link.html` and `invite.html` (B5 step 8). The magic link becomes `{{ .SiteURL }}/admin/auth/confirm?token_hash={{ .TokenHash }}&type=email&next={{ .RedirectTo }}` (`email` is the current `EmailOtpType`; `magiclink` is deprecated), and the invite uses the same URL with `type=invite`. Add the page `src/routes/admin/auth.confirm.tsx`. On GET it only renders one "Continue to Matter of Place" button inside a form that POSTs to `/api/admin/auth/verify`, so a scanner's GET changes nothing. The new route `src/routes/api/admin/auth.verify.ts` is CSRF-exempt like `send-link`, but it refuses a request whose `Origin` header is present and is not the site's own origin (403 `csrf`). It calls `supabase.auth.verifyOtp({ type, token_hash })` through `session.ts`, then does exactly what `auth.callback.ts` does today: it reads `user_roles` (no enabled row means sign out and redirect to `?state=disabled`), sets the session cookies and `mop_csrf`, and redirects to `safeNext(next)`. Remove `auth.callback.ts` and every `exchangeCodeForSession`, and drop `emailRedirectTo` to the callback from `signInWithOtp`; the template builds the link itself. Tests: (a) `tests/unit/auth-verify.test.ts` with a stubbed client: a GET of the confirm page makes zero Auth calls, a POST with a token hash sets three cookies and redirects through `safeNext`, a foreign `Origin` gets 403, and the open-redirect and disabled cases move over from `auth-callback.test.ts`. (b) `admin-signin.spec.ts`: `auth.admin.generateLink({ type: 'magiclink' })` returns `properties.hashed_token`, and the test opens `/admin/auth/confirm?token_hash=<it>&type=email` in a new browser context (not the one that asked for the link), presses the button and ends on `/admin`. (c) The same flow with `generateLink({ type: 'invite' })` and `type=invite`. Also update `tests/e2e/helpers/session.ts` (H1-15 signs in through it). ### FE-01 · critical · Dossier autosave can conflict with its own saves and publish without the last edits; the prescribed recovery throws away typed text
Lens: frontend · Touches: B7

**Problem.** use-autosave sends expected_version after a 1.5 s debounce and stops on any 409. No plan describes a single-request queue, a flush before publish, or a way to keep local edits after a conflict. Two ordinary sequences lose an editor's work. (a) The editor types and clicks Publish inside the debounce window. publish_property calls save_property({}) with the current version, succeeds and bumps the version, so the page goes live without the last edits. The pending autosave then fires with the old version, gets 409 stale and shows 'Reload, someone saved'. Reloading discards the text. Rank, related, features and unpublish all send expected_version too (B7 invariant 7), so any of them can race the pending save the same way. (b) A save that takes longer than the debounce lets a second PATCH go out with the same version, and the editor's own first save makes it fail. This touches every dossier edit, and stories through expected_updated_at.

**Evidence.** B7.md:152: 'Save autosaves drafts (1.5 s debounce, `expected_version`); a 409 `stale` shows `StaleBanner` ("Reload, someone saved") and stops autosave until the editor reloads.' B7.md:107: '`use-autosave.ts` (sends `expected_version`, stops on 409)'. B7.md:31 (invariant 7): publish, unpublish, rank and related send expected_version, and publish, unpublish, set_related and set_features call save_property(p_id, p_expected_version, '{}') first, which bumps version. B7.md:175 tests only that a 409 shows StaleBanner and sends no further save. `grep -n 'flush\|in flight\|in-flight\|beforeunload\|useBlocker' B7.md` finds nothing. No ruling in ASSUMED E, F or G covers it.

**Do this.** Specify src/admin/properties/use-autosave.ts in B7 as a serial save queue. (1) At most one PATCH is in flight. Dirty fields merge into one pending patch, and each PATCH uses the version the previous response returned. (2) The hook exports flush(): Promise<number>. PublishBar, UnpublishDialog, the rank, related and features saves, and route leave (TanStack Router useBlocker, available in react-router 1.170) await flush() and send the version it resolves. (3) On a real 409 the unsaved fields stay in component state, so nothing typed is dropped. StaleBanner offers 'Reload': it re-reads the row and keeps the editor's unsaved fields marked as unsaved edits on top of it, and the editor saves them explicitly. This keeps B7's 'no silent merge' rule. (4) A beforeunload listener is active while the queue holds unsaved work. Stories use the same hook keyed on updated_at. Tests in src/admin/properties/use-autosave.test.ts, with a fake API that takes 2 s per call: type, wait 1.6 s, type again, and expect exactly two sequential PATCHes carrying v and v+1 and no 409. Type, then publish within 500 ms, and expect the PATCH first and publish to receive v+1. A 409 from another session keeps the field text. Watched-fail: drop the in-flight guard and the first case must go red. Extend the two-context case in tests/e2e/admin-editorial.spec.ts to assert that the first editor's typed text is still in the field after Reload.

**Do this.** (a) B3 submit wizard: `src/lib/image-prep.ts` uploads, next to each original, a 480 px JPEG thumbnail `<submission_id>/<media_id>.thumb.jpg`, made with `createImageBitmap` and an OffscreenCanvas.
