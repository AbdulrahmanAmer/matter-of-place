### E2E-02 · critical · Copying a request's photographs inside one Worker request exceeds the free plan's 50-subrequest cap at about 22 photographs
Lens: end-to-end · Touches: B3, B6, B7, B8

**Problem.** `createFromSubmission` (B7) and B6's `activate` run `copySubmissionPhotos` inside the admin HTTP request. Each photograph costs one Storage `copy` fetch and one `enqueueJob` RPC, on top of the actor read, the create or activate RPC and `fanoutEvent`. A request may carry 40 photographs, which needs about 84 outbound fetches. The Workers free plan allows 50 per invocation, so the request throws at about photograph 22. A retry repeats the copy call (an 'already exists' answer counts as copied) and the enqueue for every photograph already done, so it dies at the same point. Rows past the cut stay `staged` with no job. `enforce_publish_gate` checks only that the first photograph is rendered (G66), so the property can be published with part of its gallery missing. The public `POST submissions` signs up to 40 upload URLs in one request (Turnstile, rate limit and create, then 40 signings: about 44 to 45 fetches), which leaves almost no headroom. The 50 cap is written down nowhere in the project.

**Evidence.** B6 line 65: '`copySubmissionPhotos` calls B8's `enqueueJob(db, { type: "render_variants", ... })`' for each copied photograph, after `db.storage.from("submissions").copy(source_path, staging_path)` ('an "already exists" answer counts as copied'). B3 line 86: '`submissions.create` calls `create_submission`, then for each returned media row calls `db.storage.from("submissions").createSignedUploadUrl(storage_path)`'. B3 line 133: '40 media entries pass and 41 are 422'. `grep -rn -i subrequest` over workspace/05-plans, 06-architecture, 02-tech-stack and GOTCHAS.md returns no line naming the cap, and P-009 does not list it.

**Do this.** Move the copy out of the request. `create_property_from_submission` and `activate_submission` call B8's `enqueue_job` in their own transaction for one light system job, `copy_submission_media` (`src/server/jobs/system/copy-submission-media.ts`, registered in `system/index.ts`, key `copy_submission_media:<property_id>`, data `{ property_id }`). Watched-fail: put the per-photograph copy loop back in the service.

### API-03 · major · Errors are mapped by message text, real codes become 500, and outages are reported as 500 instead of 503
Lens: api · Touches: B2, B3, B7

**Problem.** `fromRpcError` matches raised message strings against a fixed list and maps "anything else to 500 `internal`". Codes that admin-route functions already raise are missing from the list. `update_property` calls `save_property`, which raises `not_found` (P0002) for an unknown id and `invalid_patch_key` (22023). An agent that sends a stale or wrong id therefore gets a 500 instead of a 404. **Evidence.** B7.md:76: `fromRpcError` lists its codes and ends "anything else to 500 `internal` (a slice that adds an admin function raising a code not in this list adds its line here ...)", and the list has no `not_found` or `invalid_patch_key`. **Do this.** Create `src/server/lib/error-codes.ts` with `export const errorCodes = { ...every code: status } as const` as the only code list, merging B3's `errors.ts` codes and B7's list. ### API-04 · major · The sign-in link and agent-key traffic have no rate limit, so free-tier quotas can be exhausted
Lens: api · Touches: B1b, B3, B5, B7, H1

**Problem.** `POST /api/admin/auth/send-link` is anonymous, has no Turnstile, no memory limit and no DB limit. Each call makes a database lookup (`staff_can_sign_in`), and for a staff address it sends one Supabase Auth mail through Resend SMTP. Supabase throttles the same address to about one mail a minute, but a script that cycles the few staff addresses still uses up Resend's 100 mails a day. Every transactional mail shares that quota (acknowledgements, invoices, the confirm emails), and the attack also fills Supabase's project-wide auth-mail limit, which locks out staff sign-in. S16 already requires Turnstile on every form, and the sign-in form is a form. Agent keys have only a daily cap on decisions. A Claude session or routine stuck in a retry loop against `/api/admin/*` at one request a second uses most of the Worker's 100,000 requests a day, which the public site shares. An invalid bearer costs one `agent_key_by_hash` query, and nothing throttles that either.

**Evidence.** B7.md:84: "`auth.send-link.ts` calls `staff_can_sign_in`; only when it is true does it call `supabase.auth.signInWithOtp`", with no limit. `grep -n "send-link" H1.md B17.md` finds nothing. B3.md:38-40: limits exist only for `/api/public`. B1b.md:102 and H1.md:32: the one Cloudflare rule matches `starts_with(http.request.uri.path, "/api/public/")`. B7.md:27: the agent cap covers only decline and accept decisions. B7.md:83: `agent_key_by_hash` runs on every agent request. P-009: Workers free 100k requests a day, Resend free 100 a day. B5.md:159: whether auth mail counts in Resend's daily count is UNPROVEN. PROJECT-STATE S16: "Turnstile on every form".

**Do this.** (1) `send-link` uses B3's existing helpers in this order: `checkMemory('auth_link:ip', ip, 5, 60s)`; `verifyTurnstile` (S16; the sign-in form renders the widget), where `fail` answers 200 `sent` and does nothing; then one `rate_limit_check` call with two checks, `auth_link:ip` at 10 per hour and `auth_link:email` (sha256 of the lower-cased address) at 5 per hour. A limit hit still answers 200 `sent`, so nothing is revealed, and logs `auth_link_limited`. Seed the Supabase Auth email rate limit in `supabase/config.toml` `[auth.rate_limit] email_sent = 30` (per hour), pushed with `supabase config push`, so the provider has a ceiling too. (2) Bearer requests: `checkMemory('agent_key_fail:ip', ip, 20, 60s)` before `agent_key_by_hash` counts only failed lookups. For a valid key, `rate_limit_check` with bucket `agent:<key_id>` runs at 60 per minute and 2,000 per UTC day, the second value read from `settings.agent_daily_limits.requests_per_day`. An exceeded limit is 429 `rate_limited` with `Retry-After`. This adds one DB write per agent request, which is acceptable at agent volumes. (3) `scripts/cf-edge.mjs` widens the one free rule's expression to `starts_with(http.request.uri.path, "/api/public/") or starts_with(http.request.uri.path, "/api/admin/auth/")`, and H1-03 changes its check to match. Tests: `ratelimit.api.test.ts` adds that the sixth link for one email in an hour makes no Auth call and answers `sent`. `agent-keys.test.ts` adds that the 61st call in a minute gets 429 and makes no further RPC.
