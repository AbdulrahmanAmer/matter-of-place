### API-01 · critical · Invites fail as written, and magic links fail across devices and when mail scanners open them
Lens: api · Touches: B5, B7, H1

**Problem.** Staff sign-in sends Supabase's `{{ .ConfirmationURL }}` (a GET to `/auth/v1/verify` that uses up the one-time token). It then redirects to `auth.callback.ts`, which calls `exchangeCodeForSession`. That is the PKCE flow, and the code verifier is a cookie the Worker set on the browser that asked for the link. This causes three failures. (1) Invites: the default verify redirect puts the session in the URL fragment. A server route never receives the fragment, so every invited editor lands on a callback with no code, and onboarding is broken from the first invite. (2) Cross-device: a staff member who asks for the link on a laptop and opens it on a phone, or in a mail app's in-app browser, has no verifier cookie there, so the exchange fails. (3) Mail scanners such as Microsoft Defender Safe Links prefetch the verify URL. That uses up the token, and the real click fails with "Token has expired or is invalid". S10 makes magic links the only staff sign-in, so all three lock staff out, and nobody can see why.

**Evidence.** B7.md:84: "`auth.callback.ts` exchanges the code with `exchangeCodeForSession`" and `emailRedirectTo: <origin>/api/admin/auth/callback`. B5.md:73-74: the templates use the literal `{{ .ConfirmationURL }}` for magic link and invite. B7.md:122 and :157: invites go through `auth.admin.inviteUserByEmail`. `grep -n -i "pkce\|code_verifier\|TokenHash\|token_hash" workspace/05-plans/B5.md B7.md` finds only `scripts/probe-amr.ts` (B7.md:133), which already uses `verifyOtp({ token_hash })` but only as a dev probe. B5.md:178 accepts scanner clicks for the newsletter confirm link only. ASSUMED section G has no ruling on this. Supabase documentation (docs/guides/auth/auth-email-templates, read this session through the Supabase docs search) says: under "Email prefetching", "the `{{ .ConfirmationURL }}` sent will be consumed instantly which leads to a 'Token has expired or is invalid' error". Under "Redirecting the user to a server-side endpoint", "the session is returned in the query fragments by default, you won't be able to access it on the server-side", and it recommends `{{ .TokenHash }}` links verified with `verifyOtp`. None of this has been run on mop-dev (UNPROVEN until the tests below run).

**Do this.** Change both templates to the token-hash form in `scripts/build-auth-templates.ts` and the generated `supabase/templates/magic-link.html` and `invite.html` (B5 step 8). The magic link becomes `{{ .SiteURL }}/admin/auth/confirm?token_hash={{ .TokenHash }}&type=email&next={{ .RedirectTo }}` (`email` is the current `EmailOtpType`; `magiclink` is deprecated), and the invite uses the same URL with `type=invite`. Add the page `src/routes/admin/auth.confirm.tsx`. On GET it only renders one "Continue to Matter of Place" button inside a form that POSTs to `/api/admin/auth/verify`, so a scanner's GET changes nothing. The new route `src/routes/api/admin/auth.verify.ts` is CSRF-exempt like `send-link`, but it refuses a request whose `Origin` header is present and is not the site's own origin (403 `csrf`). It calls `supabase.auth.verifyOtp({ type, token_hash })` through `session.ts`, then does exactly what `auth.callback.ts` does today: it reads `user_roles` (no enabled row means sign out and redirect to `?state=disabled`), sets the session cookies and `mop_csrf`, and redirects to `safeNext(next)`. Remove `auth.callback.ts` and every `exchangeCodeForSession`, and drop `emailRedirectTo` to the callback from `signInWithOtp`; the template builds the link itself. Tests: (a) `tests/unit/auth-verify.test.ts` with a stubbed client: a GET of the confirm page makes zero Auth calls, a POST with a token hash sets three cookies and redirects through `safeNext`, a foreign `Origin` gets 403, and the open-redirect and disabled cases move over from `auth-callback.test.ts`. (b) `admin-signin.spec.ts`: `auth.admin.generateLink({ type: 'magiclink' })` returns `properties.hashed_token`, and the test opens `/admin/auth/confirm?token_hash=<it>&type=email` in a new browser context (not the one that asked for the link), presses the button and ends on `/admin`. (c) The same flow with `generateLink({ type: 'invite' })` and `type=invite`. Also update `tests/e2e/helpers/session.ts` (H1-15 signs in through it). ### DO-03 · critical · Monitoring depends on the things it monitors: a dead job runner, cron or database sends no alert
Lens: delivery-ops · Touches: B1b, B8, B8b, B14, H1, L1

**Ruling (CTO):** Accepted as the single liveness mechanism; see ruling JOB-04 for how the two findings merge.

**Problem.** (1) The daily `health` check is a job that the runner itself executes, and its alert path is runner -> `notify_admin` -> `send_email` -> Resend. If the runner stops (a bad function deploy, a wrong Vault `job_runner_secret`, a function that answers 401 or 500, a paused project), `health` never runs and `stale_queue` never fires. (2) The `job-runner` pg_cron row only runs `net.http_post(...)`, which queues an HTTP request. `cron.job_run_details` records `succeeded` even when the function answers 401 or 500. So the L1 preflight, the L1 step 1d proof and the week-one 'cron ticks continuing' check would all report a broken runner as healthy. (3) The two uptime monitors poll `/` and `/api/public/markets`. Both are edge-cached and, by design (rule 7, stale beats down), keep answering 200 when the database is down. The result: a stopped runner means no signup confirmations, no submission acknowledgements and no admin notices, and nothing alerts. The first signal is the Saturday audit or a complaint.

**Evidence.** architecture.md line 136: '`job-runner` every minute (B8 `<ts>_job_cron.sql`, `net.http_post` to the Edge Function)'. L1.md line 31 (preflight): '`select count(*) from cron.job_run_details where status = 'succeeded' and start_time > now() - interval '5 minutes'` is above 0 (the job runner is ticking)'. L1.md line 112: 'cron ticks continuing (`... select max(start_time) from cron.job_run_details`)'. B14.md line 70: the monitors are `https://matterofplace.com/` and `/api/public/markets`. architecture.md line 205 (rule 7): stale content is served when the database errors. `grep -n -i "heartbeat\|dead.man\|_http_response"` over 05-plans, architecture and tech-stack returns no hits.

**Do this.** Add a dead-man's switch that depends on neither the runner nor Resend, and uses only the free UptimeRobot plan that B14 already requires. (1) B8 migration `<ts>_ops_heartbeat.sql`: table `ops_heartbeats(name text primary key, at timestamptz not null, detail jsonb)` with RLS on and no policy, plus `beat(p_name text, p_detail jsonb)` (security definer, fixed `search_path`, execute granted to `service_role` only). ### JOB-04 · critical · Nothing outside the job runner notices when the runner stops, so every email and webhook stops without an alert
Lens: jobs · Touches: B1b, B8, B8b, H1, L1

**Ruling (CTO):** Accepted, unified with DO-03 into ONE liveness mechanism (H2): the table is DO-03's `ops_heartbeats(name text primary key, at timestamptz not null, detail jsonb)` written by `beat(p_name, p_detail)`; the runner's heartbeat is the row `runner` (this finding's `runner_heartbeat` table and `record_runner_tick` are not created; `runOnce` calls `beat('runner', ...)` in its `finally`); `jobs_liveness()` reads that row and the oldest due job; the token-gated health route and the third UptimeRobot monitor are DO-03's.

**Problem.** The runner can stop working in several ways: a bad deploy, a Vault `job_runner_secret` that no longer matches the function secret after a rotation, a Deno import error at boot, or the project paused. When it stops, every receipt, invoice, confirmation, inquiry forward and post stops too, and nobody is told. The `health` job and its `notify_admin` both run through the runner. `cron_failures` reads `cron.job_run_details`, where `select net.http_post(...)` always succeeds because pg_net is asynchronous, so a 401 or 500 from the function never shows there. L1's go-live check and B8 step 6 use the same table as proof that the runner is ticking. The external uptime check covers only `/` and `/api/public/markets`. The outage is found when a customer complains.

**Evidence.** B8.md:54 health is `select enqueue_job('health', ...)` run by the runner; B8.md:69 `cron_failures` = `health_cron_failures` over `cron.job_run_details` with `status = 'failed'`. L1.md:31 "`select count(*) from cron.job_run_details where status = 'succeeded' ...` is above 0 (the job runner is ticking)". architecture.md:173 "an external uptime check every 5 minutes on `/` and `/api/public/markets`". `grep -rni "heartbeat\|runner_stalled\|_http_response" workspace/05-plans workspace/06-architecture` → no hits.

**Do this.** (1) `<ts>_jobs.sql` adds a one-row table `runner_heartbeat(id int primary key check (id = 1), last_tick_at timestamptz, last_ok_at timestamptz, last_error text, release text)`, written only by `record_runner_tick(p_ok boolean, p_error text, p_release text)`. `runOnce` calls it in a `finally` block at the end of every tick. (2) `jobs_liveness()` (security definer, service role) returns `{ last_ok_at, oldest_due_age_s, http_errors_1h }`. `oldest_due_age_s` is the age of the oldest `queued` or `failed` job with `run_after <= now()`. `http_errors_1h` counts `net._http_response` rows from the last hour that are `timed_out` or have a non-2xx `status_code`; pg_net keeps these rows for 6 hours, and today the runner tick is the only pg_net caller. (4) Replace the L1 and B8 step 6 proofs with `select last_ok_at > now() - interval '2 minutes' from runner_heartbeat`. (5) Add a `scheduled.test.ts` case where a stale heartbeat gives exactly one capture, with a watched-fail.

### API-04 · major · The sign-in link and agent-key traffic have no rate limit, so free-tier quotas can be exhausted
Lens: api · Touches: B1b, B3, B5, B7, H1

**Problem.** `POST /api/admin/auth/send-link` is anonymous, has no Turnstile, no memory limit and no DB limit. Each call makes a database lookup (`staff_can_sign_in`), and for a staff address it sends one Supabase Auth mail through Resend SMTP. Supabase throttles the same address to about one mail a minute, but a script that cycles the few staff addresses still uses up Resend's 100 mails a day. Every transactional mail shares that quota (acknowledgements, invoices, the confirm emails), and the attack also fills Supabase's project-wide auth-mail limit, which locks out staff sign-in. **Evidence.** B7.md:84: "`auth.send-link.ts` calls `staff_can_sign_in`; only when it is true does it call `supabase.auth.signInWithOtp`", with no limit. `grep -n "send-link" H1.md B17.md` finds nothing. B7.md:27: the agent cap covers only decline and accept decisions. B7.md:83: `agent_key_by_hash` runs on every agent request. P-009: Workers free 100k requests a day, Resend free 100 a day. B5.md:159: whether auth mail counts in Resend's daily count is UNPROVEN. PROJECT-STATE S16: "Turnstile on every form".

**Do this.** (1) `send-link` uses B3's existing helpers in this order: `checkMemory('auth_link:ip', ip, 5, 60s)`; `verifyTurnstile` (S16; the sign-in form renders the widget), where `fail` answers 200 `sent` and does nothing; then one `rate_limit_check` call with two checks, `auth_link:ip` at 10 per hour and `auth_link:email` (sha256 of the lower-cased address) at 5 per hour.
