### E2E-06 · critical · The three S54 lanes push migrations and job-runner builds from their own branches into the one shared mop-dev, which the Supabase CLI refuses, and an edited migration drifts silently
Lens: end-to-end · Touches: B1b, B2, B4, B8, B17

**Problem.** PLAN.md runs phase 1 as three lanes, each in its own worktree and branch. Every slice proof runs `bun run db:push` against mop-dev, and `preview-db` does the same on each PR push. As soon as lane B pushes a migration that lane A's branch does not contain, lane A's next `db push` stops with the CLI error 'Remote migration versions not found in local migrations directory'. When a lane pushes a migration whose timestamp is older than one already applied, the CLI stops with 'Found local migration files to be inserted before the last migration on remote database' unless `--include-all` is passed. Both errors offer `migration repair` as the way out, and that is the hack a builder under a 48-hour clock will reach for. The proof of every database step in every lane then goes red for a reason unrelated to the step. Separately, `db push` skips a version it has already applied, so when a reviewer asks for a change and the builder edits that migration, mop-dev keeps the old DDL. B4 then generates types from the stale schema, the tests pass, and mop-prod later applies the edited file. The same collision hits the job runner: `deploy.yml` deploys `job-runner` to mop-dev from a PR branch whenever `src/server` changed, so the last lane to deploy removes the other lanes' steps. Their jobs then die with `unknown_step` (B8 runner: 'an unknown type to dead with `unknown_step`').

**Evidence.** PLAN.md lines 29-33: 'each lane in its own git worktree and branch, each landing on `main` through CI. What already makes this safe: one writer at a time on `mop-dev` (G34, the advisory lock)'. That lock serialises writers but does not reconcile migration history. B4 line 94: '`bun run db:push` (B2's name, idempotent: a migration `preview-db` already applied is skipped)'. B8 line 105: the PR job deploys `bunx supabase functions deploy job-runner --use-api --project-ref ${{ secrets.DEV_SUPABASE_PROJECT_REF }}` when `git diff ... -- supabase/functions src/server` prints anything. B2 line 162 protects only mop-prod: 'a migration already pushed to `mop-prod` is never edited'. B7 line 162 has the mop-dev rule for B7's own files only. The installed CLI (`C:/Users/DELL/scoop/apps/supabase/current/supabase.exe`, v2.98.2) contains both strings: 'Remote migration versions not found in local migrations directory.' and 'Found local migration files to be inserted before the last migration on remote database.' B1b line 83 (`preview-cleanup`) covers only the unmerged-PR case, with a comment and a manual `db:reset`.

**Do this.** (1) Put the guard in front of B2's `db:push` script: a new `scripts/db-push.mjs`, which `bun run db:push` runs before `supabase db push`. Over `DEV_DB_URL` it reads `supabase_migrations.schema_migrations.version` and fails, naming each version, when the remote holds a version that is not in the local folder ('rebase onto origin/main first'). It also fails when a local version not yet applied is older than the newest applied version ('regenerate the timestamp with `supabase migration new`', as B17 already does for its own file). After a successful push it upserts `sha256(file)` into a table `public.migration_checksums(version text primary key, sha256 text, pushed_at)`, created by B2's first migration and service-role only. On every run it fails on any applied version whose file hash differs, which is the drift check. Use a hash of our own and do not compare the CLI's `statements` column, which depends on the CLI's statement splitter. (2) Landing rule in PLAN.md and B2: a migration lands on `main` in its own small PR (migration plus regenerated `src/db/types.ts`) before the code that needs it, and every lane rebases on `origin/main` before any `db:push`. `--include-all` and `migration repair` are never used on mop-dev or mop-prod without the orchestrator. (3) Job runner: deploy `job-runner` to mop-dev only from `main` (deploy.yml on push to main) or from a branch that contains `origin/main` (check with `git merge-base --is-ancestor origin/main HEAD`). In `runner.ts`, `unknown_step` becomes `retry_at now + 15 minutes` with no attempt used, for up to 24 hours from `created_at`, and only then dead, so a missing step module (a lane gap or a rollback) never kills jobs. (4) GOTCHAS gets a P-entry for the lane collision. Proof: `bunx vitest run tests/unit/db-push-guard.test.ts` (fake history: a remote-only version, an older local version and a changed file hash each exit 1 naming the version; a clean state exits 0). Watched-fail: edit an applied migration's SQL and see `db:push` refuse it. Also `tests/unit/jobs/runner.test.ts -t unknown_step` (retry_at for 24 h, then dead).

### SEC-03 · critical · JSON-LD is serialized with plain JSON.stringify into a raw script sink, and inlineHashes would allow-list whatever script that produces
Lens: security · Touches: B13, B17, H1

**Problem.** Text from the public submission form can become stored XSS in cached public HTML. `create_property_from_submission` sets `title` from `submissions.address` and `story` from `submissions.story` (G62, B7.md:101). B13 builds RealEstateListing and Article JSON-LD from those fields. `pageHead` puts `JSON.stringify(jsonLd)` into a head script, and TanStack renders that string with `dangerouslySetInnerHTML`. `JSON.stringify` leaves `</script>` unescaped, so a title or story that contains `</script><script>...` closes the data block and starts an executable script. A published page is cached and served to every visitor on the origin that also serves /admin. B17's `inlineHashes(html)` hashes every inline script in the rendered page, so the injected script gets its own hash and stays allowed even after `csp_enforce` is switched on. Publishing still needs an editor, but S38 agents read the same public text and the seeded managing_editor agent can publish.

**Evidence.** app/src/lib/seo.ts:52 `scripts: jsonLd ? [{ type: "application/ld+json", children: JSON.stringify(jsonLd) }] : []`. node_modules/@tanstack/react-router/dist/esm/Asset.js:127-130 (data script) `dangerouslySetInnerHTML: { __html: children }`. B17.md:16 hashes `each inline script of the page`. B17.md:63 `inlineHashes(html)`. B13.md:66 extends `pageHead`'s `jsonLd` and names no escaping. A grep for `u003c|escapeJson|serializeJson` over workspace/05-plans finds nothing. B17.md:16 also has `script-src ... https://*.googletagmanager.com`, while B17.md:20 and G41 load only gtag.js from www.googletagmanager.com.

**Do this.** (1) `src/lib/seo.ts` exports `serializeJsonForScript(value)`. It runs `JSON.stringify`, then replaces `<` with `<`, `>` with `>`, `&` with `&`, U+2028 with ` ` and U+2029 with ` `. `pageHead` and every B13 JSON-LD builder use only this function. B13 adds the edit to its existing Change to seo.ts.
(2) B17 `inlineHashes`:
- Never hash a non-executable type (`application/ld+json`, `application/json`). These need no hash.
- Hash an executable inline script only when its opening tag carries TanStack's marker `class="$tsr"` (router-core/dist/esm/ssr/ssr-server.js:423; re-check the marker on each router upgrade) or when its exact text appears in an allow-list in `src/server/lib/csp-allowlist.ts` for app-owned bootstrap scripts.
- Any other executable inline script is left unhashed and reported to Sentry once per render as `csp_unexpected_inline_script`.
(3) Replace `https://*.googletagmanager.com` in script-src with `https://www.googletagmanager.com/gtag/js`. If the report-only reports on the preview show GA4 needs another path, fall back to the host `https://www.googletagmanager.com` with no wildcard and record the measurement. UNPROVEN until the reports are read.
(4) Canary test `tests/unit/csp-inline.test.ts` renders `/property/<slug>` and `/stories/<slug>` from a fixture whose every string field is `</script><script>window.__x=1</script>`. It asserts that the HTML contains no `<script>window.__x` and that the CSP hash set equals the hash set of a clean fixture.
Watched-fail: revert the serializer to `JSON.stringify`, and the test goes red.

### FE-02 · major · The admin renders inside the public root layout: site header and footer, consent notice, GA4, web vitals, service worker and the public stylesheet all reach /admin
Lens: frontend · Touches: B3, B3b, B7, B13, B16, B17

**Problem.** RootLayout in __root.tsx wraps every route in the public Header and Footer, and the root head links the public styles.css. Later slices mount more public-only behaviour in the same root: B13's Ga4Loader, B17's startWebVitals() and registerServiceWorker(), and the ConsentNotice in the footer. No plan gives the admin its own layout or excludes /admin from these. src/routes/admin.tsx is a child of the root, so every admin screen gets the public chrome and stylesheet under its AdminShell. Once a staff member has consented on the public site, GA4 loads on admin pages and sends paths such as /admin/requests/<uuid> to Google. web_vitals calls track() from admin pages, which breaks B7 invariant 10 ('admin actions do not call track()'). Global public classes such as .field in forms.css also apply to admin markup.

**Evidence.** app/src/routes/__root.tsx:57-66: RootLayout renders `<Header /> <Outlet /> <Footer />`, and head() links appCss for every route. B7.md:85: '`src/routes/admin.tsx` (layout, guard, `ssr: false`, imports `src/styles/admin/index.css`)'. B13.md:72: '__root.tsx ... also mounts `Ga4Loader` once'. B17.md:89: '__root.tsx ... one `useEffect` calls `startWebVitals()` and `registerServiceWorker()`'. B7.md:34 (invariant 10) keeps admin out of track(). src/styles/components/forms.css:3 `.field {`. `grep -rno 'pathless\|_site\.[a-z]*' workspace/05-plans` finds only `_site.sql` migration names. The only admin test of the public chrome is the print case at B7.md:175.

**Do this.** Add a route-tree ruling to ASSUMED G and B3 (the first slice to edit __root.tsx under G33). __root.tsx becomes the bare document: html, head, Scripts, QueryClientProvider, and the root loader for state and site queries only. A pathless layout src/routes/_site.tsx renders Header, Footer (with ConsentNotice), Ga4Loader and the web-vitals and service-worker effect, and its head() links styles.css. Every public page file moves under it (_site.index.tsx, _site.property.$slug.tsx and so on; URLs do not change; the generated tree is never hand-edited, G-001). src/routes/admin.tsx stays a sibling and links only the admin stylesheet. B13, B16 and B17 then edit _site.tsx instead of __root.tsx for these mounts, and G33's shared-file list names _site.tsx. Tests: tests/e2e/admin-signin.spec.ts asserts that /admin/sign-in has no .site-header and no cookie notice element, and makes no request to googletagmanager.com when consent is pre-set to granted. A unit test asserts that startWebVitals is not called when _site.tsx is not mounted.

### FE-03 · major · The live client bundle ships the local adapters and all illustrative seed data, sits near the 150 KB budget, and the budget is only checked by Lighthouse after deploy
Lens: frontend · Touches: B1b, B3, B4, B17

**Problem.** services/index.ts statically imports the local adapters, which import src/data/*, and picks a branch at runtime from siteConfig.apiBaseUrl. site.ts reads `const env = import.meta.env`, so the define plugin cannot fold the condition and the dead branch stays. Every live visitor downloads the fictional listings' text and image references, against the intent of S30 (production never shows illustrative property). The entry chunk is already about 120 KB gzip, and with the contracts and store chunks first load is about 142 KB, before B3 to B17 add Turnstile, consent, analytics batching, web-vitals and hydration. The only budget gate is Lighthouse on a deployed preview, which is late and noisy, and nothing would notice admin or seed modules leaking into a public chunk.

**Evidence.** src/services/index.ts:2-6 statically imports localCatalog, localConcierge, localInquiries/localNewsletter/localSubmissions and localSearch; :27-29 `siteConfig.apiBaseUrl ? { mode: "live", ...createHttpServices(...) } : localServices`. src/config/site.ts:9 `const env = import.meta.env;`. Measured on the existing .output build (re-run in this review): index-BYBswagr.js 380,916 bytes, 119,815 gzip, contains 'A residence shaped around the landscape' (1 match) and the '/inquiries' path; contracts-lsU-wS6I.js 12,663 gzip; useStore-BomEL289.js 9,735 gzip. B4.md:32: 'JavaScript 150 KB transferred (gzip) on first load', asserted by Lighthouse. The live-mode guard that exists is the `data-services="live"` marker (B3.md:118, checked by B13.md:93 and B17.md:130), which proves the mode but not the bundle contents.

**Do this.** (1) In src/services/index.ts branch on the literal `import.meta.env.VITE_API_BASE_URL`, which vite.config.ts's define replaces with a string at build time, so the minifier drops localServices and the unused local adapter modules. If the bundle check below shows they survive, replace the import with an alias (`@mop/local-services`) that vite.config.ts points at a throwing stub when VITE_API_BASE_URL is set. Local-mode builds (B4, B17) are unchanged. (2) Set build.manifest: true and add scripts/bundle-check.mjs, run in ci.yml after the live build. From the Vite client manifest it sums the gzip size of the entry plus the static imports of each public route chunk and fails above 150 KB. It fails when a chunk reachable from a public route contains a module under src/admin/, src/domain/admin-, or (live build) src/data/, and it greps the live output for each seed property title. Watched-fail: restore the static import of ./local/catalog in services/index.ts and the check must go red. Lighthouse stays as the field-like check. Do not make `vite build` fail without VITE_API_BASE_URL: `bun run build` and B4's local-mode builds rely on it, and the data-services marker already guards deploys.

### FE-09 · major · No browser error reporting: a JavaScript error in the client-rendered admin or a hydration failure on the site is invisible to the team
Lens: frontend · Touches: B1b, B3, B7, B17

**Problem.** Sentry covers the Worker and the Edge Function only. The route error boundary only calls console.error. The admin is fully client-rendered (ssr:false), so a broken screen after a deploy, a JSON shape mismatch, or an exception in a table or the autosave hook is found only when an editor complains. On the public site, hydration errors and failed client navigations are never seen, and nobody can tell which release broke which page.

**Evidence.** src/components/layout/route-error.tsx:8-10: `useEffect(() => { console.error(error); }, [error]);`. architecture.md:162: 'Sentry on the Worker and the Edge Function'. B1b.md:97: `captureException(error, { requestId, route, env, release })` in src/server/lib/sentry.ts with scrubEvent. A grep of workspace/05-plans, architecture.md and tech-stack.md for client-error, onerror, unhandledrejection, @sentry/ or 'browser error' finds only the csp-report route.

**Do this.** Mirror B17's csp-report route. B3 (public) and B7 (admin) add src/lib/report-error.ts: reportClientError(error, { route, requestId? }), which deduplicates by message and route per page load, sends at most 10 per page, and calls navigator.sendBeacon('/api/public/client-error', json). Add the route-table row POST /client-error: limits [{ scope: 'ip', store: 'memory', limit: 30, windowSeconds: 60 }] (G72 shape), no database write, body schema { message, stack (2 KB cap), route, release, requestId? }, 204 no-store. Its handler calls B1b's captureException inside waitUntil, tagged side=browser and passed through scrubEvent. One effect in the public layout and one in the admin layout install window error and unhandledrejection listeners, and RouteError and the admin errorComponent call reportClientError. CSP connect-src stays 'self'. Tests: a unit test that two identical errors send one beacon; a route test that the 31st request in a minute answers 429 before captureException is called; an e2e case where a page.route answering a property JSON with malformed data produces one /api/public/client-error request.
