### T-01 · critical · Every branch and every lane shares one mutable cloud schema (mop-dev): unmerged migrations break unrelated PRs and lanes, and the tests check a schema the branch does not have
Lens: testing · Touches: B1b, B2, B4, B6, B10, B11, B13, H1

**Ruling (CTO):** Accepted as the mechanism of ruling DB-01 (b): one CI job `db` on an ephemeral `supabase start` stack; seed gains the target `local` (127.0.0.1 only). See DB-01 for the single rule.

**Problem.** preview-db pushes each PR's migrations to the shared mop-dev, and the CI db job does the same, then generates types from mop-dev and diffs them against the branch. What follows: (1) Once PR A has pushed a migration, every other PR's db job fails the drift guard, even a PR with no migration of its own, because gen:types always runs and the types now include A's tables. And `supabase db push` in any PR without A's file fails with the remote-version-not-found error. (2) If a builder edits a migration in place after the first push, db push skips the version as already applied, so the tests run against the old body. (3) An abandoned PR's schema stays on mop-dev until someone runs db:reset by hand, and B2's script refuses while foreign migrations exist. (4) GitHub keeps one running and one pending job per concurrency group and cancels the older pending one, so with three lanes the db, e2e-live and preview-db jobs in group mop-dev get cancelled (B1b already accepts this and answers 'rerun'). (5) Because these jobs need secrets, Dependabot PRs get no db or e2e run at all. The same collision happens outside CI. Under S54, three lanes (PLAN.md:38) each push their own unmerged migrations to the same mop-dev from separate worktrees, and B10 and B11's step proofs run `bun run db:reset` in the Content lane while the Operations lane's migrations are live there. Either the guard refuses, or the reset wipes the other lanes' state. The gate turns red for reasons unrelated to the diff, and builders learn to rerun or ignore it.

**Evidence.** B1b.md:81 'If the push fails because mop-dev holds a migration version the branch does not have (another PR's unmerged migration), the job fails red ... recovery is the orchestrator running bun run db:reset'. B1b.md:153 'a busy hour can cancel a pending preview-db ... the fix is gh run rerun'. B4.md:94 db job: 'bun run gen:types ... and git diff --exit-code src/db/types.ts' (runs whether or not a migration changed), 'concurrency: { group: mop-dev, cancel-in-progress: false }', and the `github.actor != 'dependabot[bot]'` guard on all three jobs. B4.md:167 'a test:e2e:coming-soon toggle in a concurrent e2e-live run can change what the sweep sees ... rerun'. B2.md:74 'refusing: foreign migrations'. B10.md:176 and B11.md:130 'Proof: bun run db:reset'. PLAN.md:38 three parallel lanes. ASSUMED.md E7 'GitHub's hosted runners are not the operator's machine'. tech-stack.md:102 'No job needs Docker (S50)'.

**Do this.** CI: give the db and e2e-live jobs (and e2e, if it stays separate after T-04) a database of their own, created on the runner. Steps: `bunx supabase start -x studio,imgproxy,realtime,logflare,vector,supavisor,mailpit,edge-runtime`. This keeps Postgres 17 with pg_cron, pgmq and pg_net, plus PostgREST, GoTrue, storage-api and kong, which migration 11 and B6's bucket inserts need. Then `bunx supabase db reset --local` applies the branch's migrations from zero, followed by `bunx supabase gen types typescript --local --schema public > src/db/types.ts && git diff --exit-code src/db/types.ts`, then `bun run seed -- --target local` (F17 freezes `--target dev|prod`, so B2 adds `local` as a target that only accepts 127.0.0.1), then the tests with DEV_DB_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres and SUPABASE_URL plus the service key taken from `supabase status -o env`. Remove `group: mop-dev` and the Dependabot exclusion from those jobs. The service.ts and load-fixtures guards accept the 127.0.0.1 host as well as the mop-dev ref. mop-dev then receives migrations only from main: the deploy.yml `dev` job runs `db:push` after a merge. preview-db stops pushing PR migrations, and for a PR that changes supabase/migrations it comments 'preview needs merged schema' and skips the deploy. Lanes: the same rule applies on the laptop. A lane never pushes an unmerged migration to mop-dev. Its db tests run in its PR's CI database, and locally only on the native PostgreSQL 18 with H1's pg-shims.sql when they need no Supabase extension. B10 and B11's proofs change `db:reset` to `db:push`, as B13.md:105 already does. Add a hygiene.test.ts case that fails if a ci.yml job contains `group: mop-dev` or links DEV_SUPABASE_PROJECT_REF. Fallback if Docker on runners is refused: PGDG postgresql-17, postgresql-17-cron and postgresql-17-pgmq through apt, with H1's pg-shims.sql extended for auth and storage. Fidelity is lower (no GoTrue for admin sign-in, and pg_net is UNPROVEN in PGDG).

### API-02 · major · Admin routes have no declarative contract, so each of about 75 handler files assembles authorization, CSRF and recent-auth by hand
Lens: api · Touches: B6, B7, B8, B8b, B9, B10, B11, B14, H1

**Problem.** Public routes go through one pipeline driven by `routes.ts`. Admin routes do not. Each handler file calls `requireActor`, then `verifyCsrf` on writes, then a service that has to remember `authorize(actor, '<action>')`. Services in `team`, `settings` and the subject-request group must also remember the 15-minute recent-auth check. No admin request body has a size cap anywhere, while public bodies are capped at 64 KB. The matrix test proves that the registered actions equal the fixture. It does not prove that a handler calls the right action, or any action. H1-15 checks per-role writes over HTTP from a hand-written spec, so a route missing from that spec goes unchecked. `PATCH team/users/:id` chooses its action from the body, so its action cannot be read from the route. With AI workers writing these files across eight slices, a builder who forgets one line in one file ships a write with no authorization or no CSRF check, and every existing test stays green.

**Evidence.** tech-stack.md:230 (the "API route" path): Admin is "`src/routes/api/admin/<name>.ts` calling `requireActor(request, db)` ..., `verifyCsrf` on writes, then the service ..., which calls `authorize(actor, actionId)`". Its proof is only `tests/unit/authz.matrix.test.ts`. B7.md:26 and :69: the matrix test compares the registry with the fixture only. B7.md:35: recent-auth applies to the `team` and `settings` groups and subject export and delete, enforced per service. B7.md:70: `PATCH team/users/:id` with `{ grant }`, `{ revoke }` or `{ disabled }`. B3.md:40 defines `payload_too_large` 413 for public routes only, and `grep -n "413\|payload_too_large\|content-length" B7.md` finds nothing. H1.md:44 (H1-15) drives a hand-written Playwright spec. `grep -rn "handleAdmin\|defineAdmin\|adminRoute"` across 05-plans, 06-architecture and 02-tech-stack finds nothing.

**Do this.** Add `src/server/lib/admin-route.ts` (B7 step 1) exporting `defineAdminRoute({ method, action, input, output, bodyLimitBytes = 65536, handler })`. It runs in a fixed order: the size cap from `content-length` (413 `payload_too_large`); the JSON content type on writes (400); `requireActor`; `verifyCsrf` for session writes; the 12-hour session check; `authorize(actor, action)`, which covers scope, role and `humanOnly`; `requireRecentAuth` when the action's matrix entry has `recentAuth: true`; the Zod parse of `input` (422); `handler(ctx, input)`; and `adminJson`. Every throw goes through `fromRpcError`. Move the `recentAuth` and `humanOnly` flags into the matrix entries in `src/server/lib/permissions/<group>.ts` and the fixture of `authz.matrix.test.ts`, and remove the per-service recent-auth calls. Split the multiplexed route into `POST team/users/:id/roles`, `DELETE team/users/:id/roles/:role` and `POST team/users/:id/disable`, so every route has exactly one action. Add `tests/unit/admin-routes-parity.test.ts`, which globs `src/routes/api/admin/**/*.ts`, imports each file and fails when an exported handler was not built by `defineAdminRoute` (the wrapper tags its result with a symbol), when its `action` is not in the matrix, or when a matrix action has no route. The one exception is `submissions.activate`, which is listed in the test. Export the registry so H1-15 iterates it instead of a hand-written list. Change the tech-stack §5 "API route" row to name the wrapper and the parity test.

### CS-03 · major · Admin routes are wired by hand in every file across nine slices, and nothing checks that each write verifies CSRF
Lens: code-standards · Touches: B6, B7, B8, B8b, B9, B10, B11, B14, B16, H1

**Problem.** The public side is safe by construction: handlePublic, a route table and routes-parity.test.ts. The admin side is safe only if each builder takes care. A route that forgets verifyCsrf is a forgeable state change from a logged-in staff browser, and no test anywhere goes red. A route that forgets requireActor is caught only at H1 (H1-15 walks every write per role), which is the last phase before launch.

**Evidence.** tech-stack.md line 230 gives the admin route path as a file calling `requireActor(request, db)`, `verifyCsrf` on writes, the service, `adminJson` and `fromRpcError`. B7 line 78 defines `verifyCsrf(request)` only as a function (double submit, bearer exempt). H1-15 (H1 line 44) covers authorization per role, not CSRF.

Each route file becomes `POST: ({ request }) => handleAdmin(request)`. `tests/unit/admin-routes-parity.test.ts` fails when a file under src/routes/api/admin has no row, when a row has no file, or when a row's `action` is not in the authz matrix. Later slices add rows, not wiring. H1 gains a row: a POST to every non-GET `adminRoutes` entry with a valid session cookie and no X-MOP-CSRF header answers 403 `csrf`. Watched-fail: skip verifyCsrf in handleAdmin, and the H1 probe and a unit case in admin-routes-parity go red.

### CS-04 · major · HMAC, constant-time compare and hashing are specified in eight places; one names an API that does not exist outside Workers, and two functions share the name hashKey
Lens: code-standards · Touches: B1b, B3, B5, B7, B8, B10, B15, H1

**Problem.** Every slice that needs a signature writes its own Web Crypto code: Svix verification inline in hooks/resend.ts, the bearer compare in sentry-test.ts, sha256Hex and hashKey in ids.ts, HMAC in preview-token.ts, signBody and verifyBody in hmac.ts, appsecret_proof in meta.ts, AES-GCM in confirm-email.ts, and key hashing in agent-keys.ts. Each site can compare with `===`, mix hex, base64 and base64url, or import a key with the wrong usages. A fix in one site never reaches the others. Two concrete defects are already in the plans. (1) B1b prescribes `crypto.subtle.timingSafeEqual`, a Cloudflare Workers extension that does not exist in Node, Bun or Deno. B1b's own unit proof runs in vitest's node environment and would throw a TypeError, and any copy of it in Deno-loaded code would fail in the job runner. (2) `hashKey` means `hashKey(salt, value)` in ids.ts (B3) and a one-argument sha256 hex in agent-keys.ts (B7). H1's rotation drill imports the B7 one, so an auto-import of the wrong one gives a hash that never matches.

**Evidence.** Measured: `node -e "typeof crypto.subtle.timingSafeEqual"` prints undefined, and so do Bun and `deno eval`. B1b line 98: the sentry-test bearer is 'compared in constant time (`crypto.subtle.timingSafeEqual` over equal-length byte arrays)'. B1b line 122: proof `bunx vitest run tests/unit/sentry-test-route.test.ts`; vitest.config.ts uses environment node. B3 line 72: ids.ts `hashKey(salt, value)`, `newToken()`, `sha256Hex`. B7 line 81: agent-keys.ts `hashKey` (sha256 hex). B3 line 86: Svix check inside resend.ts. B7 line 38: preview token HMAC-SHA256. B8 line 74: `src/server/lib/hmac.ts` with `signBody` and `verifyBody`, name frozen by F17. B10 line 44: appsecret_proof HMAC-SHA256. B5 line 93: AES-GCM sealToken and openToken.

**Do this.** B1b creates `src/server/lib/crypto.ts`. It is in the Deno-portable set with `.ts` imports and reads no environment. It exports `hmacSha256(key: string | Uint8Array, message: string): Promise<Uint8Array>`; `timingSafeEqual(a: Uint8Array, b: Uint8Array): boolean`, written in plain TypeScript as a length check then an XOR-accumulate loop, never crypto.subtle.timingSafeEqual; `sha256Hex`; `toHex`; `fromBase64`; `toBase64Url`; `randomToken(bytes = 32)`; `aesGcmSeal`; and `aesGcmOpen`. The following import from it instead of calling Web Crypto: sentry-test.ts, hooks/resend.ts, ids.ts (re-exports, no second body), preview-token.ts, hmac.ts (signBody and verifyBody stay under the frozen F17 name as thin wrappers), meta.ts, confirm-email.ts and agent-keys.ts. Rename agent-keys.ts's function to `hashAgentKey`, binding B7, H1 line 74 and H1-38. `tests/unit/crypto.test.ts` runs the RFC 4231 HMAC-SHA256 vectors and Svix's documented example, in the unit project, which runs under Node. The architecture test gains a case: `crypto.subtle` appears under src/** only in src/server/lib/crypto.ts. scripts/post-callback.mjs (Node) stays separate and shares B8's contract vector.

### DB-09 · major · Manual job keys count existing rows, so after done jobs are pruned the next key collides and retry, forward or metrics refresh silently does nothing
Lens: database · Touches: B7, B8, B10, B15

**Problem.** `enqueue_job_manual` builds `<type>:<entity_id>:<n>` with `n` = 1 + the number of existing jobs with that prefix, and done jobs are deleted after 30 days (`jobs_done`). Example:
- `:1` and `:2` exist, and `:1` is pruned;
- the count is 1, so `n` = 2;
- `on conflict do nothing` fires and no job is made.

This will happen in normal use:
- `refresh_social_post_metrics` on the same post three times over two months;
- a third Omnikom re-forward of an inquiry;
- a repeat `retry_social_post`. In this case the post has already moved `failed` to `scheduled` in the same transaction, so it waits forever with no job.

Each caller still writes its audit row and answers 202. The original point about a LIKE scan is dropped: `jobs` is small after pruning.

**Evidence.** B8.md:14: "`enqueue_job_manual` ... takes a transaction advisory lock on `p_type || p_entity_id` and computes `n` = 1 + the count of jobs whose key starts with `<type>:<entity_id>:`".
B8.md:28: "Enqueue is `insert ... on conflict (idempotency_key) do nothing`".
ASSUMED.md G48: `jobs_done` (30 days, delete).
B10.md:160: `retry_social_post` moves `failed` to `scheduled` and enqueues through `enqueue_job_manual`; `refresh_social_post_metrics` uses key `reconcile:<post_id>:<n>`.
B7.md:111: forward key `webhook_omnikom:<inquiry_id>:<n>`.

**Do this.** 1. Change one expression in B8's `enqueue_job_manual`, keeping the advisory lock: `n = 1 + coalesce(max(split_part(idempotency_key, ':', 3)::int), 0)` over the keys with that prefix. Pruning only removes keys, and max + 1 can never equal a key that still exists, so B8's existing `:1` and `:2` test still holds.

2. `retry_social_post`, `forward_inquiry` and `refresh_social_post_metrics` raise `enqueue_failed` when `enqueue_job_manual` returns null, so the state change and the audit row roll back instead of reporting success.

Proof: a case in `tests/db/jobs.db.test.ts`.
- Create `:1` and `:2`, then delete `:1` under `mop.retention`.
- The next call returns a non-null id with key `:3`.

Watched-fail: restore `count(*)` and the case goes red.
