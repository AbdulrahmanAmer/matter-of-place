### JOB-03 · critical · The render_variants callback makes three Worker subrequests per photograph, so a normal 40-photo property goes over the Workers free limit of 50
Lens: jobs · Touches: B4, B8, B9

**Ruling (CTO):** Accepted as part of ruling PERF-01 (H3).

**Problem.** `onResult` runs inside the Worker request that receives the callback (B8 `handleRenderCallback`). For `render_variants` it makes three calls per photograph: the `set_media_variants` RPC, a Storage `remove`, then the `clear_media_staging` RPC. Each per-upload job renders every staged row of the property, so one callback can carry up to 40 rows, which means about 120 subrequests plus the job read and `finish_job`. The Workers free plan allows 50 subrequests per request (vendor documentation, not measured here; P-009 does not list this limit). The request fails at about photo 16. The `fail_job` that follows is itself over the limit. The job stays `running` until the 30-minute reaper re-dispatches a full Actions run, and each retry hits the same wall. This failure is deterministic on the normal path once R2 is on.

**Evidence.** B9.md:65 `onResult` "per row: calls `ctx.db.rpc("set_media_variants" ...)`; removes the staged object with `ctx.db.storage.from("submissions").remove([staging_path])`; then ... `ctx.db.rpc("clear_media_staging" ...)`" and `run` "selects the property's `property_media` rows whose `staging_path` is not null". B8.md:75: `handleRenderCallback` calls the step's `onResult` in the Worker. architecture.md:170 "25 MB and 40 files per submission". `grep -rni subrequest workspace/05-plans` → only B3.md (Turnstile). GOTCHAS P-009 has no subrequest line.

**Do this.** Keep `onResult` in the Worker but make its number of calls fixed, whatever the payload size. In B9 `render-variants.ts`: (1) one RPC `apply_media_variants(p_items jsonb)`, which runs the guarded `staging_path = p_staging_path` update for every item and returns `[{ media_id, staging_path, stored }]`; (2) one `storage.from("submissions").remove(paths)` call with every signed path; (3) one RPC `clear_media_staging(p_items jsonb)` for the rows that were stored. This keeps the clear-after-remove order of B9 watched-fail (n). Including the job read and `finish_job`, a callback then makes 5 subrequests for 1 photo or 40. In `run`, replace the per-row `createSignedUrl` with one `createSignedUrls(paths, 7200)`. Add to the B8 Contract: "an `onResult` makes a number of database or Storage calls that does not depend on the size of the result". Add the 50-subrequest line to P-009 and to architecture's free-tier list. Tests: `steps.test.ts` wraps the fake client in B4's `countingDb` and asserts exactly 3 calls from `onResult` for a 40-item result. `render-hook.test.ts` asserts at most 5 calls for a whole 40-item callback. Watched-fail: put the per-row loop back and the 40-item case goes red.

### PERF-01 · critical · Every per-photo render_variants job dispatches every staged photo of the property, so renders and Storage egress grow with the square of the upload count
Lens: performance-cost · Touches: B2, B7, B9

**Ruling (CTO):** Accepted, unified with JOB-03, JOB-08 and E2E-08 into ONE render rule (H3): one `render_variants` job per property per upload batch claims its photographs with `claim_media_for_render` (this finding), and its callback makes a fixed number of calls whatever the photo count (JOB-03's `apply_media_variants` and `clear_media_staging`). The per-photograph job key of G54, G66 and G69 (3) is superseded.

**Problem.** B7 enqueues one heavy `render_variants` job per attached, replaced or copied photograph (G66, G69 (3), G70 (3)). B9 handles each one exactly like the property-wide recipe job: `run` signs and dispatches every `property_media` row of the property whose `staging_path` is still set, and rows clear only when a callback arrives minutes later. The runner dispatches 3 heavy jobs per tick. `render.yml` uses a per-job concurrency group (B8.md:84, `render-${{ client_payload.job_id }}`), so the runs execute in parallel rather than queueing. For a 40-photo property, the first 10 to 15 dispatches each carry nearly all 40 photographs, which comes to 400 to 600 renders where 40 are needed. Each run downloads every original through a signed Storage URL (about 40 x 12 MB, roughly 0.5 GB per run), so one property can spend the whole 5 GB monthly Supabase egress plus tens of Actions minutes. The parallel runs also race. The first `onResult` removes the staged object, the later runs fail on the vanished URL, and their retries sign and dispatch again. This hits the first real property after R2 is switched on.

**Evidence.** B9.md:65: the per-upload job is "handled exactly like the recipe job" and "For a property job `run` selects the property's `property_media` rows whose `staging_path` is not null ... calls `dispatchHeavy(ctx, job, { media: [...] })`". B7.md:103: `attach_media` and `replace_media` call `enqueue_job('render_variants', ..., 'render_variants:' || <media_id> || ':' || p_staging_path, p_heavy => true)` "one job per upload". B7.md:104: copySubmissionPhotos enqueues one job per copied photograph. B8.md:32: `HEAVY_PER_TICK = 3`. B8.md:84: render concurrency `render-${{ github.event.client_payload.job_id || github.run_id }}` (never cancelled, so parallel). B8.md:14: `enqueue_job(..., p_run_after timestamptz default now(), ...)` already exists.

**Do this.** Keep the per-photo keys of G54, G69 (3) and G70 (3), and add a claim so that each row is dispatched by exactly one job. (1) B2 `20261001090300_catalog.sql`: add `property_media.render_job_id uuid null`. (2) B9 `<ts>_assets.sql`: add `claim_media_for_render(p_property_id uuid, p_job_id uuid, p_limit int default 40) returns setof property_media`, defined as `update property_media set render_job_id = p_job_id where id in (select id from property_media m where m.property_id = p_property_id and m.staging_path is not null and (m.render_job_id is null or m.render_job_id = p_job_id or not exists (select 1 from jobs j where j.id = m.render_job_id and j.status = 'running')) order by sort_order for update skip locked limit p_limit) returning *`. This needs no hook in `fail_job`: a failed or dead job's claim lapses by itself, and its retry reclaims its own rows. (3) `render-variants.ts` `run` signs and dispatches only the claimed rows. With none claimed it returns `{ status: "done", result: { skipped: "claimed_elsewhere" } }`. (4) `set_media_variants`, `clear_media_staging` and `replace_media` set `render_job_id = null`. (5) B7: `attach_media`, `replace_media` and copySubmissionPhotos pass `p_run_after => now() + interval '90 seconds'`, so the first job of an upload burst runs after the burst and claims all of it, and the rest skip. Amend G66 in one line (the claim). Proof: `bunx vitest run --project db tests/db/render-claim.db.test.ts` on `mop-dev`. With 40 staged rows and 40 queued jobs run in sequence, exactly 40 items are dispatched in total. Two concurrent claims return disjoint sets. A row claimed by a job set to `failed` can be claimed again. Watched-fail: drop the `render_job_id is null` predicate and the disjoint case goes red.

### JOB-02 · major · The plans disagree on who counts attempts, a reclaimed job never uses one, nothing limits how long a step runs, and callbacks are matched on an attempt number that a manual retry resets
Lens: jobs · Touches: B8, B9, B12

**Problem.** B8 says `fail_job` increments `attempts`. The sequence diagram says `claim_job` does. The reaper "resets" a stale running light job, with no attempt rule. A builder will either count twice, so jobs die after about 3 failures, or never count a reclaim. In the second case a step that kills its isolate is reclaimed every 5 minutes forever, with no dead state, no Sentry report and no health signal. That can be a hung provider call cut at the Edge Function wall clock (150 s on free per vendor docs, UNPROVEN here) or a step over the 2 s CPU limit. `StepContext` has no abort signal and the runner sets no per-step limit. Separately, `manual_retry` sets `attempts` to 0, so `(job_id, attempt)` repeats over a job's life. A late callback from a run that was reaped and then retried by hand can match the new dispatch. Finally, `net.http_post` in the cron row sets no timeout, so pg_net's default (5 s per vendor docs) cuts the request well before a 50 s tick ends.

**Evidence.** B8.md:120: `fail_job` "increments `attempts`"; `requeue_job` `manual_retry` "sets `attempts` to 0". workspace/03-diagrams/plans-b.md:68 "claim_job sets running, locked_by, attempts plus 1". B8.md:67 "`reaper.ts` resets stale `running` light jobs". B8.md:16 StepContext `{ db, env, log, now, job }`. B8.md:33 invariant 6 "Callbacks are matched on `job_id` and `attempt`". B8.md:53 `net.http_post` with no timeout argument. `grep -n "AbortSignal\|signal" workspace/05-plans/B8.md` → no hits.

**Do this.** (1) One attempt rule, in B8 invariant 2 and `<ts>_jobs.sql`: `claim_job` never changes `attempts`, and `fail_job` increments it. Fix plans-b.md diagram 2. (2) A claim token in the existing `locked_by` column: `claim_job` sets `locked_by = gen_random_uuid()::text` and returns it. `finish_job`, `fail_job` and `requeue_job` take `p_claim text` (second, required parameter) and act only when `status = 'running' and locked_by = p_claim`; otherwise they return false and change nothing. ### JOB-08 · major · Each per-photo render_variants job dispatches its own Actions run over every staged photo, multiplying billed minutes
Lens: jobs · Touches: B7, B8, B9, B14

**Ruling (CTO):** Accepted as part of ruling PERF-01 (H3). Free tier stays; minutes are measured as ruling DO-08 says.

**Problem.** B7 enqueues one `render_variants` job per photograph. A 40-photo upload therefore dispatches up to 3 runs a minute (`HEAVY_PER_TICK`) until the first callback. Each run renders the whole set: checkout, `bun install`, sharp, at least one billed minute each. `putIfMissing` prevents double uploads, but the minutes are spent. The repository is private and has 2,000 minutes a month shared with CI, and nothing measures the minutes per run.

B8.md:156 "batching several jobs per run is the first optimisation (not built here)". ASSUMED E9: the GitHub repo is private.

(1) B7's `copySubmissionPhotos` and upload paths enqueue with `p_run_after => now() + interval '60 seconds'`, so a burst of uploads lands in one window. (4) B9 step 10 records the billed minutes of one 40-photo run (`gh run view --json` timing) in P-009, and B14's gauge reports minutes per month.
