### CS-11 · major · Production stubs are designed in on purpose, but nothing marks them or proves they are gone at launch
Lens: code-standards · Touches: B1b, B3, B3b, B5, B8, B8b, L1

**Problem.** Sequencing slices needs stubs that a later slice replaces: emitEvent (B3, replaced in B8), requestConfirmation returning null (B3, replaced in B5), applyVisibility as a pass-through (B3, replaced in B3b), the fan-out and scheduler bodies (B8, replaced in B8b), and the not_implemented branches (B8b, replaced in B11). Under S54 three lanes merge on their own schedule. If a replacing step stays BLOCKED or a merge lands out of order, the stub ships. Production would then compile, pass tests, and silently send no confirmation email, emit no event, or skip the visibility filter. No gate notices.

**Evidence.** B3 line 78: '`emitEvent` ... a stub that logs `event_pending` ... and returns null'. B3 line 86: 'holds `requestConfirmation(token)` ..., a stub that returns null'. B3 line 85: applyVisibility is a 'pass-through in B3; ... B3b implements it'. PLAN.md: 'Every step that calls an outside account is built and tested against its stub'. PLAN.md ends with a `| Slice | Status | Closed on | Proof |` table that a script can read. A grep for `STUB(` over the plans finds 0. `grep -n -i stub H1.md L1.md` finds only H1 line 108 (pg-shims stub schemas), so no launch gate exists.

**Do this.** Ruling: every production code stub carries `// STUB(<slice>[ step n]|post-v1): <what replaces it>` on the line above the function. Plan text that says a production body is a stub names the marker. Test fakes are not marked. B1b adds `scripts/stubs.ts`: it lists every STUB marker under src, supabase and scripts, reads the status table at the end of workspace/05-plans/PLAN.md (same repository, readable from CI), and exits 1 when a marker names a slice whose status is `closed`. It runs in `check`. L1's preflight.mjs gains a check: zero markers other than `post-v1`. Watched-fail: mark B3 closed in a scratch copy of PLAN.md (passed with `--plan`) while the emitEvent marker is present, and the script exits 1 naming the file.

### FE-02 · major · The admin renders inside the public root layout: site header and footer, consent notice, GA4, web vitals, service worker and the public stylesheet all reach /admin
Lens: frontend · Touches: B3, B3b, B7, B13, B16, B17

**Problem.** RootLayout in __root.tsx wraps every route in the public Header and Footer, and the root head links the public styles.css. Later slices mount more public-only behaviour in the same root: B13's Ga4Loader, B17's startWebVitals() and registerServiceWorker(), and the ConsentNotice in the footer. No plan gives the admin its own layout or excludes /admin from these. src/routes/admin.tsx is a child of the root, so every admin screen gets the public chrome and stylesheet under its AdminShell. Once a staff member has consented on the public site, GA4 loads on admin pages and sends paths such as /admin/requests/<uuid> to Google. web_vitals calls track() from admin pages, which breaks B7 invariant 10 ('admin actions do not call track()'). Global public classes such as .field in forms.css also apply to admin markup.

**Evidence.** app/src/routes/__root.tsx:57-66: RootLayout renders `<Header /> <Outlet /> <Footer />`, and head() links appCss for every route. B7.md:85: '`src/routes/admin.tsx` (layout, guard, `ssr: false`, imports `src/styles/admin/index.css`)'. B13.md:72: '__root.tsx ... also mounts `Ga4Loader` once'. B17.md:89: '__root.tsx ... one `useEffect` calls `startWebVitals()` and `registerServiceWorker()`'. B7.md:34 (invariant 10) keeps admin out of track(). src/styles/components/forms.css:3 `.field {`. `grep -rno 'pathless\|_site\.[a-z]*' workspace/05-plans` finds only `_site.sql` migration names. The only admin test of the public chrome is the print case at B7.md:175.

**Do this.** Add a route-tree ruling to ASSUMED G and B3 (the first slice to edit __root.tsx under G33). __root.tsx becomes the bare document: html, head, Scripts, QueryClientProvider, and the root loader for state and site queries only. A pathless layout src/routes/_site.tsx renders Header, Footer (with ConsentNotice), Ga4Loader and the web-vitals and service-worker effect, and its head() links styles.css. Every public page file moves under it (_site.index.tsx, _site.property.$slug.tsx and so on; URLs do not change; the generated tree is never hand-edited, G-001). src/routes/admin.tsx stays a sibling and links only the admin stylesheet. B13, B16 and B17 then edit _site.tsx instead of __root.tsx for these mounts, and G33's shared-file list names _site.tsx. Tests: tests/e2e/admin-signin.spec.ts asserts that /admin/sign-in has no .site-header and no cookie notice element, and makes no request to googletagmanager.com when consent is pre-set to granted. A unit test asserts that startWebVitals is not called when _site.tsx is not mounted.

### SEC-08 · major · The dev loader exports every .env value into every builder shell, including production credentials and the account-admin Cloudflare token
Lens: security · Touches: B2, B3, B3b, B14, B16, H1, L1

**Problem.** Every DB test, smoke run and seed starts with a loader that exports all names in the root `.env`. That file holds `mop-admin` as `CLOUDFLARE_API_TOKEN`, which is full-account and is the variable wrangler reads automatically. It holds `SUPABASE_ACCESS_TOKEN`, which reaches all projects. From L1 on it also holds PROD_SUPABASE_SERVICE_ROLE_KEY, PROD_DB_URL and the PROD_* Worker secrets. AI builders run headless with `--dangerously-skip-permissions` (P-010). In such a shell, a stray `bunx wrangler deploy` uses the admin token, and the pinned name (G-002) is `matter-of-place`, so it overwrites production. A `--target prod` flag picks up live credentials. Any dependency running in the test process can read every one of these values. The first two exposures exist today; the production ones arrive at L1 and remain for every builder after launch.

**Evidence.** B3.md:14 and ASSUMED E10: `set -a; . <(tr -d '\r' < "/e/Matter Of Place/.env" | grep -E '^[A-Z0-9_]+='); set +a`. The same loader appears in ASSUMED, B3, B3b, B14 and B16. tech-stack.md:165-168: local `.env` holds `CLOUDFLARE_API_TOKEN` (`mop-admin`), `SUPABASE_ACCESS_TOKEN` and, at launch, `PROD_SUPABASE_SERVICE_ROLE_KEY`, `PROD_DB_URL` and the PROD_* secrets. GOTCHAS P-010, G-002.

**Do this.** (1) Split the file. `.env` keeps dev values only. A new `.env.ops`, git-ignored and in the same folder, holds `CLOUDFLARE_API_TOKEN` (mop-admin), `CF_EDGE_TOKEN`, `SUPABASE_ACCESS_TOKEN`, every `PROD_*` name and `BACKUP_PASSPHRASE` (or the age identity, see SEC-10). L1, the H1 production rows, cf-edge.mjs and the rotation runbook read it.
(2) Add `scripts/load-env.mjs --profile dev|ops`. It prints `export` lines for an explicit allow-list per profile and never prints values to the terminal. Every plan replaces the inline loader with `eval "$(node scripts/load-env.mjs --profile dev)"`. ASSUMED E10 records the new command.
(3) `scripts/lib/guard-env.mjs` is imported first by `tests/db/global-setup.ts` and by every dev script (seed, api-smoke, seed-admin-users). It throws, naming the variable, when `process.env` has any name matching `^PROD_|^SUPABASE_ACCESS_TOKEN$|^CLOUDFLARE_API_TOKEN$|^CF_EDGE_TOKEN$|^BACKUP_`. Scripts that legitimately need ops (seed `--target prod`, bootstrap-admin `--target prod`) call `guardEnv({ allowOps: true })` only behind their existing `--confirm-production` flag. Tested in `tests/unit/env-guard.test.ts`.
(4) `ready.mjs` checks that the names of both files are in their correct file.
Watched-fail: export PROD_DB_URL and run `bun run test:db`, and it aborts naming the variable.

### T-02 · major · The CI test gates land after the Operations and Content lanes open, so their first slices merge with no CI db or e2e job
Lens: testing · Touches: B1b, B2, B3, B3b, B4

**Ruling (CTO):** Accepted: phase 0 of PLAN.md is B1b, B2, B3, then B4 steps 1 to 8 and the live-forms and caching parts of step 9. Phase 1 opens when a PR shows the `db` and e2e jobs running.

**Problem.** In the 48-hour lane table, B4 is the second slice of the Public lane, after B3b. The Operations lane (B8 steps 1 to 8, B8b, B5, B7) and the Content lane (B9) start at the same moment. So migrations, RLS and job-system slices merge to main before ci.yml has a db or e2e job. RUNBOOK step 3 has the orchestrator re-run only the merged slice's own Verification, so a regression one lane causes in B2's or B3's tests is not seen. B4.md:5 already allows most of B4 to start right after B1b and B2, but PLAN.md does not use that order.

**Evidence.** PLAN.md:37 'Phase 0 Spine, one lane | B1b, then B2, then B3'; PLAN.md:38 'Public: B3b, B4, ... · Operations: B8 steps 1 to 8, ...' in parallel. B4.md:5 'B4 steps 2 and 6 may start after B1b step 5, steps 1 and 5 after B1b step 5 and B2 step 1; ... steps 7 to 9 after B2 step 10 and B3 step 12'. B3.md:144 'Watched-fail, each done once and reverted by hand, because B4 lands after this slice'. RUNBOOK.md step 3 re-runs 'the slice's Verification section'.

**Do this.** PLAN.md Phase 0 becomes 'B1b, then B2, then B3, then B4 steps 1 to 8 and the live-forms and caching parts of step 9 (they need only B3)'. Phase 1 lanes open only when `gh run view --json jobs` on a PR shows the db and e2e jobs running.
