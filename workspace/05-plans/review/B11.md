### T-01 · critical · Every branch and every lane shares one mutable cloud schema (mop-dev): unmerged migrations break unrelated PRs and lanes, and the tests check a schema the branch does not have
Lens: testing · Touches: B1b, B2, B4, B6, B10, B11, B13, H1

**Ruling (CTO):** Accepted as the mechanism of ruling DB-01 (b): one CI job `db` on an ephemeral `supabase start` stack; seed gains the target `local` (127.0.0.1 only). See DB-01 for the single rule.

**Problem.** preview-db pushes each PR's migrations to the shared mop-dev, and the CI db job does the same, then generates types from mop-dev and diffs them against the branch. What follows: (1) Once PR A has pushed a migration, every other PR's db job fails the drift guard, even a PR with no migration of its own, because gen:types always runs and the types now include A's tables. And `supabase db push` in any PR without A's file fails with the remote-version-not-found error. (2) If a builder edits a migration in place after the first push, db push skips the version as already applied, so the tests run against the old body. (3) An abandoned PR's schema stays on mop-dev until someone runs db:reset by hand, and B2's script refuses while foreign migrations exist. (4) GitHub keeps one running and one pending job per concurrency group and cancels the older pending one, so with three lanes the db, e2e-live and preview-db jobs in group mop-dev get cancelled (B1b already accepts this and answers 'rerun'). (5) Because these jobs need secrets, Dependabot PRs get no db or e2e run at all. The same collision happens outside CI. Under S54, three lanes (PLAN.md:38) each push their own unmerged migrations to the same mop-dev from separate worktrees, and B10 and B11's step proofs run `bun run db:reset` in the Content lane while the Operations lane's migrations are live there. Either the guard refuses, or the reset wipes the other lanes' state. The gate turns red for reasons unrelated to the diff, and builders learn to rerun or ignore it.

**Evidence.** B1b.md:81 'If the push fails because mop-dev holds a migration version the branch does not have (another PR's unmerged migration), the job fails red ... recovery is the orchestrator running bun run db:reset'. B1b.md:153 'a busy hour can cancel a pending preview-db ... the fix is gh run rerun'. B4.md:94 db job: 'bun run gen:types ... and git diff --exit-code src/db/types.ts' (runs whether or not a migration changed), 'concurrency: { group: mop-dev, cancel-in-progress: false }', and the `github.actor != 'dependabot[bot]'` guard on all three jobs. B4.md:167 'a test:e2e:coming-soon toggle in a concurrent e2e-live run can change what the sweep sees ... rerun'. B2.md:74 'refusing: foreign migrations'. B10.md:176 and B11.md:130 'Proof: bun run db:reset'. PLAN.md:38 three parallel lanes. ASSUMED.md E7 'GitHub's hosted runners are not the operator's machine'. tech-stack.md:102 'No job needs Docker (S50)'.

**Do this.** CI: give the db and e2e-live jobs (and e2e, if it stays separate after T-04) a database of their own, created on the runner. Steps: `bunx supabase start -x studio,imgproxy,realtime,logflare,vector,supavisor,mailpit,edge-runtime`. This keeps Postgres 17 with pg_cron, pgmq and pg_net, plus PostgREST, GoTrue, storage-api and kong, which migration 11 and B6's bucket inserts need. Remove `group: mop-dev` and the Dependabot exclusion from those jobs. Lanes: the same rule applies on the laptop. A lane never pushes an unmerged migration to mop-dev. Its db tests run in its PR's CI database, and locally only on the native PostgreSQL 18 with H1's pg-shims.sql when they need no Supabase extension. B10 and B11's proofs change `db:reset` to `db:push`, as B13.md:105 already does. Add a hygiene.test.ts case that fails if a ci.yml job contains `group: mop-dev` or links DEV_SUPABASE_PROJECT_REF. ### API-02 · major · Admin routes have no declarative contract, so each of about 75 handler files assembles authorization, CSRF and recent-auth by hand
Lens: api · Touches: B6, B7, B8, B8b, B9, B10, B11, B14, H1

**Problem.** Public routes go through one pipeline driven by `routes.ts`. Admin routes do not. Each handler file calls `requireActor`, then `verifyCsrf` on writes, then a service that has to remember `authorize(actor, '<action>')`. Services in `team`, `settings` and the subject-request group must also remember the 15-minute recent-auth check. No admin request body has a size cap anywhere, while public bodies are capped at 64 KB. The matrix test proves that the registered actions equal the fixture. It does not prove that a handler calls the right action, or any action. H1-15 checks per-role writes over HTTP from a hand-written spec, so a route missing from that spec goes unchecked. `PATCH team/users/:id` chooses its action from the body, so its action cannot be read from the route. With AI workers writing these files across eight slices, a builder who forgets one line in one file ships a write with no authorization or no CSRF check, and every existing test stays green.

**Evidence.** tech-stack.md:230 (the "API route" path): Admin is "`src/routes/api/admin/<name>.ts` calling `requireActor(request, db)` ..., `verifyCsrf` on writes, then the service ..., which calls `authorize(actor, actionId)`". Its proof is only `tests/unit/authz.matrix.test.ts`. B7.md:26 and :69: the matrix test compares the registry with the fixture only. B7.md:35: recent-auth applies to the `team` and `settings` groups and subject export and delete, enforced per service. B7.md:70: `PATCH team/users/:id` with `{ grant }`, `{ revoke }` or `{ disabled }`. B3.md:40 defines `payload_too_large` 413 for public routes only, and `grep -n "413\|payload_too_large\|content-length" B7.md` finds nothing. H1.md:44 (H1-15) drives a hand-written Playwright spec. `grep -rn "handleAdmin\|defineAdmin\|adminRoute"` across 05-plans, 06-architecture and 02-tech-stack finds nothing.

**Do this.** Add `src/server/lib/admin-route.ts` (B7 step 1) exporting `defineAdminRoute({ method, action, input, output, bodyLimitBytes = 65536, handler })`. It runs in a fixed order: the size cap from `content-length` (413 `payload_too_large`); the JSON content type on writes (400); `requireActor`; `verifyCsrf` for session writes; the 12-hour session check; `authorize(actor, action)`, which covers scope, role and `humanOnly`; `requireRecentAuth` when the action's matrix entry has `recentAuth: true`; the Zod parse of `input` (422); `handler(ctx, input)`; and `adminJson`. Every throw goes through `fromRpcError`. Move the `recentAuth` and `humanOnly` flags into the matrix entries in `src/server/lib/permissions/<group>.ts` and the fixture of `authz.matrix.test.ts`, and remove the per-service recent-auth calls. Split the multiplexed route into `POST team/users/:id/roles`, `DELETE team/users/:id/roles/:role` and `POST team/users/:id/disable`, so every route has exactly one action. Add `tests/unit/admin-routes-parity.test.ts`, which globs `src/routes/api/admin/**/*.ts`, imports each file and fails when an exported handler was not built by `defineAdminRoute` (the wrapper tags its result with a symbol), when its `action` is not in the matrix, or when a matrix action has no route. The one exception is `submissions.activate`, which is listed in the test. Export the registry so H1-15 iterates it instead of a hand-written list. Change the tech-stack §5 "API route" row to name the wrapper and the parity test.

### CS-03 · major · Admin routes are wired by hand in every file across nine slices, and nothing checks that each write verifies CSRF

### CS-08 · major · Logging has three shapes, the logger arrives after the first server code, and console is not banned, so the email scrubber can be bypassed
Lens: code-standards · Touches: B1b, B3, B5, B8, B8b, B11, B14

**Problem.** B1b writes server code (sentry.ts, start.ts) before B3 creates logLine, and tells sentry.ts to use console.error directly. Workers Logs cannot then be filtered by event or field. More important, any console call bypasses log.ts's email scrubbing, so an address can reach logs. The only console check is B3's one-off grep for `console.log` in src/server. It misses console.error, warn and info, the job runner and scripts, and does not run in CI.

**Evidence.** B1b line 97: sentry.ts failures are 'written once to `console.error` with the request id'. B3 line 73: '`logLine(level, fields)` writing one JSON line to `console`; scrubbing of email-like strings'. B8b line 46: 'logs `fanout_failed <event_id> <code>`'; B8b line 190: 'logs `fanout_failed <id>` once' (two shapes for one event). B8b lines 53, 120 and 121: `schedule_failed <key>`, `keepwarm last_run_update_failed`, `keepwarm env_missing <name>`. B14 line 49: `logLine("warn", { msg: "not_found_flush_failed", dropped })` (a third shape). architecture.md line 142: `market_open_notice_not_implemented <slug>`. B3 line 151: `grep -rn "console.log" src/server` (verification only). Measured `no-console` on today's code: 1 hit (src/components/layout/route-error.tsx line 9).

**Do this.** Move the creation of log.ts from B3 to B1b, so B3 then adds the per-request line in handlePublic. Write a ruling that binds every plan naming a log message. **Problem.** S13 settles double opt-in. ### INT-02 · major · mop-dev and production share one Resend account: dev mail spends the production daily quota, the public dev Worker can mail arbitrary addresses, and webhook events cross environments
Lens: integrations · Touches: B3, B5, B11, L1

**Problem.** (a) Quota. Resend's free limit of 100 a day is per account, but email_sent_today() counts only its own database. mop-dev (cap 90) and production (cap 90) together can try to send 180. After launch, any dev activity spends the production budget: email-test.ts sending every key, the L1 rehearsal, B11 test sends, dev magic links. Production invoices, inquiry_ack and confirmation mails then fail at Resend with daily_quota_exceeded for the rest of the UTC day. (b) Abuse. The stable dev Worker matter-of-place-dev is public on workers.dev and holds Cloudflare's always-pass Turnstile secret. Its runner sends real mail, because L1 step 2 and B5 step 5 unset EMAIL_DRY_RUN on mop-dev. Anyone can POST /api/public/subscribers or /inquiries there with any non-empty token and make matterofplace.com send a confirmation or acknowledgement to any address. Only the per-IP limits bound it. The cost is shared quota plus complaints against the brand's sending domain. (c) Webhooks. ### INT-10 · major · A crash after the broadcast send leaves the issue stuck in 'sending' or calls send again

### INT-11 · major · Resend errors are classified by HTTP status only, but each status covers several different errors
Lens: integrations · Touches: B5, B11

**Problem.** B5 maps 429 to RateLimited, 422 to Invalid and 5xx to Transient, and gives no retry time for 429. Resend's answers are finer than that. Status 429 is one of three: rate_limit_exceeded (retry in seconds), daily_quota_exceeded (retry after the UTC day rolls over) or monthly_quota_exceeded (retry next month). Treating all three alike either calls Resend every minute for a day or waits a day for a one-second limit. 409 concurrent_idempotent_requests and resource_locked mean retry shortly. 409 invalid_idempotent_request means the same key was used with a different body, which happens when a template edit lands between two attempts after the first was delivered. Recording it as failed marks a delivered mail as failed. 403 validation_error (domain not verified), restricted_api_key and suspended_api_key are unmapped, so they burn five attempts with no clear signal. 400 invalid_idempotency_key is a code bug.

**Evidence.** B5.md:90: "RateLimited (429) becomes retry_at, Transient (5xx, network) a normal retry with B8 backoff, Invalid (422) a NonRetryableError", with no 409, 401 or 403 case and no retry time. B5.md:183: Idempotency-Key behaviour is "taken from memory of the Resend API. UNPROVEN". Resend's error reference (context7 /llmstxt/resend_llms-full_txt, resend.com/docs/api-reference/errors) lists invalid_idempotency_key 400; missing_api_key and restricted_api_key 401; invalid_permission, restricted_api_key, suspended_api_key and validation_error 403; concurrent_idempotent_requests, invalid_idempotent_request and resource_locked 409; daily_quota_exceeded, monthly_quota_exceeded and rate_limit_exceeded 429; application_error 500; service_unavailable 503.

**Do this.** Classify on the body's `name` first and the status second, through one table RESEND_ERRORS in src/server/email/resend-errors.ts that both resend-client.ts and B11's resend.ts import. rate_limit_exceeded and 503: retry_at at now + max(Retry-After, 2 s). daily_quota_exceeded: retry_at at the next UTC midnight + 1 minute, plus a health warn. monthly_quota_exceeded: retry_at on the 1st of next month, plus a Sentry report (INT-04). concurrent_idempotent_requests and resource_locked: retry_at in 30 s. invalid_idempotent_request: email_message_finish 'sent' with error 'idempotent_conflict' and no resend, plus a Sentry warning. missing_api_key, restricted_api_key, suspended_api_key, invalid_permission, 403 validation_error and invalid_idempotency_key: NonRetryableError. Unknown names fall back to the status classes. To make a retry send the same body, store the rendered subject and html hash in email_messages.content_hash at email_message_begin; when a retry renders a different hash, send the stored version, or record 'content_changed'. Table-driven test resend-errors.test.ts with one case per name.
