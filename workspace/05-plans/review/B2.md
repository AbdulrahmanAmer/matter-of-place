### E2E-06 · critical · The three S54 lanes push migrations and job-runner builds from their own branches into the one shared mop-dev, which the Supabase CLI refuses, and an edited migration drifts silently

### PERF-01 · critical · Every per-photo render_variants job dispatches every staged photo of the property, so renders and Storage egress grow with the square of the upload count
Lens: performance-cost · Touches: B2, B7, B9

**Ruling (CTO):** Accepted, unified with JOB-03, JOB-08 and E2E-08 into ONE render rule (H3): one `render_variants` job per property per upload batch claims its photographs with `claim_media_for_render` (this finding), and its callback makes a fixed number of calls whatever the photo count (JOB-03's `apply_media_variants` and `clear_media_staging`). The per-photograph job key of G54, G66 and G69 (3) is superseded.

**Problem.** B7 enqueues one heavy `render_variants` job per attached, replaced or copied photograph (G66, G69 (3), G70 (3)). B9 handles each one exactly like the property-wide recipe job: `run` signs and dispatches every `property_media` row of the property whose `staging_path` is still set, and rows clear only when a callback arrives minutes later. The runner dispatches 3 heavy jobs per tick. `render.yml` uses a per-job concurrency group (B8.md:84, `render-${{ client_payload.job_id }}`), so the runs execute in parallel rather than queueing. For a 40-photo property, the first 10 to 15 dispatches each carry nearly all 40 photographs, which comes to 400 to 600 renders where 40 are needed. Each run downloads every original through a signed Storage URL (about 40 x 12 MB, roughly 0.5 GB per run), so one property can spend the whole 5 GB monthly Supabase egress plus tens of Actions minutes. The parallel runs also race. The first `onResult` removes the staged object, the later runs fail on the vanished URL, and their retries sign and dispatch again. This hits the first real property after R2 is switched on.

B8.md:84: render concurrency `render-${{ github.event.client_payload.job_id || github.run_id }}` (never cancelled, so parallel). B8.md:14: `enqueue_job(..., p_run_after timestamptz default now(), ...)` already exists.

**Do this.** Keep the per-photo keys of G54, G69 (3) and G70 (3), and add a claim so that each row is dispatched by exactly one job. (2) B9 `<ts>_assets.sql`: add `claim_media_for_render(p_property_id uuid, p_job_id uuid, p_limit int default 40) returns setof property_media`, defined as `update property_media set render_job_id = p_job_id where id in (select id from property_media m where m.property_id = p_property_id and m.staging_path is not null and (m.render_job_id is null or m.render_job_id = p_job_id or not exists (select 1 from jobs j where j.id = m.render_job_id and j.status = 'running')) order by sort_order for update skip locked limit p_limit) returning *`. ### API-03 · major · Errors are mapped by message text, real codes become 500, and outages are reported as 500 instead of 503
Lens: api · Touches: B2, B3, B7

**Problem.** `fromRpcError` matches raised message strings against a fixed list and maps "anything else to 500 `internal`". Codes that admin-route functions already raise are missing from the list. `update_property` calls `save_property`, which raises `not_found` (P0002) for an unknown id and `invalid_patch_key` (22023). An agent that sends a stale or wrong id therefore gets a 500 instead of a 404. A database that is paused or unreachable, a PostgREST connection error or a fetch abort on an admin route also becomes 500 `internal`. B3 already answers 503 `unavailable` for the same conditions on public routes, so agents get no `Retry-After` and Sentry's 5k a month fills during an outage. When the JWKS fetch fails on a cold isolate the outcome is unspecified, and if it surfaces as 401 every admin is sent round the sign-in loop during an Auth incident. Two names, `server` (B3) and `internal` (B7), mean the same 500. Nothing checks mechanically that a new raise in a later slice was added to the list. The plan only asks the slice to remember.

**Evidence.** B7.md:76: `fromRpcError` lists its codes and ends "anything else to 500 `internal` (a slice that adds an admin function raising a code not in this list adds its line here ...)", and the list has no `not_found` or `invalid_patch_key`. B2.md:122: `save_property` raises `not_found` (SQLSTATE `P0002`) and `invalid_patch_key` (SQLSTATE `22023`). B7.md:31: `update_property` calls `save_property`. B3.md:40 names the 500 `server`, B7.md:76 names it `internal`. B3.md:86: public services answer 503 `unavailable` on a database error. B7.md:41 (17b): the JWKS is "fetched once, held in module memory, refreshed on an unknown `kid`", with no failure path. `grep -rn "PGRST\|57014\|55P03" workspace` finds nothing. (`publish_not_allowed` and `invalid_target` were dropped from the original evidence. The publish gate passes `service_role`, which every admin RPC uses, and `invalid_target` is raised by a job-step function that is not called through `fromRpcError`.)

**Do this.** Create `src/server/lib/error-codes.ts` with `export const errorCodes = { ...every code: status } as const` as the only code list, merging B3's `errors.ts` codes and B7's list. ### T-07 · major · Watched-fails are a free-text ledger with no enforcement and no replay, and B2's migration mutations need two shared-database resets each
