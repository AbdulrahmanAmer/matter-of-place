Production deploys only what `ci.yml` passed (P-028, architecture 7). `ci.yml` runs on `push` to `main` as well as on pull requests into `main`, and the `production` job of `deploy.yml` is triggered by `workflow_run` of `ci` on `main` with `conclusion == 'success'` and checks out that run's `head_sha`. The first step of `production` and `dev` is `node scripts/deploy-guard.mjs`: when a newer code commit than the one being deployed is already on `main`, it prints `superseded <sha>` and every later step of the job is skipped, so a re-run of an older green `ci` run never deploys old code over new (DO-04). `production` has `needs: dev`, so the one database step (the `dev` job's `bun run db:push`, invariant 13) has finished before the production Worker deploys, and a red `dev` job skips `production` (H35: one project, migrated once per merge).
6b. Merge gate (DO-04, T-03; there is no branch protection, P-028). The orchestrator merges only with `node workspace/05-plans/merge-gate.mjs <pr>`, which refuses a PR whose head does not contain `origin/main` (`rebase first`), refuses while any check is failed or pending, posts the commit status `merge-gate=success` on the head and merges with `gh pr merge <pr> --merge --match-head-commit <headSha>`. After the merge, the `ci.yml` job `merge-gate` (push to `main` only) runs `node scripts/merge-gate.mjs`, which finds the merged PR and exits 1 with `unverified merge <sha>: <job> <conclusion>` unless the PR head carries the `merge-gate` status and every name in `REQUIRED_PR_CHECKS` concluded `success` on it. Because `production` waits for `ci` success, a merge that bypassed the gate cannot deploy. `hygiene.test.ts` imports `REQUIRED_PR_CHECKS` from `scripts/merge-gate.mjs`, so a renamed or added pull request job breaks the test.
7. Sentry never receives personal data (GS-03). The client sends the error class, a message run through the scrub, stack frames, and the tags `request_id`, `route`, `env`, `release`. It never sends emails, names, message bodies, IP addresses, cookies, `authorization`, query strings or request bodies. One exported pure function `scrubEvent(event)` is applied last, in the role of `beforeSend`: it deletes `user`, `request.data`, `request.cookies`, `request.headers`, `request.query_string`, `contexts.geo` and all breadcrumbs, replaces email-shaped strings with `[email]`, and truncates every exception value to 200 characters (ASSUMED limit). The name is kept so the `@sentry/cloudflare` fallback maps to it one to one. Input is bounded before it is parsed (ruling H39 (3)): `captureException` caps the message at 2,000 characters, the stack at 50 lines and each stack line at 500 characters before any pattern runs, and parses a frame in linear time (no pattern with two lazy groups in a row). The browser's text reaches it through B3's and B7's `/api/public/client-error`, so the caps are a security rule. `captureException(error, options)` takes `dsn`, `env` and `release` from its caller and reads no environment itself (R14, ruling H39 (4)).
7a. Sentry spends its 5,000 free events on distinct problems only (INT-12). Each isolate keeps a `Map<fingerprint, lastSentMs>` and sends at most one event per fingerprint per 60 seconds; the fingerprint is the caller's `fingerprint` when given (B8b's `job_runner_stalled`, JOB-04), otherwise the route plus the error class plus the first stack frame. A `429` answer or an `X-Sentry-Rate-Limits` header stops every send from that isolate until the window it names ends (`Retry-After` seconds for a 429). The Worker and the job runner use two client keys with per-key limits (Variables table), so Worker noise cannot starve the runner's reports.
8. The toolchain is pinned (GS-07). `package.json` `engines` holds `{"bun": "1.3.13", "node": "24.x"}` (the pin follows the laptop's local major, node 24.13.0, E11), `bun.lock` is committed, CI runs `bun install --frozen-lockfile`, and a CI step fails when the setup-bun and setup-node versions differ from `engines`. Dependabot opens grouped weekly PRs for the app (`bun` ecosystem, directory `/app`) and for `github-actions` (directory `/`); a Dependabot PR is an ordinary PR for `ci.yml`, but GitHub withholds Actions secrets from Dependabot-triggered runs, so its `preview` job is skipped (`github.actor != 'dependabot[bot]'`); a preview for Dependabot PRs is BLOCKED until the operator decides to copy the preview secrets into Dependabot secrets (`gh secret set --app dependabot`). Because of that, `scripts/merge-gate.mjs` does not require `preview` on a PR whose author is `dependabot[bot]`. The `ci.yml` jobs need no secret at all (B4's `db` job runs on an ephemeral stack, invariant 13), so they carry no Dependabot exclusion.

Edge rules live in code, not in a dashboard memory (GS-08). `scripts/cf-edge.mjs` is idempotent and B1b writes six of its parts: (1) the Cloudflare Free Managed Ruleset executed in phase `http_request_firewall_managed` (its ruleset id is looked up by name at run time, not hard coded), (2) Bot Fight Mode on, (3) the zone's single free rate-limit rule on `starts_with(http.request.uri.path, "/api/public/") or starts_with(http.request.uri.path, "/api/admin/auth/")` (the sign-in link route is anonymous, API-04) at 60 requests per 10 seconds per IP with action block (ASSUMED threshold; the free plan allows one rule and a 10 second window, P-009), and the three zone settings of G32: (6) the `www` to apex 301 redirect, (7) Always Use HTTPS on, (8) SSL mode Full (strict). Parts 4 (Brotli, HTTP/3, Early Hints) and 5 (DNS records, MTA-STS host) are B17's, which keeps its numbering. No geo block on `/admin`: agents run anywhere, so `/admin` is protected by the session or the agent key only (B7), the session verified locally against the project's ES256 key (E14) with no call to Supabase Auth. The rules apply to the zone, so they exist only after Stage 5 routes the domain to the Worker; `workers.dev` hostnames are not covered.

10. Pipeline order and never-cached list (architecture 13 rules 5 and 6). Order, outside to inside: (a) mint or accept `x-request-id` (an inbound value is kept only when it matches `^[A-Za-z0-9-]{8,64}$`, otherwise `crypto.randomUUID()` is minted, so a client cannot put arbitrary text into logs, error bodies, Sentry tags or `audit_log`), (b) never-cached rule, (c) the cache hook, (d) render. The id of (a) reaches every handler (ruling H39 (1)): `handle()` calls `deps.render(request, requestId)`, `src/start.ts` passes the id on through the router's request context (`next({ context: { requestId } })`), and a handler reads `context.requestId` and never mints one (B3's `handlePublic` and B7's `defineAdminRoute` build `ctx.requestId` from it). So every non-2xx body carries the same id as the `x-request-id` response header (STANDARDS R09), the inert 404 of `POST /api/hooks/sentry-test` included; R09 has no exception. A path under `/api/` never answers the page shell (ruling H39 (2), G-022): the router renders an API route file that has no handler for the method as a page, so when the pathname starts with `/api/` and the rendered response is `text/html`, `handle()` answers the R09 JSON instead with `Cache-Control: no-store`: 405 `method_not_allowed` when the rendered status was 200, otherwise the rendered status with code `not_found`. B3's and B7's wrappers add the `Allow` header where they know the methods; this guard stays as the backstop.
