## Risks and gotchas (link GOTCHAS ids)
- P-015: Git Bash rewrites arguments that begin with `/`; use `MSYS_NO_PATHCONV=1` and the `D:/` drive path for the render gate, or PowerShell.
- P-013: use absolute paths in launch scripts. P-008: JSON payloads via files, not inline Bash.
- G-009: history is append-only; the launch is a merge, never a force push.
- G-011 and P-009: the launch week is when traffic first tests the free limits. The Workers free plan CPU limit (10 ms) was probed in H1-30 and measured on a throwaway Worker on 2026-10-01 (E3: home 6 to 52 ms, collection 10 to 24 ms, all outcomes `ok`); check the real numbers on day 1 with `bunx wrangler tail matter-of-place --format json` from the owner's shell with the `mop-admin` token (the deploy token cannot tail, E1). If error 1102 appears, the answer is the H1 decision (edge-cache HTML first, Workers Paid second), not a retry.
- G-012: `deploy.yml` at the repository root.
- P-042: a background `bunx wrangler dev` on port 8788 (step 4h) is stopped by its parent `node.exe` or `bun.exe`, filtered by process name, then any `workerd`; killing `workerd` alone makes it respawn. Confirm `Get-NetTCPConnection -LocalPort 8788 -State Listen` is empty.
- One database from the laptop (ruling H35): the local Supabase CLI stays linked to the one project, which is production after step 1's launch switch, so the laptop's `bun run db:push` would write to production; after the switch only the `dev` job of `deploy.yml` pushes migrations from `main` (B1b, B2's `scripts/db-push.mjs` closes the single-lane exception once `settings.environment` is `production`), and every destructive or test command refuses through `scripts/lib/assert-not-production.mjs`. Recorded risk, the operator's to revisit (H35 (10)): there is no cloud database to rehearse a change on after launch; a second free project can be added later behind the scripts' `--target` argument.
- Production backups: the first dump of the production stage is step 1i's manual run, and the nightly `backup.yml` run dumps the one database from then on into the workflow artifact `mop-dev-dump` (30 or 14 days, DB-11, B1b), its only copy (ruling H33 (7)); point-in-time recovery is paid and not used (B2). Storage objects in `submissions`, `media` and `documents` are not backed up at all (H33 (7)): a lost published photograph can be made again only while its source exists, and the original is deleted once its variants exist (H33 (8)), so the restore runbook of H1 records the gap with the CEO's initials. A scheduled run that ends `backup disabled` is green, so the day 5 watch reads the logs and `last_run_at`, not only the run colour.
- G-006: production secrets set only by name through the CLIs; nothing pasted into the repo or a chat.
- DNS: a DNSSEC mismatch at the registrar during a nameserver change is the classic outage; step 4b exists for that. Zoho already owns the MX and SPF records on the apex (P-034) and Email Routing is not used; Resend uses the `send` subdomain, so they should coexist (ASSUMED, verify the apex SPF record has a single `v=spf1` and `dig TXT send.matterofplace.com +short` shows Resend's own).
- HSTS with `includeSubDomains` at launch is hard to undo; the preload list is harder still. The header goes out without `preload` at launch, and step 10 adds it only after a month of stability, a decision row and DNSSEC (GS-10). A subdomain that later needs plain HTTP would break for every browser that has the preload entry.
- Domain expiry is the quietest total outage: auto-renew can fail on a stale card without any page changing. The Namecheap reminder emails go to the admin mailbox, the expiry date is in the runbook, and the monthly gauge review (iterate loop 4) includes it (GS-10). Whether Namecheap shows the auto-renew state to an API is UNPROVEN, so that line is a signed manual check.
- DNSSEC: enabling it in the same hour as a nameserver change is the classic outage (see step 4b); step 4g waits a day and has a written way back.
- Search Console shows "Excluded by noindex" for empty market pages and thin archive URLs; that is the design (B13), not an incident.
- Supabase free projects pause after 7 idle days; the one database is kept awake by the keep-warm cron, which calls the public handler in-process and always makes one state RPC (a cache hit alone would not touch the database, F25 h); verified in the daily list, and `psql "$DEV_DB_URL" -Atc "select calls from extensions.pg_stat_statements where query ilike '%public_state%' order by calls desc limit 1"` (E15 measured it in the build stage; step 1h measures it on the production stage, F26 g, and if `pg_stat_statements` is not readable there the proof is the `keepwarm` row's `last_run_at` within 10 minutes) rises between two days even when no visitor came. A paused production database turns signups into errors.
- Coming-soon collects personal data (email, market); privacy page and the double opt-in copy must be live before the first signup (B16, B5).
- Social: posting on each channel stays disabled in production until its real token check passes (Meta, X, LinkedIn), and every post stays human-approved for 60 days (S23).
