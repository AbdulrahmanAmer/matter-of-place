Facebook and YouTube exist as disabled blocks and post nothing until switched on.

Inputs

Recipe `asset.approved` → `post_meta`, `post_x`, `post_linkedin` (each per channel_settings), `queue_digest` (architecture 5). `post_meta` serves Instagram now and Facebook when `channel_settings.facebook.enabled` is switched on. There is no YouTube step in the catalog yet; it is added by PR when YouTube is switched on.
- `channel_settings` rows `instagram`, `x`, `linkedin` (seeded by B8b; this slice's migration sets them disabled, and each is enabled on screen 20 once its credentials check passes, before launch) and `facebook`, `youtube` (seeded disabled) (architecture 3.5): `enabled`, `posting_window {days, from, to, tz}`, `approval_mode {Feature, Reach, Campaign}`, `auto_after`, `credentials_ref`. ASSUMED extra keys inside `posting_window`: `daily_cap` (default 2 posts per channel per day, below any platform limit).
- Secrets, server side only: `META_APP_SECRET`, `META_PAGE_TOKEN`, `X_CLIENT_ID`, `X_CLIENT_SECRET`, `X_ACCESS_TOKEN`, `X_REFRESH_TOKEN`, `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET`, `LINKEDIN_ACCESS_TOKEN`, `LINKEDIN_REFRESH_TOKEN` (tech-stack 4; the X and LinkedIn names are ASSUMED). ASSUMED non-secret ids: `settings.meta` = `{ page_id, ig_user_id, graph_version }`, `settings.x` = `{ user_id, handle }`, `settings.linkedin` = `{ organization_urn, api_version }`. `credentials_ref` holds the name `meta`, `x` or `linkedin`. Secrets must exist in Supabase function secrets (the steps run in the Edge Function; set with `supabase secrets set --project-ref <ref>`, no Docker) and in GitHub Actions secrets under the `DEV_` and `PROD_` prefixes (A11; this plan has no GitHub Environments, ASSUMED E9), for example `DEV_META_PAGE_TOKEN`; Cloudflare holds only what the Worker itself reads. None of these names exists yet in GitHub (E10 lists what does). tech-stack 4 lists `META_*`, `X_*`, `LINKEDIN_*` and `SOCIAL_DRY_RUN` under Supabase function secrets. Rotating tokens (X and LinkedIn access tokens expire) live in Vault, one secret per channel holding `{ access_token, refresh_token, expires_at }`: `x_oauth_token` and `linkedin_oauth_token`; the env secrets are the seed values. They are refreshed on demand by `getChannelToken` and checked daily by the reconcile job (both in Files, `oauth-tokens.ts`); there is no separate refresh schedule.
- Public media base: the post steps build every media URL with B3's `mediaUrl(key)`, which prefixes `MEDIA_BASE_URL`. The steps run in the job-runner Edge Function, so `MEDIA_BASE_URL` is set as a Supabase function secret on `mop-dev` (and later `mop-prod`) when the operator switches R2 on; `R2_PUBLIC_BASE` is not read by this slice. X and LinkedIn bytes are fetched with `fetch(mediaUrl(key))` (public immutable object, no S3 client).
- Graph API version pinned in `settings.meta.graph_version`. ASSUMED placeholder `v23.0`; step 3 replaces it with the newest version in Meta's changelog that day and records it.

Caption variants come from B9's `write_captions`: Instagram, X short, LinkedIn editorial. What each step reads from the asset is fixed in two pure functions in `src/server/channels/index.ts`, tested by `tests/unit/channels/targets.test.ts`:
- `targetsFor(kind, settings)` returns the target channels of a kind from the table above (carousel: `instagram`, plus `linkedin` when `settings.linkedin.multi_image` is true; cover: `x`, `facebook`, plus `linkedin` when it is not; story: `instagram`, `facebook`; reel: `instagram`). Only rows with `enabled = true` count. Any other kind (`newsletter_block`, `standalone_email`) has no target: the step returns `{ status: "done", result: "skipped_kind" }` and writes no row.
- `filesFor(channel, asset)` and `captionFor(channel, asset)`: Instagram carousel = the files with no `role`, in order (1080×1350), caption `caption`; Instagram story = the single story file; Instagram reel = the file with `role: video`, plus `role: poster` as `cover_url` (B12); X = the cover file with `role: x`, caption `meta.captions.x`; LinkedIn = the cover file with `role: linkedin` or the carousel files with `role: linkedin_set`, caption `meta.captions.linkedin`; Facebook = the cover file with no role, caption `meta.captions.linkedin` followed by the dossier URL (no fourth caption variant until Facebook is enabled).

Outputs
- `social_posts` rows (architecture 3.6): `asset_id`, `channel`, `status` `scheduled|posted|failed`, `scheduled_at`, `posted_at`, `remote_id`, `permalink`, `metrics jsonb`, `error`. Unique `(asset_id, channel)`. No status is added: a cancelled post is `failed` with `error = 'cancelled'`; in-flight markers live in `error` (`container:<id>` for Meta, `inflight:<UTC timestamp>` for X and LinkedIn) while the row is `scheduled`.
- After a successful publish the asset becomes `published` (architecture 3.6 asset statuses) once every enabled target channel of `targetsFor(kind, settings)` has a `posted` row. This happens inside the SQL function `mark_social_post_posted` (Data changes), which locks the asset row, so two channels finishing at once cannot both miss the last one.
- `metrics jsonb` normalised to `{ reach, views, saves, shares, likes, comments, clicks, fetched_at, raw }`; `raw` keeps the platform's answer untouched so a renamed metric loses nothing. Per channel: Instagram from Graph insights; X from the post's `public_metrics` (impressions only where the tier returns them, UNPROVEN) mapped to views, likes, shares (reposts), comments (replies); LinkedIn from the organisation share statistics (impressions, clicks, likes, comments, shares; UNPROVEN which are available to our app). Fields a channel does not return stay null, never zero.
- Rows in `campaign_reports` (sketch columns: `campaign_id, period_start, period_end, impressions, reach, clicks, video_views, ctr, geography, channel_mix, owned_distribution, top_creative`), one per campaign per ISO week, filled by `buildCampaignReport`; this slice's migration adds the unique constraint `(campaign_id, period_start)` (B2 creates the table without it).
- Channel health for screens 2 and 12: last post, last error, token expiry from `settings.meta.token_expires_at` (B8's `meta_token_refresh` job stores it from `GET /debug_token`; null means the token never expires) and from `settings.x` and `settings.linkedin` (`token_expires_at`, `token_checked_at`, written once a day by the reconcile job), with the days left shown and amber at 14 or fewer, red at 7 or fewer (GS-01). Served by `channelHealth(db)` behind `GET /api/admin/channels/health`, which reads `settings` and `social_posts` only. Screen 12 shows it in `ChannelCards.tsx`; screen 2 shows it in `src/admin/dashboard/ChannelHealthTile.tsx` (Files).
- The token itself comes from `getMetaToken(db)` (`src/server/channels/meta-token.ts`): the Vault secret `meta_page_token` when B8's refresh job has written one, otherwise the `META_PAGE_TOKEN` env secret. The Graph client never reads the env directly.

Invariants
1. Each platform API is called only from its own step (`post_meta`, `post_x`, `post_linkedin`) and the reconcile job, never from a request (architecture 1). The admin functions never call a platform: `refreshMetrics(postId)` enqueues the system job `reconcile` through `enqueueJob()` with params `{ post_ids: [postId] }` and key `reconcile:<post_id>:<n>` (B8 invariant 1, n = 1 plus the number of earlier `social_post.metrics_refresh` audit rows for the post) and answers 202; `channelHealth` reads `settings` and `social_posts` only. Every Graph call carries `appsecret_proof` (HMAC-SHA256 of the token with `META_APP_SECRET`).
2. Exactly-once posting, all inside `postToChannel` (`src/server/channels/post-to-channel.ts`), the one helper the three post steps share. On entry it reads the `social_posts` row: `posted` ends the step; `failed` with `cancelled` ends it with `skipped: cancelled`. The row moves to `posted` in the same transaction that stores `remote_id` (`mark_social_post_posted`). In-flight markers make a crash safe on every channel: Meta stores `container:<id>` in `social_posts.error` as soon as the container exists; X and LinkedIn store `inflight:<UTC timestamp>` just before the create call. A run that finds either marker first calls the adapter's `findRecentPost(caption, since = scheduled_at)` (Meta `GET /{ig-user-id}/media?fields=caption,timestamp,permalink`, X `GET https://api.x.com/2/users/:id/tweets?start_time=`, LinkedIn `GET https://api.linkedin.com/rest/posts?q=author&author=<organization_urn>`) and adopts a match by caption as `posted`; only when nothing matches does it publish (Meta publishes the stored container with `media_publish`, the others post again). Because B8 retries a thrown job after 30 seconds, this lookup happens on the retry itself, not a day later; the reconcile job runs the same lookup for a marker older than one hour. Across revisions: a re-render is a new asset row (B9), so `postToChannel` also fails the row with `revision_already_posted` when another asset with the same `(property_id, kind)` already has a `posted` row on this channel; a deliberate repost is Retry on screen 12 with `force: true`, which skips this check and is audited.
3. Outside the posting window the step returns `{ status: "retry_at", at: <next slot> }` (B8 invariant 3: no attempt consumed). The asset stays approved, the row stays `scheduled` with `scheduled_at`. `nextWindowSlot(now, window)` is a pure function that respects `tz` and daylight-saving changes and the `daily_cap`.
4. Approval modes (S23, architecture 6). The mode comes from B8b's `effectiveApprovalMode(settings, tier, today)` in `src/domain/automation.ts` (imported, never reimplemented; a null `auto_after` means manual). Because `approval_mode` lives on each channel row and an asset is approved once, an asset counts as `auto` only when the function returns `auto` for every enabled target channel of `targetsFor(kind, settings)`. `mayApprove(actor, tier, channelRows, today)` returns true for humans and, for `actor_kind = agent`, only in that case; B9's `approveAsset` calls it (403 `human_approval_required` otherwise). B9's SQL `approve_asset` is unchanged. `postToChannel` re-checks on every run: when the asset's `approved_by` is null or belongs to a `user_roles` row with `actor_kind = agent`, and `effectiveApprovalMode` for this channel is not `auto`, the row becomes `failed` with `human_approval_required` and nothing is posted. Seeds: B8b's (`Feature: "auto"`, `Reach` and `Campaign` `manual`, `auto_after` null, which `effectiveApprovalMode` reads as manual everywhere); this slice does not touch `approval_mode`. Launch (L1) sets every tier `manual` and `auto_after` to launch date plus 60 days; on day 60 a human sets `Feature = auto` on screen 20 if the approval record is clean (L1 iterate loop 5); `Reach` and `Campaign` stay `manual` (ASSUMED: S23 names only Feature and Campaign, Reach is treated like Campaign). Auto approval has no actor row: `maybeAutoApprove(db, assetId, now)` (`src/server/channels/auto-approve.ts`) calls the SQL function `auto_approve_asset` (Data changes), which calls B9's `approve_asset` with a null actor and `actor_kind = 'agent'` (so B9's function stays the only writer of `approved_by` and `approved_at`) and writes the audit row `asset.auto_approve` (`actor_id = null`, `actor_kind = 'agent'`, `note = 'system'`, the B3b and B5 convention) in the same transaction; it then emits `asset.approved` like B9's `approveAsset`. B7's agent daily cap counts only `submission.decline` and `submission.accept` rows, so auto approvals do not consume it.
4a. What starts an auto approval: the last line of B9's `onResult` in `render-cover.ts`, `render-carousel.ts`, `render-story.ts` and of `write-captions.ts` calls `maybeAutoApprove` for the asset it just updated (one line each, listed under Change). It approves only when the asset is `pending`, `files`, `caption` and `alt_text` are set (the same rule as B9's `assets_approve_guard`), `meta.caption_lint` is not `failed`, the kind has at least one enabled target channel, and the mode is `auto` as defined in invariant 4; otherwise it returns `not_eligible` with the reason (`not_pending`, `incomplete`, `lint_failed`, `no_target`, `tier_manual`) and changes nothing. A second call for an approved asset does nothing. Reels are Campaign tier only (S24) and Campaign never goes automatic, so `render-reel.ts` (B12) needs no call.
3a. Failures inside the window (GG-04). A retryable Graph error (classes `retryable` and `retry_at` of `meta-errors.ts`) is retried inside the current window while it lasts: the step throws a retryable error and B8's backoff (30 s, 1 minute, 2 minutes, ...) runs the job again. `planRetry(now, window, alreadyPostedToday, attempt, maxAttempts)` in `window.ts` (pure, zone and daylight-saving aware) decides per failure: if the next backoff time still falls inside the window and the daily cap has room, retry there; otherwise, or on the last attempt, the step returns `{ status: "retry_at", at: <next window slot>, reason: "window_moved" }` so the job is not dead-lettered and no attempt is consumed. Each move writes an `audit_log` row `social_post.rescheduled` with a note ("Instagram answered with a temporary error, moved to Tue 09:00 PT"), which screen 12 shows under the row through `entityTimeline`; `scheduled_at` is updated. After 3 moves for the same post (count of those audit rows, ASSUMED limit) the row becomes `failed` with the last error, red on screen 12 with Retry, and `notify_admin` is enqueued once. `non_retryable` errors and `token_dead` never move: they fail at once (invariant 3b).
3b. Every failure is visible: a failed row shows red on screen 12 with Retry; a token error (Graph code 190) also turns channel health red on screens 2 and 12 and sends `notify_admin`.
5. Only public HTTPS URLs are given to Meta. Meta downloads the media itself from `mediaUrl(key)` (B3, prefix `MEDIA_BASE_URL`); the URL must answer 200 without redirects or hotlink rules, and the object must be immutable. X and LinkedIn are different: the step fetches the variant with `fetch(mediaUrl(key))` and uploads the bytes (X media upload, LinkedIn image upload) before the post call. R2 is one switch held by the operator and it is off (S50, E8, F18): there is no bucket and no `MEDIA_BASE_URL`, so no real post can happen yet. Any step that needs R2 reads it through `src/server/lib/r2.ts` (created by B3, tolerant of missing `R2_*` secrets); B10 defines no second R2 client or error. Failure path while R2 is off: after the dry-run branch (`SOCIAL_DRY_RUN` is checked first, so the rehearsal still logs its payloads) and before any platform call, when `r2Configured(env)` is false or `MEDIA_BASE_URL` is unset the step writes `social_posts.error = 'r2_unavailable'` and `scheduled_at = now + 24 h`, keeps the row `scheduled` and returns `{ status: "retry_at", at: now + 24 h, reason: "r2_unavailable" }` (B8 invariant 3: no attempt consumed, the job is never dead-lettered for it). Every test below uses mocked fetch and fixture bytes, and the real posts (steps 7 to 7b) are BLOCKED on that switch.
6. Free tier: no scheduler subscription, no paid platform product. Instagram publishing is free for our own accounts. X write limits on the free tier and LinkedIn's posting limits are UNPROVEN until step 3a and 3b measure them; if X free tier cannot post at our volume (2 a day), that is a decision for PROJECT-STATE, not a silent paid plan (G-011).
7. Disabled blocks. `facebook` and `youtube` rows are seeded `enabled=false`. A step or adapter asked to publish on a disabled channel writes nothing and returns `skipped_disabled`. Facebook is served by `meta.ts` (the Page path stays in the file behind `channel_settings.facebook.enabled`); `youtube.ts` is an interface only.
8. Takedown wins. `postToChannel` re-reads `properties.editorial_state` on every run; when it is not `published` the row becomes `failed` with `property_unpublished` and nothing is posted. B7's takedown already cancels queued `post_meta` jobs; this rule covers a job that is running, sleeping on `retry_at`, or for `post_x` and `post_linkedin`.
9. Enabling a social channel needs proof of credentials. `assertMayEnable(db, channel)` (`src/server/channels/enable-guard.ts`) runs inside B8b's `putChannelSettings` when `enabled` goes from false to true: `instagram` and `facebook` need `settings.meta.page_id` and `ig_user_id` and a `settings.meta.token_checked_at` within the last 48 hours (written by B8's `meta_token_refresh`); `x` needs `settings.x.user_id` and `settings.x.token_checked_at` within 48 hours; `linkedin` needs `settings.linkedin.organization_urn` and `settings.linkedin.token_checked_at` within 48 hours (both written by the `--check` mode of the authorize scripts and by the reconcile job); otherwise 422 `credentials_unverified` with the missing item named. `youtube` is always 422 `no_adapter`.

Events emitted: none new (`asset.approved` and `asset.rejected` are B9's). Publishing state is `social_posts`, not an event (same reasoning as B8: no 15th event type).

## Risks and gotchas (link GOTCHAS ids)
- G-006: `META_*` server side only; G-011: no scheduler, no paid Meta product; P-009: reconcile adds one Edge call a day, negligible.
- Free tier and Meta limits: Instagram content publishing has a rolling 24-hour cap per account (the number, currently believed 100, is UNPROVEN and is read live from `content_publishing_limit`); our own cap of 2 per channel per day sits far below it. Graph app-level and business-use-case throttles come back as codes 4, 17, 32, 613 and 80002 and must map to `retry_at`, never to `failed`.
- Meta fetches images itself. Instagram rejects some hosts and any URL that redirects or is slow; test the real `mediaUrl(key)` URL (prefix `MEDIA_BASE_URL`) in step 7 (BLOCKED while R2 is off, E8). If R2 public access is blocked by a Cloudflare rule (bot fight mode, hotlink protection) the container fails with a media error that looks like a Meta bug.
- Carousels: images must share one aspect ratio (Instagram crops to the first); B9 produces 1080×1350 for every slide for that reason.
- Instagram rules for Stories: image stories are 9:16, 1080×1920; a story is not a feed post and does not show in the grid; metrics for stories are only available for a limited window, hence the 20-hour pull.
- Insights metrics were renamed and removed several times (impressions and others). Behaviour depends on the app's Graph version and post type; the mapping file plus stored `raw` is the guard. UNPROVEN until step 3.
- Instagram Login versus Facebook Login: this plan uses Facebook Login because one Page token covers Instagram and the later Facebook block. If Meta forces the Instagram-Login variant, tokens differ (per Instagram account, 60-day, refreshable) and `health()` must refresh them; the interface does not change.
- X (UNPROVEN): the free tier's write limits and whether media upload is included are measured in step 3a, not assumed; the API's pricing and tiers have changed more than once, so re-read them on the day. Access tokens are short-lived (about two hours, UNPROVEN), so `getChannelToken` refreshes on demand before a post and stores the new refresh token in Vault each time, under the lease, because a rotated refresh token used twice is refused (a lost refresh token means a manual re-consent with `scripts/x-authorize.ts`). The daily `checkChannelToken` writes `settings.x` once a day; every `settings` write bumps `catalog_version` (B2 trigger), so token values themselves never go to `settings`, only Vault.
- LinkedIn (UNPROVEN): product approval is the schedule risk, and a rejected application would leave two live channels. Posting versions are dated headers that expire after about a year, so `settings.linkedin.api_version` is pinned and checked by the reconcile job. Image posts need the upload step first; plain text or link posts are the fallback if multi-image is not available.
- Tone differs per channel: the X caption is short and the LinkedIn caption longer and aimed at agents and brokerages, both under the brand voice rules (B9 `write_captions`); neither claims leads or sales.
- GG-04: a moved post keeps its approval and its place in `social_posts`; it is never re-created, so the exactly-once rule (invariant 2) still holds. The 3-move limit is ASSUMED; a channel that fails for a day should turn red, not silently slide.
- GS-01: token expiry is owned by B8's `meta_token_refresh` job; this slice only reads its result and raises the screen state. If the owner uses the System User route (step 2), that token does not expire and `token_expires_at` stays null; the health card then shows "never" and the job only checks that the token is still valid. Until the owner finishes step 1 the job is `skipped: not_configured` and the health card says "not connected".
- Development-mode limits: the app works only for roles on the app. If ever the app must act for a client's account (it will not, no client posting in v1), Advanced access is required.
- P-008 style trap in tests: never type a JSON payload with backslashes inline in Bash; use files.
- Supabase free projects pause after 7 idle days; a paused project stops the runner and therefore posting. B8b's `keepwarm` covers it.
