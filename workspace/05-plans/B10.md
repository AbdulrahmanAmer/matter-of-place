Invariants
1. Each platform API is called only from its own step (`post_meta`, `post_x`, `post_linkedin`) and the reconcile job, never from a request (architecture 1). Every Graph call carries `appsecret_proof` (HMAC-SHA256 of the token with `META_APP_SECRET`).
2. Exactly-once posting: before calling Meta the step reads `social_posts`; a row already `posted` ends the step. The row moves to `posted` in the same transaction that stores `remote_id`. If the process dies between `media_publish` and the database write, the reconcile job looks for the post by caption and time before any retry, and the container id is stored as soon as it exists (`social_posts.error` holds `container:<id>` while in flight, ASSUMED convention), so a retry resumes instead of posting twice.
3. Outside the posting window the step returns `{ status: "retry_at", at: <next slot> }` (B8 invariant 3: no attempt consumed). The asset stays approved, the row stays `scheduled` with `scheduled_at`. `nextWindowSlot(now, window)` is a pure function that respects `tz` and daylight-saving changes and the `daily_cap`.
4. Approval modes (S23, architecture 6). `approve_asset` refuses an approval by an actor with `actor_kind = agent` unless `approval_mode[tier] = "auto"` and `now >= auto_after`. Each post step re-checks this and marks the row `failed` with `human_approval_required` if it is violated. Seeds: all tiers `manual`, `auto_after` null. Launch (L1) sets `auto_after` to launch date plus 60 days and `Feature = auto`; `Reach` and `Campaign` stay `manual` (ASSUMED: S23 names only Feature and Campaign, Reach is treated like Campaign). Auto approval is performed by a seeded system actor (ASSUMED `user_roles` row, `actor_kind = agent`, role `media_ops`, display name "Auto approval") and audited as `asset.auto_approve`.
3a. Failures inside the window (GG-04). A retryable Graph error (classes `retryable` and `retry_at` of `meta-errors.ts`) is retried inside the current window while it lasts: the step throws a retryable error and B8's backoff (30 s, 1 minute, 2 minutes, ...) runs the job again. `planRetry(now, window, alreadyPostedToday, attempt, maxAttempts)` in `window.ts` (pure, zone and daylight-saving aware) decides per failure: if the next backoff time still falls inside the window and the daily cap has room, retry there; otherwise, or on the last attempt, the step returns `{ status: "retry_at", at: <next window slot>, reason: "window_moved" }` so the job is not dead-lettered and no attempt is consumed. Each move writes an `audit_log` row `social_post.rescheduled` with a note ("Instagram answered with a temporary error, moved to Tue 09:00 PT"), which screen 12 shows under the row through `entityTimeline`; `scheduled_at` is updated. After 3 moves for the same post (count of those audit rows, ASSUMED limit) the row becomes `failed` with the last error, red on screen 12 with Retry, and `notify_admin` is enqueued once. `non_retryable` errors and `token_dead` never move: they fail at once (invariant 3b).
3b. Every failure is visible: a failed row shows red on screen 12 with Retry; a token error (Graph code 190) also turns channel health red on screens 2 and 12 and sends `notify_admin`.
5. Only public HTTPS URLs are given to Meta. Meta downloads the media itself from `R2_PUBLIC_BASE`; the URL must answer 200 without redirects or hotlink rules, and the object must be immutable. X and LinkedIn are different: the step downloads the variant from R2 and uploads the bytes (X media upload, LinkedIn image upload) before the post call. R2 is one switch held by the operator and it is off (S50, E8, F18): there is no bucket and no `R2_PUBLIC_BASE`, so no real post can happen yet. Any step that needs R2 reads it through `src/server/lib/r2.ts` (created by B3, tolerant of missing `R2_*` secrets) and, while R2 is unavailable, ends with the shared `r2_unavailable` error, writes no post and leaves the row `scheduled`; B10 defines no second R2 client or error; every test below uses mocked fetch and fixture bytes, and the real posts (steps 7 to 7b) are BLOCKED on that switch.
6. Free tier: no scheduler subscription, no paid platform product. Instagram publishing is free for our own accounts. X write limits on the free tier and LinkedIn's posting limits are UNPROVEN until step 3a and 3b measure them; if X free tier cannot post at our volume (2 a day), that is a decision for PROJECT-STATE, not a silent paid plan (G-011).
7. Disabled blocks. `facebook` and `youtube` rows are seeded `enabled=false`. A step or adapter asked to publish on a disabled channel writes nothing and returns `skipped_disabled`. Facebook is served by `meta.ts` (the Page path stays in the file behind `channel_settings.facebook.enabled`); `youtube.ts` is an interface only.

Events emitted: none new (`asset.approved` and `asset.rejected` are B9's). Publishing state is `social_posts`, not an event (same reasoning as B8: no 15th event type).

## Risks and gotchas (link GOTCHAS ids)
- G-006: `META_*` server side only; G-011: no scheduler, no paid Meta product; P-009: reconcile adds one Edge call a day, negligible.
- Free tier and Meta limits: Instagram content publishing has a rolling 24-hour cap per account (the number, currently believed 100, is UNPROVEN and is read live from `content_publishing_limit`); our own cap of 2 per channel per day sits far below it. Graph app-level and business-use-case throttles come back as codes 4, 17, 32, 613 and 80002 and must map to `retry_at`, never to `failed`.
- Meta fetches images itself. Instagram rejects some hosts and any URL that redirects or is slow; test the real `R2_PUBLIC_BASE` URL in step 7 (BLOCKED while R2 is off, E8). If R2 public access is blocked by a Cloudflare rule (bot fight mode, hotlink protection) the container fails with a media error that looks like a Meta bug.
- Carousels: images must share one aspect ratio (Instagram crops to the first); B9 produces 1080×1350 for every slide for that reason.
- Instagram rules for Stories: image stories are 9:16, 1080×1920; a story is not a feed post and does not show in the grid; metrics for stories are only available for a limited window, hence the 20-hour pull.
- Insights metrics were renamed and removed several times (impressions and others). Behaviour depends on the app's Graph version and post type; the mapping file plus stored `raw` is the guard. UNPROVEN until step 3.
- Instagram Login versus Facebook Login: this plan uses Facebook Login because one Page token covers Instagram and the later Facebook block. If Meta forces the Instagram-Login variant, tokens differ (per Instagram account, 60-day, refreshable) and `health()` must refresh them; the interface does not change.
- X (UNPROVEN): the free tier's write limits and whether media upload is included are measured in step 3a, not assumed; the API's pricing and tiers have changed more than once, so re-read them on the day. Access tokens are short-lived, so the refresh job must run before the first post of the day and store the new refresh token each time (a lost refresh token means a manual re-consent).
- LinkedIn (UNPROVEN): product approval is the schedule risk, and a rejected application would leave two live channels. Posting versions are dated headers that expire after about a year, so `settings.linkedin.api_version` is pinned and checked by the reconcile job. Image posts need the upload step first; plain text or link posts are the fallback if multi-image is not available.
- Tone differs per channel: the X caption is short and the LinkedIn caption longer and aimed at agents and brokerages, both under the brand voice rules (B9 `write_captions`); neither claims leads or sales.
- GG-04: a moved post keeps its approval and its place in `social_posts`; it is never re-created, so the exactly-once rule (invariant 2) still holds. The 3-move limit is ASSUMED; a channel that fails for a day should turn red, not silently slide.
- GS-01: token expiry is owned by B8's `meta_token_refresh` job; this slice only reads its result and raises the screen state. If the owner uses the System User route (step 2), that token does not expire and `token_expires_at` stays null; the health card then shows "never" and the job only checks that the token is still valid. Until the owner finishes step 1 the job is `skipped: not_configured` and the health card says "not connected".
- Development-mode limits: the app works only for roles on the app. If ever the app must act for a client's account (it will not, no client posting in v1), Advanced access is required.
- P-008 style trap in tests: never type a JSON payload with backslashes inline in Bash; use files.
- Supabase free projects pause after 7 idle days; a paused project stops the runner and therefore posting. B8b's `keepwarm` covers it.
