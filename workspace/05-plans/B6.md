## Goal and observed exit
Money is a box with two doors (tech-stack 2, S32): acceptance never depends on payment, activation does. An accepted submission gets one numbered invoice from `/admin`, a PDF made in the job runner with `pdf-lib`, emailed to the submitter (an agent or an owner, B2 invariant 22) through the seeded recipe; an admin marks it paid (or waives it) and activates the submission, which moves it to `Scheduled` and creates the property draft. Stripe can later write the same row through the same functions (S14 is superseded by S32 for launch).
Observed exit (completion map B6): "an admin issues an invoice and activates a test submission". Proven as `E2E_TARGET=dev bunx playwright test --project admin tests/e2e/admin-invoice.spec.ts` against the dev server wired to `mop-dev` (no Docker, S50): an accepted test request gets the next invoice number (the spec reads `invoice_counters.last` for the current UTC year before issuing and expects `MOP-<year>-<last + 1, four digits>`, because `mop-dev` is shared and earlier runs have used numbers), mark paid then activate leaves the submission `Scheduled` with a property draft, and issuing on an unaccepted request is refused at the UI, the server function and the database. The PDF object in the private Supabase Storage bucket `documents` is asserted today (ruling H33 (1)). One assertion depends on something that does not exist today and is BLOCKED until it does: the email with the PDF at a test inbox (it waits on B5 step 5 setting `EMAIL_LIVE=1` on the `mop-dev` runner; the Resend account, key and domains exist, ASSUMED E17, E18); until then every send on `mop-dev` is a dry run (B5 invariant 16) and the proof is the `email_messages` row `invoice` `skipped` with a `dry_` id (G14).

Acceptance before invoice, in three layers: the button is disabled in the UI; the server function refuses with 409 `not_accepted`; B2's trigger `enforce_editorial_gate` (migration `20261001090700_editorial_gate.sql`) raises for `Invoice Issued` and later states when `accepted_at` is null, and for `Scheduled` and later when no `payments` row for the submission has status `paid` or `waived` (architecture 3.4). B2's transition graph is mirrored in `src/domain/workflow.ts` (`canTransition`), which the service uses.
2. One live payment per submission: partial unique index on `payments(submission_id) where status in ('due','paid','waived')`.
3. Every state change is one SQL function (`issue_invoice`, `mark_payment_paid`, `waive_payment`, `record_waiver`, `void_payment`, `activate_submission`) that updates the row, writes `audit_log` through `write_audit` with the action ids listed under Outputs and calls `emit_event` in the same transaction (supabase-js has no multi-statement transactions; the TS server function does actor, authz, Zod and then one RPC). `payments.status` moves only from `due` to `paid` (`mark_payment_paid`), `waived` (`waive_payment`) or `void` (`void_payment`), and `record_waiver` inserts a row that is `waived` from the start; each function takes the row `for update` and raises `wrong_state` (409 through B7's `fromRpcError`, which already maps it) for any other starting status, so mark paid on `void` or `waived`, waive on `paid` and void on `paid` or `waived` all fail; `refunded` is not reachable in this slice. `mark_payment_paid` raises `paid_at_future` when `p_paid_at > now()`, and `markPaidInput` refuses a future `paid_at` with 422 before the RPC (the TS check runs first, so the SQL raise is the backstop). `issue_invoice` raises `wrong_state` from `Invoice Issued` while a live payment exists. The table lives once in `src/domain/payments.ts` as `paymentTransitions`.
4. The invoice number is assigned in the issuing transaction and never changes. A rolled-back issue consumes no number.
5. The invoice is frozen: the PDF is rendered from `payments.invoice_snapshot`, not from live settings.
6. Nothing external in a request: `issue_invoice` inserts the rows and enqueues the `invoice_pdf` job in its own transaction (`perform enqueue_job('invoice_pdf', jsonb_build_object('params', '{}'::jsonb, 'data', jsonb_build_object('payment_id', <id>)), 'invoice_pdf:' || <id>, p_max_attempts => 12)`, B8's function and job envelope; the named `p_max_attempts` matches the registry's `maxAttempts: 12`, DL-10), so a committed invoice always has its PDF job and a rolled-back one has none; the service never calls `enqueueJob` itself. Activation copies no photograph inside the request (E2E-02, PERF-07: the free Worker allows 50 subrequests per invocation and a request may carry 40 photographs): `activate_submission` reaches B7's `create_property_from_submission`, which enqueues the one light system job `copy_submission_media` (key `copy_submission_media:<property_id>`) in the same transaction, so `activate` makes a constant number of subrequests whatever the photo count. The runner renders, uploads, copies and emails. `service.test.ts` runs every action with a `fetch` stub that throws, so any outside call from a request fails the test.
7. Issuing requires readiness: `settings.site` has `legal.entity`, `legal.address` and `contact.email`, and `settings.invoice.payment_methods` has at least one method with non-empty instructions. Also `settings.invoice.terms`, `late_terms` and `tax_line` must be non-empty (seeded, so this fails only if someone blanks them). Otherwise 409 `invoice_not_ready` with the missing list, and the screen shows it (no invented address, S33).
8. Issuing is allowed from `Accepted`, and from `Invoice Issued` only when no live payment exists (after a void). Activation requires status `paid` or `waived`, submission state `Invoice Issued`. Its first statement is `perform 1 from public.submissions where id = p_submission_id for update` (DL-02), so a double click, a network retry, or Activate on screen 6 while Create property runs on screen 4 serialise on the submission and the second call sees the committed row; B2's unique index `properties_submission_id_key` and constraint `campaigns_payment_id_key` are the backstop, and their 23505 answers 409 `already_exists` through `fromRpcError`. Print (GQ-06): the admin invoice pages print cleanly on US Letter. `src/styles/admin/invoices.css` has an `@media print` block that hides every admin shell element marked `data-print="hide"` (the attribute B7 step 3 puts on the shell, top bar and navigation, proven by B7's `admin-nav.test.ts`; B6 marks its own toolbars and dialog buttons with it), shows the preview at full width in `--foreground` on `--background` with no shadows or fixed positioning, sets `@page { size: letter; margin: 0.75in; }` (literal lengths, because `@page` cannot read custom properties; ASSUMED acceptable under G-007 since no colour is involved), and keeps the invoice block on one page (`break-inside: avoid`). 12. A waiver needs no invoice (DL-01). A Five Features credit or a comp is recorded by `record_waiver(p_submission_id uuid, p_product exposure_package, p_amount numeric, p_reason text, p_actor uuid, p_actor_kind actor_kind, p_request_id text)`, never by issuing and then waiving an invoice, which would mail the submitter a numbered bill they do not owe. It locks the submission `for update`, requires state `Accepted`, or `Invoice Issued` with no live payment, inserts one `payments` row with `status = 'waived'`, `method = 'invoice_manual'`, `invoice_number` null, `invoice_snapshot` null, `due_at` null, `amount = p_amount` (the service passes `priceFor(product)`, kept for reporting, so `payments_amount_positive` holds), `waived_by = p_actor` and `notes = p_reason`, moves the submission to `Invoice Issued` (so `activate_submission` works unchanged and the partial unique index of invariant 2 still holds), writes the audit row `payments.waive` and emits `payment.marked` with `{ submission_id, payment_id, status: "waived", amount, tier, invoiced: false }` (an existing catalog type whose seeded recipe only notifies admins). It never emits `invoice.issued`, never enqueues `invoice_pdf` and never touches `invoice_counters`. The check `payments_number_unless_waived check (invoice_number is not null or status = 'waived')` keeps every other row numbered. Spending a Five Features credit is this function with reason "Five Features credit" (ruling H18).
13. Campaign windows are data (DL-09, ruling H17). `settings.invoice.campaign_days` maps each product of `exposure_package` except `Not sure yet` to a whole number of days or null, edited in screen 24's Invoicing section through `settings_put_invoice` like every other invoice setting. The seed states only what the exposure page states (`src/data/exposure.ts`: The Campaign, "A 10 to 14 day campaign window"): `{ "The Feature": null, "The Reach": null, "The Campaign": 14, "Five Features": null }`. A null window means the campaign completes 30 days after publication (G22, G60). SQL `package_duration_days(p_product exposure_package) returns int` (`language sql stable`, `set search_path = ''`, reads `settings.invoice->'campaign_days'->>p_product::text`) is the one reader; B7's `publish_property` calls it on the first publication to set `campaigns.starts_on` and `ends_on`. No window is written in code. The ASSUMED section C entry for the operator (which windows the other products have) is the orchestrator's.

Void (ASSUMED A3): an invoice issued in error is voided with a reason (3 to 500 characters, stored in `notes`), `status` becomes `void`, the number is never reused and the PDF stays in the `documents` bucket. A void row is outside the partial unique index of invariant 2, so a corrected invoice can then be issued for the same submission, which stays in `Invoice Issued` until the new invoice is issued and then continues as normal. Only `admin`, human only; a `paid` or `waived` payment cannot be voided. Waive: needs a reason (3 to 500 characters, stored in `notes`); a `due` invoice issued by mistake to a credit holder is waived with `waive_payment`, and every new credit or comp is recorded without an invoice by `record_waiver` (invariant 12). A later property from an agent who bought Five Features is recorded with reason "Five Features credit" (S3, exposure terms: declined properties do not use a credit, and a declined property never reaches a waiver). A void is also how B7's `withdraw_submission` closes a `due` invoice of a withdrawn request (reason `withdrawn`, DL-04).

## Risks and gotchas (link GOTCHAS ids)
- G-004: `payments` columns, `src/domain/payments.ts` and the API JSON are one shape; the added columns are spec changes to architecture 3.4.
- G-005: the pricing reader in `src/server` is the second allowed importer of `src/data/exposure.ts`; routes and admin components still never import it and get the amount from the API.
- G-006 and G-011: no new secret and no `VITE_*` name; the runner and the Worker reach the `documents` bucket with the service-role key they already hold. A one-page PDF is tens of kilobytes, a small part of the free 1 GB of Storage that the three buckets share (P-009, ruling H33 (8)); no paid service added (`pdf-lib` is a library).
- P-038: no Docker on the laptop; every database proof here runs through `DEV_DB_URL`, the one connection name (F6, F22): in CI it is the `db` job's ephemeral stack on the GitHub-hosted runner, after the merge it is `mop-dev` (ruling H1). `mop-dev` is the one database and becomes production at the launch switch (ruling H35): from then on these tests, `invoice-smoke.ts`, `set-invoice.ts` and the committed spec run only on the CI stack, and the scripts refuse the cloud database through `assertNotProduction`.
- F22: the database tests roll back, except the parallel invoice-number test, which is committed on purpose (two connections) and must clean up in its `committed` callback; because it writes to `mop-dev`, it takes the G34 advisory lock through `committed` when it runs against `mop-dev`; in CI it runs on the `db` job's own ephemeral stack (ruling H1, G34, F22). `admin-invoice.spec.ts` commits rows and flips `settings.site` and `settings.invoice`, so it holds the same lock through `holdDevLock()` from `beforeAll` to the end of `afterAll`; `invoice-smoke.ts` takes it on its own connection.
- P-009: a PDF render is well under a second of Edge Function time; the Worker never renders (10 ms CPU per request on the free plan), which is why the `pdf` route only answers a redirect to a signed URL.
- Void is settled (ASSUMED A3): the `void` status and an admin-only human-only action exist in this slice; architecture 3.4 and 4.2 already list them, and G26 rules that admin-screens screen 6 gains Void (admin only, reason required) and the state `void`. B2's `submission_transition_allowed` permits `Invoice Issued` to `Invoice Issued` (reissue after void, F16; B2 owns the function and this slice does not redefine it); the void db test checks it.
- Numbering and tax: sequential numbers are provided; sales tax on media services and invoice content rules depend on the entity and state and belong to the CEO's accountant. Taxes are not computed. UNPROVEN legally.
- GP-06: the default `tax_line` and `late_terms` are ASSUMED wording chosen to claim nothing (no tax rate, no late fee rate). They are configuration, editable through `set-invoice.ts` and screen 24, and lawyer review of the final text is a HARDEN gate. An invoice already issued keeps its frozen text, so a later edit never changes an old invoice.
- GQ-06: `@page` margins are literal lengths because custom properties do not resolve there, the one place a literal dimension appears in admin CSS; no colour is involved, so the token rule holds for colour. The printed preview is HTML rendered by the browser and can differ from the PDF; the PDF is the record. Browsers add their own header and footer text to printed pages unless the user turns it off; nothing here can prevent that.
- GQ-06 and B7: `data-print="hide"` is the attribute B7 step 3 puts on the shell, top bar and navigation (B7's `admin-nav.test.ts` asserts it); `invoices.css` and `print-css.test.ts` use that name, and B6 lands after B7 step 3.
- `npm:pdf-lib@1.17.1` imports and runs in the Edge runtime (measured, E5). Rendering this invoice with standard fonts in that runtime is UNPROVEN until step 5's `--upload` run stores a PDF made by the runner; the local render proves the layout and fonts under Node. Standard fonts have no glyphs beyond WinAnsi: a submitter name with characters outside it would throw; `sanitizeWinAnsi` replaces them as described under Files and logs (ASSUMED behaviour, tested in step 5 with `Zoë Łukasz 王`).
- Invoices live in Supabase Storage (ruling H33 (1)): the PDF lives in B2's private bucket `documents`, written by the runner and read by the Worker through supabase-js with the service role; there is no Worker binding, so `wrangler.toml` does not change, and it is never served on `/media/<key>`. Storage objects are not backed up (ruling H33 (7)): H1's restore path renders a lost PDF again from its `payments` row through the `invoice_pdf` job, and the frozen snapshot makes it identical. A signed URL lives 60 seconds and is minted per click, so a copied link stops working within a minute. A Storage outage makes `invoice_pdf` jobs and invoice emails retry with B8's backoff and go `dead` after five attempts, retried from screen 16.
- The invoice email is only as fast as the runner tick (up to a minute). The toast shows `JobWatcher`; the admin can open the PDF as soon as the `invoice_pdf` job finishes.
- Disabling the `send_email(invoice)` step in B8b screen 17 stops the invoice email but not the PDF (own job). Intended.
- A Five Features credit is spent through `record_waiver` (ruling H18, invariant 12); the credit balance itself (how many of the five remain) is not specified in this slice's review rows and is not built here. Refunds and partial payments are not modelled. A refund is a manual event recorded in `notes` until a decision.
