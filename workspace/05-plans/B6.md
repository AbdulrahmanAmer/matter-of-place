## Goal and observed exit
Money is a box with two doors (tech-stack 2, S32): acceptance never depends on payment, activation does. An accepted submission gets one numbered invoice from `/admin`, a PDF made in the job runner with `pdf-lib`, emailed to the agent through the seeded recipe; an admin marks it paid (or waives it) and activates the agent, which moves the submission to `Scheduled` and creates the property draft. Stripe can later write the same row through the same functions (S14 is superseded by S32 for launch).
Observed exit (completion map B6): "an admin issues an invoice and activates a test agent". Proven as `E2E_TARGET=dev bunx playwright test --project admin tests/e2e/admin-invoice.spec.ts` against the dev server wired to `mop-dev` (no Docker, S50): an accepted test request gets the next invoice number (the spec reads `invoice_counters.last` for the current UTC year before issuing and expects `MOP-<year>-<last + 1, four digits>`, because `mop-dev` is shared and earlier runs have used numbers), mark paid then activate leaves the submission `Scheduled` with a property draft, and issuing on an unaccepted request is refused at the UI, the server function and the database. The PDF object in the private Supabase Storage bucket `invoices` is asserted today (G26: invoices need no R2). One assertion depends on something that does not exist today and is BLOCKED until it does: the email with the PDF at a test inbox (BLOCKED until a Resend account and verified sending domain exist, E9); until then `mop-dev` runs with `EMAIL_DRY_RUN=1` and the proof is the `email_messages` row `invoice` `skipped` with a `dry_` id (G14).

Architecture says "from a sequence"; a Postgres sequence leaves gaps on rollback and does not reset yearly, so the function uses `invoice_counters(year, last)` with `insert ... on conflict (year) do update set last = invoice_counters.last + 1 returning last`, inside the issuing transaction. B2 creates no sequence and no `next_invoice_number` function (B2 `20261001090600_commercial.sql`: `invoice_number` nullable, no default); this slice CREATES `next_invoice_number(p_prefix text default 'MOP')` once, with the counter table, so there is no older signature to drop or overload. `issue_invoice` passes `settings.invoice->>'prefix'`. Numbering per year is ASSUMED from the `MOP-YYYY-NNNN` format in architecture 3.4.

Invariants
1. Acceptance before invoice, in three layers: the button is disabled in the UI; the server function refuses with 409 `not_accepted`; B2's trigger `enforce_editorial_gate` (migration `20261001090700_editorial_gate.sql`) raises for `Invoice Issued` and later states when `accepted_at` is null, and for `Scheduled` and later when no `payments` row for the submission has status `paid` or `waived` (architecture 3.4). B6 does not redefine the trigger; `tests/db/payments.db.test.ts` re-asserts it through the real functions so a regression in B2 shows here. B2's transition graph is mirrored in `src/domain/workflow.ts` (`canTransition`), which the service uses.
2. One live payment per submission: partial unique index on `payments(submission_id) where status in ('due','paid','waived')`.
3. Every state change is one SQL function (`issue_invoice`, `mark_payment_paid`, `waive_payment`, `void_payment`, `activate_submission`) that updates the row, writes `audit_log` through `write_audit` with the action ids listed under Outputs and calls `emit_event` in the same transaction (supabase-js has no multi-statement transactions; the TS server function does actor, authz, Zod and then one RPC). `payments.status` moves only from `due` to `paid` (`mark_payment_paid`), `waived` (`waive_payment`) or `void` (`void_payment`); each function takes the row `for update` and raises `wrong_state` (409 through B7's `fromRpcError`, which already maps it) for any other starting status, so mark paid on `void` or `waived`, waive on `paid` and void on `paid` or `waived` all fail; `refunded` is not reachable in this slice. `mark_payment_paid` raises `paid_at_future` when `p_paid_at > now()`, and `markPaidInput` refuses a future `paid_at` with 422 before the RPC (the TS check runs first, so the SQL raise is the backstop). `issue_invoice` raises `wrong_state` from `Invoice Issued` while a live payment exists. The table lives once in `src/domain/payments.ts` as `paymentTransitions`.
4. The invoice number is assigned in the issuing transaction and never changes. A rolled-back issue consumes no number.
5. The invoice is frozen: the PDF is rendered from `payments.invoice_snapshot`, not from live settings.
6. Nothing external in a request: `issue_invoice` inserts the rows and enqueues the `invoice_pdf` job in its own transaction (`perform enqueue_job('invoice_pdf', jsonb_build_object('params', '{}'::jsonb, 'data', jsonb_build_object('payment_id', <id>)), 'invoice_pdf:' || <id>)`, B8's function and job envelope), so a committed invoice always has its PDF job and a rolled-back one has none; the service never calls `enqueueJob`. The runner renders, uploads and emails. `service.test.ts` runs every action with a `fetch` stub that throws, so any outside call from a request fails the test.
7. Issuing requires readiness: `settings.site` has `legal.entity`, `legal.address` and `contact.email`, and `settings.invoice.payment_methods` has at least one method with non-empty instructions. Also `settings.invoice.terms`, `late_terms` and `tax_line` must be non-empty (seeded, so this fails only if someone blanks them). Otherwise 409 `invoice_not_ready` with the missing list, and the screen shows it (no invented address, S33).
8. Issuing is allowed from `Accepted`, and from `Invoice Issued` only when no live payment exists (after a void). Activation requires status `paid` or `waived`, submission state `Invoice Issued`; it sets `activated_by` and `activated_at`, reads `submissions.property_id` and, when it is null, calls B7's `create_property_from_submission(p_submission_id, p_actor, p_actor_kind, p_request_id)` (which returns `{ property_id, media }` and does not itself write `submissions.property_id`) and sets `submissions.property_id` to the returned id, keeping the returned `media` list for its own result (`[]` when `submissions.property_id` was already set); it then sets `payments.property_id` on the live payment to the same id, inserts one `campaigns` row when none exists for the payment (`property_id`, `submission_id`, `payment_id`, `package` = `payments.product`, `media_budget` = `coalesce(submissions.media_budget, 0)`, `starts_on` and `ends_on` null, which B10 reads as open bounds; ASSUMED: activation is the moment a campaign starts to exist, and no other plan writes `campaigns`), and is idempotent (a second call returns the same result, no second property, no second campaign, no second event). The SQL function copies no file (Storage is not reachable from SQL): the request's photographs are copied by `activate` in `src/server/payments/service.ts` from the returned `media` list (Files).
9. Stripe is a stub interface only. Registry `adapters/index.ts` contains only `invoice_manual`; `stripe.ts` implements the interface with methods that throw `NotImplementedError` (exported by `adapters/types.ts`). When Stripe arrives it adds a webhook route that verifies the signature and calls `mark_payment_paid` with a null actor and `paid_method = 'stripe'`; the state machine and screens do not change.
10. Legal fields (GP-06, architecture 10): an issued invoice shows entity, address, invoice number, issue date, due date, description, amount, currency, a tax line, payment instructions and late terms, in the PDF and in the admin preview. The list is one constant, `requiredInvoiceFields`, in `src/domain/payments.ts`; `invoice-layout.test.ts` fails when `layoutInvoice` omits any of them for a complete snapshot, and `buildInvoiceSnapshot` throws when a required value is missing. Tax is a placeholder line only: nothing is computed, and nothing in the code names a rate.
11. Print (GQ-06): the admin invoice pages print cleanly on US Letter. `src/styles/admin/invoices.css` has an `@media print` block that hides every admin shell element marked `data-print="hide"` (the attribute B7 step 3 puts on the shell, top bar and navigation, proven by B7's `admin-nav.test.ts`; B6 marks its own toolbars and dialog buttons with it), shows the preview at full width in `--foreground` on `--background` with no shadows or fixed positioning, sets `@page { size: letter; margin: 0.75in; }` (literal lengths, because `@page` cannot read custom properties; ASSUMED acceptable under G-007 since no colour is involved), and keeps the invoice block on one page (`break-inside: avoid`). The PDF stays the official copy; printing the preview is a convenience and is labelled Preview.

Void (ASSUMED A3): an invoice issued in error is voided with a reason (3 to 500 characters, stored in `notes`), `status` becomes `void`, the number is never reused and the PDF stays in the `invoices` bucket. A void row is outside the partial unique index of invariant 2, so a corrected invoice can then be issued for the same submission, which stays in `Invoice Issued` until the new invoice is issued and then continues as normal. Only `admin`, human only; a `paid` or `waived` payment cannot be voided. Waive: needs a reason (3 to 500 characters, stored in `notes`). ASSUMED use for Five Features credits: the credit balance is not tracked in v1; a later property from an agent who bought Five Features is waived with reason "Five Features credit" (S3, exposure terms: declined properties do not use a credit, and a declined property never reaches an invoice).

## Risks and gotchas (link GOTCHAS ids)
- G-004: `payments` columns, `src/domain/payments.ts` and the API JSON are one shape; the added columns are spec changes to architecture 3.4.
- G-005: the pricing reader in `src/server` is the second allowed importer of `src/data/exposure.ts`; routes and admin components still never import it and get the amount from the API.
- G-006 and G-011: no new secret and no `VITE_*` name; the runner and the Worker reach the `invoices` bucket with the service-role key they already hold. A one-page PDF is tens of kilobytes, inside Supabase's free 1 GB of storage (P-009); no paid service added (`pdf-lib` is a library).
- P-038: no Docker; every database proof here runs on `mop-dev` through `DEV_DB_URL`, the one connection name (F6, F22).
- F22: the database tests roll back, except the parallel invoice-number test, which is committed on purpose (two connections) and must clean up in its `committed` callback; because it writes to `mop-dev`, it takes the G34 advisory lock through `committed` locally and shares CI's one `mop-dev` concurrency group with the slices that run beside it (G34, F22). `admin-invoice.spec.ts` commits rows and flips `settings.site` and `settings.invoice`, so it holds the same lock through `holdDevLock()` from `beforeAll` to the end of `afterAll`; `invoice-smoke.ts` takes it on its own connection.
- P-009: a PDF render is well under a second of Edge Function time; the Worker never renders (10 ms CPU per request on the free plan), which is why the `pdf` route only answers a redirect to a signed URL.
- Void is settled (ASSUMED A3): the `void` status and an admin-only human-only action exist in this slice; architecture 3.4 and 4.2 already list them, and G26 rules that admin-screens screen 6 gains Void (admin only, reason required) and the state `void`. B2's `submission_transition_allowed` permits `Invoice Issued` to `Invoice Issued` (reissue after void, F16; B2 owns the function and this slice does not redefine it); the void db test checks it.
- Numbering and tax: sequential numbers are provided; sales tax on media services and invoice content rules depend on the entity and state and belong to the CEO's accountant. Taxes are not computed. UNPROVEN legally.
- GP-06: the default `tax_line` and `late_terms` are ASSUMED wording chosen to claim nothing (no tax rate, no late fee rate). They are configuration, editable through `set-invoice.ts` and screen 24, and lawyer review of the final text is a HARDEN gate. An invoice already issued keeps its frozen text, so a later edit never changes an old invoice.
- GQ-06: `@page` margins are literal lengths because custom properties do not resolve there, the one place a literal dimension appears in admin CSS; no colour is involved, so the token rule holds for colour. The printed preview is HTML rendered by the browser and can differ from the PDF; the PDF is the record. Browsers add their own header and footer text to printed pages unless the user turns it off; nothing here can prevent that.
- GQ-06 and B7: `data-print="hide"` is the attribute B7 step 3 puts on the shell, top bar and navigation (B7's `admin-nav.test.ts` asserts it); `invoices.css` and `print-css.test.ts` use that name, and B6 lands after B7 step 3.
- `npm:pdf-lib@1.17.1` imports and runs in the Edge runtime (measured, E5). Rendering this invoice with standard fonts in that runtime is UNPROVEN until step 5's `--upload` run stores a PDF made by the runner; the local render proves the layout and fonts under Node. Standard fonts have no glyphs beyond WinAnsi: an agent name with characters outside it would throw; `sanitizeWinAnsi` replaces them as described under Files and logs (ASSUMED behaviour, tested in step 5 with `Zoë Łukasz 王`).
- Invoices do not touch R2 (G26): the PDF lives in the private Supabase Storage bucket `invoices`, written by the runner and read by the Worker through supabase-js with the service role; there is no Worker binding, so `wrangler.toml` does not change, and R2 being off (E8) blocks nothing in this slice. A signed URL lives 60 seconds and is minted per click, so a copied link stops working within a minute. A Storage outage makes `invoice_pdf` jobs and invoice emails retry with B8's backoff and go `dead` after five attempts, retried from screen 16.
- The invoice email is only as fast as the runner tick (up to a minute). The toast shows `JobWatcher`; the admin can open the PDF as soon as the `invoice_pdf` job finishes.
- Disabling the `send_email(invoice)` step in B8b screen 17 stops the invoice email but not the PDF (own job). Intended.
- `Five Features` credit tracking, refunds and partial payments are not modelled. A refund is a manual event recorded in `notes` until a decision.
