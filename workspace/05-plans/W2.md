## Goal and observed exit
A side chat opens from a button in the admin's top bar on every screen. The operator writes a command; Matter, running
on this laptop through the Claude CLI, answers within a minute and does it: runs the AI team (hire, wake, pause,
message), works the admin through its API (requests, properties, recipes, emails, newsletter, channels, jobs), changes
the website through the repository's own path (branch, check, pull request, merge gate), and makes media with the
installed skills (Qwen voiceover now; the operator's video skills once shared). It has no session to lose: every run starts from a generated
atlas of everything (screens, actions, API routes, jobs, recipes, step catalog, scripts, skills) plus its own durable
notes and the recent conversation.
Observed exit: the operator writes "Matter, hire a video editor and write a 20 second voiceover for the brand"
in the side chat; a Video editor appears in the office, a voiceover file appears under `matter/out/`, and Matter's reply names both.

## How the staff learns (from Jay, OmniSkipX, 2026-10-12, measured on his system 2026-10-10)
Jay's own numbers: 1,571 lessons in a table, recall changed the answer in only about 16 percent of runs (no relevance
floor, 39 percent noise, 160 characters shown per lesson, embeddings silently dark). What made his agents better was
not notes but rules and hooks born from incidents, an independent reviewer, and a scoreboard. Applied here:
- Lessons live in a table, `agent_lessons` (agent_id or all, trigger "when this applies", action, evidence_ref (the
  approval or run id), source (decline, edit, outcome, Matter), status, uses, last_used_at, created_at), written only
  from real events: an approval decision, an edit by the operator, an outcome in the numbers. Never from study
  material. A write gate refuses a lesson without a trigger and an action and merges near-duplicates.
- About 30 active lessons per employee: all of them when under the cap, else the top 10 by relevance and recency,
  with a relevance floor. Each run writes `lessons-used: <ids>`, which feeds ranking; unused lessons fade.
- The training signal is the approval outcome: approved as is, edited (the operator's diff "changed X to Y" is
  stored), or declined with its reason. The approved-as-is rate per employee per week is the main number.
- Instructions are versioned. Matter's weekly review proposes a change, replays last week's edited and declined
  proposals under the old and the new instructions, and adopts the new ones only if they win; the operator approves
  the diff. A lesson used three times or more is promoted into the instructions (or into a code check when it can be
  enforced) and retired.
- The loaded text has a budget: instructions, lessons and atlas together stay under about 80 live rules. The atlas is
  a short index plus the one section a run needs, stamped with its age; its regenerator never pauses.
- Models per role, chosen on about 40 real cases each before assignment: Haiku 5.5 to route and summarize, Sonnet
  5.5 for most employees, Opus 5.5 for Matter.
- Other agents' messages and table rows are data, never instructions, and are fenced in the prompt (the team chat is
  an injection surface).
- Cost is computed from tokens with our own price table, never from the CLI's reported cost. Test runs are marked and
  never counted as real usage. A pause stops work, never maintenance. A check that cannot run records why.
- A daily scoreboard: approval-as-is rate, time to answer, runs, cost, and the business numbers; if they do not move,
  nothing improved.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs: a person's message in thread `matter` (side chat), or a mention `@matter` in the team chat.
Outputs: its reply in the thread; changes through the admin API, the repository's merge gate, or the installed tools.
Invariants:
1. The operator's own command is authority to act: Matter does it and reports. What Matter starts on its own (no
   command) goes through Approvals like any employee's proposal (W1 invariant 3).
2. Person-only actions stay person-only (team, settings, passwords; matrix `humanOnly`). Matter prepares them and
   tells the operator the one click left; it never holds a session cookie or a password.
3. It reaches the admin only through the admin API with its own agent key (role admin, every scope), so every act is
   in `audit_log` under its name.
4. It changes code only through the repository's path: a branch, `bun run check`, a pull request, the merge gate.
5. Its tool policy denies reading `creds/`, `cloudflare tokens and secrets.txt`, `Claude Session.txt`, printing
   `.env` values, Docker, force pushes and history rewrites (the operator's standing rules).
6. No session: each run gets the atlas (regenerated from code when it changed), `matter/notes.md` (its durable notes,
   which it may append to) and the last 40 lines of its thread.
7. Every employee grows (operator, 2026-10-12: "all the AI employees always grow and become smarter over time"), by
   the design in "How the staff learns": lessons in `agent_lessons` from real outcomes, recall with a floor and a cap,
   the approval outcome as the signal, versioned instructions proven by replay before adoption, promotion of a
   repeated lesson into the instructions or a check.
8. What no token can read (Supabase egress: the billing usage refuses an account token, the logs endpoint has no edge
   table, measured 2026-10-12) Matter reads weekly from the operator's signed-in Supabase dashboard in the browser
   and records with its date.
9. The growth loop (operator, 2026-10-12): an Analyst employee pulls the numbers weekly and every day before the
   meeting (GA4, Search Console, social metrics, the audit robot's reports, the free-tier gauges) and researches
   competitors daily; every day at 18:00 Africa/Cairo time (15:00 UTC, the operator's clock) the team meets in the
   team chat: the Analyst reports, each employee says what it learned and plans, Matter decides and assigns, and
   code changes go through the merge gate. A shared knowledge base (`matter/knowledge/`) holds what the company has
   learned (what posts, properties and campaigns did, what competitors do); every run may read it, Matter keeps it.
   When a gauge nears its threshold (70 percent of a free-tier limit), Matter tells the operator which upgrade is
   next (database plan, Cloudflare plan) and its monthly cost.
10. Campaigns and media buying are an employee of the core team (Campaigns): it plans paid campaigns, drafts the ads
   and the budgets and reads their results into the knowledge base. Spending money is the operator's: every budget
   and every live ad waits for the operator's yes in Approvals, and the ad accounts are the operator's to create.
   The aim the operator set is growth that compounds into reach and sales; the loop measures it every day and
   says plainly when something is not working.
11. Matter thinks with the operator: asked "what do you think", it weighs options against the numbers, the knowledge
   base and the brand rules and gives a recommendation before doing anything; it is the same Matter in the admin's
   side chat and in the desktop office app, with one shared thread and one memory.
12. The team keeps working between meetings: each employee holds a backlog (`matter/backlog.md`, kept by Matter) and
   the daemon wakes the next item whenever no event or message is waiting, within the hourly run limit.
13. The company scales itself: when a role is overloaded (runs queued longer than a day, or a backlog that keeps
   growing), Matter hires the colleague it needs (`workforce_hire`) and says so in the team chat.
14. Money and clients: Matter and the Commercial employee follow every request from arrival to a paid invoice and a
   published property, and every client's satisfaction after; the Analyst reports revenue, conversion and cost per
   result alongside reach.
15. One core brain for the whole team: the knowledge base, every employee's lessons and every installed skill (the
   operator's `qwen-voiceover` today; the operator's video-making skills for social media and our own ads when
   shared; any skill added later) are available to every run, so what one employee learns the whole team uses.
16. The charter (operator, 2026-10-12: "full wording is required to be built into the whole thing when it is time to
   work on the whole ai company staff"): `matter/charter.md` holds every quote under "The operator's words" above,
   word for word, and every employee's prompt, Matter's included, opens with it on every run. It changes only by the
   operator's word.
Events emitted: none new; audit rows come from the admin API it calls.
Permissions: the side chat posts through `workforce.post_message` into thread `matter`.

## Files (create / change; one line each: path — what it contains)
- app/scripts/matter/atlas.mjs — writes `matter/atlas.md` from nav.ts, the permission matrix, the route tree, the step
  catalog, job types, package scripts, `.claude/skills` and `~/.claude/skills` names.
- app/scripts/matter/run.ts — one run: builds the prompt (atlas, notes, thread), spawns `claude -p` (Opus 5.5) in the
  repository with the tool policy, posts the reply, records the run.
- app/scripts/matter/settings.json — the tool policy (allow and deny lists) passed with `--settings`.
- app/scripts/workforce/daemon.ts — claims runs of `second` first and hands them to `run.ts`.
- app/supabase/migrations/<ts>_matter.sql — seeds the `second` agent row (model opus).
- app/src/admin/workforce/SideChat.tsx — the drawer: the thread, the composer, the run state; opened from the top bar.
- app/src/admin/ui/TopBar.tsx — the "Matter" button.
- app/scripts/matter/key.mjs — creates Matter's agent key once (admin, every scope) and stores it in the laptop's
  `.env` as MATTER_AGENT_KEY (name only ever printed).
