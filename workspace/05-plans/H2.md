# H2 — Acceptance panel: the whole site walked through by three senior agents

Lane: Stage 4 HARDEN, one lane, after every B slice has closed and before L1's launch switch · Stage: 4 HARDEN · Owner agent: the orchestrator runs the panel (three persistent agents) and the existing build-slice workflow for the fixes · Depends on: every B slice closed on `main` (B1b to B17), H1 steps 1 to 5 (the automated checklist exists, so the panel reads its report instead of redoing it), the dev deploy of `main` serving the seeded catalog, Sentry and Workers Logs reachable from the laptop.

Sources: operator decision S66 (2026-10-04: "3 high top tier agents that will do the final walk through: senior engineer, security specialist, user journey expert ... end to end including frontend, backend, error logs, console info and the DB structure ... they talk to each other ... work together on hiring a worker per chunk ... check what he did ... merge leaving notes about what changed and what that change fixes"); the gap named by the CTO the same day: every review so far judged one group against its plan, nobody has judged the finished system as a whole.

## Goal and observed exit
Three agents with distinct charters read the finished product the way a senior engineer, a security specialist and a user-journey expert would: the deployed dev site in a browser with console and network capture, the repository, the database structure and its advisors, the Worker logs and Sentry. They keep one findings ledger, agree each finding's severity and proof between them, turn every finding at or above `medium` into a fix group of the ordinary workflow (builder, fresh reviewer, merge gate), re-verify each fix on the deployed site, and stop after two full passes that find nothing above `low`.
Observed exit: `node workspace/05-plans/acceptance/run.mjs --report` exits 0 and writes `workspace/audits/acceptance-YYYY-MM-DD.md` whose findings table has no row above `low` left `open`; `workspace/05-plans/logs/H2.md` holds the two clean passes with their dates; `CHANGES.md` at the repository root lists every fix the panel merged with what it changed and what it fixed; the operator and his partner can read both without the transcript.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs: the dev deploy of `main` (`https://matter-of-place-dev.<account>.workers.dev`) with the full seed, read through headless Chrome (`launch/engine/still.mjs`'s browser, console and failed-request capture); the repository at `main`; `mop-dev` through `bun run db:psql` (read only: `pg_catalog`, policies, grants, advisors through the Supabase MCP); Sentry issues and Workers Logs for the dev Worker; H1's report `workspace/audits/harden-YYYY-MM-DD.md`.
Outputs: `workspace/05-plans/acceptance/ledger.json` (one row per finding: id, panelist, area, severity, title, evidence, proof command, status, fix group, commit), the report above, `CHANGES.md`, the H2 log.
Invariants:
1. The panel reads and probes; it never edits product code. Every fix is a close-out group of `build-slice.js` on a lane, with a builder, a fresh reviewer and the merge gate, exactly as a build group (H54, H57). The panel's review of a fix is a second reviewer, not a replacement for the first.
2. Each finding carries a proof a person can re-run (a command, a URL and the observed console line, a SQL query) before it becomes work. A finding without a proof is a question in the ledger, not a defect.
3. Severity has four values: `critical` (data loss, security, money), `high` (a journey cannot be completed, a wrong fact shown), `medium` (a journey is confusing or slow, a standard not met), `low` (polish). `critical` and `high` block the launch; `medium` is fixed in this phase; `low` is recorded for after launch.
4. Two of three panelists must agree a severity; disagreement is written in the ledger with both reasons and the orchestrator rules.
5. Nothing reaches production data: the panel works on the dev deploy and `mop-dev` in its preview stage (H35), before L1's switch.
6. The brand guardrails and the three tests of CLAUDE.md are the user-journey panelist's yardstick; copy findings quote the line.
7. Every merged fix adds a line to `CHANGES.md`: date, finding id, files, what changed, what it fixes, the proof.
Permissions: the panelists read everything a reviewer reads; they hold no write token for GitHub, Cloudflare or Supabase beyond the lane worktrees the workflow gives the builders. Models: the three panelists run on Fable (operator decision S66, the one exception to S62's "never spawn Fable children"); builders and reviewers stay Sonnet 5.5 and Opus 5.5 at high effort.
Events emitted: none (this phase runs on the laptop; it writes files and pull requests).

## Steps (ordered; each fits half a day; each ends with the command that proves it)
1. Charters, probes and the ledger. Write the three charters, `probe.mjs` with its six commands, the ledger schema in `run.mjs` and its unit test (watched failing: a finding with one agreeing panelist is refused). Proof: `node workspace/05-plans/acceptance/probe.mjs page /` prints the status, zero console errors and the two screenshot paths for the dev deploy; `bunx vitest run --project unit tests/unit/acceptance-ledger.test.ts` passes; `node workspace/05-plans/acceptance/run.mjs --report` exits 0 on an empty ledger and writes the report.
2. The journeys. Write `journeys/*.json` for every journey of the user-journey charter and make `probe.mjs journey <name>` replay each against the dev deploy with the seeded catalog. Proof: `for j in workspace/05-plans/acceptance/journeys/*.json; do node workspace/05-plans/acceptance/probe.mjs journey $(basename $j .json); done` prints one `ok` or one named failing step per journey; a journey file with a wrong selector prints the step and exits 1 (watched).
3. The team. Write `team.mjs`: three agents on Fable with their charters, a shared ledger, the probes, read-only access, a message loop relayed to the H2 log, and the stop rule. Proof: a dry run with `--pass smoke` where each panelist reads one page and writes one finding with a proof; the ledger validates; the log shows the three agents answering each other.
4. Pass one. Run the panel over the whole site, repository, database and logs. Proof: the ledger holds every finding with proof and agreed severity; `run.mjs --report` writes the report; the open rows above `low` are listed with the slice that owns each.
5. Fixes. For each open row at or above `medium`, in severity order: `run.mjs --fix <id>` prints the close-out arguments; the orchestrator launches `build-slice.js` on the owning slice's lane with that close-out; the fix merges through the gate; the panel re-verifies on the redeployed dev site and closes or reopens the row; `CHANGES.md` gains its line. Proof: every row above `low` is `closed` with a commit, or `deferred` with the operator's word; `git log --oneline main` shows one merge per fix; `CHANGES.md` has one line per fix.
6. Pass two and the sign-off. The panel repeats the whole walk on the fixed site. Proof: `run.mjs --report` exits 0 (nothing above `low` open) twice, on two different days or after the last fix merged; the H2 log holds both passes; the report is sent to the operator with `SendUserFile` for the walk-through with his partner.

## Risks
- The panel finds more than the plan can absorb before launch. Mitigation: the severity bar and the two-of-three rule; `low` waits for after launch; `medium` is fixed only inside this phase's budget (a day), the rest goes to the operator as a list with the panel's reasons.
- Panelists improvise probes and disagree on facts. Mitigation: `probe.mjs` is the only way to look at the site, so two panelists see the same console line.
- Token cost on Fable. Mitigation: the panelists read H1's report and the plans' invariants instead of re-deriving them; the probes print summaries, not page sources; the pass is bounded by the journeys and charters, not open-ended.
- A fix changes behaviour another slice relies on. Mitigation: fixes are close-out groups with the writer-chain rule of H54 and a fresh reviewer; the panel re-verifies on the deployed site, not on the branch.
