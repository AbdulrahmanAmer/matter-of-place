## Goal and observed exit

Matter of Place sells four Property Exposure plans: name, price, one line, a list of what is included, a recommended flag and a media note. Until now they are a constant in `src/data/exposure.ts`, and a price change is a code change and a deploy. Ruling H80 (the operator's requirement) moves them into the database: a `products` setting edited from `/admin › Settings`, served through the cached site state that every public page already uses (zero database reads on a warm page), and rendered by the exposure page, the home pricing block and the invoice line. B2's settings trigger, which already raises `catalog_version` for the public keys, is the refresh. `src/data/exposure.ts` stays as the seed of the first row and as the fallback when the setting is absent.

Observed exit (completion map B18): "an admin changes a plan's price in Settings; the exposure page, the home block and the next invoice show it within a minute, with no deploy." Proven as: `E2E_TARGET=built E2E_MODE=live bunx playwright test --project admin tests/e2e/exposure-products.spec.ts` passes (step 3): it signs in as the admin, raises The Feature by 30 dollars in `/admin › Settings › Products`, previews and saves it, then polls `GET /api/public/site` until the price is the new one, checks that `x-catalog-version` rose, that `/exposure` and `/` print the new price and no longer the old one, and puts the stored value back. The invoice leg is proved at the service by `tests/unit/payments/invoice-snapshot.test.ts` (step 3): the snapshot amount and description come from the stored plan, an invoice issued before the change keeps its amount. The warm-read leg is `tests/unit/products-read-path.test.ts` (200 reads, one `public_state` call, no table read) and `bun run scripts/harden/cache-probe.ts --mode memory <base>` printing `cache memory ok`.

## Contract (inputs, outputs, invariants, events emitted, permissions)

Inputs

- `settings.products` (one row of B2's `settings` table, key `products`), value `{ "plans": [ <plan>, <plan>, <plan>, <plan> ] }`: exactly four plans, one for each of the four `exposure_package` ids. A plan is `{ id, name, price, line, note, items, cta, recommended }`. The seed is exactly the four rows of `offerings` in `src/data/exposure.ts`, in their order, with each display price turned into whole dollars (`"$1,495"` becomes `1495`).
- The words of ruling H80 map to the fields as follows. Name is `name`; price is `price`; line is `line`; description is `items` (the list of what the plan includes, the only description the plans have today) together with `cta` (the label of the link under the card); the recommended flag is `recommended`; the media note is `note` (the qualifier under the price: "Recommended media investment: $500 to $2,500+", "$250 per property"; null when there is none). `id` is the stable key and is not editable.
- Orchestrator ruling on the builder's findings (2026-10-11), recorded in H80: the setting holds exactly the four plans bound to the four `exposure_package` ids (`feature`, `reach`, `campaign`, `five-features`). What an admin edits per plan is its name, price, line, items, cta, note and recommended flag, and the order of the four. Adding a plan or removing one is refused by validation, in the schema and in SQL, with exactly the message "adding or removing a plan needs a migration".

| Field | Key | Validation (server side, `productsSettingSchema`, mirrored in SQL) | Used by |
|---|---|---|---|
| Plans | `plans` | exactly four objects keyed by the four bound ids; order is display order; at most one with `recommended` true. Any other count, or a body whose ids differ from the four bound ids (a missing, extra or repeated id), is refused with exactly "adding or removing a plan needs a migration" | exposure page, home block, FAQ, invoice |
| Id | `plans[].id` | one of `feature`, `reach`, `campaign`, `five-features`, each exactly once (the `boundPlanIds` keys); never edited by the screen | `track("package_interest")`, the invoice binding, React keys |
| Name | `plans[].name` | trimmed, 2 to 60 characters, unique ignoring case | cards, invoice description, FAQ |
| Price | `plans[].price` | a whole number of dollars, 1 to 1,000,000 (a decimal, a string, 0 and a negative are refused) | cards (`formatPrice`), invoice amount, FAQ |
| Line | `plans[].line` | trimmed, 1 to 160 characters | cards, invoice description |
| Media note | `plans[].note` | trimmed, at most 120 characters; blank becomes null | card qualifier under the price |
| Items | `plans[].items` | 0 to 12 lines, each trimmed, 1 to 140 characters; blank lines dropped | the list on the exposure card |
| Link label | `plans[].cta` | trimmed, 2 to 40 characters | the link on the exposure card |
| Recommended | `plans[].recommended` | boolean, default false | the "Recommended" flag and the lead card |

No text field may contain an em dash or an en dash (U+2014, U+2013): the brand rule is enforced by the schema, with the message "Use a comma or a full stop, not a dash." Unknown keys are refused on a write and ignored on a read.

Outputs

- `GET /api/public/site` returns B16's object (contact, legal, social, `illustrativeContent`) plus `products: ProductPlan[]` (the parsed plans, or the seed plans when the setting is absent or no longer parses). One `getPublicState(db)` call gives all of it; the route, its cache headers and its row in `src/server/public/routes.ts` are B3's and B16's, unchanged. Invariant 3 of B16 ("only `site` and `illustrativeContent`") is amended: the body also carries `products`.
- `public_state()` returns eight keys instead of seven: the new key is `products` (the stored value of `settings.products`, null when the row is missing). It amends G39 and B16's note on the seven keys.
- `GET /api/admin/settings` (screen 24, action `settings.get`) gains `products: { current: <setting> | null, defaults: <setting> }`: `current` is the stored value (null when the row is missing or no longer parses), `defaults` is the seed built from `src/data/exposure.ts` so the screen can offer "Start from the original plans" without importing `src/data`.
- `PUT /api/admin/settings/products` (action `settings.products_put`) validates the body with `productsSettingSchema`, calls `settings_put_products` once and answers the saved value. 422 `validation` with the Zod issues on an invalid body; nothing is written.
- `POST /api/admin/settings/products/preview` (action `settings.products_preview`) is the dry run. It writes nothing: no row, no audit row, no version bump. It answers `{ plans, surfaces, changes, warnings }`: `surfaces.exposure` and `surfaces.home` are the cards exactly as the public components receive them (`toOffering`), `surfaces.homeHeading` is the home block title, `surfaces.invoice` is one entry per bound product with the description and the amount an invoice would carry (`invoiceLine`, `formatUsd`), `surfaces.faq` is the cost answer; `changes` lists every plan reordered or edited against the stored value with old and new price; `warnings` are listed under invariant 7.
- Rendered surfaces: `/exposure` (the four cards with full lists, the FAQ and its JSON-LD), the home pricing block (compact cards and its title), `/faq` (the cost answer), the invoice line (`description` and `amount` of the frozen snapshot), and the dry run of screen 24.
- `src/data/exposure.ts` still exports the static copy that is not a plan: `programmatic`, `selectionSteps`, `editorialQualities`, and the FAQ builder `exposureFaqFor(plans)`.

Invariants

1. One source at runtime: `settings.products`. `src/data/exposure.ts` is the seed of the first row and the fallback when the setting is absent; the constant of plans is renamed `seedOfferings` (step 3) and only `src/server/settings/products.ts`, `src/services/local/site.ts` and the file itself import it (`tests/unit/products-source.test.ts`). A route, a component or an admin file never imports it.
2. Validation lives twice and says the same thing: Zod `productsSettingSchema` in `src/domain/exposure.ts` (the API, the screen, the read path, the seed test) and `settings_put_products` in SQL (shape, exactly four plans whose ids are the four bound ids, integer price in range, at most one recommended). Either one answers `validation` (SQLSTATE 22023 from SQL, translated by `fromRpcError`). A db test feeds both the same table of good and bad values and requires the same verdict (the `redirectSchema` and `put_redirect` pattern of B7 step 15a).
3. Whole dollars, one formatter: the stored price is an integer; `formatPrice(n)` returns `$` plus the digits with comma thousands separators, built by a regular expression and not by `toLocaleString`, so server render and browser agree (no hydration mismatch). `formatUsd` of the invoice (`$295.00`) is unchanged.
4. The public read path is `getPublicState` and nothing else (architecture 13, STANDARDS R15): `getPublicSite` reads `state.products`, parses it with `productsSettingSchema.safeParse`, and falls back to `plansFromOfferings(seedOfferings)` when it is null or does not parse. A stored value that is present and invalid is served as the seed, with one `logLine("warn", "products_invalid", ...)`; a missing value is silent. A warm page makes zero database queries; a cold memo makes the one `public_state` call it always made.
5. The refresh is B2's trigger on `settings`: its key list ('flags', 'coming_soon_global', 'site', 'environment', 'og_static') gains `products`, in the same migration, so one save raises `catalog_version` by exactly 1 in the same transaction (P-041: a new input to a public render moves the version, and a test shows it). No recipe, no job, no cache purge step.
6. The invoice does not read through the public-state memo. `readInvoiceInputs` (B6) already reads `site` and `invoice` straight from the table so a frozen snapshot never carries a cached value (B6 invariant 5); it reads `products` in the same `select`, so there is no extra query. `priceFor` and `offeringFor` become pure functions of that list. An invoice or a waiver already issued keeps its amount: nothing joins `payments` to the setting.
7. The setting holds exactly four plans, each bound to the `exposure_package` enum by one constant, `boundPlanIds` (`The Feature` to `feature`, `The Reach` to `reach`, `The Campaign` to `campaign`, `Five Features` to `five-features`); a unit test requires its keys to equal `exposurePackages` without `Not sure yet`. A name is display copy and may change; the enum label stays what forms, filters and the request screens show (changing the enum is a migration path of its own, out of scope). Adding a plan or removing one is refused by validation, in the schema and in SQL, with exactly "adding or removing a plan needs a migration" (a count other than four, or ids that differ from the four bound ids); so every product can always be invoiced, `priceFor` finds its plan by the bound id and never by name, and there is no "not on sale" state. The dry run says each of these in `warnings`: a bound plan whose name differs from its enum label ("Forms and request screens still say The Reach"), a changed price ("new invoices will use it; issued invoices keep theirs").
8. Writing is admin only, people only, within 15 minutes of sign-in (the `guarded` entry of `src/server/lib/permissions/settings.ts`). Agents are refused (`human_only`). The write is one SQL function that updates the row and audits through `write_audit` in one transaction, with the before and after values: audit action `settings.products_put`, entity `settings.products`. The service starts with `authorize(actor, "settings.products_put")`.
9. The dry run is the same code as the public pages: `toOffering`, `waysIn`, `exposureFaqFor`, `costAnswer` and `invoiceLine` are pure functions of the plan list in `src/domain/exposure.ts` and `src/data/*.ts`, called by the page, by the invoice and by the preview, so the preview cannot drift from what is shown.
10. Derived copy cannot go stale: the home title "Four ways in." becomes `waysIn(plans.length)` (always "Four ways in." while the setting holds exactly four plans, derived so that a later migration that adds a product needs no copy edit); the FAQ answer "What does it cost?" is built from the plans; the exposure FAQ entry about Five Features is built from the plan with id `five-features` and quotes its price; the exposure meta description stops naming products (`pageDescription("exposure")` in `src/lib/seo-copy.ts` becomes "How a property is presented and distributed, all after editorial review.").
11. Last write wins, as for every other settings key. The audit row keeps the full before value, so a lost edit is recoverable by pasting it back through the screen.
12. Copy stays calm: price never equals merit, no promise of leads, buyers or sales. The schema cannot judge that; the screen's help text says it in one sentence and the editor owns it.

Events emitted: none (a settings edit is an audit row and a `catalog_version` bump, not a catalog event).

## Data changes (migrations, enums, RLS, seeds)

- No new table, no new column, no new enum value: `settings` exists (B2, `value jsonb`) and so do its RLS policies. The stored value always has exactly four plans, one per bound id; adding a plan or removing one is refused ("adding or removing a plan needs a migration"; that change needs an enum value, a `boundPlanIds` entry and a change to the exact-four rule). The `exposure_package` enum and the SQL functions keyed on it (`payment_tier`, `package_duration_days`) are untouched: they key on the enum label, not on a price.
- Migration 1 (step 1), `<ts>_settings_products.sql`: the two `settings` triggers are dropped and re-created with the key list `('flags', 'coming_soon_global', 'site', 'environment', 'og_static', 'products')`; `public_state()` is replaced (eight keys, `products` is `(select s.value from public.settings s where s.key = 'products')`; this amends G39, "Public state has seven keys", which H80 records); the seed row is inserted with `on conflict (key) do nothing`, so a replay never overwrites an edit. Its `-- down:` block restores the five-key triggers and the seven-key function. The seed literal is the four rows of `seedOfferings` as `{ "plans": [...] }`, and `tests/unit/products-seed.test.ts` reads this file and requires the literal to equal `plansFromOfferings(seedOfferings)` field for field, so the seed and `exposure.ts` cannot drift.
- Migration 2 (step 2), `<ts>_settings_put_products.sql`, and the generated `<ts>_action_roles.sql`. `write_audit` refuses an action no `action_roles` row holds, so the matrix change and its migration land with the function.
- Types: step 1 changes no function signature, so `src/db/types.ts` is unchanged (`git diff --stat src/db/types.ts` prints nothing); step 2 runs `bun run gen:types` (B2's `scripts/gen-types.mjs`, cloud project `mop-dev`, no Docker).
- Each migration lands on `main` in its own small pull request before the code that needs it (R16, tech-stack section 5). The lane never pushes it to `mop-dev` (P-050, ruling H1): its db tests run on the lane as `MOP_MUTATION_SQL="$(cat supabase/migrations/<file>.sql)"` inside the rolled-back transactions of `withRollback` (P-312), with the dev profile loaded and `env -u CLOUDFLARE_API_TOKEN` in front (P-310); after the merge the `dev` job of `deploy.yml` pushes it with `bun run db:push`, and the orchestrator confirms `bunx supabase migration list --linked`.
- Seed values are the owner's approved schedule (S3) as `exposure.ts` holds them today; nothing is invented. After the launch switch the stored value is the owner's to edit; no script resets it (the e2e refuses to run there).

## Risks and gotchas (link GOTCHAS ids)

- G-004: the stored keys, `src/domain/exposure.ts`, the migration literal and the API JSON are one shape; change them together, and `products-seed.test.ts` fails when the seed and `exposure.ts` part.
- P-041: a new input to a public render must move `catalog_version`; the trigger key list is changed in step 1 and a db test and the e2e both show the version rising.
- P-050, P-310, P-312: the lane never pushes its migrations to `mop-dev`; db proofs run inside rolled-back transactions with the dev profile loaded; the e2e writes `settings.products` on the one database under the G34 lock and puts the value back.
- P-066, P-079: step 3 edits files that old registry entries mutate (`src/data/exposure.ts`, `pricing.ts`, `service.ts`); every entry whose `find` no longer occurs once is re-pointed and replayed, and every new test title has an entry before the step reports.
- P-074: step 1's `products.ts` holds the parse and the fallback; the table read, the dry run and the write join it in step 2, and nothing calls a function a later step creates.
- P-009 and page weight: the plans ride in the site query that the root loader fills on every page, so every page's dehydrated state grows by about 2.5 KB. Measured in step 3 (`wc -c` of the site body, `bundle-check`); if H1's budgets go red the plans move to a second query that only `/`, `/exposure` and `/faq` load, still from the same endpoint.
- The browser keeps a site query for five minutes (`catalogStaleTime`), so a visitor already on the site may see the old price on a client-side navigation for up to five minutes; a server render and a reload see the new one within the 15-second memo. The invoice is exact (it reads the table).
- Names versus the enum: renaming a plan changes the public and invoice wording but not the `exposure_package` label that the submit form, filters and request screens show. The dry run warns; adding or renaming enum values is a migration of its own and not part of this slice.
- The `programmatic` terms, the selection steps, the editorial qualities and the rest of the exposure FAQ stay in `src/data/exposure.ts`; a price quoted inside other static copy would drift. The two places that quoted prices (`faq.ts`, the Five Features FAQ entry) are derived; step 3's test `git grep -n '\$[0-9]' -- src/data src/routes` is reviewed for any other.
- B6 invariant "one price source, `src/data/exposure.ts` (S3)" and the line in `app/AGENTS.md` are superseded by H80; step 3 amends AGENTS.md. `B6.md` itself is not edited by this slice and its text is read with H80 in mind.
- `tests/e2e/admin-invoice.spec.ts` (E2E_FULL_STACK) is not changed: it issues at the stored plan's price, which equals the seed unless an operator edited the setting, and it puts back what it found.
- Stored value edited by hand in SQL (for example three plans, or a changed id): the read path serves the seed and logs `products_invalid`, and the invoice path does the same, so an invoice then carries the seed price until the value is saved again; the screen shows `current: null` and offers the original plans.
- Exactly four plans is a product decision (ruling 3 of the orchestrator on the builder's findings): an owner who wants one more offer, or one fewer, needs a migration; the refusal message says so in those words, and the screen's help sentence repeats it.

## Out of scope

The `exposure_package` enum and the submit form's "Preferred exposure" choices, the admin product pickers and filters (they keep the enum labels); adding or removing a plan, which the schema and SQL refuse with "adding or removing a plan needs a migration" (a later slice would add an enum migration, a `boundPlanIds` entry and a change to the exact-four rule together); programmatic media terms, the selection steps, the editorial qualities and the non-price FAQ entries (static copy in `src/data/exposure.ts`); per-market or per-agent pricing, discounts, coupons, credits and tax (B6); future-dated price changes; a revision history screen for products (the audit log holds every before and after); a separate `GET /api/public/products` route; Stripe (later, same `payments` table); currency other than USD; translations; the invoice template and PDF (B6) beyond the description and amount lines.
