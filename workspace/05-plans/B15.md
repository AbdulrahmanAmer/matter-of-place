Lane: Be found (handoff) · Stage: 3 BUILD · Owner agent: mop-builder · Depends on: B3 (inquiries API, `inquiries` table), B8 and B8b (jobs, `inquiry.received` recipe, `retry_at`, `src/server/lib/hmac.ts`), B7 (screen 11 forward action), B16 (privacy wording), Omnikom supplying an endpoint and a shared secret · Unblocks: Omnikom-side follow-up of inquiries and campaign attribution; the auditor's channel section (attribution counts)

## Goal and observed exit
Every inquiry received on the site is delivered to Omnikom as a signed JSON webhook with the first-party attribution the visitor arrived with, retried when Omnikom is down, and visibly forwarded or failed in `/admin › Inquiries` (screen 11).
Observed exit: proven in two stages. Stage 1 (buildable now, no operator input, no Docker, S50): a mock receiver `scripts/omnikom-mock.ts` verifies the signature and prints the payload after a real inquiry is submitted against `mop-dev`. The Edge Function runs in the cloud and cannot reach the laptop's localhost, so stage 1 has two receivers: the mock on `127.0.0.1` driven by a local run of the step (`scripts/omnikom-run-local.ts`), and the same mock deployed as a throwaway Worker on `https://omnikom-mock.holy-meadow-4327.workers.dev` (E1, E2) for the cloud path, deleted afterwards. Stage 2: the payload is received by the real Omnikom endpoint. Stage 2 is BLOCKED until Omnikom provides the endpoint URL and secret, and the whole endpoint contract below is ASSUMED until Omnikom's side confirms it.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- Event `inquiry.received` (architecture 3.6) → recipe steps `send_email(ack)`, `notify_admin`, `webhook_omnikom` (architecture 5). Payload of the event: `{ inquiry_id }`; the step loads the row.
- Manual forward from screen 11: `POST /api/admin/inquiries/:id/forward` enqueues a manual job `webhook_omnikom:<inquiry_id>:<n>` (B8 idempotency rule for manual system jobs).
- Secrets, server side: `OMNIKOM_WEBHOOK_URL`, `OMNIKOM_WEBHOOK_SECRET` (new, ASSUMED; tech-stack 4 does not list them, add them there). Stored as Supabase function secrets (`bunx supabase secrets set ... --project-ref $DEV_SUPABASE_PROJECT_REF`, no Docker) because the step runs in the Edge Function, and in Cloudflare only if a Worker route ever calls it (it does not). Neither exists in GitHub or `.env` today (E10); on dev the secret is a value made with `openssl rand -hex 32` for the mock, the production value comes from Omnikom (step 7).

Endpoint contract (ASSUMED, to be confirmed with Omnikom; everything in this block is a proposal)
- Method and URL: `POST <OMNIKOM_WEBHOOK_URL>`, `content-type: application/json`, body at most 64 KB, response within 10 seconds.
- Headers: `X-MOP-Event: inquiry.received`, `X-MOP-Delivery-Id: <uuid, stable across retries of the same inquiry>`, `X-MOP-Timestamp: <unix seconds>`, `X-MOP-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>" keyed by OMNIKOM_WEBHOOK_SECRET>`, `User-Agent: MatterOfPlace-Webhook/1`. The scheme is the one B8 uses for the render callback, so `signBody` and `verifyBody` in `src/server/lib/hmac.ts` are reused (the file is created by B8; this slice does not create it).
- Receiver must: verify the signature over the raw bytes, reject a timestamp older than 300 seconds, dedupe on `X-MOP-Delivery-Id`, and answer `200` or `202` when accepted, `409` when it already has the delivery (we treat that as delivered), `4xx` when the payload is refused (we do not retry), `5xx` or timeout when unavailable (we retry).
- Body, version 1:
```
{
  "id": "<delivery uuid>",
  "version": 1,
  "type": "inquiry.received",
  "occurred_at": "<ISO 8601>",
  "source": "matterofplace.com",
  "data": {
    "inquiry": { "id", "intent", "topic", "name", "email", "phone", "location", "message", "details": {}, "source_path", "received_at" },
    "subject": { "kind": "property", "slug", "title", "market", "city", "tier", "representation": { "name", "brokerage" } },
    "attribution": {
      "first_touch": { "landing_path", "referrer_host", "utm_source", "utm_medium", "utm_campaign", "utm_content", "at" },
      "last_touch":  { "landing_path", "referrer_host", "utm_source", "utm_medium", "utm_campaign", "utm_content", "at" },
      "pages_viewed": 0
    }
  }
}
```
Absent values are omitted, not null, not empty strings. `subject` is omitted for a general message.

Outputs
- `inquiries.forwarded_payload jsonb` (architecture 3.3, exists) stores the exact body sent; `inquiries.status` (`new|in_progress|forwarded|closed`, screen 11) becomes `forwarded` only after a 2xx or 409.
- `inquiries.attribution jsonb` (new column, ASSUMED) stores what the browser captured at submit time.
- `jobs.result` keeps the last HTTP status, delivery id and attempt count for the timeline on screen 16.
- Audit rows for manual forward.

Invariants
1. Privacy minimum: the payload contains only fields the visitor typed plus attribution. No IP address, no user agent, no cookies, no other events. The privacy page (B16) states that inquiries can be shared with Omnikom, and the inquiry form shows the same sentence near the submit button (a copy change owned by B16, checked here).
2. Signed and timestamped on every attempt (new timestamp and signature, same delivery id and same body bytes on retries so Omnikom can dedupe).
3. Retry outside the normal backoff: partners are down for hours, and B8's 5-attempt policy gives up after about 8 minutes. The step therefore keeps its own counter in `jobs.result.delivery_attempts` and returns `{ status: "retry_at", at }` on `5xx`, `408`, `425`, `429` (honouring `Retry-After`) and network errors, on the ladder 1 minute, 5 minutes, 30 minutes, 2 hours, 6 hours, 24 hours. After the sixth failure it throws `NonRetryableError("omnikom_unreachable")`; the job is `dead`, red on screen 16, the inquiry stays `new`, and screen 11 offers "Forward to Omnikom" again. `retry_at` does not consume B8 attempts (B8 invariant 3), which is why the counter is ours.
4. Attribution is first-party and cookie-free: `src/lib/attribution.ts` reads `utm_*` and `document.referrer` on the first page of a session and keeps them in `sessionStorage` (no cookie, no third party, no fingerprinting); it holds first touch and last touch and a page counter, and nothing else. It is included only when the visitor submits an inquiry.
5. The webhook never blocks the visitor: the API answers the inquiry as soon as the row is written; delivery is a job (architecture 1, side effects are jobs).
6. Free tier: one small HTTPS call per inquiry.
7. Secrets never appear in logs or in `forwarded_payload`; the signature header is not stored.

Events emitted: none new. Analytics: no new event (the existing `contact_inquiry`, `property_inquiry`, `showing_request` and the like are already tracked by the forms).

Permissions (admin-screens 11)
| Action | Roles |
|---|---|
| view forwarded payload | managing_editor, commercial, chief_editor |
| forward, re-forward | managing_editor, commercial, chief_editor (as screen 11) |

## Risks and gotchas (link GOTCHAS ids)
- G-006: `OMNIKOM_*` server side only.
- G-004: `attribution` names are identical in `src/domain/contracts.ts`, `src/domain/omnikom.ts` and the column; a rename touches all three.
- P-008: never type the JSON body with backslashes inline in Bash for the curl proof; use a file.
- P-038 and E7: no Docker, no local Supabase stack; the cloud Edge Function cannot call the laptop, hence the local step runner and the throwaway Worker mock. Leave no mock Worker or `OMNIKOM_*` dev secret behind.
- The whole endpoint contract is ASSUMED. If Omnikom prefers a different auth (bearer, mTLS) the client changes in one file; the step, ladder and payload do not.
- Retries and B8's `dead` semantics differ on purpose; document that `retry_at` counts are ours so a reader of `jobs.attempts` is not misled (it stays 1 for the whole ladder).
- Data protection: the inquiry contains personal data forwarded to a group company; the privacy page and the form sentence must match (B16). If the lawyer wants explicit consent, the form gets a checkbox and `attribution` stays unchanged.
- If the Omnikom secret rotates, both sides need an overlap window; ASSUMED support for a second secret `OMNIKOM_WEBHOOK_SECRET_NEXT` is NOT built now; rotation is a manual maintenance window.
- sessionStorage attribution loses information across tabs and browsers; acceptable, it is a hint, not analytics. GA4 remains the analytics source of truth.
