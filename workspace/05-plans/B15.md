## Goal and observed exit
Every inquiry received on the site is delivered to Omnikom as a signed JSON webhook with the first-party attribution the visitor arrived with, retried when Omnikom is down, and visibly forwarded or failed in `/admin › Inquiries` (screen 11).
Observed exit: proven in two stages. Stage 1 (buildable now, no operator input, no Docker, S50): a mock receiver `scripts/omnikom-mock.ts` verifies the signature and prints the payload after a real inquiry is submitted against `mop-dev`. The Edge Function runs in the cloud and cannot reach the laptop's localhost, so stage 1 has two receivers: the mock on `127.0.0.1` driven by a local run of the step (`scripts/omnikom-run-local.ts`), and the same mock deployed as a throwaway Worker on `https://omnikom-mock.holy-meadow-4327.workers.dev` (E1, E2) for the cloud path, deleted afterwards. Stage 2: the payload is received by the real Omnikom endpoint. Decision S59: the operator has no Omnikom endpoint, so the slice ships switched off: `OMNIKOM_WEBHOOK_URL` stays unset on the one project (ruling H35 (1)), every `webhook_omnikom` job ends `done` with `skipped: "not_configured"` and screen 11 shows "not configured". Stage 2 is BLOCKED until Omnikom provides the endpoint URL and secret, it is not a launch input (L1 needs nothing from it), and the whole endpoint contract below is ASSUMED until Omnikom's side confirms it.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- Event `inquiry.received` (architecture 3.6) → recipe steps `send_email(inquiry_ack)`, `send_email(inquiry_forward)` (S55, B5), `notify_admin`, `webhook_omnikom` (architecture 5; B8b seed). Payload of the event: `{ inquiry_id }`; the job carries it as `jobs.payload.data.inquiry_id` (B8 envelope `{ params, data }`); B8's runner calls `step.run(ctx, job.payload.params, job.payload.data)`, so the step reads `inquiry_id` from its third argument and loads the row. The event is written by B8's `create_inquiry(p jsonb)` in the same transaction as the row (G20); B3's service emits nothing.
- Manual forward is B7's: screen 11's button calls B7's route `src/routes/api/admin/inquiries.$id.forward.ts`, which calls B7's `forward_inquiry` (`<ts>_admin_inquiries.sql`). That function calls B8's `enqueue_job_manual('webhook_omnikom', <inquiry_id>, {"data":{"inquiry_id":...}})`, so the key is `webhook_omnikom:<inquiry_id>:<n>` with n = 1 + the largest `n` among the existing keys that start with `webhook_omnikom:<inquiry_id>:` (`coalesce(max(split_part(idempotency_key, ':', 3)::int), 0)`, under B8's advisory lock), so a third re-forward after B8's retention pruned the first `done` job still gets a fresh key (DB-09); it writes the `audit_log` row with action `inquiries.forward` (B7's matrix id, G27) in the same transaction, and when `enqueue_job_manual` returns null it raises `enqueue_failed`, so the audit row rolls back and the route answers an error instead of a silent 202 (DB-09, B7's function). The button is enabled once `isImplemented("webhook_omnikom")` is true, which this slice makes so by registering the step. B15 adds no route and no audit write.
- Secrets, server side: `OMNIKOM_WEBHOOK_URL`, `OMNIKOM_WEBHOOK_SECRET` (tech-stack §4, Edge Function secrets). Stored as Supabase function secrets (`bunx supabase secrets set ... --project-ref $DEV_SUPABASE_PROJECT_REF`, no Docker) because the step runs in the Edge Function, and in Cloudflare only if a Worker route ever calls it (it does not). Neither exists in GitHub or `.env` today (E10); on dev the secret is a value made once with `openssl rand -hex 32` and appended to the repository-root `.env` (`E:\Matter Of Place\.env`, E10; the app folder has no `.env`) as `OMNIKOM_MOCK_SECRET` (never printed; step 5a), which the mock, `scripts/omnikom-run-local.ts` and the throwaway Worker read; the production value comes from Omnikom (step 7), and until Omnikom has an endpoint neither name is set on the one project (decision S59).

Endpoint contract (ASSUMED, to be confirmed with Omnikom; everything in this block is a proposal)
- Method and URL: `POST <OMNIKOM_WEBHOOK_URL>`, `content-type: application/json`, body at most 64 KB, response within 10 seconds.
- Headers: `X-MOP-Event: inquiry.received`, `X-MOP-Delivery-Id: <uuid, stable for one inquiry: every attempt and every job, recipe or manual, sends the same id>`, `X-MOP-Timestamp: <unix seconds>`, `X-MOP-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>" keyed by OMNIKOM_WEBHOOK_SECRET>`, `User-Agent: MatterOfPlace-Webhook/1`. The scheme is the one B8 uses for the render callback, so `signBody` and `verifyBody` in `src/server/lib/hmac.ts` are reused (the file is created by B8; this slice does not create it).
- Receiver must: verify the signature over the raw bytes, reject a timestamp older than 300 seconds, dedupe on `X-MOP-Delivery-Id`, and answer `200` or `202` when accepted, `409` when it already has the delivery (we treat that as delivered), `4xx` when the payload is refused (we do not retry), `5xx` or timeout when unavailable (we retry).
- Body, version 1:
```
{
  "id": "<delivery uuid>",
  "version": 1,
  "type": "inquiry.received",
  "occurred_at": "<ISO 8601>",
  "source": "matterofplace.com",
  "test": true,
  "data": {
    "inquiry": { "id", "intent", "topic", "name", "email", "phone", "location", "message", "details": {}, "source_path", "received_at" },
    "subject": { "kind": "property", "slug", "title", "market", "city", "tier", "presented_by": "agent" | "owner", "representation": { "name", "brokerage" } },
    "attribution": {
      "first_touch": { "landing_path", "referrer_host", "utm_source", "utm_medium", "utm_campaign", "utm_content", "at" },
      "last_touch":  { "landing_path", "referrer_host", "utm_source", "utm_medium", "utm_campaign", "utm_content", "at" },
      "pages_viewed": 0
    }
  }
}
```
Absent values are omitted, not null, not empty strings. `subject` is omitted for a general message. `"test": true` is optional and present only in bodies sent by `scripts/omnikom-send-test.ts` (step 7); the step never sets it.

How the body is made and kept (all in `src/server/omnikom/payload.ts` unless named):
- `id` (and `X-MOP-Delivery-Id`) = `deliveryId(inquiryId)`, a UUID v5 of the inquiry id under the fixed namespace constant `OMNIKOM_NS` (its SHA-1 from `sha1Bytes` of B1b's `src/server/lib/crypto.ts`, CS-04, which runs in Deno and in Bun). Every job for one inquiry, recipe or manual, sends the same id, so a re-forward of something Omnikom already holds comes back `409` and counts as delivered.
- `occurred_at` = `inquiries.received_at`, so it does not move between attempts.
- `data.inquiry` is built from an explicit allow-list of `inquiries` columns (`id`, `intent`, `topic`, `name`, `email`, `phone`, `location`, `message`, `details`, `source_path`, `received_at`); `ip_hash`, `turnstile_ok`, `assigned_to`, `state` and every other column are never read into it. `data.attribution` is `inquiries.attribution`.
- `data.subject` (only when `subject_kind = 'property'`): the step selects `properties.slug, title, market_slug, city, campaign_tier, presented_by_owner` and, through `representative_id`, `representatives.name, brokerage`, by `properties.slug = inquiries.subject_slug`, in any `editorial_state` (archived included). They map to `slug`, `title`, `market`, `city`, `tier`, `presented_by` (`owner` when `presented_by_owner` is true, else `agent`; S55, B2 invariant 22) and `representation { name, brokerage }`, which is omitted for an owner's home (it has no representative). The payload carries no submitter or contact field: the person who submitted the property receives the inquiry by B5's `inquiry_forward` mail, not through Omnikom. When no row is found, `subject` carries only `kind`, `slug` and `title` (from `inquiries.subject_title`).
- First attempt of a job: the step serialises the body once and stores the exact string in `jobs.result.body`. Later attempts of the same job (after `retry_at`) resend `jobs.result.body` byte for byte with a new timestamp and signature. A new job (manual re-forward) rebuilds the body from the row. When the job ends `done`, its stored result drops `body` (the delivered body lives in `forwarded_payload`).

Outputs
- On a `2xx` or `409` the step makes one call, `ctx.db.rpc("mark_inquiry_forwarded", { p_inquiry_id: <inquiry_id>, p_payload: <the sent body parsed back to an object> })` (G43: the application writes only through SQL functions; this slice's migration creates it, Data changes). The function runs `update inquiries set forwarded_at = now(), forwarded_payload = p_payload, state = case when state in ('new','in_progress') then 'forwarded' else state end where id = p_inquiry_id and anonymised_at is null` and returns whether a row matched (`state inquiry_state` with `new|in_progress|forwarded|closed` and `forwarded_at` come from the sketch through B2's `20261001090400_intake.sql`; `forwarded_payload` is B2's addition; a closed inquiry is never reopened; an anonymised row is never refilled). `false` (the row was anonymised or deleted while the call was in flight) makes the step throw `NonRetryableError("inquiry_gone")`; an RPC error makes it throw a plain `Error("mark_inquiry_forwarded_failed:<code>")`, which consumes one B8 attempt under B8's normal backoff (B8 invariant 3), and the resend carries the same delivery id, so Omnikom answers `409` and the next run lands the write. No other outcome writes `inquiries`.
- `inquiries.attribution jsonb` (new column, ASSUMED) stores what the browser captured at submit time. It is written only by `create_inquiry`, which this slice's migration replaces so the insert also sets `attribution = coalesce(p->'attribution', '{}'::jsonb)`; B3's `create` passes the validated `attribution` inside `p`. B8's `retention_anonymise_inquiries` resets it to `'{}'` and B7's `delete_subject` anonymises it with the rest of the row.
- `jobs.result` = `{ delivery_id, delivery_attempts, last_http_status?, next_at?, body? }`, written by B8's runner from the step's return value, for the timeline on screen 16 and the delivery badge on screen 11.
- Audit rows for manual forward come from B7's `forward_inquiry` (action `inquiries.forward`, G27); the system job writes none.

Invariants
1. Privacy minimum: the payload contains only fields the visitor typed plus attribution. No IP address, no user agent, no cookies, no other events. The privacy page (B16) states that inquiries can be shared with Omnikom, and the inquiry form shows the same sentence near the submit button (a copy change owned by B16: `t.forms.sharedWithOmnikom` directly above the submit button of `contact-form.tsx` and `inquiry-dialog.tsx`, and Omnikom named in the "Who receives it" section of `/privacy`, asserted by B16's `tests/unit/legal-pages.test.tsx`, which B15's Verification re-runs after step 3 has edited both form files).
2. Signed and timestamped on every attempt (new timestamp and signature, same delivery id and same body bytes on retries so Omnikom can dedupe).
3. Retry outside the normal backoff: partners are down for hours, and B8's 5-attempt policy gives up after about 8 minutes. The step therefore keeps its own counter in `jobs.result.delivery_attempts` and returns `{ status: "retry_at", at }` on `5xx`, `408`, `425`, `429` (honouring `Retry-After`) and network errors, failures 1 to 6 are rescheduled at +1 minute, +5 minutes, +30 minutes, +2 hours, +6 hours, +24 hours (or at `Retry-After` when that is later). The seventh failure throws `NonRetryableError("omnikom_unreachable")`; the job is `dead`, red on screen 16, the inquiry state is unchanged, and screen 11 shows "Not reached" and offers "Forward to Omnikom" again.
3b. On `refused` (any `4xx` other than `408`, `409`, `425`, `429`) the step throws `NonRetryableError("omnikom_refused:<status> <first 500 characters of the response body>")`, which B8's runner stores in `jobs.error`; the job is `dead` after one attempt, the inquiry state is unchanged, and screen 11 shows "Refused by Omnikom" and offers "Forward to Omnikom" again. A missing `inquiries` row or one with `anonymised_at` set throws `NonRetryableError("inquiry_gone")` before any call. `retry_at` does not consume B8 attempts (B8 invariant 3), which is why the counter is ours.
4. Attribution is first-party and cookie-free: `src/lib/attribution.ts` reads `utm_*` and `document.referrer` on the first page of a session and keeps them in `sessionStorage` (no cookie, no third party, no fingerprinting); it holds first touch and last touch and a page counter, and nothing else. `captureAttribution(location)` runs on the first client render and on every resolved client navigation: `first_touch` is written once per session (when the stored object is absent); `last_touch` is replaced only when the URL of that navigation carries any `utm_*` parameter or `document.referrer` is on another host (the first call sets it equal to `first_touch`); `pages_viewed` grows by one on every call. It is sent only when the visitor submits an inquiry: `readAttribution()` is called inside the submit handler, and no other request carries it.
5. The webhook never blocks the visitor: the API answers the inquiry as soon as the row is written; delivery is a job (architecture 1, side effects are jobs). Nothing under `src/server/inquiries/` or `src/routes/api/public/` imports `src/server/omnikom/` or calls the endpoint (Verification grep), and a submit while no receiver is running still answers success (step 5a).
6. Free tier: one small HTTPS call per inquiry.
7. Secrets never appear in logs or in `forwarded_payload`; the signature header is not stored.

Events emitted: none new. Analytics: no new event (the existing `contact_inquiry`, `property_inquiry`, `showing_request` and the like are already tracked by the forms).

## Risks and gotchas (link GOTCHAS ids)
- G-006: `OMNIKOM_*` server side only.
- G-004: `attribution` names are identical in `src/domain/contracts.ts`, `src/domain/omnikom.ts` and the column; a rename touches all three.
- P-008: never type the JSON body with backslashes inline in Bash for the curl proof; use a file.
- P-038 and E7: no Docker, no local Supabase stack; the cloud Edge Function cannot call the laptop, hence the local step runner and the throwaway Worker mock. Leave no mock Worker or `OMNIKOM_*` dev secret behind: the one project becomes production at L1's launch switch (ruling H35), and a leftover mock URL there would send real inquiries to a test receiver.
- Decision S59: no Omnikom endpoint exists. The switched-off state is the shipped state, visible as "not configured" on screen 11, not an error; turning it on is step 7's one `secrets set`.
- The whole endpoint contract is ASSUMED. If Omnikom prefers a different auth (bearer, mTLS) the client changes in one file; the step, ladder and payload do not.
- Retries and B8's `dead` semantics differ on purpose; document that `retry_at` counts are ours so a reader of `jobs.attempts` is not misled (it stays 1 for the whole ladder).
- Data protection: the inquiry contains personal data forwarded to a group company; the privacy page and the form sentence must match (B16; its "Who receives it" section already names Omnikom for forwarded inquiries). If the lawyer wants explicit consent, the form gets a checkbox and `attribution` stays unchanged.
- Data-subject deletion: a fulfilled delete request (B7 `delete_subject`, screen 25) for an inquiry with `forwarded_at` set is relayed to Omnikom by email from the person handling the request, by hand, and recorded in the request's note; an automated deletion webhook to Omnikom is out of scope for v1. A `webhook_omnikom` job that still holds `jobs.result.body` (dead, or queued between retries) has the body removed (`result = result - 'body'`) by B7's `delete_subject` and by B8's `retention_anonymise_inquiries` for that inquiry (G16), and a later run of such a job throws `inquiry_gone` with no call (step 4 case); dead jobs themselves are deleted after 90 days by B8's retention job (`jobs_dead`).
- If the Omnikom secret rotates, both sides need an overlap window; ASSUMED support for a second secret `OMNIKOM_WEBHOOK_SECRET_NEXT` is NOT built now; rotation is a manual maintenance window.
- sessionStorage attribution loses information across tabs and browsers; acceptable, it is a hint, not analytics. GA4 remains the analytics source of truth.
