The report `workspace/audits/harden-YYYY-MM-DD.md` has no red row. Two rehearsals have been done for real: restore from a backup, and roll the Worker back.
Observed exit: `node scripts/harden/run-all.mjs --env dev --report` exits 0 and writes the report; the report lists H1-01 to H1-34 each `pass` or `signed` (manual, with initials and date), the free-tier gauge table has no line at 70 percent or more without a recorded decision, and the CEO's sign-off line is present.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs: the `mop-dev` stack and a production-configured preview (same build as production, `MOP_ENV=production` catalog rules), the GitHub repository settings, the Cloudflare zone, Supabase projects.
Outputs: `scripts/harden/*` (runner plus checks), `docs/runbook-rollback.md`, `docs/runbook-restore.md`, `docs/security.md` (what is protected and how), the sign-off report, fixes to whatever the checks find.
Invariants
1. Every checklist item has a proof that a person can re-run: a command with expected output, or a named manual check with an owner. "Looks fine" is not a proof.
2. Every new automated check is watched-fail: break the thing it guards, see the check red for the right reason, restore (global rule 2).
3. Findings are fixed in the slice that owns them; H1 does not patch features silently. Each fix is a commit that names the H1 item.
4. No production data touched. Restore rehearsal runs against a local Postgres, never against `mop-prod`, and Supabase's free plan allows only the two projects `mop-dev` and `mop-prod`, so there is no third cloud project to restore into (P-009 context).
5. Nothing new is paid for. If a check shows a limit is reached, the result is a decision row in PROJECT-STATE (G-011), not a plan upgrade.
Events emitted: none. Permissions: needs admin access to GitHub, Cloudflare, Supabase; runs from a developer machine and from CI.

## Steps (ordered; each fits half a day; each ends with the command that proves it)
1. Checklist as data and the runner. Write `checklist.json` and `run-all.mjs`; wire the already existing checks. Proof: `node scripts/harden/run-all.mjs --env dev --only H1-18` prints the table row with `pass` and exit 0; `node scripts/harden/run-all.mjs --list` prints 34 items.
2. Security batch A: headers, CSP, Turnstile coverage, rate limits, upload probes, HMAC. Proof: `node scripts/harden/run-all.mjs --env prod-config --only H1-01,H1-02,H1-03,H1-04,H1-05,H1-11,H1-12`. Fix findings in place.
3. RLS review. `rls-review.sql` returns, from `pg_catalog`: every table in `public` with `relrowsecurity` and `relforcerowsecurity`, every policy (`pg_policies`) with roles and command, and `has_table_privilege` for `anon` and `authenticated` on every table and function; `rls-review.ts` fails when (a) any `public` table has RLS off, (b) `anon` has any privilege on an admin table or on `audit_log`, `events`, `jobs`, `agent_keys`, `payments`, `subscribers`, (c) a table has no policy for a role that architecture 3.7 lists, (d) a table has an update or delete policy where 3.7 says insert-only (`audit_log`, `events`, `automation_revisions`), (e) a `security definer` function lacks a fixed `search_path` or is executable by `anon`. `rls-matrix.db.test.ts` then acts as each of the six roles through `set local role` plus JWT claims and asserts the allowed and refused writes of architecture 3.7. Proof: `bun run scripts/harden/rls-review.ts --env dev` exit 0 and `bunx vitest run tests/db/rls-matrix.db.test.ts`; plus `supabase db advisors --linked --type security`.
4. Security batch B: secrets and scans. `gitleaks` in CI, `bun audit`, and the `claude-security:scan` skill with its report saved and each finding closed or accepted in writing. Proof: `node scripts/harden/run-all.mjs --only H1-06,H1-07,H1-08,H1-09,H1-10` all `pass`; the scan report file exists.
5. States and honesty. 404 with a real 404 status, 500 boundary with request id, loading skeletons, legal entity, illustrative purge, coming-soon signup, SEO checker in production mode. Proof: `bunx playwright test tests/e2e/states.spec.ts tests/e2e/coming-soon.spec.ts` and `node scripts/harden/run-all.mjs --env prod-config --only H1-24,H1-25,H1-26,H1-29`.
6. Backups and the restore rehearsal. `backup.yml` runs `pg_dump --format=custom --no-owner` for schemas `public` and the `auth` data, through the Supabase session-mode pooler connection string (Actions runners have no IPv6 and the free direct host is IPv6 only, UNPROVEN until the first run), with the client version at least equal to the server's, encrypts with `age` to the CEO's public key (the private key is held offline; the dump contains subscriber emails) and uploads to R2 with a 30-day lifecycle rule. Rehearsal `restore-rehearsal.sh`: download the newest dump with the S3 API, decrypt with the offline key, start a local database with `supabase start`, `pg_restore --clean --if-exists`, run `scripts/harden/rowcounts.sql` on both sides, compare counts for `properties`, `submissions`, `subscribers`, `audit_log`, `payments`, `jobs`, and check that the latest `audit_log.at` is within 24 hours of the dump time. Proof: `gh workflow run backup.yml && gh run watch` green, then `bash scripts/harden/restore-rehearsal.sh` prints `restore ok` and the minutes taken, written into `docs/runbook-restore.md`. R2 originals are not part of the dump (R2 is the durable store; versioning is off, ASSUMED acceptable at launch, recorded as a known gap).
7. Rollback drill. Deploy a build that adds a visible marker (`<meta name="x-drill" content="v2">` on `/`), confirm it, then `bunx wrangler rollback` (to the previous version, or `bunx wrangler rollback <version-id>` after `bunx wrangler versions list`), confirm the marker is gone and record the seconds. Also record the rule that a rollback does not undo migrations: destructive schema changes follow expand then contract across two releases, so the previous Worker still works against the newer schema. Proof: `bash scripts/harden/rollback-drill.sh` prints `deployed v2 marker ok`, `rollback ok`, `elapsed <n>s`; `docs/runbook-rollback.md` contains the command sequence. Caveat noted: rollback covers the code and vars of that Worker version, not Supabase secrets or R2 (UNPROVEN, confirm from the drill).
8. Performance and platform limits: Lighthouse on the production-rules preview, accessibility sweep, CPU probe against the 10 ms free-plan limit, gauges. Proof: `node scripts/harden/run-all.mjs --env prod-config --only H1-27,H1-28,H1-30,H1-33`. If H1-30 fails, the first response is edge caching of SSR HTML by `catalog_version` (already the design), the second is a recorded decision to pay for the Workers plan (G-011); never a silent binding.
9. Automations and observability drills, then the sign-off report. `fail-drill`, `health-drill`, `sentry-probe`, parity test, manual items signed. Proof: `node scripts/harden/run-all.mjs --env prod-config --report` exits 0 and `workspace/audits/harden-<date>.md` shows 34 of 34 with the manual items signed; the CEO's line is added by hand.

## Risks and gotchas (link GOTCHAS ids)
- G-011 and P-009: H1-30 and H1-33 are where a free-tier limit shows up first. The Workers free plan gives 10 ms CPU per request; SSR of a cold page may exceed it. This is UNPROVEN until measured; the mitigation order is cache first, decision second.
- G-012: `backup.yml` and `audit-deps.yml` live in the root `.github/workflows/`.
- G-006: H1-07 proves G-006 mechanically.
- G-001: never edit `routeTree.gen.ts` to add the probe routes; probes live under `scripts/`.
- P-015: on this Windows machine `curl` and `render-gate` arguments beginning with `/` are rewritten by Git Bash; prefix `MSYS_NO_PATHCONV=1` for `node ... render-gate.mjs http://... / /properties` or run from PowerShell.
- P-008: never type JSON with backslashes inline in Bash; the probes read fixture files.
- P-013: use absolute paths in every drill script.
- P-014 and P-017: any long drill run by a headless agent must stay in the foreground and poll; the rehearsal scripts print timings themselves so a truncated run is obvious.
- Supabase free projects pause after 7 idle days; if `mop-dev` paused while HARDEN ran, restore it before trusting a red result.
- The `claude-security` scan is a review aid, not a proof of absence; the RLS matrix test and the header probes are the deterministic backbone.
- Dependency audits on `bun` require a recent bun; if `bun audit` is unavailable, `npm audit --omit=dev` on a lockfile export is the ASSUMED substitute.
