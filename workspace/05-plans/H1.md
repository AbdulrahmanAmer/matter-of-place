## Goal and observed exit
A single command runs every automatable check and prints a table of item, result, evidence; the items that cannot be automated are done by a named person and recorded with a date. The report `workspace/audits/harden-YYYY-MM-DD.md` has no red row. Four rehearsals have been done for real: restore from a backup, roll the Worker back, roll a migration back, and walk the incident runbook on `mop-dev`. Two runbooks a person can follow at 3 a.m. exist as files: `docs/runbooks/incident.md` and `docs/runbooks/rotation.md`.
Observed exit: `node scripts/harden/run-all.mjs --env dev --report` exits 0 and writes the report; the report lists H1-01 to H1-39 each `pass` or `signed` (manual, with initials and date), the free-tier gauge table has no line at 70 percent or more without a recorded decision, and the CEO's sign-off line is present.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs: the `mop-dev` stack and a production-configured preview (same build as production, `MOP_ENV=production` catalog rules), the GitHub repository settings, the Cloudflare zone, Supabase projects.
Outputs: `scripts/harden/*` (runner plus checks), `docs/runbooks/incident.md`, `docs/runbooks/rotation.md`, `docs/runbooks/rollback.md`, `docs/runbooks/restore.md`, `docs/security.md` (what is protected and how), the sign-off report, fixes to whatever the checks find.
Invariants
1. Every checklist item has a proof that a person can re-run: a command with expected output, or a named manual check with an owner. "Looks fine" is not a proof.
2. Every new automated check is watched-fail: break the thing it guards, see the check red for the right reason, restore (global rule 2).
3. Findings are fixed in the slice that owns them; H1 does not patch features silently. Each fix is a commit that names the H1 item.
4. No production data touched. Restore rehearsal runs against a local Postgres, never against `mop-prod`, and Supabase's free plan allows only the two projects `mop-dev` and `mop-prod`, so there is no third cloud project to restore into (P-009 context).
5. A runbook is a proof, not prose: `scripts/harden/runbook-lint.mjs` fails a runbook that lacks a required heading or names a command, script or file that does not exist, and the incident runbook is walked once by a person who did not write it (manual item below).
6. Nothing new is paid for. If a check shows a limit is reached, the result is a decision row in PROJECT-STATE (G-011), not a plan upgrade.
Events emitted: none. Permissions: needs admin access to GitHub, Cloudflare, Supabase; runs from a developer machine and from CI.

## Risks and gotchas (link GOTCHAS ids)
- G-011 and P-009: H1-30 and H1-33 are where a free-tier limit shows up first. The Workers free plan gives 10 ms CPU per request; SSR of a cold page may exceed it. This is UNPROVEN until measured; the mitigation order is cache first, decision second.
- G-012: `backup.yml` and `audit-deps.yml` live in the root `.github/workflows/`.
- G-006: H1-07 proves G-006 mechanically.
- G-001: never edit `routeTree.gen.ts` to add the probe routes; probes live under `scripts/`.
- P-015: on this Windows machine `curl` and `render-gate` arguments beginning with `/` are rewritten by Git Bash; prefix `MSYS_NO_PATHCONV=1` for `node ... render-gate.mjs http://... / /properties` or run from PowerShell.
- P-008: never type JSON with backslashes inline in Bash; the probes read fixture files.
- P-013: use absolute paths in every drill script.
- P-014 and P-017: any long drill run by a headless agent must stay in the foreground and poll; the rehearsal scripts print timings themselves so a truncated run is obvious.
- GS-08: the Cloudflare free plan has one rate-limit rule and five custom rules; the managed ruleset on free is the Free Managed Ruleset and Bot Fight Mode is a zone setting (ASSUMED both available; check in the dashboard). Whether the free managed ruleset blocks the probe string is UNPROVEN, if it returns 200 the check reports it and the config checks stay the proof. The zone only serves traffic after L1 step 4, so the API-side checks run in H1 and the live probe is repeated after cut-over. `CF_API_TOKEN` for these reads is read-only and separate from the deploy token.
- GD-03: the retention drill deletes objects in the dev R2 bucket; it must never read `MOP_ENV=production` credentials (the script refuses when `--env prod-config` points at a production database URL). Analytics rows sit in monthly partitions (architecture 3.3); retention drops whole partitions and deletes within the current one, and the drill must cover both.
- GD-07: rollback of a migration is rehearsed on a local database only, never on `mop-dev` shared state; destructive migrations are expand then contract, so an irreversible one needs its written reason and the CEO's initials in `docs/runbooks/rollback.md`.
- GS-01: the Supabase key system offers new secret keys that can be created and revoked separately (ASSUMED for the current project generation); if `mop-prod` is on legacy JWT keys, rotating the service role means rotating the JWT secret and every dependent token at once, which the runbook must say before anyone starts. Meta token expiry is enforced by Meta, not by us; the 7 day alert comes from B8's job and is proven there.
- GS-05: the runbook names roles and mailboxes, not people, because staffing is a business decision; a runbook nobody has walked is fiction, so the game day is a signed manual item, not optional.
- Supabase free projects pause after 7 idle days; if `mop-dev` paused while HARDEN ran, restore it before trusting a red result.
- The `claude-security` scan is a review aid, not a proof of absence; the RLS matrix test and the header probes are the deterministic backbone.
- Dependency audits on `bun` require a recent bun; if `bun audit` is unavailable, `npm audit --omit=dev` on a lockfile export is the ASSUMED substitute.

## Out of scope
