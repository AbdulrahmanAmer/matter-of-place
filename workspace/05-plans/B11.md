## Goal and observed exit
Place Notes is assembled automatically every 14 days from what was published since the last issue, reviewed and approved by a human on `/admin › Newsletter` (screen 13), and sent through Resend Broadcasts to confirmed subscribers only; Campaign-tier properties also get a standalone email to the property's market audience.
Observed exit (completion map B11, adjusted: it says weekly, S25 says every two weeks and wins): "broadcast delivered to a test audience." Proof: step 8 sends an approved issue to an audience of three test addresses and shows delivered events, then an unsubscribe on one address removes it from the next send.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- Event `asset.approved` → step `queue_digest` (mode `enqueue`); B8b's seed already limits it with `conditions.kinds = ["newsletter_block"]`, and the step re-checks `data.kind` itself. Event `digest.due` (emitted by B8b's `runDueSchedules` when `schedule_settings.digest` is due, default every 14 days) → step `queue_digest` (mode `build_issue`) then `notify_admin`. One catalog step `queue_digest` with param `mode: "enqueue" | "build_issue"` (default `enqueue`); the params schema is B8b's (`src/server/automation/step-specs.ts`, architecture 5, closed catalog of 17 steps) and B8b's seed already sets `build_issue` for `digest.due`.
- Resend contacts are B11's (A7). Event `subscriber.confirmed` is emitted by B3's `confirm_subscriber` and its seeded recipe stays empty (B8b). The contact is created by the system job `contact_sync` (Files), which the trigger `subscribers_contact_sync` of `<ts>_newsletter.sql` enqueues in the same transaction that sets `subscribers.confirmed_at`. Outcome: `resend_contact_id` stored, contact added to the audience `place-notes` only when `source` does not start with `interest:` (B3b invariant 7: an interest signup is not Place Notes consent), and to `market-<ca|ny|fl>` for each entry of `subscribers.markets`.
- Admin actions from screen 13: build, edit, preview, send test, approve (with optional `send_at`), unapprove.
- Resend webhook events arrive at B3's `POST /api/hooks/resend` (A6), which verifies them and calls B5's `applyEmailEvent`; B5 stores each one in `email_events` with the broadcast id (delivery, bounce, complaint, and, when tracking is on, open and click) and turns `contact.updated` with `unsubscribed: true` into `subscribers.unsubscribed_at` (B5 invariant 9). B11 only aggregates `email_events`.
- Secrets: `RESEND_API_KEY` (tech-stack 4), in Supabase function secrets because the send job runs in the Edge Function. No Resend account exists yet (ASSUMED E9): every step that calls Resend for real is BLOCKED until the operator creates the account, verifies the domain and puts the key in `.env` and the function secrets; unit tests with Resend mocked do not need it. The Worker never calls Resend (B5): screen 13's send test and every send run as jobs in the Edge Function. With `EMAIL_DRY_RUN=1` (B5, set on `mop-dev` until A3) every Resend call of this slice makes no network call and its job ends `{ skipped: "dry_run" }`.
- Sender of broadcasts: `settings.resend.from_notes` when set, else B5's `RESEND_FROM`; it must be an address on the verified domain (Risks).

Outputs
- `newsletter_issues` rows (architecture 3.6): `number`, `scheduled_for`, `status` `draft|approved|sending|sent`, `blocks jsonb`, `subject`, `resend_broadcast_id`, `metrics jsonb`, `approved_by`. ASSUMED extra columns `preheader text`, `sent_at`, `updated_at`, `send_error text`, `approval_count int not null default 0`. There is no `send_at` column: approve writes `send_at` (null means now) into `scheduled_for`, and the preview and send jobs compare against `scheduled_for` and `approval_count`.
- `blocks` is an ordered array: `{ id, type: "intro" | "property" | "story", asset_id?, property_id?, story_id?, text? }`. Property blocks point at an approved `newsletter_block` asset; story blocks point at a published `stories` row.
- Resend objects: audiences (`place-notes`, `market-ca`, `market-ny`, `market-fl`; named with the prefix `dev-` whenever `SITE_URL` is not `https://matterofplace.com`, because `mop-dev` and production share one Resend account), their ids kept in `settings.resend.audiences`, one Broadcast per issue (`newsletter_issues.resend_broadcast_id`) and per standalone email (`assets.meta.broadcast = { id, recipients, sent_at }` on the `standalone_email` asset). ASSUMED adapter risk: Resend has been reorganising Audiences into a newer contacts and segments model; the spec says Audiences and Broadcasts, the adapter `src/server/channels/resend.ts` is the only file that knows the API, and step 2 re-reads the current docs before coding.
- `newsletter_issues.metrics`: `{ recipients, delivered, bounced, complained, opened, clicked, unsubscribed, per_property: { <property_id>: { clicks } }, updated_at }`.
- Rendered issue HTML from `src/templates/email/place-notes.tsx` (masthead, optional intro line, property blocks via B9 `NewsletterBlock`, story blocks, footer with the Omnikom legal entity and postal address, Resend unsubscribe variable).

Invariants
1. Never send an empty issue. `queue_digest` in mode `build_issue` with zero eligible properties and zero eligible stories creates no draft and returns `{ status: "done", result: { issue_id: null } }`; the recipe's `notify_admin` then says "Nothing to send this cycle" (the `digest.due` change to B5's resolver, Files). The schedule is advanced by B8b's `runDueSchedules` claim (`last_run_at`, `next_run_at`), not by this slice. Coming-soon reality (S30): the first issues will be editorial only or absent.
2. Recipients are exactly: `confirmed_at is not null and unsubscribed_at is null and archived_at is null` and the address is not in `email_suppressions` (B5: hard bounces and spam complaints, GG-05); for `place-notes` also `source not like 'interest:%'` (B3b invariant 7), for `market-<x>` also `<market slug> = any(markets)`. SQL `newsletter_recipient_count(p_audience text)` counts them. Anything else is never added to an audience. An unsubscribe on Resend's hosted page reaches `subscribers.unsubscribed_at` through B5's `applyEmailEvent` (`contact.updated` with `unsubscribed: true`, B5 invariant 9) within the webhook's latency; Resend itself stops mailing that contact, and `removeStaleContacts` (Files) removes it from every audience before the next send. There is no Matter of Place unsubscribe endpoint.
3. Human approval always. No agent can approve or send an issue (ASSUMED, conservative: S23 covers social posts only, email is irreversible and affects sender reputation). `approve` requires `actor_kind = human`. Screen 13 send-test is allowed for agents.
4. Footer completeness gate: the send job and `sendStandalone` throw `NonRetryableError("footer_incomplete")` (after writing `send_error`) when `loadSiteContext(db)` (B5, reading `settings.site`, filled by B16) returns a null `legal.entity` or `legal.address`, or when `{{{RESEND_UNSUBSCRIBE_URL}}}` is missing from the rendered HTML. Every broadcast carries `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`: `createBroadcast` passes them in `headers` unless step 2 records in `docs/runbook-newsletter.md` that Resend adds them itself to broadcasts that use the unsubscribe variable. Reason: postal address and working unsubscribe are legal requirements for commercial email (CAN-SPAM).
5. Free-tier gate (P-009): before sending, `assertQuota(db, recipients, now)` adds the audience's `newsletter_recipient_count` to `email_sent_today()` (B5's function, which `<ts>_newsletter.sql` extends to count broadcast recipients too) and compares the sum with `settings.email.daily_cap` (B5, default 90, which is the 90 percent headroom of the free 100 a day); it adds the recipients to the month total (`email_messages` with `sent_at` this UTC month plus `broadcast_recipients_since(<start of month>)`) and compares with 2,700 (90 percent of 3,000). When today is the only problem the job returns `{ status: "retry_at", at: next UTC midnight plus 1 minute, reason: "quota" }` (no attempt consumed, B8 invariant 3) and enqueues one `notify_admin` with the numbers (key `notify_admin:quota:<issue_id>:<UTC date>`); when the recipients alone exceed the daily cap it throws `NonRetryableError("quota_exceeds_plan")`, writes `send_error` and notifies admin. The issue stays `approved` and nothing is split silently. A broadcast to more than about 90 contacts cannot leave in one day on the free tier; that is the first paid-tier trigger (Resend Pro, decision required per G-011).
6. Idempotent send: `newsletter_approve_issue` enqueues the system job `newsletter_send` with key `newsletter_send:<issue_id>:<approval_count>` and `run_after = scheduled_for`; the broadcast is created at most once (`resend_broadcast_id` written right after create and before send, and checked first). A crash after "create" resumes with "send". The handler exits `{ skipped: "stale" }` when the issue is no longer `approved` or `sending` or its `approval_count` differs from the job's; `{ skipped: "channel_disabled" }` (with one `notify_admin`) when `channel_settings.newsletter.enabled` is false. Status moves `approved` → `sending` before create and `sending` → `sent` with `sent_at = now()` when `sendBroadcast` returns 2xx; there is no poll and no webhook wait. Resend 429 returns `retry_at` from `Retry-After`, 5xx and network errors throw (B8 backoff), other 4xx throw `NonRetryableError` after writing `send_error`.
7. Subject and preheader are built by rule, not by a model (S20): `Place Notes No. <n>: <first block title>` truncated at a word boundary to 60 characters, preheader = first block deck up to 110 characters, no em dashes, editable by a human before approval.
8. Link hygiene: every link in an issue carries `utm_source=place_notes&utm_medium=email&utm_campaign=issue-<n>&utm_content=<slug>` so B15 attribution and GA4 see it; no third-party redirect tracking beyond what Resend adds when open and click tracking are switched on (ASSUMED on for clicks, off for opens: opens are unreliable after mail privacy features and are recorded as soft).
9. Standalone email (Campaign tier): template key `standalone` (B5's row, B8b's seeded `property.published` step, B9's layout in `standalone.tsx`), sent as one Broadcast to `market-<property market>` only, never through B5's one-address `sendTransactional`. Mechanism: B5's `send_email` step, when `params.template = "standalone"` and after its template-enabled check, calls `sendStandalone(ctx, data)` (Files) instead of the per-recipient path. `sendStandalone` reads the approved `standalone_email` asset of `data.property_id` (highest revision), renders the `standalone` row with `{ subject, preheader, block }` from the asset's `meta`, applies the footer gate (invariant 4), the channel switch and the quota gate (invariant 5), calls `removeStaleContacts`, `ensureAudience("market-<ca|ny|fl>")`, `createBroadcast` (skipped when `assets.meta.broadcast.id` is already set; the id is written right after create) and `sendBroadcast`, then writes `meta.broadcast.recipients` and `sent_at`. It requires the pending `standalone_email` asset to be approved on screen 10; approving that asset also approves the linked `waiting_approval` `send_email(standalone)` job in one click (ASSUMED link: matched by property id and step type), so a human does not approve twice.

10. List hygiene (GG-05). B5 supplies the template, columns, SQL functions and helpers; this slice schedules and calls them and owns the Resend side. The system job `newsletter_hygiene` runs daily (pg_cron `0 16 * * *` UTC, key `newsletter_hygiene:<UTC date>`, Data changes) and, in order: (a) calls B5's `repermission_candidates(20)` and `enqueueRepermissionEmail(db, id)` for each row, so at most 20 re-permission emails a day (template `repermission`, B5's job key `send_email:<subscriber_id>:rp:<hash12>`, `repermission_sent_at` set by `issue_repermission`); (b) calls B5's `lapseSubscribers(db)`, which archives and unsubscribes every subscriber asked more than 30 days ago with no engagement and writes one `audit_log` row with the count (no personal data); (c) calls `removeStaleContacts(db)`, which removes from every audience each contact whose subscriber is unsubscribed, archived or in `email_suppressions` (bounce and complaint suppressions recorded by B5 included) and clears its `resend_contact_id`; (d) enqueues `contact_sync` for at most 50 eligible confirmed subscribers whose `resend_contact_id` is null (heals syncs skipped while Resend was not configured). Nothing here can re-add a suppressed address (invariant 2). A subscriber is inactive when `coalesce(last_engaged_at, confirmed_at)` is older than 12 months (B5's definition); a click on the confirm link confirms again through B3's `confirm_subscriber`, and B5's trigger `subscribers_engagement` then sets `last_engaged_at` and clears `repermission_sent_at`. Opens never count as engagement (invariant 8).
11. Automatic previews (GG-06). `newsletter_approve_issue`, in the same transaction that sets `approved`, enqueues the system job `newsletter_preview` with key `newsletter_preview:<issue_id>:<approval_count>` and `run_after = scheduled_for - 24 h` when that is in the future, otherwise now (the admin is then told it arrives with the send). The job re-reads the issue first: if its status is no longer `approved` or its `approval_count` differs from the job's (unapproved, or approved again with a new `send_at`), it exits `{ skipped: "stale" }` without sending. Otherwise it sends the rendered issue (desktop layout, subject prefixed `Preview:`) to every address of B5's `resolveAdminRecipients(db)` (`settings.notifications.recipients` first: admin@ and the CEO) through B5's `sendOne`, one `email_messages` row per address (kind `transactional`, `template_key` `newsletter_preview`); with no address it throws `NonRetryableError("no_recipients")`. Screen 13's send test uses the same handler with `data.test = true` and the actor's address, kind `test`, subject prefixed `[Test]`. Standalone property emails (invariant 9) send on approval with no schedule, so they have no 24 hour preview; the approval on screen 10 is their preview.
12. Weekly KPI email to the CEO (GG-03). Every Saturday at 15:00 UTC (pg_cron, Data changes) the system job `kpi_weekly` (key `kpi_weekly:<UTC date>`) computes the KPIs for the last full ISO week (Monday to Sunday in `America/New_York`, ASSUMED owner zone) with the SQL function `kpi_weekly(p_week_start date)` and emails them to every address of `resolveAdminRecipients(db)` through B5's `sendOne` (one `email_messages` row per address, `template_key` `kpi_weekly`, so the daily cap counts it; a 429 returns `retry_at`). The definitions live in one file, `src/server/kpi/definitions.ts`, and are: submissions received (`submissions.created_at`); acceptance rate (accepted decisions divided by accepted plus declined decisions made in the week, shown as "n of m", never a percentage of zero; a decision is an `events` row of type `submission.accepted` or `submission.declined`, dated by `events.at`, matched by `payload->>'submission_id'`); time to decision (median hours from `submissions.created_at` to the first such event of that submission); invoices issued and invoices paid (count and amount from `payments.issued_at` and `paid_at`, `void` excluded); properties published (`published_at`); posts by channel (`social_posts.posted_at`); newsletter growth (confirmed in the week, unsubscribed in the week, net, total confirmed); inquiries per published property (received in the week divided by published properties, with the top five properties by count; "no published properties yet" when there are none). Each value shows the change against the previous week. No model writes it (S20). B14's audit report reads the same function so the two never disagree.
13. Resend contacts (A7). Start: the trigger `subscribers_contact_sync` (after update of `confirmed_at` on `subscribers`, when the new value is not null) calls B8's `enqueue_job('contact_sync', jsonb_build_object('params', '{}'::jsonb, 'data', jsonb_build_object('subscriber_id', new.id)), 'contact_sync:' || new.id || ':' || extract(epoch from new.confirmed_at)::bigint)`, so a double opt-in click and a re-permission click each start one job. The handler skips (`{ skipped: "not_eligible" }`) a subscriber that invariant 2 excludes, calls `ensureAudience` and `addContact` for each audience of the Inputs rule (a contact that already exists counts as added), and stores `resend_contact_id`; a second run makes no new contact. Removal: `removeStaleContacts` (invariant 10 c, and before every broadcast). Forgetting (CCPA, B3 GP-01): the trigger `subscribers_contact_forget` (before update of `email`, when the new value ends with `.invalid`, which is how B7's `delete_subject` anonymises an address, and `old.resend_contact_id` is not null) enqueues `contact_forget` with key `contact_forget:<subscriber_id>` and `data = { resend_contact_id }` (no address in the payload); its handler calls `deleteContact` and treats 404 as done. Failures in both handlers: 429 returns `retry_at` from `Retry-After`, 5xx and network errors throw (B8 backoff), other 4xx throw `NonRetryableError`; with `EMAIL_DRY_RUN=1` they skip, and without `RESEND_API_KEY` they throw `NonRetryableError("resend_not_configured")` (B5's convention), healed later by invariant 10 d.

Events emitted: none new. Consumed: `asset.approved`, `digest.due`. `subscriber.confirmed` keeps its empty recipe; contact creation hangs on the `confirmed_at` change itself (invariant 13), the same row change that emits the event.

- G-004: `src/domain/newsletter.ts` block types and `newsletter_issues.blocks` shape change together; `blocks` is jsonb so the Zod schema is the guard, backed by the DB check `jsonb_typeof(blocks) = 'array'`.
- G-007: email HTML needs colours inline, so the issue template reads them from B5's generated `src/templates/theme.gen.ts` (`scripts/gen-theme.ts`, from `tokens.css`) rather than copying hex; this slice creates no tokens file.
- Timezone: `scheduled_for` (which holds `send_at`) is stored in UTC; the editor shows the owner's timezone from `settings`.
- Two Resend environments, one account: the `dev-` audience prefix keeps `mop-dev` test sends away from production subscribers; a builder who removes it can mail real people from a test.
- Legal: the privacy page (B16) must say email addresses are held for Place Notes and that inquiries can be forwarded to Omnikom (B15). Otherwise footer and privacy disagree.
- GG-05: re-permission mail counts toward the 100 a day of P-009: it is sent by B5's `send_email`, whose daily cap reads `email_sent_today()`, which counts broadcasts too after this slice; the 20 a day cap keeps it from starving transactional mail. Lapsing a silent subscriber is irreversible for us (they can sign up again); the thirty day wait and B5's audit row are the safeguards. Engagement uses clicks only, so a subscriber who reads without clicking is asked once a year, which the copy must make painless.
- GG-06: the preview reaches the same inbox that receives `notify_admin`; if the recipients list (B7 screen 24) is empty the job fails loudly rather than skipping, because a silent missing preview defeats its purpose. The preview is of the frozen issue; approval locks edits, so what arrives is what sends.
- GG-03: the KPIs are counts and medians over tables that are empty before launch (S30), so the first emails say zero; that is correct. "Week" is ISO in the owner zone; if the CEO wants another day or zone, it is one constant in `definitions.ts`.
