## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- `markets.coming_soon` (default true), `markets.interest_copy`, `settings.coming_soon_global` (default `false`; the fail-safe is `markets.coming_soon` defaulting to `true`, so no second migration is needed and L1 only verifies the state on `mop-prod`), `settings.environment` (`development | preview | production`, default `development`), `subscribers.markets text[]`, `properties.status` (`Illustrative` for every seeded property).
- `Market.comingSoon: boolean` and `interestCopy?: string` in the API payload (mapped by B3: `comingSoon = coming_soon_global OR markets.coming_soon`).
- `settings.flags` (GQ-05): one row, `value jsonb` of boolean feature flags, seeded by this slice's migration as `{"new_channels": false, "archive_pages": false}`. `settings.coming_soon_global` stays its own row (architecture 3.1 names it) and is exposed as the flag `coming_soon` by the reader below, so coming-soon is a flag to the code without a second stored copy (ASSUMED reading of "coming-soon is a flag").

Outputs
- Empty states on `/`, `/properties`, `/stories`, `/$market`, `/$market/$region`, and the "Opening soon" badge on market cards (`/markets`, home).
- `InterestForm`: one email field, the market preselected on market and region pages, a three-market chooser elsewhere, writing `subscribers.markets` through the existing `POST /api/public/subscribers`.
- `IllustrativeNotice`: the viewer statement, shown wherever an illustrative property is on the page, never in production.
- The database guard, the direct market-opening proof (the recipe step that opens a market on first publication is B8b's), and the interest counts view `market_interest_counts` (created here; B7 reads it and creates no `market_interest` view).
- `ConsentNotice` (GP-02): a footer-anchored notice that asks once whether Google Analytics may count page reads, and the small consent library behind it (`src/lib/consent.ts`). No popup, no overlay, nothing on load that takes focus or covers content.
- `getFlags(db)` (GQ-05, caching contract S52 rule 1, F24): the one Worker-side reader of feature flags, a thin function over `getPublicState(db)` (B3) that makes no query of its own, returning `{ coming_soon, new_channels, archive_pages }` (flag keys are snake_case in code as in the database, G18; B17 adds `csp_enforce` and `maintenance` under the same spelling); B8b reads `new_channels`; B13 reads `archive_pages` from the same public state: archive pages exist only when the flag is on and B13's threshold of 3 is met (G18), and the seeded value is false, so an admin turns it on (screen 24). Its caller on every page request is B1b's pipeline: `src/start.ts` passes `deps.getFlags = () => getFlags(getDb())` to `handle`, which hands the result to `securityHeaders` and `cspFor` (B1b's default `async () => ({})` is replaced here). On a failed state read `getFlags` returns what B3's `getPublicState` returns (the last good state, `stale: true`); with no good state yet in the isolate it throws B3's `unavailable` error and the page answers 503 like every other public read. B3b's `visibility.ts` and B3's `toMarket` read the same public state directly (`comingSoonGlobal`, `comingSoonMarkets`), so every reader of coming-soon sees one value.

Rules
1. A market is open when `comingSoon` is false. A collection is empty when it has no visible property. The empty state renders when a collection is empty, whatever the flag says (a market flipped open by mistake still shows the honest empty state).
2. Effective coming-soon for a market is `settings.coming_soon_global OR markets.coming_soon`. The global flag is the kill switch and is edited in `/admin/settings` (screen 24); the per-market flag in `/admin/markets` (screen 15).
3. The API hides properties of a coming-soon market from lists and returns 404 for their detail routes. In production it also hides `status = 'Illustrative'` rows (defence in depth: the database already refuses them).
4. First publication opens the market. When a property becomes `published` and its market is still `coming_soon`, the `property.published` recipe's `bump_catalog_version` step (parameter `flip_coming_soon`, default true; B8b step 4, architecture 10, ASSUMED A8) sets `coming_soon = false` and writes the `audit_log` row through B8b's SQL function `open_market_on_publish(p_property_id, p_notify)` (B8b Data changes), which in the same transaction enqueues the interest-signup notice of rule 7 (G15). This slice ships no trigger and no market-opening function for it and does not depend on B8b: it proves that a market opens by changing the market directly (`tests/db/market-opening.db.test.ts`, step 4), and the proof through the `bump_catalog_version` recipe step belongs to B8b step 4. Until B8b lands, a market is opened by hand in `/admin/markets` (B7 screen 15, whose `set_market_coming_soon` enqueues the rule 7 notice through B8's `enqueue_job` in the transaction that opens the market, G58) or with `update markets set coming_soon = false`, which enqueues no notice. System writes to `audit_log` use `actor_id = null`, `actor_kind = null`, `note = 'system'` (B2's convention, G43; no system row is written as `agent`; B7 shows them as "System").
5. Stories are editorial writing and stay visible whether or not a market is open. Seeded stories exist only in development and preview (B2), so production shows none until real ones are published, and the stories page then shows its empty state.
6. Submissions stay open in coming-soon mode; the "Submit a Property" calls to action are unchanged.
7. Interest signups are separate consent from Place Notes (G15). A subscriber whose `source` starts with `interest:` receives one mail when its market opens, and nothing else until they also sign up through a Place Notes form (`source` without that prefix) and confirm that signup: for an address already confirmed as interest-only, B3's `upsert_subscriber` keeps the `interest:` source, holds the Place Notes source in `pending_source` and sends a new confirmation, and only the click moves it into `source` (DL-06), so nobody can enrol another person in Place Notes by typing their address: both ways a market opens enqueue it inside the transaction that opens the market (G58), B8b's `bump_catalog_version` step through `open_market_on_publish` and B7's `set_market_coming_soon` (screen 15), each with the system job `market_open_notice` through B8's SQL `enqueue_job` (key `market_open:<market>`, so it sends once; `enqueue_job` writes one `created` row in `job_events`) handled by B11's `src/server/jobs/system/market-open-notice.ts` with template `market_open` (added by B11) to the confirmed `interest:` subscribers of that market. Campaign standalones go to confirmed Place Notes subscribers only (B11). B5 words the confirmation mail accordingly. This slice writes the `source` and `markets` those jobs select on and builds none of the sending.
8. Flags are read in one place (GQ-05) and that place is the public state (architecture 13 rule 1, F24). `getFlags(db)` in `src/server/lib/flags.ts` takes the keys `flags` and `comingSoonGlobal` from `getPublicState(db)` (B3: one `public_state()` RPC returning the seven keys of G39, `catalog_version`, `flags`, `coming_soon_global`, `coming_soon_markets`, `site`, `illustrative_content` and `og_static`, key names final, F25 b as amended by G39, which B3 maps to `catalogVersion`, `flags`, `comingSoonGlobal`, `comingSoonMarkets`, `site`, `illustrativeContent` and `ogStatic`; memoised 15 seconds per isolate through `CATALOG_VERSION_TTL_MS`; the database client is an argument, so tests inject a counting client, F25 e), validates with `flagsSchema` (unknown keys are ignored, a missing or malformed row yields `defaultFlags`, all false), and has no memo, no query and no table access of its own, so a flag or coming-soon decision never costs a database call beyond the state check the whole Worker already shares. `applyVisibility(rows, ctx)` in `visibility.ts` is called only by B3's `getCatalog`, once per snapshot version, with `ctx = { state, env: { MOP_ENV } }` (`state` is the `PublicState` from `getPublicState(db)`, `MOP_ENV` comes from `readVar("MOP_ENV")` of B3's `src/server/lib/runtime-env.ts`, read by `getCatalog` in `state.ts` and never from `env.ts`, G39, so `visibility.ts` also loads in the job runner and imports neither `env.ts` nor `runtime-env.ts` itself); it takes no database client, calls neither `getCatalog` nor `getFlags`, and reads only `ctx.state.comingSoonGlobal`, `ctx.state.comingSoonMarkets` and `ctx.state.illustrativeContent`, so neither it nor `getFlags` reads `markets`, `settings` or `properties` per request. A change to `settings` (flags, `coming_soon_global`, `site`, `environment`) or to `markets.coming_soon` bumps `catalog_version` through B2's triggers (F25 a; no application code bumps the version by hand), so it reaches every page within the memo, not the 5-minute `s-maxage`. Flags are never sent to the browser as a bag; the browser sees only their effects (`Market.comingSoon`). Adding a flag is one line in `featureFlags` (`src/domain/flags.ts`) plus its default, and the admin switch is B7 screen 24 (`admin` only).

Invariants
1. Production (`settings.environment = 'production'`) cannot contain an `Illustrative` property: a trigger raises on insert or update, and `set_environment('production')` refuses while one exists.
2. `bun run seed -- --target dev --mode full` (B2's `scripts/seed.ts`; targets are `dev` and `prod`, never `local`) refuses to run against a project whose `settings.environment` is `production` (B2 guard, tested here: this slice moves the check into the pure function `refuseProductionSeed(environment)` in `scripts/lib/seed-guard.mjs`, beside B2's `reset-guard.mjs`, which `scripts/seed.ts` calls with the value it reads before any write; `tests/unit/seed-guard.test.ts`, step 3).
3. Copy follows the brand rules: calm, brief, specific, no em dashes, no hyperbole, no guarantee of leads, buyers or sales, markets California, New York and Florida only. A Vitest scan enforces the mechanical parts.
4. Sections set vertical padding only; `.section-wrap` owns width (G-007). The two section roots of this slice, `.coming-soon` (in `coming-soon.css`) and `.consent-notice` (in `consent.css`), use `padding-block` and set no `padding` shorthand, horizontal padding, `width`, `max-width` or `margin-inline` (step 10 checks it). No hex in CSS; new spacing or colour goes into `tokens.css` first.
5. Every user action calls `track()` with a name from `analyticsEvents`: `interest_signup`, `coming_soon_view` and `consent_set` (new; the notice calls `track("consent_set", { analytics })` for a click, B13's loader tracks only automatic changes such as Global Privacy Control).
6. One `h1` per page. Empty states use `h2`; the home empty hero supplies the home `h1`.
7. Analytics consent (GP-02, architecture 10). Google Analytics (gtag.js only; there is no Tag Manager container, G41) never loads, and no request to a Google host is made, until the stored consent record says `analytics: true` for the current `CONSENT_VERSION` and the browser does not send Global Privacy Control (`navigator.globalPrivacyControl === true` counts as declined without asking; ASSUMED, matches B13 and B16). The record is client side only: `localStorage` key `mop_consent`, value `{ version, analytics, decided_at }` (the shape B13's `Ga4Loader` reads). Raising `CONSENT_VERSION` asks again. First-party `track()` events (`sendBeacon` to `/api/public/events`) are anonymous and exempt, so they keep working whatever the choice. ASSUMED: consent is required everywhere, not only where law demands, because region detection costs more than the rule.
8. The notice is not a popup (GP-02). It is an in-flow block at the top of the footer, not `position: fixed`, so it never covers the sticky property action bar (P-021) or the concierge button; it has `role="region"` and an accessible name, takes no focus on load and is not a dialog. Until the visitor decides, analytics stay off and nothing else changes. A "Cookie settings" button in the footer reopens it at any time.

Events emitted: none new. `subscriber.confirmed` (B3, after the confirmation click, B5 mail) is unchanged. Permissions: public. The toggles are admin server functions: B7's `setComingSoon` (`markets.coming_soon`, chief_editor and managing_editor) for a market and B7's `putComingSoon` (`settings.coming_soon_put`, admin) for the global switch; every flag in `settings.flags` is written only by B8b's `putFlags` (`automation.flags_put`, admin, humans only).

## Risks and gotchas (link GOTCHAS ids)
- G-005: routes read through `queries` and `services`. The empty-state decision is made from the payload (`market.comingSoon`, empty lists), never from `src/data/*`. The only bundled-data mode is local, where `comingSoon: false` keeps today's behaviour.

- G-004: `Market.comingSoon` and `interestCopy` (types), the API payload and `markets.coming_soon`, `markets.interest_copy` (columns) already agree from B2 and B3; this slice adds no field. Adding one later changes all three.
- G-006: no new `VITE_*` name. The environment marker is a database row, not a build variable, so a wrong build cannot show illustrative content on the production database.
- F22: the harness belongs to B2 and B4 extends it; this slice creates none of it. Committed mode is allowed only where a second connection must see the rows, so `tests/api/coming-soon.api.test.ts` commits (with mandatory cleanup; B2's `committed(fn, cleanup)` holds the G34 advisory lock on its connection, and CI runs it in B4's `db` job on that job's own ephemeral stack, H1 (b)) and the four `tests/db` files roll back. The one connection name is `DEV_DB_URL`.
- G-011: no paid feature. A view, two functions and a trigger.
- Empty pages are thin content. `/properties`, market and region pages are `noindex` while their pool is empty (ASSUMED A9), set here in `pageHead`; B13 owns the shared `indexable(count)` decision (`noindex, follow`) that replaces the inline checks and keeps those pages out of the sitemap. Market and region pages keep their editorial text for visitors.
- The guard protects the database. An illustrative property could still exist on a production database that was never marked production; `set_environment('production')` is therefore a launch checklist item and `assert-coming-soon.mjs` fails when it was skipped.
- Local mode cannot show empty states (it serves bundled data). There is no local stack (S50); designers run live mode against `mop-dev` with `coming_soon_global` set to true; the runbook says how.
- CSP `connect-src 'self'` is enough for the signup (same-origin `POST`); no new origin.
- Cache (architecture 13, S52, F24, F25): flipping `coming_soon` or a flag bumps `catalog_version` through B2's `markets` and `settings` triggers, so the edge key changes and pages change within the 15-second state memo (B3), not after the 5-minute `s-maxage`. Coming-soon HTML is cached like any public page and is identical for every visitor: the empty state, the form and the badge come from the catalog and state, and consent, the stored choice and the market preselection from the route happen in the browser after hydration (`ConsentNotice` renders nothing until mounted). The interest signup `POST /api/public/subscribers` is never cached (rule 6) and stays cheap (rule 8): Turnstile and the in-memory limit run before any database call, and the write is one insert. This slice adds no cache module, no key kind (`html`, `json`, `doc` are B3's) and no header of its own; it adds no inline script, so the Content-Security-Policy hashes stored with each page's cache entry (B3 stores, B17 computes) are unaffected. On `workers.dev` and in `vite dev` only the memory layer acts; the edge layer is proved locally under `bunx wrangler dev` by B3 and B4 (E16, reading `x-mop-cache` for miss then hit) and confirmed on the custom domain at L1.
- GP-02 and the footer-anchored notice: an in-flow block at the top of the footer is seen by people who scroll to it, so many visitors will never decide and analytics will undercount. That is the price of no popup (CEO rule); the first-party events still count everyone. UNPROVEN whether the consent rate is workable; revisit with B14's numbers. The notice makes no claim beyond what B13 loads (Google Analytics only); if a second analytics vendor is ever added, the sentence and `CONSENT_VERSION` change together.
