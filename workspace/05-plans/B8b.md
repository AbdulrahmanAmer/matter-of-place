## Goal and observed exit
Automations are settings, not code (S34, S38). Five tables hold what happens on each event, every email, every decline reason, every channel switch and every clock. A fixed catalog of 17 step types stays in code with a Zod parameter schema each. The planner turns an event into jobs by reading the recipe at trigger time, so an edit applies to the next event with no deploy. Every change is a revision with a named actor. An admin, or an agent with the `automation` scope, edits all of it from `/admin › Automation` (screens 17 to 21) or through `/api/admin/automation/*`.
Observed exit (completion map B8b): "an admin switches a step off, publishes, and the dry-run and the real run both skip it". Proven in two parts. Part 1 (after step 5, no UI): `bun run scripts/automation-smoke.ts` on `mop-dev` disables step `notify_admin_received` in `submission.received`, runs the planner in dry-run mode, then emits a real `submission.received` event and lets the runner fan out; both outputs list the step as skipped with reason `step_disabled` and no job row exists for it. Part 2 (after step 10, needs B5 and B7): the same switch from screen 17 by a session and by an agent key, then a submission from `/submit`, and `tests/e2e/automation-exit.spec.ts` sees the skip in the dry-run panel and no `notify_admin` job in screen 16.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- An `events` row (B8). The planner never reads anything but the event, the recipe row and the step specs.
- Admin edits through the `automation` group of architecture 4.2: `recipes` get and put, `templates` get, put and preview (B5 owns render and preview), `reasons`, `channel-settings`, `schedule-settings`, `dry-run`, `revisions` and restore. Handlers are thin; each maps to one function in `src/server/automation/service.ts`.

Outputs
- Five tables of architecture 3.5 plus `automation_revisions`, exactly as named (`decline_reasons` is created by B2 and altered here): `automation_recipes`, `email_templates`, `decline_reasons`, `channel_settings`, `schedule_settings`.

- Dry-run result `{ trigger, recipe_enabled, planned: [{ step_id, type, heavy, status, params, idempotency_key }], skipped: [{ step_id, type, reason }], warnings: [...] }`. It inserts nothing and takes no lock.

Invariants
1. Step specs live in one file, `src/server/automation/step-specs.ts`: `{ type, label, description, heavy, paramsSchema, fields }`. The step modules of B8 import their `paramsSchema` and `heavy` from it, so the recipe editor, the planner and the runner cannot disagree. A step type exists only if it is in that file; admins cannot add one (S34, no workflow engine).
2. A step is `implemented` when `getStep(type)` in B8's registry returns a module. The planner skips an unimplemented step with reason `not_implemented` instead of creating a job that would die; the same skip is shown in dry-run and in real fan-out. When B9 lands `render_cover`, the seeded recipe starts using it with no migration.
3. Real fan-out and dry-run call the same pure function `planEvent`. Dry-run cannot drift from the real run because there is no second code path. Watched-fail below.
4. Fan-out is idempotent (B8 invariant 1: `insert ... on conflict (idempotency_key) do nothing`). Jobs are inserted first and `events.processed_at` is set last, so a crash re-plans and inserts nothing new. A per-event `fanoutEvent` after commit and the runner's sweep may overlap safely.
5. The recipe is read when the event is planned, params are snapshotted into `payload.params`. Editing a recipe never changes a job already created.
6. Jobs created from one event have no dependency between them (there is no dependency column). A step that needs another's output must return `{ status: "retry_at", at, reason }` (B8 invariant 3) until it exists. Stated for B9 to B12 in their plans.
7. Every write to the five tables writes one `automation_revisions` row by trigger, with the actor set in the same transaction (`set_config('mop.actor_id', ..., true)` inside the SQL function). A direct edit in Supabase Studio is still recorded, with a null actor and note `direct`.
8. Recipes are never created or deleted by admins: one row per event type exists from the seed (17 rows, the full catalog in architecture 3.6), so any event can gain steps without code. `trigger` cannot be edited.
9. Save-time validation (server): step ids unique per recipe (slug, at most 40 chars), at most 20 steps, `step_type` in the catalog, params parse with that step's schema, `conditions.tiers` within `Feature|Reach|Campaign`, `conditions.markets` within `california|new-york|florida`, `send_email.template` and `notify_admin.template` name an existing `email_templates` row. Errors carry a JSON path so the form shows them inline (screen 17 state "invalid").
10. Effective approval mode for a channel (S23): `manual` unless the tier's mode is `auto` and `auto_after` is set and today is on or after it. Pure function `effectiveApprovalMode(settings, tier, today)` in `src/domain/automation.ts`; B10 calls it. A null `auto_after` means never automatic.
11. Schedules driven by the runner: `digest`, `prune`. `keepwarm` is driven by the Worker cron trigger and `scheduled()` (invariant 15 c), not by the runner, because only the Worker can request its own page in-process; its row still holds `cron`, `enabled`, `last_run_at` and `next_run_at`. `audit`, `reconcile` and `backup` are external clocks (the auditor routine and GitHub Actions, S27, architecture 7); their rows are stored, shown with an "external clock" badge and editable, and the runner ignores them. ASSUMED; an external clock can read its row through `GET /api/admin/automation/schedule-settings` with an agent key.
12. `digest` cadence is every 14 days (S25) and cron cannot express that, so ASSUMED new column `schedule_settings.interval_days int null`: the runner fires when `cron` matches and at least `interval_days` days passed since `last_run_at`. This adds a column to architecture 3.5; update the architecture in the same commit (G-004).
13. Time zones (GD-06, architecture 10). Every `channel_settings.posting_window` carries `tz`, an IANA zone name (`America/Los_Angeles`, `America/New_York`, `UTC`); `channelSettingsSchema` refuses a window without `tz`, with an unknown zone (checked with `Intl.DateTimeFormat(undefined, { timeZone })`), or with `from` not before `to`, and a database check `posting_window ? 'tz'` backs it. `days`, `from` and `to` are wall time in that zone, so a window keeps its local hours across daylight saving; B10's `nextWindowSlot` converts with it. Schedules are different: `schedule_settings.cron` and `next_run_at` are UTC and screen 20 labels them "UTC" and shows the next run in the reader's market zone through B7 `LocalTime`. Times in `automation_revisions` and `jobs` are UTC in the database, displayed by the screens in the market zone (B7 invariant 12).
14. Feature flags (GQ-05, architecture 10). The `settings` row with key `flags` holds one jsonb object; the Worker reads it through `getFlags(db)` in `src/server/lib/flags.ts`, which is `getPublicState(db).flags` with the defaults merged under it (caching contract, architecture 13 rule 1: one read path, memoised 15 seconds per isolate by `getPublicState`, `CATALOG_VERSION_TTL_MS`). `getFlags` never queries `settings` itself and keeps no memo of its own, so a flag change reaches every isolate within 15 seconds and the database is not asked per request. The set of flags is closed and defined in one Zod schema, `flagsSchema` in `src/domain/flags.ts` (`archive_pages` default true, `new_channels` default false; adding a flag is a PR, like a step type); unknown keys are refused on save. Coming-soon stays its own keys (`markets.coming_soon`, `settings.coming_soon_global`, B7 screen 24 Site section); the flags editor links to it and does not duplicate it. Flags are trust decisions: an agent gets 403 `human_only` on `PUT`, and every change writes an `audit_log` row `settings.flags_put` with before and after (the row is not one of the five automation tables, so it has no `automation_revisions` row).

15. Caching contract (S52, architecture 13, F24). B8b owns keep-warm and `purge_cache` as housekeeping, and keeps the rest of the contract true: (a) every public read here (`getFlags`) goes through `getPublicState`, never a table; (b) the cache key changes only by `catalog_version` (rule 4). Writes to `settings` (flags, `coming_soon_global`, `site`, `environment`), `markets.coming_soon`, `redirects` and `slug_history` bump it by triggers in B2 (F25 a), so `putFlags`, the market-opening function and the flags seed bump nothing by hand, and flag or coming-soon changes refresh cached pages within one 15 second state check. The `bump_catalog_version` recipe step covers the publication events of the seeded recipes (`property.published`, `property.unpublished`), and after it runs `getPublicState` returns the new `catalog_version` within one state check; no purge call is needed for correctness. The key kinds are `html`, `json` and `doc` (F25 c), and the state keys read here are `catalog_version`, `flags`, `coming_soon_global`, `coming_soon_markets`, `site` and `illustrative_content`, final (F25 b); (c) keep-warm (rule 11, F25 h) requests one public page in-process through the Worker's own fetch handler, so the middleware order of B1b and the cache of B3 run (the Content-Security-Policy header comes from the page's cache entry, stored by B3 and computed by B17, F25 d), and every tick makes exactly one state RPC and writes `last_run_at`, so the database is touched even when the page is a cache hit and the free project does not pause; (d) the tick calls no outside API (rule 10); (e) admin reads of this group are never cached and are paginated at 50 with an index (rule 9): `GET revisions` takes `limit` (at most 50) and a `before` cursor on `at`, and the recipe, template, reason, channel and schedule lists are small closed sets (17, about 12, 6, 6, 6 rows) read in one query each; (f) every `/api/admin/automation/*` response and every `/admin` screen document of this plan is `Cache-Control: no-store` (rule 6, set by B7's admin middleware; this plan asserts it), and the session is verified locally by B7 against the project's ES256 key (rule 9, E14, F25 i), so these handlers add no per-request call to Supabase Auth; (g) when the database errors, `getFlags` serves the last good public state (rule 7, inherited from `getPublicState`) and the keep-warm tick logs a failed state RPC or `last_run_at` update instead of throwing; (h) `getFlags`, `getPublicState` and the keep-warm handler take the injectable database client of B3 (F25 e), which the counting tests of this plan and B4 use; H1 counts the real queries with `pg_stat_statements` (E15), and this plan adds only the one state RPC and one `last_run_at` update per tick.

Events emitted: none new. The runner-driven `digest` schedule emits the existing `digest.due`; `prune` enqueues the system job of B8 with key `prune:<UTC date>`; `keepwarm` requests one public page in-process, makes one state RPC and records `last_run_at` (invariant 15 c).

## Risks and gotchas (link GOTCHAS ids)
- G-004: recipe, reason, channel and schedule fields are snake_case in the domain, the API and the columns; change all together. `interval_days` is a spec change to architecture 3.5.
- G-011 and P-009: no new paid feature. `cron-parser` is a small dependency and runs in Deno through an `npm:` specifier (measured 2026-10-01: `npm:cron-parser@5` with `CronExpressionParser` runs in the Edge runtime, deployed with `--use-api`; ASSUMED E5). Deno is not installed locally, so there is no local `deno check`; the Edge Function deploy itself is the proof.
- G-006: `credentials_ref` stores a secret NAME only; screen 20 shows connected or expired and never a value.
- G-007: `automation.css` uses tokens only; the admin status colours (danger, warning, success) are added to `tokens.css` by B7 step 3, not here.
- Steps have no dependency column; the seeded `property.published` fans out renders in parallel. B9 to B12 must return `retry_at` until prerequisites exist (invariant 6). UNPROVEN until B9.
- `purge_cache` needs a Cloudflare API token with Cache Purge and a zone id in the Edge Function secrets; the deploy token `mop-github-actions` has only Workers Scripts Write, Workers R2 Storage Write and Workers KV Storage Read (E1), so a purge token is needed: a narrow token (Cache Purge on the one zone) that the orchestrator mints with the admin token `mop-admin` from the local `.env`, with no operator step (F19), and it is listed for Actions only in tech-stack 4. BLOCKED only until the orchestrator has minted it and stored it as an Edge Function secret. The cache key carries `catalog_version` (architecture 13 rule 4), so purge is housekeeping and never needed for correctness; B3 or B13 implements it. Until then the step is unimplemented and skipped and the site stays correct.
- `write_captions` uses Haiku (S20); an `ANTHROPIC_API_KEY` secret is not in tech-stack 4. ASSUMED to be added by B9.
- Two drivers for `prune` would double-run it; step 4 unschedules the pg_cron entry in the same migration set as the runner change.
- Runner-driven schedules fire only while the runner ticks (pg_cron runs on `mop-dev` only, never on a local cluster, E7); a paused Supabase project (P-009, 7 idle days) misses them; the Cloudflare keep-warm cron is the guard (B8b, invariant 15 c).
- GD-06: a posting window stores wall time in its own zone, so a `from` of 09:00 stays 09:00 local across daylight saving; a cron stays UTC and therefore moves one hour against local time twice a year. That is intended for `digest` and `audit` (say it on screen 20) and is why windows, not crons, gate posting.
- GQ-05: flags are read from `settings`, not from build-time env, so a change needs no deploy; the public state memo means up to 15 seconds of disagreement between isolates. A flag that gates money or legal behaviour must not be added to this set without a decision (the closed schema makes that a PR). G-004: `flagsSchema`, the API JSON and the stored object are one shape.
- Recipe steps that name `standalone` (Campaign email) point to a template B5 seeds disabled and B11 completes; a disabled template means `send_email` returns skipped (B5), so the seed never fails.
