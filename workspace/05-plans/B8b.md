## Goal and observed exit
Automations are settings, not code (S34, S38). Five tables hold what happens on each event, every email, every decline reason, every channel switch and every clock. A fixed catalog of 17 step types stays in code with a Zod parameter schema each. The planner turns an event into jobs by reading the recipe at trigger time, so an edit applies to the next event with no deploy. Every change is a revision with a named actor. An admin, or an agent with the `automation` scope, edits all of it from `/admin › Automation` (screens 17 to 21) or through `/api/admin/automation/*`.
Observed exit (completion map B8b): "an admin switches a step off, publishes, and the dry-run and the real run both skip it". Proven in two parts. Part 1 (after step 5, no UI): `bun run scripts/automation-smoke.ts` on `mop-dev` disables step `notify_admin_received` in `submission.received`, runs the planner in dry-run mode, then emits a real `submission.received` event and lets the runner fan out; both outputs list the step as skipped with reason `step_disabled` and no job row exists for it. Part 2 (after step 10, needs B5 and B7): the same switch from screen 17 by a session and by an agent key, then a submission from `/submit`, and `tests/e2e/automation-exit.spec.ts` sees the skip in the dry-run panel and no `notify_admin` job in screen 16.

## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- An `events` row (B8). The planner never reads anything but the event, the recipe row and the step specs.
- Admin edits through the `automation` group of architecture 4.2: `recipes` get and put, `templates` get, put and preview (B5 owns render and preview), `reasons`, `channel-settings`, `schedule-settings`, `dry-run`, `revisions` and restore. Handlers are thin; each maps to one function in `src/server/automation/service.ts`.

Outputs
- Five tables of architecture 3.5 plus `automation_revisions`, exactly as named (`decline_reasons` is created by B2 and altered here): `automation_recipes`, `email_templates`, `decline_reasons`, `channel_settings`, `schedule_settings`.
- Jobs with the envelope pinned in B8: `payload = { params, data }`, `idempotency_key = event_id:step_id`, `heavy` from the step spec, `status = waiting_approval` when the step requires approval, else `queued` plus a pgmq send. `recipe_id` and `step_id` are set.
- Dry-run result `{ trigger, recipe_enabled, planned: [{ step_id, type, heavy, status, params, idempotency_key }], skipped: [{ step_id, type, reason }], warnings: [...] }`. It inserts nothing and takes no lock.

Invariants
1. Step specs live in one file, `src/server/automation/step-specs.ts`: `{ type, label, description, heavy, paramsSchema, fields }`. The step modules of B8 import their `paramsSchema` and `heavy` from it, so the recipe editor, the planner and the runner cannot disagree. A step type exists only if it is in that file; admins cannot add one (S34, no workflow engine).
2. A step is `implemented` when `getStep(type)` in B8's registry returns a module. The planner skips an unimplemented step with reason `not_implemented` instead of creating a job that would die; the same skip is shown in dry-run and in real fan-out. When B9 lands `render_cover`, the seeded recipe starts using it with no migration.
3. Real fan-out and dry-run call the same pure function `planEvent`. Dry-run cannot drift from the real run because there is no second code path. Watched-fail below.
4. Fan-out is idempotent (B8 invariant 1: `insert ... on conflict (idempotency_key) do nothing`). Jobs are inserted first and `events.processed_at` is set last, so a crash re-plans and inserts nothing new. A per-event `fanoutEvent` after commit and the runner's sweep may overlap safely. Callers: `fanoutEvent(db, event_id)` is called best effort after commit by the admin services of B6, B7 and B9 (B7 invariant 1), and by `fanoutPendingEvents(db, limit)`, which B8's runner calls every tick for the oldest unprocessed events (events written in SQL by B3 and B5, G20, wait for this sweep). Failure: `fanoutPendingEvents` catches each event's error, logs `fanout_failed <event_id> <code>` and goes on to the next event, so one bad event never blocks the others; the event stays unprocessed and is re-planned on the next tick (a transient database error heals by itself). An event still failing one hour after its `at` also gets one `notify_admin` job through B8's `enqueueJob(db, { type: "notify_admin", idempotencyKey: "fanout_failed:<event_id>", params: { headline: "Event could not be planned" }, data: { summary: "<type> <event_id>: <code>", link_path: "/admin/jobs" } })` (G13 shape; the key makes it one alert per event). A payload that fails `eventPayloadSchemas` is still planned with the raw payload and logged once as `fanout_payload_invalid <event_id>`: a step that needs a missing field dies on its first run and shows red on screen 16, and conditions on a missing field do not match (invariant 9).
5. The recipe is read when the event is planned, params are snapshotted into `payload.params`. Editing a recipe never changes a job already created.
6. Jobs created from one event have no dependency between them (there is no dependency column). A step that needs another's output must return `{ status: "retry_at", at, reason }` (B8 invariant 3) until it exists. Stated for B9 to B12 in their plans.
7. Every write to the five tables writes one `automation_revisions` row by trigger, with the actor set in the same transaction (`set_config('mop.actor_id', ..., true)` inside the SQL function). A direct edit in Supabase Studio is still recorded, with a null actor and note `direct`. One exception: an update of a `schedule_settings` row that changes only `last_run_at`, `next_run_at` and `updated_at` while the transaction set no actor (`nullif(current_setting('mop.actor_id', true), '') is null`: the runner, keep-warm, `backup.yml`) writes no revision, so screen 21 shows people's changes and not clock ticks. A put function always sets the actor, so a human or agent `PUT` of `last_run_at` alone (L1 setting the first digest date) writes one revision. `automation_revisions` itself is append-only (B2 invariant 3): trigger `automation_revisions_immutable` raises on update and delete even for the service role.
8. Recipes are never created or deleted by admins: one row per event type exists from the seed (18 rows, the full catalog in architecture 3.6, G29), so any event can gain steps without code. `trigger` cannot be edited. Enforced in the database: `automation_recipes` has an update policy and no insert or delete policy, `automation_put_recipe` updates by `trigger` and never inserts (an unknown trigger raises `unknown_trigger`), and the before-update trigger `automation_recipes_trigger_locked` raises `trigger_locked` when `new.trigger <> old.trigger`.
9. Save-time validation (server): step ids unique per recipe (slug, at most 40 chars), at most 20 steps, `step_type` in the catalog, params parse with that step's schema, `conditions.tiers` within `Feature|Reach|Campaign`, `conditions.markets` within `california|new-york|florida`, `conditions.kinds` within the asset kinds of architecture 3.6 (`variants|cover|carousel|story|reel|newsletter_block|standalone_email`; `variants` is accepted for parity with that list but never matches, because `render_variants` stores its variants on `property_media` and creates no `assets` row, so no `asset.approved` or `asset.rejected` payload carries it, G61), `send_email.template` and `notify_admin.template` name an existing `email_templates` row (until B5 lands the check reads the `email_templates.key` column only). `matchesConditions` in `plan.ts` reads the event payload: `tiers` against `payload.tier`, `markets` against `payload.market` or any entry of `payload.markets`, `kinds` against `payload.kind`; a condition key whose payload field is absent does not match. There is no condition on `markets` of a subscriber: the one `subscriber.created` step sends `interest_confirm` and B5's `send-email.ts` swaps it to `newsletter_confirm` when `subscribers.markets` is empty (G12). An unknown trigger in `automation_put_recipe` raises `unknown_trigger` (invariant 8). Errors carry a JSON path so the form shows them inline (screen 17 state "invalid").
10. Effective approval mode for a channel (S23): `manual` unless the tier's mode is `auto` and `auto_after` is set and today is on or after it. Pure function `effectiveApprovalMode(settings, tier, today)` in `src/domain/automation.ts`; B10 calls it. A null `auto_after` means never automatic.
11. Schedules driven by the runner: `digest`, `prune`, `reconcile`, `kpi_weekly`, `newsletter_hygiene` (G9, G10). `runDueSchedules(db, now)` in `src/server/jobs/scheduler.ts` is called by B8's runner every tick (pg_cron, every minute). It selects the enabled rows of those five keys, applies `isDue(row, now)`, and claims each due row with one call, `db.rpc("claim_schedule", { p_key: <key>, p_guard: true, p_old_last_run_at: <old last_run_at>, p_last_run_at: <now>, p_next_run_at: <scheduleNext(row, now)> })` (invariant 12; this slice's SQL function, Data changes; the runner writes no table directly, G43); `false` means another tick claimed it or the row was switched off, and nothing is done; an RPC error is logged as `schedule_claim_failed <key>` and the row is left for the next tick. Then: `digest` calls `emitEvent(db, { type: "digest.due", entity: "system", entityId: null, payload: { scheduled_for: <now, ISO UTC> } })` (B8 `src/server/lib/events.ts`); `prune` calls `enqueueJob(db, { type: "prune", idempotencyKey: "prune:<UTC date>" })` (B8 `src/server/lib/jobs.ts`); `reconcile` calls `enqueueJob(db, { type: "reconcile", idempotencyKey: "reconcile:<UTC date>T<HH:MM>", data: { since: <old last_run_at> } })` with the minute rounded down to the quarter hour (B8 invariant 1; `data` is `{}` when the old `last_run_at` is null, and B8's handler then falls back to its own `since`), whose handler is B8's `src/server/jobs/system/reconcile.ts` (it calls B3's `reconcileUploads`; B10 and B11 append to it, G10); there is no `reconcile_uploads` job, file or pg_cron row; `kpi_weekly` and `newsletter_hygiene` call `enqueueJob(db, { type: <key>, idempotencyKey: "<key>:<UTC date>" })` for B11's system jobs of the same names (`src/server/jobs/system/kpi-weekly.ts`, `src/server/jobs/system/newsletter-hygiene.ts`; B11 schedules no pg_cron row for them, G9). Before claiming a `kpi_weekly` or `newsletter_hygiene` row the scheduler asks `getStep(<key>)` (B8's registry, which merges the system types); when it returns no module, it advances only `next_run_at` with the same guarded `claim_schedule` call whose `p_last_run_at` is the old `last_run_at`, so `last_run_at` stays untouched (screen 20 never shows a run that did not happen) and logs `schedule_not_implemented <key>` once per due slot. When an emit or enqueue throws, the scheduler sets `last_run_at` and `next_run_at` back to their old values with one more `claim_schedule` call (`p_guard` true, `p_old_last_run_at` the claimed `<now>`, `p_last_run_at` and `p_next_run_at` the old values) and logs `schedule_failed <key>`, so the next tick retries (a `false` or an error from that call, a row switched off in between, is logged as `schedule_rollback_missed <key>` and the row keeps the claimed time); a job that fails later follows B8's backoff and a dead job shows red on screen 16. `keepwarm` is driven by the Worker cron trigger and `scheduled()` (invariant 15 c), not by the runner, because only the Worker can request its own page in-process; its row holds the switch (`enabled`), `last_run_at` and `next_run_at`, and its `cron` mirrors `wrangler.toml`. `audit` and `backup` are external clocks: the audit routine (S27, B14) and `.github/workflows/backup.yml` (B1b). Their rows, and the `keepwarm` row, are shown on screen 20 with an "external clock" badge and the cron read-only with the note "set in wrangler.toml", "set in the routine" or "set in backup.yml"; `putScheduleSettings` refuses a `cron` change for `keepwarm`, `audit` and `backup` with 422 `external_clock`, and their `enabled` stays editable. The audit routine reads its row through `GET /api/admin/automation/schedule-settings/audit` with an agent key of scope `automation` and records each run through B14's action `audit.record_run` (agent scope `audit`), which sets only `audit.last_run_at` (G9). `backup.yml` (B1b) reads `backup.enabled` on scheduled runs (`f` or no row ends the run green with `backup disabled`) and writes `last_run_at` with no actor after a good dump, so screen 20's switch pauses it and shows the last good backup (G9). `PUT /api/admin/automation/schedule-settings/:key` accepts `cron`, `interval_days`, `enabled` and `last_run_at` and nothing else (G9; L1 sets the first digest date through the `last_run_at` of the `digest` row): `scheduleSettingsPutSchema` (strict; `last_run_at` an ISO 8601 UTC timestamp, `interval_days` an integer 1 to 90 or null, `cron` parsed by `nextRun`) refuses any other key with 422, and `putScheduleSettings` makes one call to `automation_put_schedule(p_key, p_patch, p_actor, p_actor_kind, p_request_id)`, which applies only those four keys, raises `external_clock` for a `cron` change of `keepwarm`, `audit` or `backup`, sets `next_run_at` to null whenever `cron`, `interval_days` or `last_run_at` changes (`dueAt` then recomputes it, invariant 12), and writes one revision (invariant 7). `getScheduleSettings` fills a null `next_run_at` with `dueAt(row, now)` for display only.
12. `digest` cadence is every 14 days (S25) and cron cannot express that, so the column `schedule_settings.interval_days int null` (architecture 3.5 already lists it): the runner fires at the first slot of `cron` on or after the UTC calendar date `interval_days` days after the UTC date of `last_run_at` (dates, not durations, so a run claimed a few seconds late does not slip a fortnight). Exactly, in `src/server/automation/cron.ts`: `scheduleNext(row, from)` is `nextRun(row.cron, startOfUtcDay(from) + row.interval_days days minus 1 minute)` when `row.interval_days` is set, else `nextRun(row.cron, from)`; `dueAt(row, now)` is `row.next_run_at` when it is not null, else `scheduleNext(row, row.last_run_at)` when `last_run_at` is not null, else `nextRun(row.cron, now minus 1 minute)`; `isDue(row, now)` is true when `row.enabled` and `dueAt(row, now) <= now`. There is no separate date test: the interval is carried by `next_run_at`. Every claim of invariant 11 stores `p_next_run_at = scheduleNext(row, now)` (for `digest`, the first Tuesday 14:00 UTC on or after the UTC date 14 days after the run), so screen 20 and B11's `scheduled_for` read the real next run. A tick that is missed or slow therefore runs the slot on the next tick, once, and several missed slots collapse into one run. A seeded row with null `next_run_at` and null `last_run_at` first fires at the next slot of its cron. L1's first digest follows: `last_run_at` set to Wednesday 2026-10-07 gives the first `digest.due` at Tuesday 2026-10-27 14:00 UTC, and the next at Tuesday 2026-11-10 14:00 UTC.
13. Time zones (GD-06, architecture 10). Every `channel_settings.posting_window` carries `tz`, an IANA zone name (`America/Los_Angeles`, `America/New_York`, `UTC`); `channelSettingsSchema` refuses a window without `tz`, with an unknown zone (checked with `Intl.DateTimeFormat(undefined, { timeZone })`), or with `from` not before `to`, and a database check `posting_window ? 'tz'` backs it. The window also carries `daily_cap` (integer 1 to 25, default 2, the per-channel daily post limit B10 reads); a `daily_cap` of 0 is 422 with the JSON path `posting_window.daily_cap`. `days`, `from` and `to` are wall time in that zone, so a window keeps its local hours across daylight saving; B10's `nextWindowSlot` converts with it. Schedules are different: `schedule_settings.cron` and `next_run_at` are UTC and screen 20 labels them "UTC" and shows the next run in the reader's market zone through B7 `LocalTime`. Times in `automation_revisions` and `jobs` are UTC in the database, displayed by the screens in the market zone (B7 invariant 12).
14. Feature flags (GQ-05, architecture 10). The `settings` row with key `flags` holds one jsonb object; the Worker reads it through `getFlags(db)` in `src/server/lib/flags.ts`, which is `getPublicState(db).flags` with the defaults merged under it (caching contract, architecture 13 rule 1: one read path, memoised 15 seconds per isolate by `getPublicState`, `CATALOG_VERSION_TTL_MS`). `getFlags` never queries `settings` itself and keeps no memo of its own, so a flag change reaches every isolate within 15 seconds and the database is not asked per request.
