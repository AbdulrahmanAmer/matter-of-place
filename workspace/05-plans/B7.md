## Goal and observed exit
The admin portal is the operating system (S18, S34): sign in, work the queue, decide, write the dossier, manage media, publish, run the team, all from `/admin`, by a human or by an agent holding a key (S38). This slice builds the shell (auth, permission matrix, shared UI kit) and screens 1, 2, 3, 4, 7, 8, 9, 11, 14, 15, 23, 24 and 25. Screens 5 and 6 are B6, 10 is B9, 12 is B10, 13 and 22 are B11 and B10, 16 is B8, 17 to 21 are B8b.

Part 1 (after step 10, before B6): `tests/e2e/admin-editorial.spec.ts` signs in as a `managing_editor` on the preview stack, starts review on three test requests, declines one with a reason (the toast shows the queued `send_email` job and the `declined` mail is sent), accepts one, and publishes a seeded draft property whose checklist is green (a property without a submission needs no payment). ## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- Session cookie (Supabase Auth magic link, S10) or `Authorization: Bearer <agent key>` (S38) on every `/api/admin/*` route.
- Zod input schemas per feature in `src/domain/` (`admin-submissions.ts`, `admin-properties.ts`, `admin-media.ts`, `admin-inquiries.ts`, `admin-stories.ts`, `admin-markets.ts`, `admin-team.ts`, `admin-settings.ts`). Roles come from `contracts.ts` (`appRoles`, `roleLabels`) and the state graph from `src/domain/workflow.ts`, both created by B2. ASSUMED: admin API JSON is the snake_case row shape (as generated types and B8 `job_events`); the public camelCase contracts of `contracts.ts` are not reused for admin (G-004: change domain, API and column together).
- Secrets (server only, G-006): `SUPABASE_SERVICE_ROLE_KEY` (exists), `PREVIEW_TOKEN_SECRET` (draft preview links), the `R2_*` names of B8 for presigned uploads.

Outputs
- Route group `/admin/*` with layout `src/routes/admin.tsx`. ASSUMED: the layout sets `ssr: false`, so admin pages never spend Worker CPU on server rendering (10 ms per request on the free plan, P-009) and loaders run in the browser with `ensureQueryData`. The layout guard runs before load, skips `/admin/sign-in`, calls `GET /api/admin/me` and redirects to sign-in on 401. Every admin route sets `head()` through `pageHead()` with `noindex: true`; dynamic routes throw `notFound()`.
- `/api/admin/*` route handlers, thin: parse, call one server function, return JSON (architecture 4.2). Two small additions to the 4.2 list, ASSUMED: `me` (`GET /api/admin/me` returns actor, roles, kind, scopes) and `auth` (`send-link`, `callback`, `sign-out`), which sign-in cannot do without; plus `dashboard` (`GET /api/admin/dashboard`) for screen 2.
- Audit action names follow `<entity>.<verb>` (`submission.decline`, `property.publish`, `team.agent_key_create`). Every state change writes `audit_log` (actor, `actor_kind`, before, after, `request_id`) inside the SQL function that changes the row.

Invariants
1. Every state change is: TS server function (actor, authz, Zod, guardrails) then ONE `security definer` SQL function that changes rows, writes `audit_log` through `write_audit` and calls `emit_event` in the same transaction (architecture 1 and 5; supabase-js has no multi-statement transactions). After commit the server function calls `fanoutEvent(db, event_id)` best effort; the runner's sweep is the safety net (B8b invariant 4).
2. Authorization lives in one matrix, `src/server/lib/authz.ts`, assembled from group files `src/server/lib/permissions/<group>.ts` (`submissions`, `properties`, `media`, `inquiries`, `stories`, `markets`, `team`, `settings`, `audit`, `dashboard` here; `jobs` in B8, `automation` in B8b, `payments` in B6 each add one file and one import line to `permissions/index.ts`). Entry: `{ action, group, roles: AppRole[], humanOnly?: true }`. The UI only hides buttons through `<RoleGate>`; the server is the check (tech-stack 5, admin action path).
3. Agents (S38, architecture 6): scope = route group name in `agent_keys.scopes`; an agent may act only inside its scopes and only where its `user_roles` role allows; groups `team` and `settings` are never available to agents (403 `human_only`), nor any action flagged `humanOnly`. A daily decision cap `settings.agent_daily_limits.decisions_per_day` (seed 25, ASSUMED) counts audit rows `submission.decline` and `submission.accept` per agent per UTC day; over the cap is 429 `agent_daily_limit`.
4. Roles are the enum `app_role`: `chief_editor`, `managing_editor`, `visual_editor`, `media_ops`, `commercial`, `admin` (S26, architecture 3.2). `admin` alone does not decide submissions (architecture 3.7 lists only chief and managing editors), so the CEO must hold `admin` and `chief_editor` together. CONFLICT with B2, which ASSUMED `unique (user_id)` on `user_roles` (one role per person); the sketch had `unique (user_id, role)`. ASSUMED resolution: the `admin_team` migration (step 14) restores `unique (user_id, role)`; B2's `role_in(variadic app_role[])` already works with several rows. Until then the CEO test account holds `chief_editor` and the admin screens are reached with a second account. `appRoles` and `roleLabels` (B2 replaced `editorialRoles` in `contracts.ts`) are the only role lists.
5. The submission state machine is B2's `src/domain/workflow.ts` (`submissionTransitions`, `canTransition(from, to, ctx)`, mirrored by the database function `submission_transition_allowed` and the trigger `enforce_editorial_gate`); B7 adds no second copy and only adds `allowedActions(state)` to `src/domain/admin-submissions.ts` for the buttons. States of architecture 3.3: `Submitted`, `Under Review`, `Accepted`, `Declined`, `Awaiting Assets`, `Invoice Issued`, `Scheduled`, `Published`, `Distribution Active`, `Completed`; B2 already corrected `submissionStates` in `contracts.ts`; step 4 only verifies). Transitions owned here: `Submitted` to `Under Review` (start review); `Under Review` to `Declined`, `Accepted`, `Awaiting Assets`; `Accepted` to `Awaiting Assets`; `Awaiting Assets` back to `Accepted` when `accepted_at` is set, else to `Under Review` (action `assets_received`, ASSUMED, audit only, no catalog event); `Scheduled` to `Published` (in `publish_property`). B6 owns `Accepted` to `Invoice Issued` to `Scheduled`. Each RPC checks the current state under `select ... for update` and returns 409 `wrong_state` otherwise.
6. Preview equals send: the decline and accept previews call B5 `previewTemplate` with the same variables the `send_email` step will resolve.
7. Optimistic concurrency on editors: `PATCH properties/:id` and stories send `expected_updated_at`; a mismatch is 409 `stale` and the screen offers a reload. Human and agent edits meet here.
8. Publishing is gated in TS (checklist) and in SQL (hero present and at least 6 images with alt); a property from a submission also requires the submission at `Scheduled` (which the B6 trigger only allows after payment paid or waived). Property edits after publish save to the live row and are audited (before and after); "Publish changes" bumps `catalog_version`. ASSUMED reading of "edits create a new version": history is the audit trail, not a second copy.
9. Admin components never import `src/server/**`, `src/db/**` or `src/data/**`; each feature has `src/admin/<feature>/<feature>-api.ts` (typed fetch wrappers, the admin equivalent of `services`, same pattern as B8's `jobs-api.ts`). Enforced by `tests/unit/admin-boundaries.test.ts`.
10. `track()` posts to the public `/events` endpoint and would pollute product analytics. ASSUMED deviation from AGENTS.md ("every user action calls track()"): admin actions are recorded by `audit_log`, which is their analogue. Update AGENTS.md when this lands.

Events emitted (existing catalog only): `submission.declined`, `submission.accepted`, `submission.awaiting_assets` from the decision RPCs (payloads: `{ submission_id, decline_reason_id?, note?, tier, market }`); `property.published` `{ property_id, slug, tier, market, submission_id? }` and `property.unpublished`. `submission.received` is B3's; `invoice.issued`, `payment.marked`, `submission.activated` are B6's. Story, market, media, inquiry and settings changes emit no event (they write audit and bump `catalog_version` where public).

## Screens (route, components, server functions, who, states)
1. Sign in `/admin/sign-in` (`sign-in.tsx`). Email field, "Send link", note that agents use keys. `POST auth.send-link` sends only when the address has a `user_roles` row with `disabled_at` null; the answer is the same for known and unknown addresses (no enumeration) except the disabled-account state, which is only shown after a valid link is used. States: idle, sent, invalid, disabled account. Mail goes through Supabase Auth with Resend SMTP (B5 step 8). `auth.callback` exchanges the code, sets the cookie, redirects to `/admin`.
2. Dashboard `/admin` (`index.tsx`, `src/admin/dashboard/`). Tiles Submitted, Under Review, Awaiting Assets, Invoice Issued, Scheduled from view `dashboard_counts`; jobs failed in 24 hours and the pinned dead count (from `jobs`); assets pending (from `assets`, zero until B9); next digest date (`schedule_settings.digest`, "not scheduled" until B8b seeds it); channel health per channel (`channel_settings`, "not connected" until B10); free-tier gauges (P-009): database size, emails sent today and this month from `email_messages`, "not measured" for the rest until the audit robot (B14); "what happened today" feed from `audit_log`. Every tile opens the filtered list. States: loading, empty ("Quiet day"), degraded (last `health` job failed: red banner). Route `GET dashboard`. All roles.
3. Requests `/admin/requests` (`requests.index.tsx`). `DataTable`: received, address, city and state, agent, brokerage, package, state pill, days waiting; filters state, market, package, search (address, agent, brokerage); saved views "Needs decision" (`Submitted`, `Under Review`) and "Awaiting assets"; bulk start-review for the selection (CE, ME). Keyboard as in the kit. States: loading, empty per filter, error. Route `GET submissions`, `POST submissions/start-review`.
4. Request detail `/admin/requests/:id` (`requests.$id.tsx`). Header (address, state pill, days). Left: every submitted field grouped Property, People, Links, Story, Significance (`SubmittedFields`); photo strip from `submission_media` with upload status and signed URLs. Right: decision panel by state, internal notes, timeline (audit plus job events, actor and agent pill). Actions by role: Start review; Decline; Accept; Request assets; Assets received; Add note (VE, MO too); Open invoice and Create property after accept (invoice link points at B6 screen 6, hidden until B6 registers its nav entry). States: Submitted, Under Review, Declined (read-only, shows reason), Accepted, Awaiting Assets, Invoice Issued, Scheduled, Published (links to the property).
7. Properties `/admin/properties` (`properties.index.tsx`). Table: title, market and region, editorial state, tier, ranks, published date, source; filters; "New from request" lists accepted requests without a property (CE, ME, VE); publish and unpublish inline (CE, ME) through the same dialogs as the editor. States: draft, review, published, archived.
8. Property editor `/admin/properties/:id` (`properties.$id.tsx`). Tabs Narrative (title, deck, story paragraphs, place), Facts (numeric and enum fields, architect, designer, style, type, status), Sequence (gallery order, hero, orientation, alt, uses media functions), Representation, Placement (hero rank, featured rank, tier, related), Preview (iframe of the public page with a 15 minute draft token). Publish bar with the checklist: hero set, at least 6 images with alt, narrative of at least 2 paragraphs, representation for live listings. Save autosaves drafts (1.5 s debounce, `expected_updated_at`). Publish and unpublish: CE, ME. States: draft (autosave), review, published (edits audited, "Publish changes" bumps `catalog_version`), archived. The "request re-render of assets" button appears when B9 registers `assets.re_render`.
9. Media `/admin/media` (`media.index.tsx`). Grid by property; drag upload (browser PUT to a presigned R2 URL, then `attach`); variant status thumb, card, hero, og, carousel; alt editor; replace; delete only when the image is not on a published property and not referenced by an asset. States: uploading, waiting for publish (ASSUMED label; variants are made at publish, S11), processing (a `render_variants` job is queued or running), ready, failed (Retry calls the B8 job retry). ## Risks and gotchas (link GOTCHAS ids)
- G-001: never edit `src/routeTree.gen.ts`; the many `admin/*.tsx` files are picked up by the generator. Flat dotted names (`requests.$id.tsx`, `automation.recipes.tsx`) match the style B8 already uses.
- G-004: admin domain files, API JSON and columns are one shape (snake_case); the state enum name is `Invoice Issued` (B2 replaced `Awaiting Payment`); grep the old name across `contracts.ts`, `workflow.ts` and the migrations before finishing. B2's `enforce_publish_gate` lets `admin` set `published` at database level while this matrix allows only CE and ME; the server is stricter on purpose.
- G-005: admin components use `src/admin/<feature>/<feature>-api.ts` only; no `src/data/*`.
- G-006: `SUPABASE_SERVICE_ROLE_KEY`, `PREVIEW_TOKEN_SECRET` and `R2_*` are Worker or Edge Function secrets; nothing admin-related is `VITE_*`. The browser holds no Supabase key: the session cookie is httpOnly and set by the Worker.
- G-007: admin CSS is plain, tokens only; the four status tokens are added to `tokens.css` first.
- G-011 and P-009: `ssr: false` keeps Worker CPU low; the dashboard endpoint must stay a handful of indexed counts (10 ms CPU budget); if it exceeds, cache it 30 seconds in the browser. Supabase Auth mail shares the Resend quota (B5).
- Supabase built-in mail is rate limited to a few messages per hour; magic links need the Resend SMTP of B5 step 8 before step 2's real-inbox proof. BLOCKED on B5 for that one proof only; local Inbucket proves the rest.
- Browser upload straight to R2 needs a CORS rule on the bucket (PUT from the site origins); if missing the upload fails with an opaque network error. Runbook step in `docs/runbook-admin.md`.
- `@supabase/ssr` in the Worker runtime and the TanStack Start cookie helpers are UNPROVEN until step 2 runs on a preview Worker.
- The Supabase Auth admin API (invite, create agent user, ban) is called from the Worker with the service role; it is external work inside a request, allowed here because it is an operator click, not an automation (architecture 1 forbids it for recipes). Rate: a handful per week.
- Agents are staff (S38): the guardrails in invariant 3 add `humanOnly` and a daily cap beyond the three in architecture 6 (roles, agent keys, settings). Flag for the CEO.
- "Admin" alone cannot decline or accept (architecture 3.7). The CEO should hold `admin` plus `chief_editor`; the team screen makes that one click.
- The plan relies on `properties` and `stories` columns of the B2 migration (`editorial_state`, `published_at`, `hero_rank`, `featured_rank`, `campaign_tier`, `source`, `submission_id`, `author_id`) and on the story to property link; verify against generated types in steps 7 and 12 before writing the functions.
- The publish checklist item "representation for live listings" needs a definition of live listing; ASSUMED `properties.status` of `For Sale` or `For Rent` means live; confirm against `src/domain/property.ts` in step 7.
