Two small additions to the 4.2 list, ASSUMED: `me` (`GET /api/admin/me` returns actor, roles, kind, scopes, `actions` (invariant 2) and `environment`, the Worker var `MOP_ENV` (`production`, `preview` or `local`, B1b and B3) read through B3's `src/server/lib/env.ts`; `tests/unit/actor.test.ts` also calls the `me.ts` handler with a fake actor and asserts the body carries `environment`) and `auth` (`send-link`, `callback`, `sign-out`), which sign-in cannot do without; plus `dashboard` (`GET /api/admin/dashboard`) for screen 2.

3. Agents (S38, architecture 6): scope = route group name in `agent_keys.scopes`; an agent may act only inside its scopes and only where its `user_roles` role allows; groups `team` and `settings` are never available to agents (403 `human_only`), nor any action flagged `humanOnly`. A daily decision cap `settings.agent_daily_limits.decisions_per_day` (seed 25, ASSUMED) counts audit rows `submissions.decline` and `submissions.accept` per agent per UTC day; over the cap is 429 `agent_daily_limit`. The count runs in SQL so two parallel calls cannot both pass: `decline_submission` and `accept_submission` first call `assert_agent_daily_cap(p_actor, p_actor_kind)` (in `<ts>_admin_submissions_decisions.sql`), which returns at once for `human`, and for `agent` takes `pg_advisory_xact_lock(hashtext(p_actor::text))`, counts `audit_log` rows with `actor_id = p_actor`, `action in ('submissions.decline', 'submissions.accept')` and `at >= date_trunc('day', now() at time zone 'utc') at time zone 'utc'` (B2's index `audit_log (actor_id, at)`), reads the cap from `settings`, and raises `agent_daily_limit`, which `admin-errors.ts` maps to 429. A scope miss is 403 `out_of_scope` from `authorize`. One exception to the scope rule: the action `me` (registered in `src/server/lib/permissions/dashboard.ts` with all six roles and `scopeFree: true`) is not scope-checked, so any enabled agent key may call `GET /api/admin/me` whatever its scopes; `authorize(actor, "me")` checks only that the key is valid and has an enabled role. `tests/unit/authz.matrix.test.ts` asserts that an agent with scopes `["submissions"]` gets 200 from `me` and 403 `out_of_scope` from `dashboard.get`.

14. Agent review (GG-07). "Send preview to agent" is `POST properties/:id/agent-preview`: it signs a token in B2's format `<property_id>.<exp>.<hmac>`, where `hmac` is HMAC-SHA256 with `PREVIEW_TOKEN_SECRET` over `<property_id>.<exp>.<preview_nonce>` (7 days; the editor iframe token is the same format with 15 minutes), moves `editorial_state` from `draft` or `review` to `agent_review` (B2's enum value) and returns the URL `/property/<slug>?preview=<token>` for the editor to copy. The public route treats it like the 15 minute editor token: skips the `published` filter, answers `Cache-Control: no-store` (B1b's pipeline sets exactly that on a preview-token request, G65), and adds `X-Robots-Tag: noindex, nofollow` plus the `noindex` meta. The agent's approval is recorded by the editor moving the state back to `review` with a note. Revoking: "Revoke preview links" (action `properties.revoke_previews`, route `POST properties/:id/revoke-previews`) calls `rotate_preview_nonce(p_property, p_actor, p_actor_kind, p_request_id)`, which sets `preview_nonce = gen_random_uuid()` and writes the audit row whose action is the matrix id `properties.revoke_previews`; every outstanding agent and editor link of that property then fails verification (404), and other properties' links are untouched (state this in the dialog).
15. Data-subject requests (GP-01, architecture 10). Requests arrive through B3 `POST /api/public/subjects/request` into `subject_requests` (B3, `20261001100000_public_write_functions.sql`), each with a 45 day due date and one of the kinds `access`, `deletion`, `opt_out`, `correction` (G29). Screen 25 lists them with days left. The functions take the request as `p_subject_request_id uuid` (the actor triple's `p_request_id` stays the HTTP request id). Identity first (B3 invariant 13): `set_subject_request_status(p_subject_request_id, p_action, p_note, ...)` with `p_action` `start_verification` (`received` to `verifying`), `confirm_identity` (sets `verified_at = now()`, status stays `verifying`), `reject` (from `received` or `verifying` to `rejected`, note required) or `fulfil_correction` (kind `correction` only, after the editor has corrected the row by hand on the screen that owns it, which writes its own audit row; note required, names what was changed); audit action `audit.subject_status`. Each fulfilling function refuses a request whose `verified_at` is null (`not_verified`), whose kind is not its own (`wrong_kind`) or that is already `fulfilled` or `rejected` (`wrong_state`), all 409. `export_subject(p_subject_request_id)` (kind `access`) returns one JSON bundle of what the address appears in (`subscribers`, `inquiries`, `submissions` and their notes) and `delete_subject(p_subject_request_id)` (kind `deletion`) anonymises those rows (email replaced by a hash at the `.invalid` domain, name, phone, message and `details` cleared; on `inquiries` the same column set as B8's `retention_anonymise_inquiries`: `name` and `message` set to `''`, `phone` and `location` to null, `details` to `'{}'`, `attribution` to `'{}'` when B15 has added the column (checked through `information_schema.columns`), `forwarded_payload` to null, `email` to `<sha256 of the old value>@anonymised.invalid`, and `anonymised_at = now()`, so screen 11 shows both paths the same way) instead of hard deleting, because nothing hard-deletes except the retention job (GD-04). In the same transaction `delete_subject` scrubs the stored body of every `webhook_omnikom` job of those inquiries with the statement B8's `retention_anonymise_inquiries` uses, `update jobs set result = result - 'body' where type = 'webhook_omnikom' and payload->'data'->>'inquiry_id' = <id>::text and result ? 'body'` (G16; `jobs` has no update guard, B8), so a dead job keeps no copy of the old email or message. `opt_out_subject(p_subject_request_id, ...)` (kind `opt_out`) sets `subscribers.unsubscribed_at = now()` on the row whose `lower(email)` matches, where it is null, and inserts `email_suppressions (email, reason)` with `lower(email)` and `manual` (`on conflict do nothing`, B5's table), so no recipe, digest or broadcast mails the address again and B11's `syncAudience(db, audience)` (`src/server/newsletter/audience.ts`, G14), run before each broadcast and in the daily hygiene run, removes the contact from Resend. The three fulfilling functions write `audit_log` rows (`audit.subject_export`, `audit.subject_delete`, `audit.subject_opt_out`) whose before and after hold ids and counts, never the personal data, and mark the request `fulfilled` with `fulfilled_at = now()` and `handled_by = p_actor` (B3's columns). Admin only, humans only, recent sign-in required (invariant 11).
16. Redirects (GG-01). The `redirects` table (`from_path`, `to_path`, `status`, `archived_at`; B2) is edited only on screen 24. A row is valid when `from_path` starts with `/`, is not under `/admin` or `/api`, has no query string, is unique among active rows, `to_path` is a site path starting with `/` (B2's check on `redirects` refuses anything else; an external target is not supported in v1), `status` is 301 or 302, and the pair creates no loop with another active row (`redirectSchema` in `admin-settings.ts`, mirrored by a SQL check; a row that fails either answers 422 `invalid_redirect`). Removing a row sets `archived_at` (soft delete, GD-04). Every write bumps `catalog_version` through B2's trigger on `redirects` (no function here bumps it by hand, F25 a), so the Worker's edge lookup refreshes, and is audited. The Worker serves redirects before routing (B1b and B3 own that lookup, which reads the redirect map from the catalog snapshot, `getCatalog`, that carries the enabled `redirects` and `slug_history` (F25 b), never from the table).
17. Caching contract (S52, architecture 13, rulings F24 and F25). B7 owns the admin side. (a) Every `/api/admin/*` response and every `/admin` document is `Cache-Control: private, no-store` from the handler, replaced by exactly `no-store` in B1b's pipeline (rule 6, G65), and never touches the Cache API. (b) The session is verified locally (rule 9, F25 i): `session.ts` checks the JWT signature with `jose` against the project's ES256 key (E14: `mop-dev` signs with an asymmetric EC key, so no shared secret is needed), taken from the JWKS (fetched once, held in module memory, refreshed on an unknown `kid`), reads the claims, and makes no network call to Supabase Auth on a request; only the cookie refresh when the token has expired (about hourly) uses the network. The sign-in instant that `session-policy.ts` compares comes from the `amr` timestamp claim of that token (ASSUMED, not `iat`, which moves on refresh; UNPROVEN until step 2 reads a real `mop-dev` token). (c) Every admin list is paginated at 50 at most (`adminPageSchema` in `src/domain/admin-page.ts`: `limit` default 50 and capped at 50, keyset cursor) and every list view filters and sorts on an index created by the same migration. (d) The dashboard is one RPC of indexed counts (`admin_dashboard()`), one database call per load. (e) Publishing, unpublishing, editing a published property (including its media order, alt text or removal and its ranks), a story publish or unpublish, a market edit or coming-soon toggle, a redirect write, a `slug_history` write and a write to a public `settings` key (`flags`, `coming_soon_global`, `site`, `environment`, `og_static`) bump `catalog_version` through B2's triggers in the same transaction as the write (architecture 13 rule 4, F25 a as narrowed by G21); no function or server code in this slice calls `bump_catalog_version()` by hand. The admin-only keys `invoice`, `notifications` and `agent_daily_limits` do not bump it (G21). A draft property row, a submission, a note and an inquiry do not touch a bumping table, so they leave the version unchanged; `property_media` has a plain B2 trigger, so a media change bumps even on an unpublished property (one extra refresh, harmless). The `purge_cache` step stays housekeeping. Every service function in this slice takes the database client as an argument (B3's injectable client, F25 e), so B4's counting client can be passed in. Two admin reads keep one database lookup per request, on purpose, so a revocation takes effect at once: for an agent, `verifyKey` calls `agent_key_by_hash` (one indexed row with the agent's enabled roles, so `revoke_all_agent_keys` and a disabled agent bite on the next call); for a session, `requireActor` reads the user's `user_roles` rows (`select role, disabled_at from user_roles where user_id = $1`, the leading column of B2's `unique (user_id, role)` index), so a revoked role or a disabled account bites on the next request. The JWT carries no roles (no custom access token hook). (f) The public preview paths (`draft_token` and `?preview=`) are the one place a public request reads a draft row, through one RPC, `preview_property`, called only by `src/server/previews/service.ts` (outside the folders B3's `readpath.test.ts` scans) after the token signature and expiry pass; `cachedResponse` in B3's `cache.ts` checks for either search parameter before anything else and then calls `build()` with no lookup and no store. They answer `Cache-Control: no-store` and `x-mop-cache: bypass`, are never stored and never served from the cache (rule 6), and a page request carrying `?preview=` skips the cache lookup even though the page key drops query strings (rule 3); since no entry is stored for them, no Content-Security-Policy header is stored for them either (F25 d).
