## Contract (inputs, outputs, invariants, events emitted, permissions)
Inputs
- Session cookie (Supabase Auth magic link, S10) or `Authorization: Bearer <agent key>` (S38) on every `/api/admin/*` route.
- Zod input schemas per feature in `src/domain/` (`admin-submissions.ts`, `admin-properties.ts`, `admin-media.ts`, `admin-inquiries.ts`, `admin-stories.ts`, `admin-markets.ts`, `admin-team.ts`, `admin-settings.ts`). Roles come from `contracts.ts` (`appRoles`, `roleLabels`) and the state graph from `src/domain/workflow.ts`, both created by B2. ASSUMED: admin API JSON is the snake_case row shape (as generated types and B8 `job_events`); the public camelCase contracts of `contracts.ts` are not reused for admin (G-004: change domain, API and column together).
- Secrets (server only, G-006): `SUPABASE_SERVICE_ROLE_KEY` (exists), `PREVIEW_TOKEN_SECRET` (draft preview links: 15 minutes for the editor iframe, 7 days for the signed agent link), the `R2_*` names of B8 for presigned uploads.

Outputs
- Route group `/admin/*` with layout `src/routes/admin.tsx`. ASSUMED: the layout sets `ssr: false`, so admin pages never spend Worker CPU on server rendering (10 ms per request on the free plan, P-009) and loaders run in the browser with `ensureQueryData`. The layout guard runs before load, skips `/admin/sign-in`, calls `GET /api/admin/me` and redirects to sign-in on 401. Every admin route sets `head()` through `pageHead()` with `noindex: true`; dynamic routes throw `notFound()`.
- `/api/admin/*` route handlers, thin: parse, call one server function, return JSON (architecture 4.2). Two small additions to the 4.2 list, ASSUMED: `me` (`GET /api/admin/me` returns actor, roles, kind, scopes) and `auth` (`send-link`, `callback`, `sign-out`), which sign-in cannot do without; plus `dashboard` (`GET /api/admin/dashboard`) for screen 2.
- Audit action names follow `<entity>.<verb>` (`submission.decline`, `property.publish`, `team.agent_key_create`, `team.agent_keys_revoke_all`, `subject.export`, `subject.delete`). Every state change writes `audit_log` (actor, `actor_kind`, before, after, `request_id`) inside the SQL function that changes the row.
- Transport rules on every `/api/admin/*` response and every `/admin` document: `Cache-Control: private, no-store` and `Vary: Cookie, Authorization`, so nothing admin ever reaches the public cache path. The session cookie is `httpOnly; Secure; SameSite=Lax`, and a second cookie `mop_csrf` (readable by script) carries the double-submit token that `POST`, `PUT`, `PATCH` and `DELETE` must echo in the header `X-MOP-CSRF` (403 `csrf` otherwise). Bearer-key requests carry no cookie and are exempt.
- Additional routes from the sweep (architecture 10): `properties/:id/agent-preview` (POST), `team/agents/revoke-all` (POST), `settings/redirects` (GET, PUT, DELETE), `audit/subject-requests` (GET), `audit/subject-requests/:id/export` and `.../delete` (POST). Each is one server function and one row of the matrix below.

Invariants
1. Every state change is: TS server function (actor, authz, Zod, guardrails) then ONE `security definer` SQL function that changes rows, writes `audit_log` through `write_audit` and calls `emit_event` in the same transaction (architecture 1 and 5; supabase-js has no multi-statement transactions). After commit the server function calls `fanoutEvent(db, event_id)` best effort; the runner's sweep is the safety net (B8b invariant 4).
2. Authorization lives in one matrix, `src/server/lib/authz.ts`, assembled from group files `src/server/lib/permissions/<group>.ts` (`submissions`, `properties`, `media`, `inquiries`, `stories`, `markets`, `team`, `settings`, `audit`, `dashboard` here; `jobs` in B8, `automation` in B8b, `payments` in B6 each add one file and one import line to `permissions/index.ts`). Entry: `{ action, group, roles: AppRole[], humanOnly?: true }`. The UI only hides buttons through `<RoleGate>`; the server is the check (tech-stack 5, admin action path).
3. Agents (S38, architecture 6): scope = route group name in `agent_keys.scopes`; an agent may act only inside its scopes and only where its `user_roles` role allows; groups `team` and `settings` are never available to agents (403 `human_only`), nor any action flagged `humanOnly`. A daily decision cap `settings.agent_daily_limits.decisions_per_day` (seed 25, ASSUMED) counts audit rows `submission.decline` and `submission.accept` per agent per UTC day; over the cap is 429 `agent_daily_limit`.
4. Roles are the enum `app_role`: `chief_editor`, `managing_editor`, `visual_editor`, `media_ops`, `commercial`, `admin` (S26, architecture 3.2). `admin` alone does not decide submissions (architecture 3.7 lists only chief and managing editors), so the CEO must hold `admin` and `chief_editor` together. CONFLICT with B2, which ASSUMED `unique (user_id)` on `user_roles` (one role per person); the sketch had `unique (user_id, role)`. ASSUMED resolution: the `admin_team` migration (step 14) restores `unique (user_id, role)`; B2's `role_in(variadic app_role[])` already works with several rows. Until then the CEO test account holds `chief_editor` and the admin screens are reached with a second account. `appRoles` and `roleLabels` (B2 replaced `editorialRoles` in `contracts.ts`) are the only role lists.
5. The submission state machine is B2's `src/domain/workflow.ts` (`submissionTransitions`, `canTransition(from, to, ctx)`, mirrored by the database function `submission_transition_allowed` and the trigger `enforce_editorial_gate`); B7 adds no second copy and only adds `allowedActions(state)` to `src/domain/admin-submissions.ts` for the buttons. States of architecture 3.3: `Submitted`, `Under Review`, `Accepted`, `Declined`, `Awaiting Assets`, `Invoice Issued`, `Scheduled`, `Published`, `Distribution Active`, `Completed`; B2 already corrected `submissionStates` in `contracts.ts`; step 4 only verifies). Transitions owned here: `Submitted` to `Under Review` (start review); `Under Review` to `Declined`, `Accepted`, `Awaiting Assets`; `Accepted` to `Awaiting Assets`; `Awaiting Assets` back to `Accepted` when `accepted_at` is set, else to `Under Review` (action `assets_received`, ASSUMED, audit only, no catalog event); `Scheduled` to `Published` (in `publish_property`). B6 owns `Accepted` to `Invoice Issued` to `Scheduled`. Each RPC checks the current state under `select ... for update` and returns 409 `wrong_state` otherwise.
6. Preview equals send: the decline and accept previews call B5 `previewTemplate` with the same variables the `send_email` step will resolve.
7. Optimistic locking on the dossier (GD-01): `properties.version int` (B2 column) is returned by every read and sent back as `expected_version` by `PATCH properties/:id`, `publish`, `unpublish`, `rank` and `related`; `update_property` compares it under `select ... for update`, increments it by one on success and returns the new value. A mismatch is 409 `stale`, and screen 8 stops autosave and shows "Reload, someone saved" with the reload button (no silent merge). Stories keep `expected_updated_at` (ASSUMED: the gap names dossiers only) and answer with the same 409 `stale`. Human and agent edits meet here.
8. Publishing is gated in TS (checklist) and in SQL (hero present and at least 6 images with alt); a property from a submission also requires the submission at `Scheduled` (which the B6 trigger only allows after payment paid or waived). Publish is allowed from `review` or `agent_review`. Property edits after publish save to the live row and are audited (before and after); "Publish changes" bumps `catalog_version`. ASSUMED reading of "edits create a new version": history is the audit trail, not a second copy. The slug is immutable once `published_at` is set: `update_property` refuses a slug change with 422 `slug_locked`; before publish a rename writes the old value to `slug_history` (GD-02, table owned by B2).
9. Admin components never import `src/server/**`, `src/db/**` or `src/data/**`; each feature has `src/admin/<feature>/<feature>-api.ts` (typed fetch wrappers, the admin equivalent of `services`, same pattern as B8's `jobs-api.ts`). Enforced by `tests/unit/admin-boundaries.test.ts`.
10. `track()` posts to the public `/events` endpoint and would pollute product analytics. ASSUMED deviation from AGENTS.md ("every user action calls track()"): admin actions are recorded by `audit_log`, which is their analogue. Update AGENTS.md when this lands.
11. Session hardening (GS-02, architecture 10). An admin session lasts 12 hours from sign-in: `session-policy.ts` compares the user's `last_sign_in_at` with now and answers 401 `session_expired` past 12 h (Supabase's own session time-box is believed to be a paid Pro feature, UNPROVEN, and G-011 forbids buying it, so the Worker enforces the limit). The `team` and `settings` groups and `subject_requests` export and delete also need a sign-in within the last 15 minutes (ASSUMED window): otherwise 401 `reauth_required`, and the UI sends the actor through `/admin/sign-in?next=<path>` and back. CSRF and the no-store headers of Outputs apply to every admin route. Agent keys are not sessions and skip the 12 h and re-auth rules; they are refused on `team` and `settings` anyway (invariant 3).
12. Time (GD-06). The database stores UTC. Every timestamp an admin screen shows goes through `<LocalTime>` and `src/domain/market-time.ts`: `marketTimezone(market_slug)` returns `America/Los_Angeles` for `california` and `America/New_York` for `new-york` and `florida` (architecture 10); an entity with no market shows `America/New_York` (ASSUMED owner zone) and a small "ET" or "PT" suffix, so the zone is never implicit. Inputs typed by an editor (a scheduled date) are converted to UTC on the way in. `channel_settings.posting_window.tz` (B8b, B10) is an IANA name and is displayed as typed.
13. Takedown (GP-03, architecture 10). `unpublish_property(p_property, p_reason, p_takedown, ...)` requires a `reason` from `unpublishReasons` in `admin-properties.ts` (`owner_request`, `rights_takedown`, `factual_error`, `other`, with a note when `other`). Both `unpublish_reason` and `unpublished_at` are stored on the row and audited. With `p_takedown = true` (a rights or owner takedown, not an ordinary unpublish) the same transaction also sets `taken_down_at`, cancels the property's `queued` and `waiting_approval` `post_meta` jobs through B8 `cancel_job`, and emits `property.unpublished` with `takedown: true`; B8b's recipe then bumps `catalog_version` and purges the cache. `taken_down_at` is the 410 marker: B13 serves `410 Gone` for that slug and the slug is never reused. The 24 hour target is a working rule for the editor, shown on the dialog. Posts already live on Instagram or Facebook are withdrawn by hand (runbook); the plan cannot prove more.
14. Agent review (GG-07). "Send preview to agent" is `POST properties/:id/agent-preview`: it signs a token (HMAC-SHA256 with `PREVIEW_TOKEN_SECRET`, payload `{ property_id, kind: "agent", exp }`, 7 days), moves `editorial_state` from `draft` or `review` to `agent_review` (a value B2 adds to the enum, ASSUMED: architecture 3.1 lists `draft|review|published|archived`, and the sweep adds the optional state) and returns the URL `/property/<slug>?preview=<token>` for the editor to copy. The public route treats it like the 15 minute editor token: skips the `published` filter, answers `Cache-Control: private, no-store`, and adds `X-Robots-Tag: noindex, nofollow` plus the `noindex` meta. The agent's approval is recorded by the editor moving the state back to `review` with a note. The link cannot be revoked before it expires except by rotating `PREVIEW_TOKEN_SECRET` (state this in the dialog).
15. Data-subject requests (GP-01, architecture 10). Requests arrive through B3 `POST /api/public/subjects/request` into `subject_requests` (B2), each with a 45 day due date. Screen 25 lists them with days left; `export_subject(p_request_id)` returns one JSON bundle of what the address appears in (`subscribers`, `inquiries`, `submissions` and their notes) and `delete_subject(p_request_id)` anonymises those rows (email replaced by a hash at the `.invalid` domain, name, phone, message and `details` cleared) instead of hard deleting, because nothing hard-deletes except the retention job (GD-04). Both write `audit_log` rows whose before and after hold ids and counts, never the personal data, and mark the request `fulfilled` with `fulfilled_by` and `fulfilled_at`. Admin only, humans only, recent sign-in required (invariant 11).
16. Redirects (GG-01). The `redirects` table (`from_path`, `to_path`, `status`, `archived_at`; B2) is edited only on screen 24. A row is valid when `from_path` starts with `/`, is not under `/admin` or `/api`, has no query string, is unique among active rows, `to_path` is a path or an https URL, `status` is 301 or 302, and the pair creates no loop with another active row (`redirectSchema` in `admin-settings.ts`, mirrored by a SQL check). Removing a row sets `archived_at` (soft delete, GD-04). Every write bumps `catalog_version` so the Worker's edge lookup refreshes, and is audited. The Worker serves redirects before routing (B1 and B3 own that lookup).

Events emitted (existing catalog only): `submission.declined`, `submission.accepted`, `submission.awaiting_assets` from the decision RPCs (payloads: `{ submission_id, decline_reason_id?, note?, tier, market }`); `property.published` `{ property_id, slug, tier, market, submission_id? }` and `property.unpublished` `{ property_id, slug, market, reason, takedown }`. `submission.received` is B3's; `invoice.issued`, `payment.marked`, `submission.activated` are B6's. Story, market, media, inquiry and settings changes emit no event (they write audit and bump `catalog_version` where public).

## Data changes (migrations, enums, RLS, seeds)
- No new tables. Everything uses B2 tables (architecture 3.1 to 3.3 and 10: `subject_requests`, `slug_history`, `redirects`), `decline_reasons` (B8b), `events` and `jobs` (B8). Additive migrations only, in the order of the steps: `admin_audit`, `admin_submissions`, `admin_properties` (three property columns and the `agent_review` value, see Files), `admin_media`, `admin_dashboard` (views `dashboard_counts`, `submission_list`), `admin_content`, `admin_team` (relaxes `user_roles` to `unique (user_id, role)`, helper functions for `last_admin`, key lookup and `revoke_all_agent_keys`, which sets `revoked_at` on every unrevoked key and returns the count), `admin_settings` (redirect functions), `admin_privacy` (`export_subject`, `delete_subject`). Each migration states its down path or is marked irreversible in its header comment (GD-07); the three column additions have a `drop column` down path.
- `properties.version` is a B2 column; `update_property` and every function that edits a property row increments it. The read views and generated types must expose it, or the lock cannot work (verify in step 7).
- RLS (architecture 3.7): `select` for every role in `user_roles` on admin tables; writes by feature role as in the matrix (defense in depth, the service role writes through the functions); `audit_log` and `events` insert-only; `delete` for nobody except `admin` on `agent_keys`. `tests/db/admin.db.test.ts` proves a `commercial` session cannot update `submissions` and no one can update `audit_log`.
- Functions: `security definer`, `execute` revoked from `anon` and `authenticated`, granted to `service_role`; every one takes `p_actor uuid, p_actor_kind text, p_request_id text`.
- Seeds: `settings.agent_daily_limits = { "decisions_per_day": 25 }` (configuration seed, also in production); dev and preview admin users by `scripts/seed-admin-users.ts` only.

## Risks and gotchas (link GOTCHAS ids)
- G-001: never edit `src/routeTree.gen.ts`; the many `admin/*.tsx` files are picked up by the generator. Flat dotted names (`requests.$id.tsx`, `automation.recipes.tsx`) match the style B8 already uses.
- G-004: admin domain files, API JSON and columns are one shape (snake_case); the state enum name is `Invoice Issued` (B2 replaced `Awaiting Payment`); grep the old name across `contracts.ts`, `workflow.ts` and the migrations before finishing. B2's `enforce_publish_gate` lets `admin` set `published` at database level while this matrix allows only CE and ME; the server is stricter on purpose.
- G-005: admin components use `src/admin/<feature>/<feature>-api.ts` only; no `src/data/*`.
- G-006: `SUPABASE_SERVICE_ROLE_KEY`, `PREVIEW_TOKEN_SECRET` and `R2_*` are Worker or Edge Function secrets; nothing admin-related is `VITE_*`. The browser holds no Supabase key: the session cookie is httpOnly and set by the Worker.
- G-007: admin CSS is plain, tokens only; the four status tokens are added to `tokens.css` first.
- G-011 and P-009: `ssr: false` keeps Worker CPU low; the dashboard endpoint must stay a handful of indexed counts (10 ms CPU budget); if it exceeds, cache it 30 seconds in the browser. Supabase Auth mail shares the Resend quota (B5).
- Supabase built-in mail is rate limited to a few messages per hour; magic links need the Resend SMTP of B5 step 8 before step 2's real-inbox proof. BLOCKED on B5 for that one proof only; local Inbucket proves the rest.
- Browser upload straight to R2 needs a CORS rule on the bucket (PUT from the site origins); if missing the upload fails with an opaque network error. Runbook step in `docs/runbook-admin.md`.
- `@supabase/ssr` in the Worker runtime and the TanStack Start cookie helpers are UNPROVEN until step 2 runs on a preview Worker.
- The Supabase Auth admin API (invite, create agent user, ban) is called from the Worker with the service role; it is external work inside a request, allowed here because it is an operator click, not an automation (architecture 1 forbids it for recipes). Rate: a handful per week.
