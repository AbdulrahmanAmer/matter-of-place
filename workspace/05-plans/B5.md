## Goal and observed exit
Every transactional and notification email the business sends is a row in `email_templates` (subject, preheader, blocks, variables, enabled, version) rendered through React Email components in `src/templates/email`; the two exceptions are code layouts owned by B11, the Place Notes issue (`src/templates/email/place-notes.tsx`) and the weekly KPI email (`src/templates/email/ceo-weekly.tsx`). Template rows are sent by the `send_email` and `notify_admin` steps as jobs, delivered through Resend, with delivery, bounce and complaint events coming back through a signed webhook. Place Notes and market-interest signups use double opt-in with hashed tokens (S13, S30, S32, S34).
Observed exit (completion map B5): "test subscriber confirms; each template renders and sends". Proven as (the live parts BLOCKED until the Resend account, API key and verified domain exist): `bun run scripts/email-test.ts all <address>` sends every enabled key of `emailTemplateKeys` (a disabled row, `standalone` as seeded, is reported `skipped`) to a real inbox on `mop-dev` and each arrives with no unreplaced `{{`, each passes the HTML email lint and renders at 600 px without horizontal overflow (`scripts/email-shots.ts`); then a signup for `California` through `POST /api/public/subscribers` produces a confirmation email, the link confirms the row (`confirmed_at` set, hash cleared) and a `subscriber.confirmed` event exists; a Resend test bounce address marks the message `bounced` and adds a suppression.

Invariants
1. A template renders only from the database row. The React files supply layout and seed defaults; editing a row in screen 18 changes the next email with no deploy (S34).
2. Preview equals send: the decline preview of B7 and the test send of screen 18 call the same `renderTemplate(row, variables, site)` and the same `resolveVariables` as `send_email`. There is no second renderer.
3. A missing variable at send time is a `NonRetryableError("missing_variable:<name>")`, so nobody receives `Hello {{name}}`; at save time it is a warning (screen 18 state "missing variable warning").
4. Idempotency, per recipient: the Resend `Idempotency-Key` header is `<job idempotency_key>:<first 12 hex of sha256(lower(to_email))>`, so the second recipient of one `notify_admin` job never reuses the first one's key (ASSUMED supported by Resend for 24 hours; verify against current Resend docs in step 4, UNPROVEN until then). A retry after a successful send finds the `email_messages` row already `sent` and does not call Resend; a crash between Resend's answer and the row update is covered by the key, which returns the same Resend id. Either way no second email.
5. Daily and monthly ceilings by class (S13 free tier: 100 per day, 3,000 per month, P-009; INT-02, INT-03, PERF-11, DL-07, E2E-04). `mop-dev` and production share one Resend account, so each database holds its own share in `settings.email` = `{ daily_cap, bulk_cap, monthly_cap, dev_recipients }`, seeded from `settings.environment`: exactly `production` gives `{ daily_cap: 75, bulk_cap: 50, monthly_cap: 2600, dev_recipients: [] }`, anything else gives `{ daily_cap: 15, bulk_cap: 5, monthly_cap: 300, dev_recipients: ["admin@matterofplace.com", "admin+*@matterofplace.com", "*@resend.dev"] }` (Resend's own test addresses, used by steps 6 and 9, are allowed) (ASSUMED values; 75 plus 15 leaves 10 a day for Supabase Auth mail, which uses the same Resend SMTP and quota and is also capped at Supabase, step 8). `sendOne` counts with `email_sent_today()` (B5's body counts `email_messages` rows whose `sent_at` falls in the current UTC day whatever their later status, `sent`, `delivered`, `bounced`, `complained`, and not `queued`, `failed` or `skipped` rows, which have no `sent_at`; B11 later replaces the body with the same signature to add broadcast recipients) and `email_sent_month()` (the same count over the current UTC month; B11 replaces its body the same way). Per class: `bulk` sends while `email_sent_today() < bulk_cap`, else it returns `{ status: "retry_at", at: next UTC day 01:00, reason: "daily_cap_bulk" }`; `transactional` and `test` send while `email_sent_today() < daily_cap`, else `{ status: "retry_at", at: next UTC midnight plus 1 minute, reason: "daily_cap" }`; `alert` ignores the local daily and monthly ceilings, and only Resend's own refusal stops it (invariant 14 gives alerts a second path). Every class but `alert` also returns `{ status: "retry_at", at: the 1st of next UTC month 00:01, reason: "monthly_cap" }` once `email_sent_month() >= monthly_cap`. A `retry_at` consumes no attempt (B8 invariant 3). The bulk ceiling always leaves room for transactional mail, so a market opening or a re-permission run never pushes an invoice, a decision letter or a confirmation to the next day.
6. Suppression is checked before every send; a suppressed address yields a done job with result `{ skipped: "suppressed" }`. A disabled template yields `{ skipped: "template_disabled" }` (a switch admins can use). A recipient whose domain ends in `.invalid`, `.test` or `.example` is never sent to: the row is `skipped` with `error = 'reserved_domain'` and the result is `{ skipped: "reserved_domain" }`, with no call to Resend, whether or not the dry run is on (G14; this is what keeps B4's live specs and B8's anonymised `@anonymised.invalid` addresses off the quota). On any `MOP_ENV` other than exactly `production`, a recipient that matches no pattern of `settings.email.dev_recipients` (a `*` matches any run of characters before the `@`, compared on `lower(email)`) is written `skipped` with `error = 'not_allow_listed'` and the result `{ skipped: "not_allow_listed" }`, before Resend is called (INT-02); the public dev Worker therefore cannot mail an arbitrary address whatever Turnstile does, and the L1 rehearsal, whose recipients are `+rehearsal` aliases of admin@, still arrives.

## Risks and gotchas (link GOTCHAS ids)
- P-009: Resend free is 3,000 per month and 100 per day, per account, and `mop-dev` and production share the account. Invariant 5 splits it as data: production 75 a day (bulk stops at 50), `mop-dev` 15 (bulk stops at 5), 10 left for Supabase Auth mail (magic links, invites), which `[auth.rate_limit] email_sent = 10` also caps at Supabase; monthly 2,600 and 300. A Place Notes list above the bulk ceiling cannot go out in one day; B11 must spread sends or the plan upgrades ($20, tech-stack 1). Audience limit 1,000 contacts. The values are ASSUMED and editable in `settings.email`; L1's preflight checks production's.
- G-006: `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET` (B3), `CONFIRM_TOKEN_SECRET` are never `VITE_*`; `CONFIRM_TOKEN_SECRET` must be identical in the Worker (seals) and the Edge Function (opens). Supabase function secrets and Cloudflare secrets are two stores; missing one gives a runner that cannot send while the Worker looks healthy.
- G-004: `email_templates` columns, `src/domain/email.ts` and the API JSON are one shape. `email_messages` and `email_suppressions` are additions to the architecture; the diagram and architecture text change in the same commit.
- G-007: email HTML needs literal colour values; they come only from `theme.gen.ts`, generated from `tokens.css`. Fonts fall back to Georgia and Helvetica in clients that block web fonts.
- Edge Function runtime: React Email rendering runs in Deno through `npm:` specifiers. Measured 2026-10-01 (E5): `npm:@react-email/render@1` and `npm:react@19` import and run on supabase-edge-runtime 1.77.0, deployed without Docker with `supabase functions deploy <name> --use-api`. Still open: the bundle size and cold start with every template file, measured in step 4a and recorded in the runbook; if too heavy, fall back to pre-rendering with `renderToStaticMarkup` only (same components).
- Worker CPU is 10 ms per request on the free plan (P-009): B8b's preview endpoint `automation.templates.preview.ts` calls `previewTemplate`, which renders one small email; `scripts/email-cpu.ts` measures it in step 3 (an in-process timing on the laptop, a proxy for Worker CPU). If the p95 is above 8 ms, `previewTemplate` returns the resolved blocks and the browser renders them with the same components.
- Email scanners can click a GET confirm link. Impact is a subscriber confirmed by a security scanner; accepted for a newsletter (B3 owns the route). ASSUMED. DL-06 (d), a confirm page whose one button POSTs the confirm, is optional in the review and needs an operator decision; it is not built. Staff sign-in is different: its link is token-hash and confirmed by a POST (API-01, B7), because a spent staff link locks the person out.
- Resend contacts: B5 creates and removes none. Resend contacts are B11's: `syncAudience(db, audience)` in `src/server/newsletter/audience.ts` adds them before each broadcast and removes suppressed or lapsed ones (G14); B5 only stores `email_events` and sets `unsubscribed_at` from `contact.updated`.
- B11 later changes B5 files, and each such change is done only when `bunx vitest run tests/unit/email` still passes: `send-email.ts` (the `standalone` key delegates to B11's `sendStandalone` after the template-enabled check), `variables.ts` and `notify-admin.ts` (the `digest.due` notice waits for the sibling `queue_digest` job and returns `retry_at` meanwhile), and the bodies of `email_sent_today()` and `email_sent_month()` (add broadcast recipients, same signatures), and the `class` of every template it adds. `sendOne` already accepts pre-rendered content, so B11 needs no change to it.
- Deliverability needs DMARC and warm-up; a new domain with a burst of test mails (one per key) can land in spam. Send tests to a real inbox, not only Resend's sink addresses; the Zoho mailbox admin@matterofplace.com is one, and Zoho may file service mail under its Notification folder (P-034).

- GQ-04: the lint is hand-written and covers the rules that have hurt email before (scripts, relative images, missing `alt`, clipping, leftover variables); it is not a substitute for looking at a real inbox. Screenshots come from Chromium, not from Gmail or Outlook, so table-layout and dark-mode quirks of real clients are UNPROVEN; step 5's real send to a real inbox (BLOCKED until setup A3) is the only client check, and a Gmail and an Apple Mail screenshot are added to the runbook by hand.
