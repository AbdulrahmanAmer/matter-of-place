## Goal and observed exit
Every email the business sends is a row in `email_templates` (subject, preheader, blocks, variables, enabled, version) rendered through React Email components in `src/templates/email`, sent by the `send_email` and `notify_admin` steps as jobs, delivered through Resend, with delivery, bounce and complaint events coming back through a signed webhook. Place Notes and market-interest signups use double opt-in with hashed tokens (S13, S30, S32, S34).
Observed exit (completion map B5): "test subscriber confirms; each template renders and sends". Proven as: `bun run scripts/email-test.ts all <address>` sends the eleven templates to a real inbox on `mop-dev` and each arrives with no unreplaced `{{`, each passes the HTML email lint and renders at 600 px without horizontal overflow (`scripts/email-shots.ts`); then a signup for `California` through `POST /api/public/subscribers` produces a confirmation email, the link confirms the row (`confirmed_at` set, hash cleared) and a `subscriber.confirmed` event exists; a Resend test bounce address marks the message `bounced` and adds a suppression.

Block model (architecture 3.5): `body` is an ordered array of `{ type: "heading", text, level? } | { type: "paragraph", text } | { type: "button", label, url } | { type: "facts", rows: [{ label, value }] } | { type: "signature", text? }`. Text and URLs may contain `{{variable}}` (letters, digits, underscore only; no expressions, no conditionals). A block whose interpolated text is empty is dropped, which is how `note_paragraph` disappears when the admin typed no note.

Inputs
- Job envelope of B8: `params = { template, attach?, to? }`, `data` = event payload with `submission_id`, `inquiry_id` or `subscriber_id` (and `decline_reason_id`, `decline_note`, `payment_id` where relevant).
- Secrets (server side only, G-006), in Cloudflare and in Supabase function secrets because `send_email` runs in the Edge Function: `RESEND_API_KEY`, `RESEND_FROM` (ASSUMED `Matter of Place <hello@matterofplace.com>`), `RESEND_WEBHOOK_SECRET` (Worker only), `CONFIRM_TOKEN_SECRET` (Edge Function only), `ADMIN_NOTIFY_EMAIL` (fallback recipient, ASSUMED). No `VITE_*` names.

Outputs
- `email_messages` row per attempt to send (status `queued|sent|delivered|bounced|complained|failed|skipped`). ASSUMED new table, not in architecture 3.3 to 3.6; needed for the daily cap, the bounce rate on the dashboard (architecture 8), idempotency and audit. Reconcile architecture in the same commit (G-004).
- `email_suppressions` row on permanent bounce or complaint. ASSUMED new table.
- `email_events` row per Resend webhook event (delivery, bounce, complaint, and open and click when tracking is on), with the broadcast id when present. ASSUMED new table; B11 aggregates Broadcast metrics from it. Deduplicated by B3's `webhook_receipts (provider, id)`.
- `subscribers.last_engaged_at` and `subscribers.repermission_sent_at` (GG-05, ASSUMED new columns; B5 adds them to B2's table in its own migration and reconciles architecture 3.3 and `docs` in the same commit, G-004). `last_engaged_at` is set when a subscriber confirms or re-confirms (trigger on `confirmed_at`) and when a click event arrives for their address; opens are not used, because mail privacy features make them unreliable.
- `subscribers.confirmed_at` after a click is B3's `confirm_subscriber` (it also emits `subscriber.confirmed`); B5 supplies the email that carries the link.

Invariants
1. A template renders only from the database row. The React files supply layout and seed defaults; editing a row in screen 18 changes the next email with no deploy (S34).
2. Preview equals send: the decline preview of B7 and the test send of screen 18 call the same `renderTemplate(row, variables, site)` and the same `resolveVariables` as `send_email`. There is no second renderer.
3. A missing variable at send time is a `NonRetryableError("missing_variable:<name>")`, so nobody receives `Hello {{name}}`; at save time it is a warning (screen 18 state "missing variable warning").
4. Idempotency: Resend `Idempotency-Key` header equals the job's `idempotency_key` (ASSUMED supported by Resend for 24 hours; verify against current Resend docs in step 4, UNPROVEN until then). A retry after a successful send returns the same Resend id and creates no second email.
5. Daily cap (S13 free tier: 100 per day, 3,000 per month, P-009): `send_email` counts `email_messages` with `sent_at` in the current UTC day; at or above `settings.email.daily_cap` (ASSUMED default 90, leaving 10 for Supabase magic-link mail, which uses the same Resend SMTP and the same quota) it returns `{ status: "retry_at", at: next UTC midnight plus 1 minute, reason: "daily_cap" }` and consumes no attempt (B8 invariant 3).
6. Suppression is checked before every send; a suppressed address yields a done job with result `{ skipped: "suppressed" }`. A disabled template yields `{ skipped: "template_disabled" }` (a switch admins can use).
7. Double opt-in keeps B3's flow (`POST subscribers` stores the row with `confirm_token_hash`, never confirms). B5 wires B3's stub `requestConfirmation(subscriber, token)`: the raw token is sealed with AES-GCM (WebCrypto, key `CONFIRM_TOKEN_SECRET`, 32 bytes base64) before it goes into the job payload, so `jobs.payload` at rest never holds a usable token; the `send_email` step opens it, puts `confirm_url` into the variables and sends. The job key is `send_email:<subscriber_id>:<first 12 hex of the token hash>` (B8 manual-job key form, one job per issued token). Only the hash is stored in `subscribers` (B3); the raw token exists in the email and, sealed, in the job.
8. Email bombing guard is B3's: 5 signups per hour per IP and 3 per hour per email (DB rate limits). B5 adds nothing to it; `requestConfirmation` is called only for a new or still unconfirmed address and the public response is identical in every case (no enumeration).
9. Webhooks: verification, the 300 second window and replay protection are B3's (`hooks/resend.ts`, `webhook_receipts`). B5 adds what happens after verification: `applyEmailEvent` writes `email_events`, moves `email_messages.status` forward only (`sent`, `delivered`, then `bounced` or `complained`), suppresses on a permanent bounce, on a complaint, and on the third transient (soft) bounce for one address within 30 days (GG-05; ASSUMED threshold, read from `email_events.data->>'bounce_type'`). B3 already sets `unsubscribed_at` on a complaint. Architecture 4.3 names the path `/api/hooks/resend/events`; B3 names it `/api/hooks/resend`. ASSUMED: B3 step 9 renames its route file to `resend.events.ts`; B5 must not create a second route.
10. Nothing external happens in a Worker request (architecture 1): the Worker inserts rows and jobs; the runner talks to Resend.
11. No em dashes and no hex colours in template copy or CSS; colours come from `tokens.css` through a generated theme file (see Files).
12. List hygiene (GG-05). Bounces and complaints suppress (invariant 9) and a suppressed address is never mailed again by any template or by B11's issues. A confirmed, not archived, not unsubscribed, not suppressed subscriber whose `coalesce(last_engaged_at, confirmed_at)` is older than 12 months is a candidate (`repermission_candidates(p_limit)`); B11's hygiene job asks each one once with the `repermission` template (a fresh sealed token, job key `send_email:<subscriber_id>:rp:<first 12 hex of the token hash>`, `repermission_sent_at` set by `issue_repermission`). A click confirms through B3's `confirm_subscriber`, which sets `confirmed_at`; the trigger then sets `last_engaged_at = now()` and clears `repermission_sent_at`. 30 days after the ask with no engagement, `lapse_subscribers(p_grace)` archives the subscriber (`archived_at`, `unsubscribed_at`; soft, B2 invariant 4) and writes one `audit_log` row with the count. B5 supplies the template, columns, functions and helpers; B11 schedules and calls them and removes the Resend contact.
13. Every template is linted and looked at (GQ-04). Each rendered template, with its sample variables, must pass `lintEmail` (rules under Files) and must render at 600 px in headless Chrome with `scrollWidth <= 600` (also at 375 px); the screenshot is saved for review and never compared pixel by pixel.

Events emitted: none by B5 directly. B3's `requestConfirmation` emits `subscriber.created` (catalog event, ASSUMED A7) and the default recipe for it runs `send_email(confirm)`, so the confirmation email is editable in Admin › Automation like every other email; `subscriber.confirmed` is emitted by B3's `confirm_subscriber`. `enqueueConfirmEmail` remains as the step's implementation, not a bypass of the recipe engine.

## Risks and gotchas (link GOTCHAS ids)
- P-009: Resend free is 3,000 per month and 100 per day. Auth mail (magic links, invites) shares the quota; the cap of 90 leaves room. A Place Notes list above about 90 confirmed subscribers cannot go out in one day; B11 must spread sends or the plan upgrades ($20, tech-stack 1). Audience limit 1,000 contacts.
- G-006: `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET` (B3), `CONFIRM_TOKEN_SECRET` are never `VITE_*`; `CONFIRM_TOKEN_SECRET` must be identical in the Worker (seals) and the Edge Function (opens). Supabase function secrets and Cloudflare secrets are two stores; missing one gives a runner that cannot send while the Worker looks healthy.
- G-004: `email_templates` columns, `src/domain/email.ts` and the API JSON are one shape. `email_messages` and `email_suppressions` are additions to the architecture; the diagram and architecture text change in the same commit.
- G-007: email HTML needs literal colour values; they come only from `theme.gen.ts`, generated from `tokens.css`. Fonts fall back to Georgia and Helvetica in clients that block web fonts.
- Edge Function runtime: React Email rendering runs in Deno through `npm:` specifiers. UNPROVEN until step 5 runs on `mop-dev`; if the bundle or cold start is too heavy, fall back to pre-rendering with `renderToStaticMarkup` only (same components).
- Worker CPU is 10 ms per request on the free plan (P-009): the preview endpoint renders one small email; measure it in step 3. If it exceeds the budget, the endpoint returns the resolved blocks and the browser renders them with the same components.
- Email scanners can click a GET confirm link. Impact is a subscriber confirmed by a security scanner; accepted for a newsletter (B3 owns the route). ASSUMED.
- Cross-plan mismatches to settle: B11 assumes B5 creates the Resend contact on `subscriber.confirmed`, but the 14-step catalog has no step for it. ASSUMED here: B11 does it (a system job `contact_sync` enqueued by B3's confirm path, calling B11's `channels/resend.ts addContact`), B5 only stores `email_events`. - Deliverability needs DMARC and warm-up; a new domain with a burst of 11 test mails can land in spam. Send tests to a real inbox, not only Resend's sink addresses.
- Legal footer: marketing mail needs a postal address and an unsubscribe link (CAN-SPAM). B5 mails are transactional and carry the entity line only when `settings.site` is set (B16); Place Notes issues (B11) add the unsubscribe token. The unsubscribe endpoint is B11's.
