# Engineering architecture — Matter of Place v1 (build from this)

Companion to `02-tech-stack/tech-stack.md` (choices) and `05-plans/` (slices). Diagrams: `03-diagrams/architecture.md`.
Written 2026-09-30 by the CTO session, no worker agents (S38). Every table, route and screen here has a slice in `05-plans/`.

## 1. Shape
One repository, one Cloudflare Worker, one Supabase project for every stage (ruling H35): the project the build uses becomes the production database at L1's launch switch, and no second project is created.

```
browser ── edge cache ── Worker ──┬── pages (SSR, TanStack Start)
                                  ├── /api/public/*   anonymous, rate-limited, Turnstile on writes
                                  ├── /api/admin/*    Supabase Auth session or agent API key; role-checked server functions
                                  ├── /api/hooks/*    signed callbacks: render workflow, Resend events, Sentry test (no Stripe or Meta hook in v1)
                                  └── /media/<key>    objects of the public Storage bucket `media`, streamed and edge-cached (B3, ruling H33)
Worker ── service role ── Postgres (migrations = source of truth) ── pgmq + pg_cron ── Edge Function job runner
                                                                      └── workflow_dispatch ─── GitHub Actions render workflow ── Supabase Storage (`media`)
Postgres ── service role, claim_job ── captions runner on the operator's laptop (class `local` jobs only, ruling H34)
```

Rules that hold everywhere:
- The browser never holds a Supabase key. Public reads come from the Worker with edge cache; writes are validated with Zod at the Worker and again by database constraints.
- Shapes come from the database: `supabase/migrations/*.sql` → `supabase gen types` → `src/db/types.ts`. `src/domain/*` re-exports row types and holds Zod input schemas only.
- Every state change goes through a server function in `src/server/<feature>/` that (1) resolves the actor, (2) checks the role, (3) performs the change in a transaction, (4) writes `audit_log`, (5) emits an event that the recipe engine turns into jobs. UI never calls the database.
- Every side effect is a job with an idempotency key. Nothing external (email, post, render) happens inside a request.

## 3. Data model v2 (migrations; the sketch schema is superseded)
Conventions: `uuid` ids (`gen_random_uuid()`), `timestamptz` for time, money as `numeric(12,2)` + `char(3)` currency (USD only at launch, check constraint), soft state via enums, every mutable table has `created_at`, `updated_at` (trigger), and RLS enabled with policies per role. Enum values keep the sketch's names where the frontend already uses them.

## 5. The recipe engine
1. A server function commits and inserts an `events` row in the same transaction.
2. Fan-out is TypeScript, not a trigger. After the commit the server function calls `fanoutEvent(db, event_id)` (B8b `src/server/automation/fanout.ts`) best effort, logging and ignoring its error; the runner's `fanoutPendingEvents(db, limit)` sweeps every event with `processed_at is null` on each tick, so a lost call is picked up within a minute. Both read the enabled recipe for `events.type`, call the pure `planEvent(recipe, event, ctx)` (B8b `src/server/automation/plan.ts`, the same function dry-run uses), which filters steps by `conditions` against the payload (tier, market, kind), and write through one `fanout_insert_jobs(p_event_id, p_jobs)` RPC per event: in one transaction it inserts one `jobs` row per planned step with `idempotency_key = event_id:step_id` (`on conflict do nothing`), `heavy` from the step type, `status = waiting_approval` if `requires_approval`, else `queued` plus a pgmq send (none for a step of class `local`, rule 9), and sets `events.processed_at` last. A crash before the commit leaves nothing and the next sweep re-plans the same keys; overlapping calls insert each key once. Proof: `bunx vitest run tests/unit/automation/fanout.test.ts` (B8b; `fanoutEvent` and dry-run plan the same list, exactly one `fanout_insert_jobs` RPC per event).
3. Edge Function `job-runner` (pg_cron every minute, and pgmq `read` with visibility timeout) pops light jobs and runs the step, and never touches a `local` job (below); for heavy jobs it calls the `workflow_dispatch` of `render.yml` (JOB-01; the dispatch token is a fine-grained GitHub token the orchestrator makes (S59) and holds Actions read and write plus Metadata read on this repository only, no Contents, SEC-02) with the job id, its claim and the payload, marks `running`, and the Actions workflow posts results to `hooks/render/callback`, which matches them on the job's `claim`, never on the attempt number (JOB-02). The runner claims a job with `claim_job`, which sets `running` and a fresh `locked_by` claim and leaves `attempts` unchanged (`fail_job` increments it); a handled message is deleted from the queue, never archived (JOB-10).
4. Failures: `attempts++`, exponential `run_after`, `dead` after `max_attempts`; dead jobs appear red in `/admin › Jobs` with a retry button. Every transition is a `job_events` row (3.6) for the timeline in the UI.
5. Dry-run: given a trigger and a sample payload, returns the list of jobs the engine would create, without inserting.
6. Keep-warm: B8b owns the Worker `scheduled()` handler and the cron trigger line in `wrangler.toml` (B1b leaves a marker comment for it); the `keepwarm` row of `schedule_settings` is its switch, with cron `*/10 * * * *` (G9).
7. Social dry-run: one flag, `SOCIAL_DRY_RUN`, makes every channel adapter log instead of post; `META_DRY_RUN` is retired. Every image or video a post carries is addressed as `https://matterofplace.com/media/<key>` (the Worker's own origin before launch), so Instagram, X and LinkedIn fetch it from our domain, never from a `supabase.co` address (ruling H33 (4)).
8. Clocks. Fixed pg_cron jobs, each created by a migration that unschedules by name first (owner, migration): `analytics-partitions` monthly (B2 `20261001090500_analytics_partitions.sql`), `job-runner` every minute (B8 `<ts>_job_cron.sql`, `net.http_post` to the Edge Function with `timeout_milliseconds := 55000`, JOB-02; liveness comes from `ops_heartbeats`, `ops_health` and the token-gated `GET /api/hooks/ops-health/<token>`, not from `cron.job_run_details`, DO-03, ruling H9), `health` daily (B8 `<ts>_system_jobs.sql`), `retention` and `meta_token_refresh` daily (B8 `<ts>_retention.sql`). There is no pg_cron row for `reconcile_uploads` (G10), `kpi_weekly` or `newsletter_hygiene` (G9). B8 also schedules `prune`; B8b's `<ts>_automation_schedules.sql` unschedules it so the runner drives it from `schedule_settings`. `job-runner` calls the runner and `analytics-partitions` calls B2's idempotent function (a failed run is recorded in `cron.job_run_details` and the next run retries); every other cron row only enqueues a job with a dated idempotency key, so a double fire runs once and a failure follows the job backoff. Every other schedule is a `schedule_settings` row (3.5), so screen 20 can pause every clock: `digest`, `prune`, `reconcile` (`*/15 * * * *`; B8's system job `src/server/jobs/system/reconcile.ts` calls B3's `reconcileUploads`, B10 appends its social reconcile guarded to run once a day, whose daily part also moves due `Distribution Active` submissions to `Completed` (G60), B11 appends `aggregateRecentIssues`, G10), `kpi_weekly` (Saturdays 15:00 UTC, B11's `src/server/jobs/system/kpi-weekly.ts`) and `newsletter_hygiene` (daily 16:00 UTC, B11's `src/server/jobs/system/newsletter-hygiene.ts`) run from `runDueSchedules` in `src/server/jobs/scheduler.ts` (B8b) on each runner tick, which claims a due row by moving its `last_run_at` and `next_run_at` in one statement, emits `digest.due` (for `digest`) or enqueues the system job with a dated idempotency key, and puts the claim back if that fails (proof: `bunx vitest run tests/unit/automation/scheduler.test.ts`, B8b); `keepwarm` from the Worker cron trigger; `audit` and `backup` are external clocks (the B14 routine and `backup.yml`). Captions (ruling H34). `write_captions` is the one step of class `local`. `scripts/captions-runner.ts` (`bun run captions`, B9) runs on the operator's laptop by hand and from a Windows scheduled task every 15 minutes while he is signed in (`scripts/install-captions-task.ps1` registers it; the orchestrator runs that script at launch with the operator's word). ## 6. Agents as staff (S38)

## 13. Caching contract (S52): a public read never reaches the database when warm
The goal is a number: after warm-up, a public page view or catalog read costs **zero database queries**, and the database is asked at most once per catalog version per isolate, plus one small state check per isolate every 15 seconds. Writes are never cached. Everything here is free tier: no KV, no paid cache feature (G-011). The free Workers plan also allows at most 50 outbound subrequests per invocation (every Supabase RPC, Storage call and Turnstile call counts; vendor documentation, UNPROVEN here), so no request loops per photograph: B3 signs at most 20 upload URLs per request, a request's photographs are copied by B7's `copy_submission_media` job, and a render callback makes a fixed number of calls whatever the photo count (E2E-02, PERF-07, JOB-03; `tests/unit/subrequest-budget.test.ts`).

| Media | objects of the Storage bucket `media` under content-hashed keys, served by the Worker at `/media/<key>` from the Cache API (`cf.cacheEverything`), `immutable, max-age=31536000`, no database query (ruling H33 (4)) | forever | a new upload is a new key; a takedown removes the keys from Storage and purges their `/media/<key>` addresses (H33 (6)) |

Rules (each one is a test in the slice named):
1. **One read path.** `getPublicState(db)` returns `catalog_version`, flags, `coming_soon_global`, `coming_soon_markets`, `settings.site`, `og_static` (`settings.og_static`, `{}` when absent) and `illustrative_content` (seven keys, G39; `illustrative_content` is true only when `settings.environment` is `development` or `preview`; the Worker also forces it false when `MOP_ENV` is `production`) from one RPC (`public_state()`), memoised 15 seconds per isolate (`CATALOG_VERSION_TTL_MS`, `0` in tests). `getCatalog(db)` returns the snapshot for that version from one RPC (`public_catalog_snapshot()`), mapped once and memoised per isolate. Every public list and detail endpoint, every server-rendered loader (in-process, no network hop), search, concierge, sitemap, llms files, redirects and `getFlags` read from these two and never query a table themselves. The snapshot carries the enabled `redirects` and `slug_history`, and `updated_at` is one of the public keys of every property and story object (the sitemap's `lastmod`, G59). Free-text search is an index built in the Worker over the snapshot (whole tokens and prefixes of three or more characters, with plurals folded on both sides), so a search costs no database query. Both functions take the database client as an argument, so a test can inject a counting client. B2 creates the two RPCs, B3 the read path and the query hydration in `src/router.tsx` (the server render dehydrates, the browser makes no second catalog fetch on load).
2. **HTML is cached, not only JSON.** The request middleware in `src/start.ts` answers GET and HEAD for public pages from the Cache API before rendering, and stores the render after. This is what keeps Worker CPU under the free limit (E3: the home page renders in 6 to 52 ms; a cache hit costs about 1 ms). A cached render is a pure function of (release, version, path) and reads no clock (PERF-05). B1b creates the middleware order, B3 the cache module it calls.
3. **The key.** `https://cache.mop.internal/<release>/v<catalogVersion>/<kind>/<pathname>` where `release` is `SENTRY_RELEASE` (the git commit of the build) and `kind` is `html`, `json` or `doc` (sitemap, robots, llms files and feeds). The release is in the key so a deploy never serves HTML that points at asset files of the previous build. Query strings are dropped from the key for pages (filters run in the browser) and allow-listed per API route, so a random query string cannot be used to bypass the cache. The key never depends on a cookie or a request header.
4. **Invalidation is the version.** Anything that changes what a public page shows bumps `catalog_version`: publishing, unpublishing or editing published content, and also a write to the public keys of `settings` only (`flags`, `coming_soon_global`, `site`, `environment`, `og_static`; channel, token and other private keys do not bump, G21), to `markets.coming_soon`, to `redirects` and to `slug_history`. The triggers are B2's and skip the `catalog_version` row itself; the only other caller is the `bump_catalog_version` recipe step, which calls B2's function. No code writes the row directly. The next state check sees it and every key changes. A publication is visible everywhere within 15 seconds without a purge call. The `purge_cache` step is housekeeping, never needed for correctness.
5. **Identical for every visitor.** Server-rendered HTML carries nothing personal. Consent, saved state and the concierge act in the browser after hydration. `x-request-id` and the static security headers are added by the middleware after the cache lookup and are never stored. Because HTML is cached, an enforced Content-Security-Policy uses hashes, never a per-request nonce (B17, H1); the policy header that carries the hashes of a page's inline scripts is computed at render and stored with that page's cache entry, so a hit and a miss answer with the same policy.
6. **Never cached** (`Cache-Control: no-store`): every POST, every write under `/api/public/`, all of `/api/admin/*`, `/api/hooks/*` and `/admin`, preview-token pages, any response with `Set-Cookie`, the 405, 404 and 406 the pipeline writes itself (ASSUMED H39 (2), H41 (1)), and every 5xx. The value is set, not merged: on these classes the pipeline replaces whatever `Cache-Control` the handler set with exactly `no-store` (B1b, G65).
7. **Stale beats down.** The last good snapshot stays in memory and under a `last-good` key in the Cache API: `last-good/<release>/html/<pathname>` for html (the release keeps an old build's HTML from pointing at missing assets) and release-free for json and doc, each stored with `s-maxage=604800` (DO-09). When the database errors or does not answer in 2 seconds, public reads serve the last good copy with `x-mop-cache: stale`, log once a minute and report to Sentry. A paused or unreachable database must not take the public site down.
8. **Writes stay cheap.** Turnstile and the in-memory limit run before any database call. Analytics events are batched in the browser (flushed every 10 seconds and on `visibilitychange`, at most 20 per beacon) and stored with one multi-row insert. Rate-limit rows are pruned by the `prune` schedule.
9. **Admin reads are not cached and stay cheap.** The session is verified locally (JWT signature against the project's keys, cached in memory), not by a network call to Supabase Auth on every request. Lists are paginated at 50 with indexes. The dashboard is one RPC of indexed counts.
10. **Outside APIs are never called on a page view.** Channel metrics, Search Console and analytics are read by scheduled jobs and the audit robot only.
11. **Keep-warm** (B8b) runs on a schedule measured in minutes (longer than the 15 second memo, so every run finds it expired), calls the public handler in-process and so always makes one state RPC, which keeps an isolate warm and keeps the free database from pausing after a week without activity (a cache hit alone would not touch the database).
12. **Observable.** Public responses carry `x-mop-cache: hit|miss|stale|bypass` and `x-catalog-version` (the GET reads and the two POST reads `search` and `concierge`; a write response and an error answered before the service call carry `bypass` and no version, B3 invariant 16). The Cache API does nothing on `workers.dev`, so previews run on the memory layer alone. It does work under local `bunx wrangler dev` (measured 2026-10-01: miss, then hit, and a random query string still hits), so the edge layer is proved locally by B3 and B4 and confirmed on the custom domain at L1.

Proof (B4 and H1): the database client is wrapped with a call counter. A test warms the Worker, sends 1,000 requests across the public pages and catalog endpoints, and asserts the counter moved only by state checks (at most one per 15 seconds of test time) and by nothing else; watched-fail by switching the memo off. H1 measures the hit ratio on the custom domain (target 95 percent or better) and the audit robot (B14) reports it every week. The snapshot has a byte budget: 100 synthetic properties of 30 photographs each serialise to at most 1,500,000 bytes (B2 `tests/db/snapshot-budget.db.test.ts`, PERF-03; past it, variants are stored compactly as one content hash plus `w` and `h` per size, with URLs derived in B3's mapper, rather than the budget raised). Revisit the single-snapshot design when the snapshot exceeds 1 MB, or the first request after a bump exceeds the CPU limit in B1b step 7's or H1's `wrangler tail` measurement (which includes one case: the first request after a `bump_catalog_version()` with the 100-property fixture loaded on `mop-dev`), not at a property count. B3 builds the search token index lazily, on the first `search` or `concierge` call of a version, not inside `getCatalog`.
