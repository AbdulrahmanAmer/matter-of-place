# Engineering architecture — Matter of Place v1 (build from this)

Companion to `02-tech-stack/tech-stack.md` (choices) and `05-plans/` (slices). Diagrams: `03-diagrams/architecture.md`.
Written 2026-09-30 by the CTO session, no worker agents (S38). Every table, route and screen here has a slice in `05-plans/`.

## 1. Shape
One repository, one Cloudflare Worker, one Supabase project per environment.

```
browser ── edge cache ── Worker ──┬── pages (SSR, TanStack Start)
                                  ├── /api/public/*   anonymous, rate-limited, Turnstile on writes
                                  ├── /api/admin/*    Supabase Auth session or agent API key; role-checked server functions
                                  └── /api/hooks/*    signed callbacks: render workflow, Resend events, Sentry test (no Stripe or Meta hook in v1)
Worker ── service role ── Postgres (migrations = source of truth) ── pgmq + pg_cron ── Edge Function job runner
                                                                      └── repository_dispatch ── GitHub Actions render workflow ── R2
```

Rules that hold everywhere:
- The browser never holds a Supabase key. Public reads come from the Worker with edge cache; writes are validated with Zod at the Worker and again by database constraints.
- Shapes come from the database: `supabase/migrations/*.sql` → `supabase gen types` → `src/db/types.ts`. `src/domain/*` re-exports row types and holds Zod input schemas only.
- Every state change goes through a server function in `src/server/<feature>/` that (1) resolves the actor, (2) checks the role, (3) performs the change in a transaction, (4) writes `audit_log`, (5) emits an event that the recipe engine turns into jobs. UI never calls the database.
- Every side effect is a job with an idempotency key. Nothing external (email, post, render) happens inside a request.

## 3. Data model v2 (migrations; the sketch schema is superseded)
Conventions: `uuid` ids (`gen_random_uuid()`), `timestamptz` for time, money as `numeric(12,2)` + `char(3)` currency (USD only at launch, check constraint), soft state via enums, every mutable table has `created_at`, `updated_at` (trigger), and RLS enabled with policies per role. Enum values keep the sketch's names where the frontend already uses them.

### 3.7 RLS in one sentence per table
Public tables: anonymous select of `published` rows only through the Worker (service role), never direct. Admin tables: `select` for every role; `insert/update` per feature (submissions decide: chief_editor, managing_editor; properties write: chief_editor, managing_editor, visual_editor; assets approve: media_ops, chief_editor; payments: managing_editor, admin; automation tables: chief_editor, media_ops, admin, except `decline_reasons`: chief_editor, managing_editor, admin (screen 19, B2's policy, which B8b keeps); team: admin); `delete` nowhere except `admin` on `agent_keys`. `audit_log`, `events`, `automation_revisions`: insert-only. Agent guardrail `human_only` (403 for agents) applies to mark-paid, waive, void and activate (A5, §6).

### 3.8 Views, database functions and triggers (owner slice, migration)
Rule: every function below is `security definer`, `set search_path = ''`, with execute revoked from `public`, `anon` and `authenticated` and granted to `service_role` only (the RLS helpers `role_in` and `is_staff` keep B2's grants). A function an admin route calls takes `p_actor, p_actor_kind, p_request_id` and writes `audit_log` through B7's `write_audit` in the same transaction. A new view, function or trigger is added to this list, with its slice and migration, in the same commit as the plan that creates it. Proof that the list and the database agree after a slice lands: `bun run db:psql -- -Atc "select proname from pg_proc where pronamespace = 'public'::regnamespace order by 1"` on `mop-dev` prints no name that is missing here (B2 creates `db:psql`; before B2 lands there is no schema to compare).

## 4. API surface
### 4.1 Public (`/api/public/*`), JSON, edge-cached where marked
`GET properties`, `GET properties/:slug`, `GET markets`, `GET markets/:slug`, `GET stories`, `GET stories/:slug` (cached, `Cache-Tag: catalog`, keyed by `catalog_version`); `POST inquiries`, `POST submissions` (returns signed upload URLs), `POST subscribers` (with `markets[]`), `GET subscribers/confirm?token` (redirects to `/stories?confirmed=` in B3; B5 moves the route and its tests to `/place-notes?confirmed=1|0`), `POST events` (204; the allow-list includes `consent_set`, `web_vitals` and `csp_report`), `POST search`, `POST concierge` (rule-based), `GET site` (B16, `src/routes/api/public/site.ts`; the `settings.site` object plus `illustrativeContent` from `getPublicState`, cached like the catalog), `POST subjects/request` (B3, `subjects.request.ts`; CCPA access, deletion or opt-out, inserts `subject_requests` through `create_subject_request`, 201 `Receipt`, `no-store`), `POST csp-report` (B17, `csp-report.ts`; `application/reports+json`, 204, `no-store`). The route table in `src/server/public/routes.ts` (B3, each later slice adds its row) is the source for every limit and header. Form writes (`inquiries`, `submissions`, `subscribers`, `subjects/request`) require a Turnstile token and DB-backed limits; beacons (`events`, `csp-report`) and POST reads (`search`, `concierge`) take no Turnstile and are rate limited in isolate memory only. Sliding-window rate limits stored in a small `rate_limits` table (no KV), request id in every log line and error body.

### 4.2 Admin (`/api/admin/*`), session cookie (Supabase Auth) or `Authorization: Bearer <agent key>`
Every route maps 1:1 to a server function; the handler only parses and returns. Groups: `submissions` (list, get, start-review, decline, accept, request-assets, activate, note), `payments` (issue-invoice, mark-paid, waive, void, list, get, pdf; `POST /api/admin/payments/:id/void` is admin only and `human_only`), `properties` (list, get, create-from-submission, update, publish, unpublish, rank, related), `media` (upload-url, attach, reorder, alt, delete, variants-status), `assets` (list, approve, reject, re-render), `channels` (posts list, retry, metrics-refresh), `newsletter` (issues list, build, preview, approve, send-test), `inquiries` (list, get, assign, forward, close), `stories`, `markets`, `jobs` (list, get, retry, cancel, approve), `automation` (recipes get/put, templates get/put/preview, reasons, channel-settings, schedule-settings, dry-run, revisions, restore), `team` (users, roles, agent keys), `settings` (site config, coming-soon), `reports` (campaign report, export), `audit` (list). ## 5. The recipe engine
1. A server function commits and inserts an `events` row in the same transaction.
2. A trigger (or the same function) loads the enabled recipe for `events.type`, filters steps by `conditions` against the payload (tier, market), and inserts one `jobs` row per enabled step with `idempotency_key = event_id:step_id`, `heavy` from the step type, `status = waiting_approval` if `requires_approval`, else `queued`; enqueues on pgmq.
3. Edge Function `job-runner` (pg_cron every minute, and pgmq `read` with visibility timeout) pops light jobs and runs the step; for heavy jobs it calls GitHub `repository_dispatch` with the job id and payload, marks `running`, and the Actions workflow posts results to `hooks/render/callback`.
4. Failures: `attempts++`, exponential `run_after`, `dead` after `max_attempts`; dead jobs appear red in `/admin › Jobs` with a retry button. Every transition is a `job_events` row (3.6) for the timeline in the UI.
5. Dry-run: given a trigger and a sample payload, returns the list of jobs the engine would create, without inserting.
6. Keep-warm: B8b owns the Worker `scheduled()` handler and the cron trigger line in `wrangler.toml` (B1b leaves a marker comment for it); the `keepwarm` row of `schedule_settings` is its switch.
7. Social dry-run: one flag, `SOCIAL_DRY_RUN`, makes every channel adapter log instead of post; `META_DRY_RUN` is retired. Real posts also need R2 (`r2_unavailable` blocks them while R2 is off).
8. Clocks. Fixed pg_cron jobs, each created by a migration that unschedules by name first (owner, migration): `analytics-partitions` monthly (B2 `20261001090500_analytics_partitions.sql`), `job-runner` every minute (B8 `<ts>_job_cron.sql`, `net.http_post` to the Edge Function), `health` daily and `reconcile_uploads` every 15 minutes (B8 `<ts>_system_jobs.sql`), `retention` and `meta_token_refresh` daily (B8 `<ts>_retention.sql`), `kpi_weekly` Saturdays and `newsletter_hygiene` monthly (B11 `<ts>_kpi.sql`). B8 also schedules `prune`; B8b's `<ts>_automation_schedules.sql` unschedules it so the runner drives it from `schedule_settings`. `job-runner` calls the runner and `analytics-partitions` calls B2's idempotent function (a failed run is recorded in `cron.job_run_details` and the next run retries); every other cron row only enqueues a job with a dated idempotency key, so a double fire runs once and a failure follows the job backoff. Every other schedule is a `schedule_settings` row (3.5): `digest`, `prune`, `reconcile` run from `runDueSchedules` in `src/server/jobs/scheduler.ts` (B8b) on each runner tick; `keepwarm` from the Worker cron trigger; `audit` and `backup` are external clocks (the B14 routine and `backup.yml`). Vault rows per environment, created by the B8 runbook and never by a migration: `job_runner_url`, `job_runner_secret` (step 6), and `meta_page_token` (written by `set_vault_secret` from `meta_token_refresh`, read by B10's `getMetaToken`). Proof on `mop-dev`: `bun run db:psql -- -Atc "select jobname from cron.job order by 1"` lists exactly the fixed jobs whose slices have landed.

Step catalog (code; grows only by PR; `workspace/05-plans/check-plans.mjs` enforces it): `send_email`, `render_variants`, `render_cover`, `render_carousel`, `render_story`, `render_reel`, `write_captions`, `build_newsletter_block`, `post_meta`, `queue_digest`, `notify_admin`, `webhook_omnikom`, `bump_catalog_version`, `purge_cache`, `render_og_static` (manual-only: OG covers for non-property pages, B9), `post_x`, `post_linkedin` (S48; `post_meta` covers Instagram now and Facebook when enabled; a `post_youtube` step is added by PR when YouTube is switched on). ## 6. Agents as staff (S38)
- An agent is a Supabase Auth user with `user_roles.actor_kind = 'agent'` and a role; it authenticates with an `agent_keys` bearer key (hashed at rest, scoped to route groups).
- Everything an agent can do is an `/api/admin/*` route, so a Claude session, a scheduled routine or a headless worker can run the queue: list submissions → read one → decline with reason or accept → write dossier → publish → approve assets. The same audit trail shows `actor_kind = agent`.
- Guardrails: agents cannot change roles, agent keys, or `settings`, and get 403 `human_only` on mark-paid, waive, void and activate (A5); signed preview links use the Worker secret `PREVIEW_TOKEN_SECRET` (also a key in the GitHub secret `PREVIEW_WORKER_SECRETS_JSON` for preview Workers); `approval_mode` can require a human for a channel regardless of who approved the asset; an `agent_daily_limits` setting caps decisions per day.
- The CTO session adjusts automations through the same API (`automation.*`), so "adjust freely using you" needs no deploy.

## 13. Caching contract (S52): a public read never reaches the database when warm
The goal is a number: after warm-up, a public page view or catalog read costs **zero database queries**, and the database is asked at most once per catalog version per isolate, plus one small state check per isolate every 15 seconds. Writes are never cached. Everything here is free tier: no KV, no paid cache feature (G-011).

Layers, outermost first:
| Layer | What it holds | Lifetime | Invalidation |
|---|---|---|---|
| Browser | fingerprinted JS, CSS and bundled images: `immutable, max-age=31536000`; `/media/*` one week; HTML `max-age=0, must-revalidate`; catalog JSON `max-age=60` | per header | new build, new file names |
| Browser data | TanStack Query, `staleTime` 5 minutes, hydrated from the server render so a page load causes no second fetch | 5 minutes | reload |
| Edge (Cache API inside the Worker, `caches.default`) | the rendered HTML of every public page and every catalog JSON response | `s-maxage=300, stale-while-revalidate=86400`; 404 pages 60 seconds; sitemap, robots and llms files one hour | the key changes (below) |
| Isolate memory | one catalog snapshot per catalog version (already mapped to API shapes), the public state (version, flags, coming-soon, site settings) and the redirect map | until the version changes or the isolate is recycled | version check every 15 seconds |
| Database | one RPC for the public state, one RPC for the whole published catalog | n/a | `bump_catalog_version()` trigger (B2) |
| Media | R2 variants under content-hashed keys, `immutable, max-age=31536000` (when R2 is on) | forever | a new upload is a new key |

Rules (each one is a test in the slice named):
1. **One read path.** `getPublicState(db)` returns `catalog_version`, flags, `coming_soon_global`, `coming_soon_markets`, `settings.site` and `illustrative_content` (true only when `settings.environment` is `development` or `preview`; the Worker also forces it false when `MOP_ENV` is `production`) from one RPC (`public_state()`), memoised 15 seconds per isolate (`CATALOG_VERSION_TTL_MS`, `0` in tests). `getCatalog(db)` returns the snapshot for that version from one RPC (`public_catalog_snapshot()`), mapped once and memoised per isolate. Every public list and detail endpoint, every server-rendered loader (in-process, no network hop), search, concierge, sitemap, llms files, redirects and `getFlags` read from these two and never query a table themselves. The snapshot carries the enabled `redirects` and `slug_history`. Free-text search is an index built in the Worker over the snapshot (whole tokens and prefixes of three or more characters, with plurals folded on both sides), so a search costs no database query. Both functions take the database client as an argument, so a test can inject a counting client. B2 creates the two RPCs, B3 the read path and the query hydration in `src/router.tsx` (the server render dehydrates, the browser makes no second catalog fetch on load).
2. **HTML is cached, not only JSON.** The request middleware in `src/start.ts` answers GET and HEAD for public pages from the Cache API before rendering, and stores the render after. This is what keeps Worker CPU under the free limit (E3: the home page renders in 6 to 52 ms; a cache hit costs about 1 ms). B1b creates the middleware order, B3 the cache module it calls.
3. **The key.** `https://cache.mop.internal/<release>/v<catalogVersion>/<kind>/<pathname>` where `release` is `SENTRY_RELEASE` (the git commit of the build) and `kind` is `html`, `json` or `doc` (sitemap, robots, llms files and feeds). The release is in the key so a deploy never serves HTML that points at asset files of the previous build. Query strings are dropped from the key for pages (filters run in the browser) and allow-listed per API route, so a random query string cannot be used to bypass the cache. The key never depends on a cookie or a request header.
4. **Invalidation is the version.** Anything that changes what a public page shows bumps `catalog_version`: publishing, unpublishing or editing published content, and also a write to `settings` (flags, `coming_soon_global`, `site`, `environment`), to `markets.coming_soon`, to `redirects` and to `slug_history`. The triggers are B2's and skip the `catalog_version` row itself; the only other caller is the `bump_catalog_version` recipe step, which calls B2's function. No code writes the row directly. The next state check sees it and every key changes. A publication is visible everywhere within 15 seconds without a purge call. The `purge_cache` step is housekeeping, never needed for correctness.
5. **Identical for every visitor.** Server-rendered HTML carries nothing personal. Consent, saved state and the concierge act in the browser after hydration. `x-request-id` and the static security headers are added by the middleware after the cache lookup and are never stored. Because HTML is cached, an enforced Content-Security-Policy uses hashes, never a per-request nonce (B17, H1); the policy header that carries the hashes of a page's inline scripts is computed at render and stored with that page's cache entry, so a hit and a miss answer with the same policy.
6. **Never cached** (`Cache-Control: no-store`): every POST, every write under `/api/public/`, all of `/api/admin/*`, `/api/hooks/*` and `/admin`, preview-token pages, any response with `Set-Cookie`, and every 5xx.
7. **Stale beats down.** The last good snapshot stays in memory and under a `last-good` key in the Cache API. When the database errors or does not answer in 2 seconds, public reads serve the last good copy with `x-mop-cache: stale`, log once a minute and report to Sentry. A paused or unreachable database must not take the public site down.
8. **Writes stay cheap.** Turnstile and the in-memory limit run before any database call. Analytics events are batched in the browser (flushed every 10 seconds and on `visibilitychange`, at most 20 per beacon) and stored with one multi-row insert. Rate-limit rows are pruned by the `prune` schedule.
9. **Admin reads are not cached and stay cheap.** The session is verified locally (JWT signature against the project's keys, cached in memory), not by a network call to Supabase Auth on every request. Lists are paginated at 50 with indexes. The dashboard is one RPC of indexed counts.
10. **Outside APIs are never called on a page view.** Channel metrics, Search Console and analytics are read by scheduled jobs and the audit robot only.
11. **Keep-warm** (B8b) runs on a schedule measured in minutes (longer than the 15 second memo, so every run finds it expired), calls the public handler in-process and so always makes one state RPC, which keeps an isolate warm and keeps the free database from pausing after a week without activity (a cache hit alone would not touch the database).
12. **Observable.** Public responses carry `x-mop-cache: hit|miss|stale|bypass` and `x-catalog-version`. The Cache API does nothing on `workers.dev`, so previews run on the memory layer alone. It does work under local `bunx wrangler dev` (measured 2026-10-01: miss, then hit, and a random query string still hits), so the edge layer is proved locally by B3 and B4 and confirmed on the custom domain at L1.

Proof (B4 and H1): the database client is wrapped with a call counter. A test warms the Worker, sends 1,000 requests across the public pages and catalog endpoints, and asserts the counter moved only by state checks (at most one per 15 seconds of test time) and by nothing else; watched-fail by switching the memo off. H1 measures the hit ratio on the custom domain (target 95 percent or better) and the audit robot (B14) reports it every week. Revisit the single-snapshot design when the published catalog passes 500 properties.
